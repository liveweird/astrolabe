### The Flow sync (v1.5.0, released 2026-11-08)

Read before touching `flow/`, `FlowOrigins`, the Flow stub or the Flow pages. **What it is:** Astrolabe reads Flow (the sibling app) through its read-only service token and mirrors one document - every team with its dated members and its sprints - into typed tables; **nothing is ever written to Flow**. It is all built: V24, the connection registry, Test connection, the run, the status and polling, the team binding with the roster panel, the capacity import (preview, then apply), the pages (Administration, Flow; the team page's Flow section) and the e2e (`flow-sync.spec.ts`, a Flow describe in `accessibility.spec.ts`; `test-fixtures.md` "The e2e Flow world"). **It is proven against the built-in Flow stub only and not yet against a real Flow** ("First real-Flow walk-through" below is the first real test). The shape is `jira-sync.md`'s on purpose: read it for the registry, the scheduler and the status, which are the SAME code (`sync/`).
Related: schema `persistence.md` ("The Flow sync tables (V24)"); outbound guard `security.md` "The Flow consumer"; audit events and the run log lines `observability.md` ("Sync runs", "The Flow run"); per-route guards `authorization.md`; the stub `sample-data/flow/README.md`; the plan `~/.claude/plans/astrolabe-v1.5.0-flow.md`.

## The transport and origins

Flow is the sibling app, reached over `GET /api/v1/integration/me` and `GET /api/v1/integration/teams?sprintsSince=YYYY-MM-DD` with `Authorization: Bearer flow_int_<43 base64url>`. The allow-list is OPERATOR configuration (`flow.*`, `security.md` "The Flow consumer"): a connection's `baseUrl` is exactly one listed origin and its identity (a `PUT` with another is `409`). The wire contract is written in two places that must agree ("The contract and drift" below). Failure codes (`FetchException.code`): `AUTHENTICATION_FAILED` (401: Flow's one uniform answer - revoked, expired or wrong), `NOT_FOUND` (a Flow older than 1.57.0), `UPSTREAM_UNAVAILABLE` (5xx), `RATE_LIMITED` (429), `REDIRECT`, `LIMIT_EXCEEDED` (the 1 MiB response cap), `INVALID_RESPONSE`, `TIMEOUT`, `BLOCKED_HOST`. Config (`flow.*`, env `FLOW_*`, every key boot-validated): `requestTimeoutSeconds` 30 (5..120), `requestDeadlineSeconds` 60 (10..600), `maxResponseBytes` 1 MiB (64 KiB..1 MiB), `maxConcurrentRequests` 1 (1..2), `maxRetries` 2 (0..8), `sprintsSinceDays` 365 (30..1095). The 1 MiB / 2 ceilings are what keep Flow inside the heap reserve without a second heap-fit check (`security.md`: worst case 30 MiB parsed, the defaults 15 MiB, the real document about 150 KB).

**Origins are OPERATOR configuration, never an admin's.** `FLOW_ALLOWED_HOSTS` / `FLOW_ALLOWED_CIDRS` / `FLOW_CA_BUNDLE` carry a TLS Flow (https to a listed `host[:port]`, a private range only for a listed host inside a CIDR, an extra CA alongside the JVM defaults, no skip-TLS switch); `FLOW_INSECURE_ORIGINS` (exact `http://host[:port]` origins) carries the stub and a plain-http Flow on OrbStack and is honoured in development mode ONLY (a non-blank value outside it refuses boot). An insecure host may resolve to a loopback, private or docker address and **never** to a link-local (the metadata address), any-local, multicast, `0.0.0.0/8`, `::/96`, 6to4 or Teredo one. A connection's `baseUrl` is exactly one listed origin in its **canonical form only** (`FlowOrigins.baseUrlVerdict`): lowercase scheme and host, the scheme's default port OMITTED (`https://flow.example`, never `https://flow.example:443`, and no leading zeros in a port), no path, trailing slash, query or credentials. **The verdict is one of three** (`FlowBaseUrlVerdict`) and the `400` says WHICH refused, never quoting the value: `NOT_CANONICAL` (a spelling problem: "baseUrl must be the origin alone, in lowercase and without the default port, path, trailing slash, query or credentials") or `NOT_LISTED` (a well-formed origin nobody listed: "baseUrl is not one of the Flow origins this server is configured to allow (GET /api/v1/integrations/flow/origins lists them; the operator sets FLOW_ALLOWED_HOSTS, or FLOW_INSECURE_ORIGINS in development)"). A port is never the reason a base URL is refused: only an unlisted origin is. **`GET /api/v1/integrations/flow/origins`** (ADMIN, `{items}`, `FlowOrigins.allowedOrigins()`: the listed TLS hosts as `https://host[:port]` with 443 omitted plus, in development only, the insecure ones as `http://host[:port]` with 80 omitted, distinct and sorted; a bounded operator-curated set, so the plain `{items}` wrapper of `list-endpoints.md`) feeds the create form's hint "Allowed on this server: …"; it is the donor's `allowedOrigins` shape (Flow's data-source kinds), disclosure to ADMIN only, and widens nothing (the guard judges every call). A stored URL the operator has since delisted is refused on every call (`BLOCKED_HOST`, audited once, no retry), while a `PUT` never asks the list (an admin can still disable or re-token it).

## The contract and drift

| Document | Fields (`?` = nullable, and omitted by Flow when null) |
|---|---|
| `GET /integration/me` | `tokenId, name, createdAt, expiresAt?, lastUsedAt?` |
| `GET /integration/teams?sprintsSince=YYYY-MM-DD` | `asOf, sprintsSince, teamsTruncated, sprintsTruncated, items[]` |
| a team | `id, name, managerName?, defaultCapacityMd?, members[], sprints[]` |
| a member | `accountId, displayName?, validFrom, validTo?` (a HALF-OPEN interval `[validFrom, validTo)` in epoch ms; `validTo` null = still a member) |
| a sprint | `sprintId, connectionId, name, state, startAt?, endAt?, completeAt?, hasCalendar, capacityMd?, capacitySource?` (epoch ms; `capacityMd` is a TOTAL for the sprint whatever its source; `capacitySource` is `CALENDAR`, `TEAM_DEFAULT`, `DEFAULT` or null and kept as text, as is `state`) |

The caps are 1,000 teams (`teamsTruncated`) and 2,000 sprints (`sprintsTruncated`). Every error is Flow's uniform `application/problem+json` (`401` "Missing or invalid service token" for every authentication failure; only the status is used). **The drift rule:** the stub's documents are produced only by `sample-data/flow/contract.mjs`, the server decodes only through `flow/FlowDocument.kt` (`@Serializable`, `ignoreUnknownKeys`; strict on lists and flags, lenient on nullable scalars: ledger F1), and `FlowStubFixtureTest` / `FlowClientTest` replay the stub's documents into the decoder against `expected.json`. If a real Flow 1.57.0 ships a different field or path, the fix is two files and one test: edit `contract.mjs` and `FlowDocument.kt`, regenerate (`node sample-data/flow/generate.mjs`), and those tests prove them aligned.

## Test connection and the probes

`FlowConnector.testConnection` runs two required probes in sequence (10 s each, 30 s in all, never throwing; every outcome is a row, **never a 502**): `me` (the token is live; `NOT_FOUND` carries the hint "Flow 1.57.0 or later") and `teams` (the document decodes; the result adds "N teams, M sprints" and `truncated`; `SKIPPED` when `me` failed), plus the one `stored_token` row (`TOKEN_UNREADABLE`) when the stored token cannot be decrypted. `POST …/{id}/test` records `last_tested_at/ok` unless the row was edited meanwhile (`recorded`) and audits `flow.connection_tested`. **Test connection never writes the mirror**: the run is its single writer; a passing test is what makes the connection pollable, so the first run follows within a tick.

## The run

`FlowObserver` (the `Connector` of kind `FLOW`, registered by `configureFlow`) does, per claimed run: read the connection and its token in one short transaction (`FlowConnectionService.readForRun`, the second of the two decrypting readers) - then NO database transaction is open until the call has returned; ONE `GET /integration/teams?sprintsSince=` where `sprintsSince` is today in the CONNECTION's zone minus `flow.sprintsSinceDays`; `FlowMirrorStore.replace` in one transaction, which re-reads the connection under its row lock (`FOR NO KEY UPDATE`) and writes nothing when it was deleted (`GONE`) or disabled (`DISABLED`) meanwhile. It OBSERVES: no plan lock, no revision, nothing sent to Flow beyond the one GET.

| Situation | Run | Mirror |
|---|---|---|
| a document | `SUCCEEDED`; `observed` = teams, `gone` = ACTIVE bindings whose Flow team the document lacks, `calls` = 1 | replaced wholesale, `teams_at` stamped |
| `401` | `FAILED` `AUTHENTICATION_FAILED` (a revoked or expired token; rotate it with a `PUT`: that makes the connection due at once) | keeps its last document |
| `5xx` / `429` | `FAILED` `UPSTREAM_UNAVAILABLE` / `RATE_LIMITED`, then the registry's doubling back-off (one interval, doubling, capped at 6 h) plus the deterministic jitter | keeps its last document |
| a body that is not the contract | `FAILED` `INVALID_RESPONSE` | keeps its last document |
| unreadable token / unknown zone | `FAILED` `TOKEN_UNREADABLE` / `TIME_ZONE_INVALID`, no call | untouched |
| connection deleted / disabled while the call was in flight (judged under the row lock at the write: `FlowMirrorWrite.GONE` / `DISABLED`) | `FAILED` `CONNECTION_GONE` / `CONNECTION_DISABLED` | nothing written (a deleted connection's mirror and token are already gone; a disabled one keeps its last document and `teams_at`) |
| `sprintsTruncated` | `SUCCEEDED` + a WARN (counts only) | the document Flow sent is kept |
| `teamsTruncated` | `SUCCEEDED` + a WARN; `gone` is **0** | the teams it carries are replaced, **every other mirrored team is kept whole** |

**The `teamsTruncated` rule.** Flow caps a document at 1,000 teams (and 2,000 sprints). A team absent from a truncated document was merely not sent, so it is neither deleted from the mirror nor counted `gone` (and the panel and 1.6's `TEAM_GONE`, which derive `gone` from the mirror, never see it vanish); the next complete document is authoritative. The cost: a team really removed from Flow stays mirrored while Flow keeps truncating. `FlowRunWireTest` pins it (three documents: complete, truncated, complete).

**The token never appears** in a log line, an audit, a run row or a problem body: the run's error text is fixed (`Flow fetch failed: {code} ({status})`, never the exception message, which quotes a URL), `clampErrorDetail` is only the backstop, and `FlowRunWireTest`, `SyncRunRoutesTest` assert it with a ROOT `LogCapture`.

## Polling and status

Polling is the 1.3 scheduler unchanged (`observability.md` "Sync runs"); Flow's parts: the default interval is **60 minutes** (5..1440, `null` = manual only; STALE after 3 intervals, so 3 h), `ready` = a Test connection passed (`last_test_ok`) OR a run has mirrored a document (`teams_at`) - sticky like Jira's `discovered_at`, so a token or zone `PUT` (which clears the test verdict) or a Test that hit a Flow outage never stops a connection that has run from polling; a never-tested, never-run connection is not polled, `changedAt` = the later of `updated_at` and `last_tested_at`, so a rotated token or a fresh passing test makes the connection due at once whatever a back-off says. `pollRows` (`FlowConnectionPolling.kt`) reads eight columns and never the token. Every connection answers a derived `status` and `lastRun` (`SyncStatusKernels.derive`, the same rule and readers as Jira's: the registry, the telemetry `sync` block; nothing is stored). Proven by `FlowRunTest` (the stub: NEVER_SYNCED to CURRENT, the mirror equals `sample-data/flow/expected.json`, day two drops Billing and counts the bound team gone, an outage, a revoked token), `FlowRunWireTest` (MockEngine), `FlowConnectionStatusTest`, `SyncSchedulerTest` ("a tested Flow connection is polled, an untested one is not") and `TelemetryRoutesTest`.

## Bindings

A binding links ONE Astrolabe team to ONE Flow team of a connection (V24 `flow_team_bindings`; 1:1 both ways over the ACTIVE rows, and a team has one Flow team across ALL connections). It feeds the team's roster panel and the capacity import. Not plan state: no plan lock, no revision; the link and the unlink call Flow never (they read the mirror) and ride no rate bucket. A binding follows the Flow team's **id**; `flow_team_name` is display text frozen at link time (a rename in Flow changes nothing).

**Match by name** (`FlowTeamMatchKernels`, pure): a Flow team is *suggested* to an Astrolabe team when the folded names are equal - trim, collapse every run of whitespace to one space, lowercase; **accents count** ("Płatności" is not "Platnosci": a wrong automatic link is worse than a missing one) - and the Astrolabe team is the ONLY unbound active team with that folded name. The rule is symmetric: two Flow teams that fold to one name are suggested nothing (so "Link all suggested" can never ask for one team twice). A bound team is never re-suggested, and neither is a Flow team that is bound. `GET /integrations/flow/teams` shows the suggestion per Flow team; `POST …/connections/{id}/team-bindings/match` (ADMIN) links every current suggestion in ONE transaction and reports `bound[{bindingId, teamId, flowTeamId}]` and `skipped[{flowTeamId, reason}]` (`ALREADY_BOUND`, `NO_MATCH`).

**`GET /integrations/flow/teams?connectionId=` is unpaged, by decision** (recorded in `list-endpoints.md` with the view endpoints' shape exception: an unpaged `{connectionId, teamsAt, items[≤ 1,000]}`; the paged envelope stays for every ordinary resource list): it is the mirror of ONE Flow document, which Flow itself caps at 1,000 teams (the real figure is 15-100), and the suggestion needs every unbound team at once, so it is a bounded document of `{connectionId, teamsAt, items[≤ 1,000]}` like the view endpoints, not a `{items, page, pageSize, total}` envelope. Items come by name then id. It serves the connection page (ADMIN) and the manager's link dialog.

**The link** (`FlowTeamBindingService.bind`): one transaction under a global advisory lock (`FLOW_BIND_LOCK_KEY`, "AstroFBT": links are human clicks, and the two uniqueness checks are exact over rows that may not exist yet), the connection row `FOR SHARE` (a delete or a run's mirror replace waits), the Flow team read from the mirror as it is now, the team row `FOR SHARE`, the guard again, then the checks and the insert. **A soft-deleted team keeps its ACTIVE binding** (`teams/` may not name `flow/`): the link and the match RELEASE a dead team's holder of the Flow team (soft-delete, audited `flow.team_unbound` reason `TEAM_GONE`, the Jira bind's dead-node idiom), and `bindingsOf`, the match, the list, the panel and the unlink's lookup all filter on ACTIVE teams, so a Flow team once linked to a deleted team can be linked again and a dead team's binding is invisible (404 to unlink). A connection delete soft-deletes its bindings in its own transaction, so a deleted connection's bindings are hidden at once.

**The panel** (`GET /teams/{id}/flow`, `FlowTeamService.panel`, its own read, not a member of the team view): `binding` (connection NAME, enabled flag, the connection's `SyncStatus`, `observedAt`, `gone`), `roster` and `sprints{count, nextStart}`, all null for an unlinked team; `roster` and `sprints` are also null when the Flow team is **gone**. `gone` is derived at read time and never stored: the connection HAS mirrored a document (`teams_at` set) and the Flow team is not in it (consistent with the run's `gone` count, which skips a truncated document). `can{link, unlink, importCapacity}` is ADMIN or the team's active manager (one verdict, three flags). **`connections[{id, name, enabled}]`** is always present, whoever asks: every ACTIVE connection (enabled or not) by name then id, cut at 100 (`MAX_PANEL_CONNECTIONS`; the registry has no cap) - it is how a manager, who cannot read the ADMIN-only registry, finds the connection for the link dialog, which then reads `GET /integrations/flow/teams?connectionId=`; never a base URL, token, zone, interval or test detail. **The roster** (Q2a: every signed-in user sees it - one predicate, `rosterVisibleTo`): memberships are half-open instant intervals `[validFrom, validTo)`; *current* when `validFrom <= now < validTo` (an open end never ends), *former* when `validTo <= now`; a membership that has not started is in neither list; dates are the instants in the connection's time zone (a zone this JVM no longer knows reads as UTC, the run reports it); a null display name reads **"Unknown account"** (server-side text); a person with two intervals appears once per interval. Account ids never leave the server. `nextStart` is the first mirrored sprint start that is today (in the zone) or later.

Proven by `FlowTeamMatchKernelsTest`, `FlowTeamBindingTest`, `FlowTeamMatchTest` (a scripted MockEngine document with this test's unique team names, a real run behind it), `FlowTeamPanelTest`, `AuditTest`.

## The capacity import

**The rule, in the user's words:** a sprint's man-days from Flow are spread over the sprint's WORKING days (Astrolabe's calendar: Monday-Friday minus the public-holiday dictionary), so the weekly capacity Astrolabe computes over the sprint adds up to what Flow says, within rounding - a holiday inside the sprint raises the figure instead of losing man-days. `mdPerWeek = round2(5 x flowMd / workingDays)` (BigDecimal, `HALF_UP`), one capacity period per sprint (a period holds until the next one, so a gap between sprints keeps the previous figure; the weeks before a team's first imported sprint stay "no capacity"). Example: 40 MD over 10 working days is 20.00 a week; over 9 (one holiday) it is 22.22, and `weekCapacity` over those two weeks sums back to 40.00.

**The span and the days a sprint holds are Flow's own** (Flow `metrics.md` A42; `DeriveSprintStep`, `resolveSprintWindow`). `spanEndOf` (`CapacityImportKernels.kt`) is the ONE place the rule lives: the **planned end first** (`endAt`), a completion (`completeAt`) standing in only for a missing planned end - so a sprint completed before its planned end keeps its planned days (Flow's own figures are spread over them); `end = dayOf(max(startAt, spanEnd - 1 ms))` in the connection's zone, so an end at local midnight adds no day and a zero-length sprint is one day; a sprint with a start and neither end stays `NO_DATES` (Flow falls back to one day: a recorded, deliberate difference), and an end BEFORE the start stays `NO_DATES` too - yet such a sprint still HOLDS its start day, as in Flow (`sprintSpan`: `end ?: complete ?: start`). **A day belongs to the first sprint holding it** - the sprints within the 60-day cap first (lower start, then lower id), then the long ones: every sprint with a start holds at least its start day, and one with a usable end (on or after the start) holds `[start, end]`, whatever its capacity or skip reason (`NO_CAPACITY`, `ZERO_CAPACITY`, `OUT_OF_RANGE`, `NO_WORKING_DAY`), and a later in-cap sprint takes only the days no earlier sprint holds, `effectiveFrom = max(start, claimedEnd + 1 day)` where `claimedEnd` is the latest day an earlier sprint holds - which may be a Saturday: a period may start on any date. Walked in start order (long windows aside), the days earlier sprints hold inside a sprint are always a prefix of it, so `[effectiveFrom, end]` IS the set of days no earlier sprint holds. A Monday-to-Monday series therefore has W = 11 for the first sprint and 10 for each next, and two sprints that merely overlap both count (the later one from the day after the earlier one's end). Only a sprint WHOLLY inside earlier ones (`effectiveFrom > end`) counts no day: `OVERLAPS`, as in Flow, and it advances nothing. **A sprint over Flow's 60-day calendar cap** (`FLOW_MAX_CALENDAR_DAYS`, more than 60 calendar days from start to end) **claims LAST** (Flow 1.57.1, PR #469; F11): it gets no calendar, is listed with the info `LONG_WINDOW` (check its dates in Jira) and is never ticked, and it never advances `claimedEnd`, so every sprint within the cap is planned as if it were absent. Its own claim is the days of `[start, end]` that no in-cap sprint holds and no earlier long-window sprint (start, then id) took - not necessarily a prefix, so the kernel computes them as the gaps between the held intervals (`longClaims`); `effectiveFrom` is the first such day (possibly a weekend day) and `workingDays` counts the working ones. No leftover day is `OVERLAPS`, no leftover working day `NO_WORKING_DAY`. **Its figure is partial:** `mdPerWeek` spreads Flow's total over ALL the leftover runs, but the row becomes ONE period that holds only until the next period starts (which may be an in-cap sprint inside the window), so once applied the weekly capacity does not sum to Flow's total over the sprint; the row is unticked, and its info says so. The working days, the existing-period lookup, `MANUAL_PERIOD_INSIDE` and every removal rule use `effectiveFrom`, never the raw start.

**The promise: a hand-entered period is NEVER changed or removed by the import.** A sprint whose `effectiveFrom` already holds a manual period is `MANUAL_PERIOD` (left alone, shown with the figure it would have had); a manual period that starts INSIDE a sprint (after `effectiveFrom`, up to its end) adds the info `MANUAL_PERIOD_INSIDE(date)` - the sprint's figure will not hold from that date. Only periods the import itself wrote (V24 `source = FLOW`) are updated or removed; a manual PUT on one makes it manual (C8).

`CapacityImportKernels.plan(sprints, zone, calendar, today, existingPeriods, from, includeClosed)` is pure (`flow/CapacityImportKernels.kt`; the vectors are counted by hand in `CapacityImportKernelsTest`). Dates are the mirror's raw instants in the CONNECTION's zone, so a zone `PUT` takes effect at once. Per sprint, in start order (undated last), the first rule that fires:

| Step | Outcome |
|---|---|
| no start, no `endAt`/`completeAt`, or an end before the start | `SKIP` `NO_DATES` (asked first) |
| `capacityMd` null (Flow has none) | `SKIP` `NO_CAPACITY` |
| `effectiveFrom > end` (the sprint lies wholly inside earlier ones: Flow counts no day for it) | `SKIP` `OVERLAPS` |
| no working day from `effectiveFrom` to `end` | `SKIP` `NO_WORKING_DAY` |
| figure beyond the man-day bounds of a period (`validateManDays`) | `SKIP` `OUT_OF_RANGE` |
| no ACTIVE period starts on `effectiveFrom` | `CREATE` |
| a `FLOW` period does, with another figure, sprint id or name | `UPDATE` (the WIP limit is kept: Flow has none) |
| a `FLOW` period does, equal | `UNCHANGED` |
| a `MANUAL` period does | `MANUAL_PERIOD` |

Every sprint HOLDS its days for the sprints after it, whatever rule refused it (an `OUT_OF_RANGE`, `NO_CAPACITY` or `NO_WORKING_DAY` sprint claims its days; a `NO_DATES` one only its start day; an `OVERLAPS` one nothing; a long window nothing for the in-cap sprints - it claims last). **The figure's divisor is the days the sprint holds, except for a `TEAM_DEFAULT` or legacy `CONFIGURED` sprint** (Flow's `capacitySource` for the team's default figure, a fixed per-sprint total that claims do not reduce, F12): its `mdPerWeek = round2(5 x capacityMd / workingDays of its OWN window [start, end])`, while the period still starts at `effectiveFrom` and the row's `workingDays` still counts the days it holds - and when the window has more working days than the row holds, the row carries the info `FIXED_FIGURE` with `days` = the window's working days ("…spread over the sprint's N working days; some of its days belong to an earlier sprint"). **A sprint with 0 man-days** (Flow's DEFAULT is 0 for a team without members) is planned like any other but is never ticked and carries the info `ZERO_CAPACITY`. The `ticked` flag is: not closed, not zero-capacity, not a long window, and a CREATE or an UPDATE.

**Upgrade note (1.5.1).** 1.5.0 used `min(endAt, completeAt)` and skipped any sprint starting before the previous kept one's end. A team imported under it may, on its next preview, be offered a removal and a new period (and an UPDATE of the earlier sprint's figure) for sprints that followed an early completion, and new periods for sprints that merely overlapped one: the stale Flow period is a removal by rule (b) or (c) - (c) also for a sprint that is closed now, provided closed sprints are listed ("Include closed sprints") - and the sprint a CREATE at its new `effectiveFrom`; the old period of a sprint that is now wholly inside another (`OVERLAPS`), or whose new date holds a hand-entered period (`MANUAL_PERIOD`), is offered too. Hand-entered periods are never touched. Re-import the team (vectors: `CapacityImportKernelsTest` "periods imported under the 1.5.0 rule", "…once closed sprints are listed", "…holds no day").

**Closed sprints.** `from` (default: today in the connection's zone - a recorded default, "Decisions") is the first day the import is about; a sprint whose `end` is before it is closed, listed only with `includeClosed` and never ticked (`ticked` = not closed, not zero-capacity, not a long window, and CREATE or UPDATE). Overlaps are decided by the dates alone, before the toggle hides anything. **`removals[]`** are the team's `FLOW` periods that no listed sprint reuses and that (a) belong to a sprint missing from the mirror's document and lie in the window (`date >= from`, or any date with `includeClosed`) - a sprint older than `flow.sprintsSinceDays` leaves Flow's document and its history must not be offered for deletion - or (b) start inside `(effectiveFrom, end]` of a sprint the import covers (not closed, **not a long window**; CREATE, UPDATE or UNCHANGED), where they would cut the figure short (a re-dated sprint), or (c) belong to a LISTED sprint - closed or not, whatever its action or skip reason (planned, `MANUAL_PERIOD`, `OVERLAPS`, `NO_WORKING_DAY`, `NO_CAPACITY`, …) - without being the period its item reuses (a sprint moved, or one that now holds no day: its old period is stale). **A refused row keeps its own period:** a listed sprint that is `SKIP` but still holds days (`NO_CAPACITY`, `OUT_OF_RANGE`, `NO_WORKING_DAY`, `NO_DATES`) keeps the FLOW period at its own `effectiveFrom` (for `NO_DATES`, the one carrying its sprint id at its start day) - Astrolabe keeps the last good figure rather than inviting its deletion when it cannot compute a new one - while its OTHER old FLOW periods are still offered; an `OVERLAPS` row (or any wholly-inside one) keeps nothing. A closed sprint hidden by the toggle is history: its periods are not offered. A MANUAL period is never offered. The modal's removals intro adds: "Removing a period without importing its sprint's new row leaves the earlier sprint's figure in force over those days." **A removal is never preselected** by a client: it is listed and the person ticks it. A Flow team that is not in the mirror (gone, or never mirrored) previews an EMPTY plan with `observedAt` null: nothing is removed on the strength of an absence. A disabled connection still previews (the preview reads the mirror, never Flow). A closed sprint, or a team's first import, leaves the weeks before it untouched; the last sprint's figure stays in force until the next import (the modal's footer says so).

**The preview** (`POST /integrations/flow/team-bindings/{id}/capacity-preview {from?, includeClosed?}`, `CapacityImportService.preview`): one `READ ONLY REPEATABLE READ` snapshot of the binding and its connection's zone, the holiday calendar, the Flow team's mirrored sprints and the team's ACTIVE periods (`TeamCapacityService.importRowsOf`); the clock is injectable (`now`, a test pins "today"). It stores, locks, audits and sends NOTHING. Response: `{bindingId, teamId, observedAt, zone, from, includeClosed, totals{create, update, unchanged, skip, removals}, items[…], removals[…]}` - `from` is the RESOLVED date and `includeClosed` an echo, so the apply can send both back and re-run the kernel identically; `skip` counts `SKIP` and `MANUAL_PERIOD`; `mdPerWeek` is a number with at most two decimals; an item carries `start`, `end`, `effectiveFrom`, a removal its `flowSprintId`. The apply (below) re-runs the kernel under the team row lock and skips a row that no longer equals what the preview showed; its UPDATE also rewrites `flow_sprint_id` (a period reused for another sprint). Proven by `CapacityImportKernelsTest`, `CapacityImportPreviewTest` (the stub's E2E Flow Team equals `expected.json`: 20/18/22/20/19/21 MD a week; a seeded public holiday inside a sprint gives 9 working days and 22.22) and, for the shared day, the stub's Identity team (below).

**The apply** (`POST /integrations/flow/team-bindings/{id}/capacity-import {from?, includeClosed, items[{sprintId, expected{action, effectiveFrom, mdPerWeek}}], removals[periodId]}`, `CapacityImportService.apply` → `TeamCapacityService.applyImport`; `CapacityApplyKernels` is the pure decision). The client sends what the person ticked in a preview, with the preview's echoed `from` and `includeClosed`. **Guard order is the preview's** (binding `404` → `403` → body `400`), and the body is bounded (≤ 2,000 `items` and `removals`, each sprint and period at most once, `expected.action` only `CREATE` or `UPDATE`, a valid date and a man-day figure). Then ONE transaction, team data, no plan lock and no revision:

1. `Teams.lockActiveForWrite` (the team is gone: `404`), then the guard AGAIN under the lock (`lockedIsActiveManager`: a manager cleared while the request waited is `403` and nothing is written).
2. The team's ACTIVE periods are re-read under the lock; the binding is re-read inside the transaction (a plain read - the binding row is not locked - so an unlink committed before it is `404`, one committed after it is not noticed); the Flow team and its sprints are read NOW in ONE statement (`FlowMirrorStore.teamSprintsOf`; a Flow team no longer in the mirror re-plans as EMPTY: every row is then skipped - nothing is imported or removed on the strength of an absence).
3. `CapacityImportKernels.plan` runs again over those rows with the echoed `from` and `includeClosed` (today in the connection's zone when `from` is absent).
4. **Each requested item is written only when the re-computed plan lists its sprint as `CREATE` or `UPDATE` with the SAME `action`, `effectiveFrom` and `mdPerWeek` as `expected`** - otherwise it is skipped `CHANGED`. That covers a figure that moved in Flow, a sprint that was re-dated or left the document, a row that was never in the plan, and - the dangerous one - a start date a person took over meanwhile (the plan now says `MANUAL_PERIOD`). The period an UPDATE rewrites is the plan's `existing` period, never an id from the request.
5. **A removal is applied only when its period is one of the re-computed plan's `removals`** (a Flow-sourced period); a MANUAL period, a period deleted meanwhile and an unknown id are skipped `CHANGED`.
6. **A MANUAL period is never written by any path**: not as an item (a forged `CREATE`/`UPDATE` for the sprint whose start it holds is `CHANGED`), not as a removal; and `applyImport` re-checks every write against the locked rows and in each statement's `WHERE` (`persistence.md`).
7. Writes, in this order: removals (soft delete), updates (`md_per_week`, `flow_sprint_id`, `flow_sprint_name`, `updated_at`; the WIP limit is KEPT), creates (`insertRows`, `source = FLOW`).

**What `expected` does not cover:** a MANUAL period entered INSIDE a sprint's span after the preview is not part of `expected` (only the sprint's own start date is) - the CREATE or UPDATE still applies, and the manual period cuts the sprint's figure short from its date, exactly as the preview's `MANUAL_PERIOD_INSIDE` info warned.

Response `200 {created[{periodId, sprintId}], updated[{periodId, sprintId}], deleted[periodId], skipped[{sprintId|null, periodId|null, reason}]}` - a skipped row is data, not an error; the only reason is `CHANGED`. The apply is idempotent in effect: the same body sent twice writes once (the second finds every row `UNCHANGED` or gone and skips it), and a re-import right after is all `UNCHANGED` with nothing written. Audits (`observability.md`): ONE `team.capacity_imported` plus the existing `team.capacity_period_created/updated/deleted` per period with `sourceTo`/`sourceFrom` = `FLOW`. A manual `PUT` on a `FLOW` period makes it `MANUAL` and clears the sprint fields (V24, C1), so the next preview lists the sprint `MANUAL_PERIOD`. Proven by `CapacityImportApplyTest` (creates/updates/removals and every audit, the re-import, the forged requests, the `CHANGED` skips, the matrix and the order, the service's guard rails), `CapacityImportApplyRaceTest` (a manager cleared / team deleted / binding unlinked while the apply waits on the team row lock; the apply queued behind a manager's capacity POST; two applies) and `TeamViewTest` (the stub's E2E Flow Team imported, the view's weeks carry 20/18/22/20/19/21 MD a week).

## Deviations (1.6.0)

**What it is:** per bound team and per current-or-future sprint, where the plan's capacity differs from what Flow would make it carry; nothing is stored and nothing is written to Flow. **Built in 1.6.0 so far: the pure kernel and the vocabulary** (`flow/CapacityDeviation.kt`, `CapacityDeviationKernels.kt`, `CapacityDeviationKernelsTest`); the service and `GET /views/capacity-deviations` (C2), the Deviations page section and the team page line (C3) are not built yet. The vocabulary is `flow/`'s own, because a Jira deviation is a binding on a plan node (`jira/DeviationView.kt`) and `jira/` and `flow/` may not name each other; only `planning.DeviationSeverity` (the WARNING/INFO scale), `CapacityPeriod` and `capacityOn` (the team view's capacity-in-force rule, so the deviation compares what the team view shows) are imported from `planning` (`PackageBoundaryTest`).

| Kind | Rule | Severity | Silent |
|---|---|---|---|
| `CAPACITY_DIFFERS` | `abs(planMd - flowMd) >= 0.50` on the two figures rounded to two decimals (`CAPACITY_DEVIATION_THRESHOLD_MD`), over the days the sprint holds | WARNING when the plan has MORE (`gapMd > 0`), INFO when less | a gap below 0.50 |
| `CAPACITY_MISSING` | no period in force on ANY working day of the sprint's held days (`planMd` and `gapMd` null) | INFO | silent when Flow's figure is 0 too (both say nobody); a partly covered sprint is a `CAPACITY_DIFFERS` (the uncovered days count 0, as the team view counts them) |
| `TEAM_GONE` | the bound Flow team is no longer in the document (`gone` as the panel derives it); the ONLY row of the team, every detail member null | WARNING | a never-mirrored connection, a truncated document (the team stays mirrored) |

**Which sprints.** The kernel takes the import's own plan (`CapacityImportKernels.plan(..., from = null, includeClosed = false)`), so the windows, the days each sprint holds and the figures are the import's and preview and deviation can never disagree. Current or future = `end >= today` in the connection's zone (the import's `closed` inverted). **Silent:** every `SKIP` row (`NO_DATES`, `NO_CAPACITY`, `OVERLAPS`, `NO_WORKING_DAY`, `OUT_OF_RANGE`: Flow has no comparable figure; the preview lists the reason) and every `LONG_WINDOW` row (a partial, possibly non-contiguous figure the import never ticks; F11). **Compared like any other:** `MANUAL_PERIOD` rows (the point of the feature) and `ZERO_CAPACITY` ones (plan 20 a week against Flow's 0 is a WARNING; a plan on hold at 0 is nothing).

**The arithmetic (like with like).** Over the days the sprint holds, `[effectiveFrom, end]` (the import's claim), with `W` = its working days:

- `flowMd = round2(mdPerWeek x W / 5)` - what the import would make the plan carry over those days (HALF_UP). For a CALENDAR or DEFAULT sprint this is Flow's own `capacityMd` within 0.06 (`round2` on `mdPerWeek` costs at most 0.005 x W / 5); for a `TEAM_DEFAULT` sprint sharing a day (`FIXED_FIGURE`: its total is spread over its OWN window, `W_own > W`) it is the pro-rated share, which is exactly what the import writes - the raw total would raise a false INFO on every one of Onboarding's 21 shared-day sprints (F12). `flowTotalMd` carries Flow's raw `capacityMd` beside it.
- `planMd` is the team view's arithmetic over the same days (`weekCapacity`, `planning/LoadKernels.kt`): each held working day contributes `capacityOn(day) / 5` at scale 6 (a day before the first period contributes 0), the sum rounded ONCE to two decimals, HALF_UP. `gapMd = planMd - flowMd`; both sides are rounded before the comparison, so what is shown is what is flagged.
- Both sides read the same working-day calendar, so a holiday never raises a deviation by itself. A holiday ADDED after an import lowers `planMd` (fewer covered days) while `flowMd` re-spreads over the remaining days: an INFO that a re-import clears (the preview then offers an UPDATE); a holiday removed is the mirror image (a WARNING). A manual period INSIDE a sprint (`MANUAL_PERIOD_INSIDE`) adds its figure over its days: a deviation only when the total differs by 0.50.
- The result is ordered by `effectiveFrom`, then sprint id.

**No acknowledge** (1.6.0 Q1a): the remedy is one click away (Import capacity... rewrites the Flow periods; a hand-entered period is the manager's own decision; a `ZERO_CAPACITY` sprint is never preselected, so an earlier sprint's figure carried over it stays a WARNING until its row is ticked by hand or a 0.00 period entered) and the horizon is rolling, so a fingerprint-keyed acknowledgement would churn as sprints open and close. Backlog: `BACKLOG.md`. Proven by `CapacityDeviationKernelsTest` (hand-counted vectors: a clean import, the stub's six E2E sprints against a manual 20 a week, the threshold on both sides, missing, a period starting mid-sprint, a manual period inside a sprint, a holiday added and removed, every skip reason, a long window, zero capacity, a shared-day `TEAM_DEFAULT` sprint, closed against current, gone, the order).

## The token's life

Encrypted at write (`FieldCipher`, `enc:v1:` envelope), write-only on the wire (`hasApiToken`), masked in every `toString` (`SecretToStringTest`), decrypted in memory by exactly two readers in `FlowConnectionService`: `readForTest` and `readForRun`. A `PUT` with a token rotates it; a changed token or zone clears `last_tested_at/ok`. Deleting a connection sets the column to NULL, soft-deletes its bindings and removes its runs and mirror in one transaction.
