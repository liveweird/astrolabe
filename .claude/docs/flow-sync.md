### The Flow sync (v1.5.0, in progress)

Read before touching `flow/`, `FlowOrigins`, the Flow stub or the Flow pages. **What it is:** Astrolabe reads Flow (the sibling app) through its read-only service token and mirrors one document - every team with its dated members and its sprints - into typed tables; **nothing is ever written to Flow**. The connection registry, Test connection, the run, the status and polling (C1-C5), the team binding with the roster panel (C6) the capacity import's kernel and preview (C7) and its apply (C8) are built. **It is proven against the built-in Flow stub only and not yet against a real Flow** (the plan's first real-Flow walk-through is the first real test). The shape is `jira-sync.md`'s on purpose: read it for the registry, the scheduler and the status, which are the SAME code (`sync/`).
Related: schema `persistence.md` ("The Flow sync tables (V24)"); outbound guard `security.md` "The Flow consumer"; audit events and the run log lines `observability.md` ("Sync runs", "The Flow run"); per-route guards `authorization.md`; the stub `sample-data/flow/README.md`.

Rate bucket: `flow-test` 10/min per IP (`FLOW_TEST_RATE_LIMIT_PER_MINUTE`, 1..100; the e2e stacks pin 30), Test connection only, its own bucket (a Flow test never spends a Jira one). A run, a poll and a refresh ride no bucket (one call, serialised by the claim).

## The transport

Flow is the sibling app, reached over `GET /api/v1/integration/me` and `GET /api/v1/integration/teams?sprintsSince=YYYY-MM-DD` with `Authorization: Bearer flow_int_<43 base64url>`. The allow-list is OPERATOR configuration (`flow.*`, `security.md` "The Flow consumer"): a connection's `baseUrl` is exactly one listed origin and its identity (a `PUT` with another is `409`). The wire contract is written in two places that must agree and are proven aligned by `FlowClientTest` and `FlowStubFixtureTest`: `flow/FlowDocument.kt` (the decoder) and `sample-data/flow/contract.mjs` (the stub's builders). Failure codes (`FetchException.code`): `AUTHENTICATION_FAILED` (401: Flow's one uniform answer - revoked, expired or wrong), `NOT_FOUND` (a Flow older than 1.57.0), `UPSTREAM_UNAVAILABLE` (5xx), `RATE_LIMITED` (429), `REDIRECT`, `LIMIT_EXCEEDED` (the 1 MiB response cap), `INVALID_RESPONSE`, `TIMEOUT`, `BLOCKED_HOST`. Config (`flow.*`, env `FLOW_*`): `requestTimeoutSeconds` 30, `requestDeadlineSeconds` 60, `maxResponseBytes` 1 MiB, `maxConcurrentRequests` 1, `maxRetries` 2, `sprintsSinceDays` 365 (30..1095).

## Test connection and the probes

`FlowConnector.testConnection` runs two required probes in sequence (10 s each, 30 s in all, never throwing; every outcome is a row, **never a 502**): `me` (the token is live; `NOT_FOUND` carries the hint "Flow 1.57.0 or later") and `teams` (the document decodes; the result adds "N teams, M sprints" and `truncated`; `SKIPPED` when `me` failed), plus the one `stored_token` row (`TOKEN_UNREADABLE`) when the stored token cannot be decrypted. `POST …/{id}/test` records `last_tested_at/ok` unless the row was edited meanwhile (`recorded`) and audits `flow.connection_tested`. **Test connection never writes the mirror**: the run is its single writer; a passing test is what makes the connection pollable, so the first run follows within a tick.

## The run

`FlowObserver` (the `Connector` of kind `FLOW`, registered by `configureFlow`) does, per claimed run: read the connection and its token in one short transaction (`FlowConnectionService.readForRun`, the second of the two decrypting readers) - then NO database transaction is open until the call has returned; ONE `GET /integration/teams?sprintsSince=` where `sprintsSince` is today in the CONNECTION's zone minus `flow.sprintsSinceDays`; `FlowMirrorStore.replace` in one transaction, which re-reads the connection under its row lock (`FOR NO KEY UPDATE`) and writes nothing when it was deleted (`GONE`) or disabled (`DISABLED`) meanwhile. It OBSERVES: no plan lock, no revision, nothing sent to Flow beyond the one GET.

| Situation | Run | Mirror |
|---|---|---|
| a document | `SUCCEEDED`; `observed` = teams, `gone` = ACTIVE bindings whose Flow team the document lacks, `calls` = 1 | replaced wholesale, `teams_at` stamped |
| `401` | `FAILED` `AUTHENTICATION_FAILED` (a revoked or expired token; rotate it with a `PUT`: that makes the connection due at once) | keeps its last document |
| `5xx` / `429` | `FAILED` `UPSTREAM_UNAVAILABLE` / `RATE_LIMITED`, then the registry's doubling back-off (one interval, doubling, capped at 6 h) plus the deterministic jitter | keeps its last document |
| a body that is not the contract | `FAILED` `INVALID_RESPONSE` | keeps its last document |
| unreadable token / unknown zone | `FAILED` `TOKEN_UNREADABLE` / `TIME_ZONE_INVALID`, no call | untouched |
| connection deleted / disabled while the call was in flight (judged under the row lock at the write: `FlowMirrorWrite.GONE` / `DISABLED`) | `FAILED` `CONNECTION_GONE` / `CONNECTION_DISABLED` | nothing written (a deleted connection's mirror and token are already gone; a disabled one keeps its last document and `teams_at`) |
| `sprintsTruncated` | `SUCCEEDED` + a WARN (counts only) | the document Flow sent is kept |
| `teamsTruncated` | `SUCCEEDED` + a WARN; `gone` is **0** | the teams it carries are replaced, **every other mirrored team is kept whole** |

**The `teamsTruncated` rule.** Flow caps a document at 1,000 teams (and 2,000 sprints). A team absent from a truncated document was merely not sent, so it is neither deleted from the mirror nor counted `gone` (and the panel and 1.6's `TEAM_GONE`, which derive `gone` from the mirror, never see it vanish); the next complete document is authoritative. The cost: a team really removed from Flow stays mirrored while Flow keeps truncating. `FlowRunWireTest` pins it (three documents: complete, truncated, complete).

**The token never appears** in a log line, an audit, a run row or a problem body: the run's error text is fixed (`Flow fetch failed: {code} ({status})`, never the exception message, which quotes a URL), `clampErrorDetail` is only the backstop, and `FlowRunWireTest`, `SyncRunRoutesTest` assert it with a ROOT `LogCapture`.

## Polling and status

Polling is the 1.3 scheduler unchanged (`observability.md` "Sync runs"); Flow's parts: the default interval is **60 minutes** (5..1440, `null` = manual only; STALE after 3 intervals, so 3 h), `ready` = a Test connection passed (`last_test_ok`) OR a run has mirrored a document (`teams_at`) - sticky like Jira's `discovered_at`, so a token or zone `PUT` (which clears the test verdict) or a Test that hit a Flow outage never stops a connection that has run from polling; a never-tested, never-run connection is not polled, `changedAt` = the later of `updated_at` and `last_tested_at`, so a rotated token or a fresh passing test makes the connection due at once whatever a back-off says. `pollRows` (`FlowConnectionPolling.kt`) reads eight columns and never the token. Every connection answers a derived `status` and `lastRun` (`SyncStatusKernels.derive`, the same rule and readers as Jira's: the registry, the telemetry `sync` block; nothing is stored). Proven by `FlowRunTest` (the stub: NEVER_SYNCED to CURRENT, the mirror equals `sample-data/flow/expected.json`, day two drops Billing and counts the bound team gone, an outage, a revoked token), `FlowRunWireTest` (MockEngine), `FlowConnectionStatusTest`, `SyncSchedulerTest` ("a tested Flow connection is polled, an untested one is not") and `TelemetryRoutesTest`.

## Bindings

A binding links ONE Astrolabe team to ONE Flow team of a connection (V24 `flow_team_bindings`; 1:1 both ways over the ACTIVE rows, and a team has one Flow team across ALL connections). It is what feeds the team's roster panel now and the capacity import (C7) next. Not plan state: no plan lock, no revision; the link and the unlink call Flow never (they read the mirror) and ride no rate bucket. A binding follows the Flow team's **id**; `flow_team_name` is display text frozen at link time (a rename in Flow changes nothing).

**Match by name** (`FlowTeamMatchKernels`, pure): a Flow team is *suggested* to an Astrolabe team when the folded names are equal - trim, collapse every run of whitespace to one space, lowercase; **accents count** ("Płatności" is not "Platnosci": a wrong automatic link is worse than a missing one) - and the Astrolabe team is the ONLY unbound active team with that folded name. The rule is symmetric: two Flow teams that fold to one name are suggested nothing (so "Link all suggested" can never ask for one team twice). A bound team is never re-suggested, and neither is a Flow team that is bound. `GET /integrations/flow/teams` shows the suggestion per Flow team; `POST …/connections/{id}/team-bindings/match` (ADMIN) links every current suggestion in ONE transaction and reports `bound[{bindingId, teamId, flowTeamId}]` and `skipped[{flowTeamId, reason}]` (`ALREADY_BOUND`, `NO_MATCH`).

**`GET /integrations/flow/teams?connectionId=` is unpaged, by decision** (recorded in `list-endpoints.md` with the view endpoints' shape exception: an unpaged `{connectionId, teamsAt, items[≤ 1,000]}`; the paged envelope stays for every ordinary resource list): it is the mirror of ONE Flow document, which Flow itself caps at 1,000 teams (the real figure is 15-100), and the suggestion needs every unbound team at once, so it is a bounded document of `{connectionId, teamsAt, items[≤ 1,000]}` like the view endpoints, not a `{items, page, pageSize, total}` envelope. Items come by name then id. It serves the connection page (ADMIN) and the manager's link dialog.

**The link** (`FlowTeamBindingService.bind`): one transaction under a global advisory lock (`FLOW_BIND_LOCK_KEY`, "AstroFBT": links are human clicks, and the two uniqueness checks are exact over rows that may not exist yet), the connection row `FOR SHARE` (a delete or a run's mirror replace waits), the Flow team read from the mirror as it is now, the team row `FOR SHARE`, the guard again, then the checks and the insert. **A soft-deleted team keeps its ACTIVE binding** (`teams/` may not name `flow/`): the link and the match RELEASE a dead team's holder of the Flow team (soft-delete, audited `flow.team_unbound` reason `TEAM_GONE`, the Jira bind's dead-node idiom), and `bindingsOf`, the match, the list, the panel and the unlink's lookup all filter on ACTIVE teams, so a Flow team once linked to a deleted team can be linked again and a dead team's binding is invisible (404 to unlink). A connection delete soft-deletes its bindings in its own transaction, so a deleted connection's bindings are hidden at once.

**The panel** (`GET /teams/{id}/flow`, `FlowTeamService.panel`, its own read, not a member of the team view): `binding` (connection NAME, enabled flag, the connection's `SyncStatus`, `observedAt`, `gone`), `roster` and `sprints{count, nextStart}`, all null for an unlinked team; `roster` and `sprints` are also null when the Flow team is **gone**. `gone` is derived at read time and never stored: the connection HAS mirrored a document (`teams_at` set) and the Flow team is not in it (consistent with the run's `gone` count, which skips a truncated document). `can{link, unlink, importCapacity}` is ADMIN or the team's active manager (one verdict, three flags). **The roster** (Q2a: every signed-in user sees it - one predicate, `rosterVisibleTo`): memberships are half-open instant intervals `[validFrom, validTo)`; *current* when `validFrom <= now < validTo` (an open end never ends), *former* when `validTo <= now`; a membership that has not started is in neither list; dates are the instants in the connection's time zone (a zone this JVM no longer knows reads as UTC, the run reports it); a null display name reads **"Unknown account"** (server-side text); a person with two intervals appears once per interval. Account ids never leave the server. `nextStart` is the first mirrored sprint start that is today (in the zone) or later.

Proven by `FlowTeamMatchKernelsTest`, `FlowTeamBindingTest`, `FlowTeamMatchTest` (a scripted MockEngine document with this test's unique team names, a real run behind it), `FlowTeamPanelTest`, `AuditTest`.

## The capacity import

**The rule, in the user's words:** a sprint's man-days from Flow are spread over the sprint's WORKING days (Astrolabe's calendar: Monday-Friday minus the public-holiday dictionary), so the weekly capacity Astrolabe computes over the sprint adds up to what Flow says, within rounding - a holiday inside the sprint raises the figure instead of losing man-days. `mdPerWeek = round2(5 x flowMd / workingDays)` (BigDecimal, `HALF_UP`), one capacity period per sprint (a period holds until the next one, so a gap between sprints keeps the previous figure; the weeks before a team's first imported sprint stay "no capacity"). Example: 40 MD over 10 working days is 20.00 a week; over 9 (one holiday) it is 22.22, and `weekCapacity` over those two weeks sums back to 40.00.

**The span is Flow's own, and consecutive sprints share a day** (Flow `metrics.md` A42; `DeriveSprintStep`: the window is `[dayOf(start), dayOf(max(start, end - 1 ms))]`). `spanEnd = min(endAt, completeAt)` when both exist (a sprint completed early ends when it was completed), else whichever exists; `end = dayOf(max(startAt, spanEnd - 1 ms))` in the connection's zone, so an end at local midnight adds no day and a zero-length sprint is one day; an end BEFORE the start stays `NO_DATES` (never a one-day sprint). Real Jira sprints end on the day the next one starts: **that shared day belongs to the EARLIER sprint** (Flow's rule: the first sprint holding a day claims it), and the later sprint's period starts on `effectiveFrom = max(start, previous kept sprint's end + 1 day)` - which may be a Saturday: a period may start on any date. A Monday-to-Monday series therefore has W = 11 for the first sprint and 10 for each next. The working days, the existing-period lookup, `MANUAL_PERIOD_INSIDE` and every removal rule use `effectiveFrom`, never the raw start. Only a start BEFORE the previous kept sprint's end is a genuine overlap (`OVERLAPS`); so is a sprint with nothing left after the shared day.

**The promise: a hand-entered period is NEVER changed or removed by the import.** A sprint whose `effectiveFrom` already holds a manual period is `MANUAL_PERIOD` (left alone, shown with the figure it would have had); a manual period that starts INSIDE a sprint (after `effectiveFrom`, up to its end) adds the info `MANUAL_PERIOD_INSIDE(date)` - the sprint's figure will not hold from that date. Only periods the import itself wrote (V24 `source = FLOW`) are updated or removed; a manual PUT on one makes it manual (C8).

`CapacityImportKernels.plan(sprints, zone, calendar, today, existingPeriods, from, includeClosed)` is pure (`flow/CapacityImportKernels.kt`; the vectors are counted by hand in `CapacityImportKernelsTest`). Dates are the mirror's raw instants in the CONNECTION's zone, so a zone `PUT` takes effect at once. Per sprint, in start order (undated last), the first rule that fires:

| Step | Outcome |
|---|---|
| no start, no `endAt`/`completeAt`, or an end before the start | `SKIP` `NO_DATES` (asked first) |
| `capacityMd` null (Flow has none) | `SKIP` `NO_CAPACITY` |
| starts before the end of the previous sprint that was kept, or `effectiveFrom > end` | `SKIP` `OVERLAPS` (the earlier start wins) |
| no working day from `effectiveFrom` to `end` | `SKIP` `NO_WORKING_DAY` |
| figure beyond the man-day bounds of a period (`validateManDays`) | `SKIP` `OUT_OF_RANGE` |
| no ACTIVE period starts on `effectiveFrom` | `CREATE` |
| a `FLOW` period does, with another figure, sprint id or name | `UPDATE` (the WIP limit is kept: Flow has none) |
| a `FLOW` period does, equal | `UNCHANGED` |
| a `MANUAL` period does | `MANUAL_PERIOD` |

"Kept" = got past `NO_DATES`, `NO_CAPACITY`, `OVERLAPS` and `NO_WORKING_DAY` (an `OUT_OF_RANGE` sprint still claims its days). **A sprint with 0 man-days** (Flow's DEFAULT is 0 for a team without members) is planned like any other but is never ticked and carries the info `ZERO_CAPACITY`.

**Closed sprints.** `from` (default: today in the connection's zone - decided here, §11 of the plan was silent) is the first day the import is about; a sprint whose `end` is before it is closed, listed only with `includeClosed` and never ticked (`ticked` = not closed, not zero-capacity, and CREATE or UPDATE). Overlaps are decided by the dates alone, before the toggle hides anything. **`removals[]`** are the team's `FLOW` periods that no listed sprint reuses and that (a) belong to a sprint missing from the mirror's document and lie in the window (`date >= from`, or any date with `includeClosed`) - a sprint older than `flow.sprintsSinceDays` leaves Flow's document and its history must not be offered for deletion - or (b) start inside `(effectiveFrom, end]` of a sprint the import covers (not closed; CREATE, UPDATE or UNCHANGED), where they would cut the figure short (a re-dated sprint), or (c) belong to such a covered sprint without being the period its item reuses (a sprint moved later). **A removal is never preselected** by a client: it is listed and the person ticks it. A Flow team that is not in the mirror (gone, or never mirrored) previews an EMPTY plan with `observedAt` null: nothing is removed on the strength of an absence. A disabled connection still previews (the preview reads the mirror, never Flow). A closed sprint, or a team's first import, leaves the weeks before it untouched; the last sprint's figure stays in force until the next import (the modal's footer says so).

**The preview** (`POST /integrations/flow/team-bindings/{id}/capacity-preview {from?, includeClosed?}`, `CapacityImportService.preview`): one `READ ONLY REPEATABLE READ` snapshot of the binding and its connection's zone, the holiday calendar, the Flow team's mirrored sprints and the team's ACTIVE periods (`TeamCapacityService.importRowsOf`); the clock is injectable (`now`, a test pins "today"). It stores, locks, audits and sends NOTHING. Response: `{bindingId, teamId, observedAt, zone, from, includeClosed, totals{create, update, unchanged, skip, removals}, items[…], removals[…]}` - `from` is the RESOLVED date and `includeClosed` an echo, so the apply can send both back and re-run the kernel identically; `skip` counts `SKIP` and `MANUAL_PERIOD`; `mdPerWeek` is a number with at most two decimals; an item carries `start`, `end`, `effectiveFrom`, a removal its `flowSprintId`. The apply (below) re-runs the kernel under the team row lock and skips a row that no longer equals what the preview showed; its UPDATE also rewrites `flow_sprint_id` (a period reused for another sprint). Proven by `CapacityImportKernelsTest`, `CapacityImportPreviewTest` (the stub's E2E Flow Team equals `expected.json`: 20/18/22/20/19/21 MD a week; a seeded public holiday inside a sprint gives 9 working days and 22.22) and, for the shared day, the stub's Identity team (below).

**The apply** (`POST /integrations/flow/team-bindings/{id}/capacity-import {from?, includeClosed, items[{sprintId, expected{action, effectiveFrom, mdPerWeek}}], removals[periodId]}`, `CapacityImportService.apply` → `TeamCapacityService.applyImport`; `CapacityApplyKernels` is the pure decision). The client sends what the person ticked in a preview, with the preview's echoed `from` and `includeClosed`. **Guard order is the preview's** (binding `404` → `403` → body `400`), and the body is bounded (≤ 2,000 `items` and `removals`, each sprint and period at most once, `expected.action` only `CREATE` or `UPDATE`, a valid date and a man-day figure). Then ONE transaction, team data, no plan lock and no revision:

1. `Teams.lockActiveForWrite` (the team is gone: `404`), then the guard AGAIN under the lock (`lockedIsActiveManager`: a manager cleared while the request waited is `403` and nothing is written).
2. The team's ACTIVE periods are re-read under the lock; the binding is re-read inside the transaction (a plain read - the binding row is not locked - so an unlink committed before it is `404`, one committed after it is not noticed); the Flow team and its sprints are read NOW in ONE statement (`FlowMirrorStore.teamSprintsOf`; a Flow team no longer in the mirror re-plans as EMPTY: every row is then skipped - nothing is imported or removed on the strength of an absence).
3. `CapacityImportKernels.plan` runs again over those rows with the echoed `from` and `includeClosed` (today in the connection's zone when `from` is absent).
4. **Each requested item is written only when the re-computed plan lists its sprint as `CREATE` or `UPDATE` with the SAME `action`, `effectiveFrom` and `mdPerWeek` as `expected`** - otherwise it is skipped `CHANGED`. That covers a figure that moved in Flow, a sprint that was re-dated or left the document, a row that was never in the plan, and - the dangerous one - a start date a person took over meanwhile (the plan now says `MANUAL_PERIOD`). The period an UPDATE rewrites is the plan's `existing` period, never an id from the request.
5. **A removal is applied only when its period is one of the re-computed plan's `removals`** (a Flow-sourced period); a MANUAL period, a period deleted meanwhile and an unknown id are skipped `CHANGED`.
6. **A MANUAL period is never written by any path**: not as an item (a forged `CREATE`/`UPDATE` for the sprint whose start it holds is `CHANGED`), not as a removal; and `applyImport` re-checks every write against the locked rows and in each statement's `WHERE` (`persistence.md`).
7. Writes, in this order: removals (soft delete), updates (`md_per_week`, `flow_sprint_id`, `flow_sprint_name`, `updated_at`; the WIP limit is KEPT), creates (`insertRows`, `source = FLOW`).

**What `expected` does not cover:** a MANUAL period entered INSIDE a sprint's span after the preview is not part of `expected` (only the sprint's own start date is) - the CREATE or UPDATE still applies, and the manual period cuts the sprint's figure short from its date, exactly as the preview's `MANUAL_PERIOD_INSIDE` info warned.

Response `200 {created[{periodId, sprintId}], updated[{periodId, sprintId}], deleted[periodId], skipped[{sprintId|null, periodId|null, reason}]}` - a skipped row is data, not an error; the only reason is `CHANGED`. The apply is idempotent in effect: the same body sent twice writes once (the second finds every row `UNCHANGED` or gone and skips it), and a re-import right after is all `UNCHANGED` with nothing written. Audits (`observability.md`): ONE `team.capacity_imported` plus the existing `team.capacity_period_created/updated/deleted` per period with `sourceTo`/`sourceFrom` = `FLOW`. A manual `PUT` on a `FLOW` period makes it `MANUAL` and clears the sprint fields (V24, C1), so the next preview lists the sprint `MANUAL_PERIOD`. Proven by `CapacityImportApplyTest` (creates/updates/removals and every audit, the re-import, the forged requests, the `CHANGED` skips, the matrix and the order, the service's guard rails), `CapacityImportApplyRaceTest` (a manager cleared / team deleted / binding unlinked while the apply waits on the team row lock; the apply queued behind a manager's capacity POST; two applies) and `TeamViewTest` (the stub's E2E Flow Team imported, the view's weeks carry 20/18/22/20/19/21 MD a week).

## The token's life

Encrypted at write (`FieldCipher`, `enc:v1:` envelope), write-only on the wire (`hasApiToken`), masked in every `toString` (`SecretToStringTest`), decrypted in memory by exactly two readers in `FlowConnectionService`: `readForTest` and `readForRun`. A `PUT` with a token rotates it; a changed token or zone clears `last_tested_at/ok`. Deleting a connection sets the column to NULL, soft-deletes its bindings and removes its runs and mirror in one transaction.

| # | Assumption | Status | Where it shows |
