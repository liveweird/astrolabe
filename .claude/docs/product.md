## What Astrolabe is

A planning and roadmapping app in the spirit of Jira Plans — better UX, more opinionated, Gantt-centred — for a multi-stream / multi-program / multi-team environment. It keeps its
**own** plan data. Later it syncs with Jira and Flow only to **detect deviations**; corrections are made in Astrolabe, never written back. The name is the instrument: a tool for
reading where everything stands against time.

Scale assumed: about 15 teams, 5 work streams, 20 programs, 100 projects, 1,000 milestones.

## Domain decisions taken with the user

- **Hierarchy.** Work stream (start, owner; end set only on close) → program (owner; span derived from its projects) → project (owner; **optional target window**; real span derived
  from milestones; drift flagged) → milestone (start/end, man-day estimate, exactly one team, no owner). All have a name and a description.
- **Capacity.** A team has man-days per week with effective-from periods. A milestone's estimate is **spread evenly** over its working days; the weekly load is compared with capacity.
  **Built (0.5.0), on the user's answers of 2026-11-01:** a period takes effect on **any date** (a weekend date applies from the next working day; the week it starts in counts each working day at the figure in force that day), carries an **optional WIP limit** (the most milestones in progress on one working day; parallel work is allowed, too much of it only warns) and is added, edited and deleted by the team's manager or ADMIN. The team page (`/teams/:id`) shows it as a sticky strip under the dates, orange badges on the facts line and a Weekly load table (the accessible surface); overload and WIP are orange warnings, nothing moves. **Override UI (Q8b):** the row menu (Move up / down / to top / to bottom) and a "Reset order" button are the deterministic path and are built; the row handle's pointer drag follows in its own commit.
- **Scheduling.** Manual drag/resize first. **Auto-proposal built (0.8.0)**: rank + dependencies + capacity → a proposal the manager accepts or adjusts; it never writes by itself.
  **Built (0.8.0), on the user's answers** (the plan `astrolabe-v0.8.0-auto-proposal.md` §1.2 of 2026-11-01 and §8 of 2026-11-02; **the user's own decisions** are marked, the rest are the defaults below): (1) **what may move: not yet started** (the user) - unscheduled milestones and scheduled ones whose start is after today; in-progress and past ones are fixed. (2) **duration from the estimate** (the user): ceil(estimate / capacity share), share = capacity / WIP limit; greedy in the team's milestone order, after dependencies, within capacity and WIP, on the holiday calendar. (3) **one team per run** (the user), run by the team's manager or ADMIN from the team page; other teams' dates are fixed constraints. Q1 **re-plan every not-started milestone from the earliest possible day, pulling earlier** (the user, option a). Q2 **a link into another team's fixed milestone is placed anyway** and shown red "would be violated", never reordered (the user). Q3 **days with no capacity period, or on hold, are not usable**; a team with none gets "add a capacity period first" (the user). Q4 **a milestone changed since the proposal is skipped, the rest are written** ("1 skipped: rescheduled in the meantime") (the user). Q5 **a 0 MD checkpoint takes one working day after its dependencies and counts toward WIP that day** (the user). Q6 **the target window is a target, not a constraint** (the user). Details and the algorithm: `planning-model.md` "The auto-proposal".
- **Dependencies.** milestone↔milestone (cross-project), milestone↔project, project↔project. Types FS/SS/FF/SF plus a lag. Violations **warn only** (a red link and a conflict list),
  never cascade-move anything.
  **Built (0.4.0), on the defaults the user confirmed on 2026-11-01** (recorded here so overturning one is a known change): (1) who may link — the **successor's** project chain or ADMIN
  (the predecessor's owner sees the arrow and its warning but cannot remove it; overturned = C1 guard/matrix/tests, C3 `can.delete`, the dialog intro); (2) the lag is an integer of
  **working days, negative allowed (a lead), |lag| ≤ 365** (V15's CHECK is immutable); (3) an **unscheduled end is not evaluated** — status UNSCHEDULED, no warning, no arrow, "Not scheduled yet" in
  the table; (4) a link is created **on the successor's project page** (`POST /projects/{id}/dependencies`, the successor fixed to that project or one of its milestones; the predecessor is a free
  search); (5) the project's **summary row** shows only while the project itself is an endpoint; (6) **at most one active link per unordered pair** of ends (a reverse pair answers the same 409 "already
  linked"; the type and lag are edited in place with `PUT /dependencies/{id}`, the ends never: pointing a link at another end = delete + add). The UI shows these as: the Dependencies table (violated first = the conflict list), the red "N conflicts" badge, the dialog's
  successor-first form, the cycle notice with its path. The start-to-finish rule is `W(A.effStart) − 1 + lag`.
- **Ranking.** **One global project rank**. A team's milestone order follows it by default; the team may override locally (and reset).
  **Built (0.5.0, V17), on the user's confirmed reading "A" (2026-11-01)** — two ranks with two meanings: the PROJECT rank is the top-down SUGGESTION of the order in which projects should be delivered; the MILESTONE order is the order of ACTUAL EXECUTION and is per TEAM (each team's manager orders their own team's milestones, and a lower-ranked
  project's milestone may come before a higher-ranked project's). The project rank is only the DEFAULT of a team's order, used until the team overrides it and again after a Reset. **A manager's override is never reshuffled by a later project-rank change**: the stored positions are the team's own, and only milestones the team did not list (new, or moved onto the team) slot in after the listed ones, in project-rank order.
  The "rank-vs-time inversion between projects sharing a team" is a WARNING (built in 0.6.0, below). The order is written wholesale (`PUT /teams/{id}/milestone-order`, `[]` = reset) against the team's OWN order revision, so only that team's order write stales a reorder.
- **Roadmap and programs timelines.** **Shipped in 0.6.0, on the user's answers of 2026-11-01** (the plan `astrolabe-v0.6.0-roadmap-programs.md` §2, §9): (1) the Roadmap is a **Timeline** (one row per project in rank order; rank by row drag and the row menu; the unranked projects under an "Unranked" divider, a drag across it = Rank/Unrank); (2) a project row = its derived span bar over the **target window as a band**, no milestone segments; (3) `/programs` is a collapsible tree work stream → program → project, a program's bar its derived span, **no target window on programs**, a roll-up count of its projects' flags; (4) the **program pick** is a multi-select on both pages, default all, remembered in the browser (one key for both pages); (5) **drift:** ending later than the target end = WARNING, a late start or finishing ahead = INFO; (6) **rank inversion** = WARNING: A ranked above B, both with scheduled work on team T, B's work on T starting before A's, **raised for adjacent pairs per team** (the volume decision: 184 flags on the sample plan against 1,038 for all pairs), and an INFO for an adjacent pair that shares no team; (7) flags show as a row icon (orange warning / grey info) and a collapsible panel, a click scrolls to the row; (8) the **target window by drag** (move/resize the band, draw across a row with none) and by the row menu's dialog / Clear as the keyboard path, on both pages, by ADMIN, an owner above the project or a `ROADMAP_EDITOR` (no new rights); (9) **arrows:** direct project↔project links plus one rolled-up arrow per project pair for their milestone links (red when any is violated); (10) **Month / Quarter / Year** zoom on these two pages (Year new, no Week, default Quarter, no time-axis virtualisation); (11) roadmap filters besides the pick: work stream, team, owner, flagged only. Nothing is stored for any of it (no migration): spans, drift and flags are derived at request time (`planning-model.md`).
- **Owners.** A **people directory** (name, email, optional link to a login) — owners are people, not necessarily users.
- **Plans.** One live plan; plan-wide baselines to compare it with (built in 0.9.0); no scenarios.
  **Built (0.9.0), on the user's answers of 2026-11-02** (the plan `astrolabe-v0.9.0-baselines.md` §6, §8; all nine questions answered with the recommended option, so each is **the user's own decision**): (Q1a) a baseline **captures** every active milestone (name, project, team, dates, estimate) and every active project (name, program, work stream, target window, rank position, derived span) - the dated structure everything the timelines draw; links, capacity periods, holidays and team orders are not copied. (Q2a) **ADMIN or a `ROADMAP_EDITOR`** takes, renames and deletes; reads are every authenticated user's. (Q3a) **plan-wide only**: one object at one plan revision, which every page filters to its own rows. (Q4a) it shows **everywhere, two ways**: a thin gray shadow bar under the current bar on all four timelines, a Movement table on the project and team pages ("Changed only" on by default), and a plan-wide comparison page per baseline (`/baselines/:id`). (Q5a) **no baseline by default**: a Baseline picker on the toolbar lists them newest first (the newest marked "latest"), one pick remembered in the browser for every timeline page. (Q6a) movement is **working days, start AND end, on the current calendar** ("start 4 working days later, end 5 working days later"); a later end is an orange "Later" badge, an earlier one gray. (Q7a) **rows for everything**: an added milestone keeps its bar and reads "new since the baseline"; a removed or unscheduled one gets a dimmed appended row with only its shadow bar (on the team page also "moved to {team}"). (Q8a) **a cap of 100 active baselines** (a `409` at the cap; delete makes room; a delete is a soft delete). (Q9a) a **change to the team's plan since a proposal** writes nothing and the page proposes again at once, keeping the ticks for the milestones that still move (the v0.8 per-milestone STALE rule stays). Details: `planning-model.md` "Baselines", `timeline.md` "The baseline overlay (v0.9.0)".
- **Permissions (owner-scoped).** ADMIN may do everything. Ownership cascades down (work stream → program → project). A project owner edits the project and its milestones' plan fields
  (name, description, team, estimate, dependencies) but **not dates**. **Milestone dates are set only by the team's manager** (or ADMIN). The global rank is edited by ADMIN and by users with the
  per-user **ROADMAP_EDITOR** grant. A team manager edits the team's capacity and team order. Reads are open to every authenticated user. (Rules land in `authorization.md` as each route does.)
- **Jira sync.** **Decided 2026-11-06** (the plan `astrolabe-v1.1.0-jira-sync.md` §1.2 and §10; the six decisions are the user's own, the nine questions were all answered with the recommended option): (1) work streams are categories and never live in Jira (nothing maps, binds or imports one); (2) programs, projects and milestones each map to ONE configurable Jira hierarchy level per connection (milestone = Epic by default; the mapping names the integer `hierarchyLevel`, not a type list); (3) bindings are 1:1 per node and per Jira item, and the plan can later be IMPORTED from Jira (preview, then apply; never overwriting); (4) the field mappings are configurable and the defaults come from Jira Plans ("Target start"/"Target end", then "Start date"/`duedate`); (5) no real Jira site exists yet, so everything is proven against a stub and the first real test must be cheap; (6) from Flow, capacity and team membership "for now" (1.5, blocked on a read-only Flow token). The §2 answers: the cut is 1.1 connection + mapping + manual bindings + Refresh + Deviations, 1.2 import, 1.3 polling/acknowledge/markers, 1.4 coverage, 1.5 Flow; **estimates convert only with a declared unit or factor** (otherwise the Jira figure is only shown); **linking** is the node's owner chain or ADMIN; **import** is ADMIN or an owner of every target, dates copied only where the caller may schedule; re-import never overwrites; orphans go under a default parent, else are skipped; a milestone's team on import is a name match, else the default team, else skipped. The sync **detects**; deviations warn only and nothing is written to Jira. The overnight defaults D1 (one link per site across connections), D2 (deleting a connection unlinks its bindings), D3 (discovery stored even if other probes fail), the empty-sweep default and a disabled connection's bindings staying visible were **kept by the user on 2026-11-07** (`jira-sync.md` "Decisions"). **Coverage (1.4, decided 2026-11-07, all six questions answered with the recommended option):** the run observes the census into a mirror and the views read only the database (Q1a); coverage surfaces as three deviation KINDS on the parent's binding, not a page of its own (Q2a); the child level is re-listed once a day by an id sweep and in full on every full read (Q3a); `UNLINKED_IN_JIRA` is a warning, `UNLINKED_IN_PLAN` and `CHILDREN_DONE` infos (Q4a); the roll-up is compact dimmed text after the Jira key (Q5a); the `jira-test` bucket became configurable instead of spending the tenth call (Q6a).
- **Gantt.** A custom shared timeline component: DOM rows + SVG arrows, dnd-kit, TanStack Virtual (`timeline.md`).
- **Brand.** Deep cyan / ocean (`astrolabe` colour tuple, primary `#0b7285` light, `#095c6b` dark); the logo is a stylised astrolabe (limb ring with ticks, rete star pointers, alidade).
  Success is green, red = blocking, orange = warning (`web/CLAUDE.md`).

## Assumptions (not asked — change on request)

Day-precision dates; Monday–Friday working days, fixed, minus the public-holiday dictionary (built in 0.7.0); week / month / quarter zoom (month / quarter / year on the roadmap and programs pages); EN and PL kept; the scale above.

**Defaults taken for v0.8.0 (overnight, 2026-11-02; not asked, change on request):** (a) **the pin rule** - a scheduled milestone the proposal cannot place keeps its stored dates and its load (it is listed as unplaced, and the run repeats to a fixed point, so accepting never overloads a week through it); (b) **the weekly capacity check** - capacity is checked per ISO week as well as per day, so a proposal never adds load to a week the team view would show overloaded; (c) **no toast on accept** - the outcome note under the table carries the message ("3 scheduled", "2 scheduled · 1 skipped: rescheduled in the meantime"); (d) **link warnings assume every move is accepted** - the proposal's link check shows the plan after ALL moves, not the ticked subset; (e) **per-team fixed point** - each run reaches its own fixed point, and other teams' dates are constraints, so a later run after another team accepted may move milestones again (measured: 213 of Platform's 275 after the other 14 teams were accepted); (f) **the accept's scope** - v0.8 saw only writes to the milestones IN the batch, a known limitation; **it is closed by the v0.9 scope check (C4)** (user answer Q9a: a scope fingerprint `scopeHash` plus a `schedule_revision` sweep, `409 stale-scope`, nothing written, the page proposes again at once and keeps the ticks; the per-item `STALE` rule stays); (g) **the size budget** - <= 150 KB uncompressed for the largest team. v0.8 first raised it to 250 KB (170,731 B on the sample plan's Platform); **the budget is back to <= 150 KB after v0.9 C3** slimmed `dependencies[]` (only the links violated before or after the moves, ends `{kind, id, name, projectName}`): 88 KB measured (88,214 B; 88,293 B in C11).

**Defaults taken for v0.9.0 (not asked, change on request):** (a) **the overlay and comparison size budgets** - measured in C11 with the whole sample plan re-planned: the team view Platform with the overlay 254.7 KB uncompressed against a 240 KB estimate (22.7 KB gzip), the comparison document 320.8 KB against 180 KB (30.9 KB gzip), the roadmap and programs overlays +20 and +24 KB against about +8 KB. The response shapes are kept as planned and the gates are revised to the measured figures (team view <= 260 KB, comparison <= 340 KB uncompressed), because responses are gzip-compressed on the wire; slimming is the `BACKLOG.md` item "Slim the baseline overlays"; (b) **`createdBy` names the person** - the creating login's linked active person's name, else the login's display name, never the email; (c) **the stale-scope check compares a fingerprint of the team's planning inputs** (its milestone set and estimates, its order, capacity periods, the links touching it with the foreign ends' spans, the holidays); the team's own milestone dates are covered by the per-milestone revision checks, so a colleague's drag of one batch item skips that item instead of refusing the whole batch; (d) **a pick of a deleted baseline clears itself** - the page that gets `400 unknown-baseline` drops the browser-remembered pick and fetches the plain view; (e) **"Changed only" counts an estimate-only change as changed** - the row keeps the movement kind UNCHANGED but its status reads "Re-estimated" and it is listed; (f) **the comparison page's "Changed projects only" filter, on by default** - a project that did not move and has no listed row is hidden; (g) **an undated frozen milestone gets no appended timeline row** - it has no span to draw as a shadow bar, so the Movement table lists it; (h) **"Show without a baseline"** on a page whose view fails while a pick is set (any error but the deleted baseline), so a broken overlay never locks the page out; (i) **the picker is disabled while a write is in flight** (a drag, a rank change or an open proposal), so the write's answer cannot land in another view entry; (j) **baselines are soft-deleted only and their rows are frozen at the database**, so nothing purges them; a purge needs its own migration.
