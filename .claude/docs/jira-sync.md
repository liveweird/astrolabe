# Jira sync

Owns: the Jira connector (gateway, Test connection, discovery, mapping, bindings, the run, deviations, the plan's links, the import, coverage, acknowledge, timeline flags, the stub, the real-site walk-through, the assumptions ledger). Not here: runs, scheduler, status, failure codes, token life (`sync.md`); guard orders (`authorization.md`); audit events (`observability.md`); tables (`persistence.md` "Jira"); the outbound guard (`security.md` "The Jira consumer"); Flow (`flow-sync.md`); the pages (`web-internals.md`); the stub's data (`sample-data/jira/README.md`).

## Rules

- **Nothing is ever written to Jira.** The sync observes and warns; a correction is made in Astrolabe. The one Jira-derived write to the plan is the import (ADMIN or an owner of every target, under the plan lock).
- **A stored site URL never steers authenticated traffic.** Every authenticated call goes to `https://api.atlassian.com/ex/jira/{cloudId}/rest/api/3/...`; only the unauthenticated `GET https://<site>/_edge/tenant_info` goes to the site and supplies the `cloudId` (`HttpJiraClient.resolveCloudId`; validated as a UUID before it is stored or spliced into a path). One guarded client serves the app.
- **The registry is ADMIN only on every operation, reads included, `requireAdmin` before the body.** Its token is write-only (`sync.md` "A stored token's life"). Test connection never answers 502: every outcome is a row of a `200`.
- **A binding is 1:1** per plan node and per Jira issue, across the active connections of a site. Binds serialize on `BIND_LOCK_KEY`; the one Jira call of a bind is outside any transaction; a binding is not plan state (no plan lock, no revision bump).
- **A run observes and holds no plan lock,** never keeps a transaction across a Jira call and writes whole chunks (at most 100 bindings) in short transactions. The views read only the database.
- **The mapping is the connection's state.** A mapping a later discovery outgrew is reported (`problems[]`), never rewritten; a stale one is `409 jira-mapping-invalid` on a bind and Peek and a `FAILED` run with `MAPPING_INVALID`.
- **A bound issue that leaves the listing is probed by id until Jira answers.** A verdict (404 `DELETED`, 403 `FORBIDDEN`) is final and never asked again; a probe never fails the run; a connection that never answers is backed off.
- **Deviations only warn.** The kernel is pure; dates compare in working days; nothing is moved.
- **Disclosure.** Every reader of the Deviations view, the bindings list and the timeline chips sees a moved item's current key (it may name a project outside the connection's keys) and the Jira keys (never a summary) of unbound items; never a connection's email, token or mapping.

## The transport and the gateway

Files: `jira/Jira.kt`, `JiraHttp.kt`, `JiraClient.kt`, `infra/fetch/`.

- A site URL that no longer has the genuine tenant shape is refused (`BLOCKED_HOST`) before any client exists (`infra/outbound/AtlassianSites.kt`).
- `authScheme` per connection: `BASIC` (`base64(email:token)`) or `BEARER`. Which one a site and token need is NOT verified (Assumptions ledger). A scoped token missing a scope answers **401, not 403**; the probe rows carry the scope hint for that reason.
- The transport is `infra/fetch/` (Flow's: retry, per-tenant pause, `X-RateLimit-NearLimit` = a 1 s sleep, byte, node and page ceilings); its codes are `FetchCodes` plus `JiraRunCodes.CURSOR_EXPIRED` (`sync.md` "Failure codes").
- One outbound permit pool (`jira.maxConcurrentRequests`) serves the run, the probes, Peek, the import and the binds. A bind queues for a permit at most `jira.bindPermitWaitMillis`, then answers `502 BUSY`, so binds never hold a Test connection behind them.
- `search/jql` returns only `id` unless `fields` is named; the run names every field it reads (timestamps: `JiraTime`).
- **Development only:** `jira.stubBaseUrl` (`JIRA_STUB_BASE_URL`) reroutes BOTH hosts of a `stub-` site, and no other, to the stub; a non-blank value outside development mode refuses boot naming the key.
- **Boot configuration** (`jira.*`, env `JIRA_*`, boot-validated; the first five via `infra/fetch/TransportConfig.kt`), default and bounds: `requestTimeoutSeconds` 30 (5..120); `requestDeadlineSeconds` 180 (10..600); `maxResponseBytes` 4 MiB (64 KiB..16 MiB); `maxConcurrentRequests` 2 (1..8); `maxRetries` 4 (0..8); `bindPermitWaitMillis` 5000 (100..60000); `pageSize` 100 (1..500); `incrementalOverlapMinutes` 10 (0..1440); `censusHours` 24 (1..168; also the hours between two scheduled re-asks of a readable gone item).

## Test connection and the probes

`JiraConnector.testConnection` runs the probes in sequence (10 s each, 30 s in all, never throwing); every row is required. In this order, with the scope each needs:

1. `tenant_info`: `GET /_edge/tenant_info`, unauthenticated; supplies the `cloudId`.
2. `myself` (`read:jira-user`).
3. `issuetype` (`read:issue-type:jira`): supplies the type ids the search narrows by.
4. `search` (`read:jql:jira`): `GET /search/jql`, `maxResults=1`, `fields=id`; the JQL is the connection's scope AND `issuetype in (<ids at the mapped milestone level, else Epic level 1, else level 0>)`.
5. `field` (`read:field:jira`).
6. `projects` (`read:project:jira`): `GET /project/search?keys=…` with exactly the configured keys; then one `project:<KEY>` row per key (a key the token cannot see fails `PROJECT_NOT_VISIBLE`).
7. `issue` (`read:issue-details:jira`): `GET /issue/{id}` on the first id the search returned; no row at all when the search returned nothing.

- **When `tenant_info` fails** the gateway rows (`myself` to `projects`) read `SKIPPED` (`ok: false`, no status, no scope hint; `gatewayProbe`, `ProbeRun.skip` in `infra/fetch/ConnectionProbes.kt`, shared with Flow): there is no gateway to call. They count as failed required rows; the UI shows a gray "Skipped" and counts only the real failure. No `project:<KEY>` or `issue` row appears.
- **Other row codes,** by object: `FetchCodes` `SKIPPED`, `BLOCKED_HOST`, `TIMEOUT`, `INVALID_RESPONSE` (a malformed body); `SyncErrorCodes.TOKEN_UNREADABLE` (one `stored_token` row, nothing called); `JiraRunCodes.PROJECT_NOT_VISIBLE`.
- `POST …/connections/test` is ad hoc (carries the token, stores nothing). `POST …/{id}/test` uses the stored token and records `last_tested_at/ok`, `cloud_id` (only when resolved) and **the discovery whenever both `field` and `issuetype` answered, even if another probe failed**, so a failing first test still leaves the report that diagnoses it; only if the row was not edited meanwhile (`recorded`); audited `jira.connection_tested`, never with the token.

Pinned by: `JiraTestConnectionTest`, `JiraConnectionTest`, `JiraBootTest`.

## Discovery

`GET …/{id}/discovery` answers the stored snapshot (`409 jira-not-discovered` before the first recorded test).

- `fieldCount`/`issueTypeCount` as the site reported them; the usable fields (`date`, `datetime`, `number`, the customs `atlassian-team`, `gh-epic-link`, `jpo-custom-field-parent`), capped at 2,000, markers first (`fieldsTruncated`); the issue types (cap 500); `levels[{level, typeNames}]` (non-sub-task types by `hierarchyLevel`).
- The **markers** the report prints: `targetStart`/`targetEnd` (a **date** field named "Target start"/"Target end", else `schema.custom` `jpo-custom-field-baseline-start`/`-end`), `startDate` ("Start date"), `dueDate` (`duedate`), `storyPoints` (the first `number` field named like "story point"), `team` (`atlassian-team`), `legacyEpicLink`, `legacyParentLink`.

## Mapping

Files: `jira/JiraMapping*.kt`, `JiraPeek.kt`. One canonical JSONB document per connection (`jira_connections.mapping`): `levels.{program,project,milestone}` = `{hierarchyLevel, fields{start, end, estimate}}` (program and project optional, milestone required), `estimate{unit POINTS|HOURS|DAYS, manDaysPerUnit|null}`, `teamFieldId`.

- `PUT …/{id}/mapping` (204) checks the shape before any database read (levels ≥ 0 and strictly decreasing program > project > milestone, field ids of the Jira shape, factor `0 < x ≤ 1000` with at most two decimals), then under the row lock against the discovery: every named level has a non-sub-task type, start/end are `date` fields (a `datetime` is refused: time zones), the estimate is a `number`, the Team field is the site's `atlassian-team` one; `409 jira-not-discovered` with no discovery.
- `jira.mapping_changed` audits the before/after SHA-256 of every accepted PUT; one that changes the document sets `mapping_changed_at` (the next run reads in full). `GET` answers `{stored, defaults, effective, discoveredAt, problems[]}`.
- **Defaults** (pure `JiraMappingDefaults.resolve(discovery)`, used until a mapping is saved): milestone = Jira level 1 (Epic) if the site has a non-sub-task type there, else level 0; project = level 2, program = level 3 when present; start = "Target start", else "Start date"; end = "Target end", else `duedate` (`date` fields only); estimate = the story-points field **on the milestone only**, unit `POINTS`, no factor (shown, never compared); `teamFieldId` = the `atlassian-team` field.
- The bind, the import and the run share one resolution (`resolveEffectiveMapping`): stored-or-defaults, re-validated against the CURRENT discovery; an undecodable document is `MAPPING_UNREADABLE`.
- **Peek** (`GET …/{id}/peek?key=ABC-12`, `jira-test` bucket): one `GET /issue/{key}`, answered as `{issue, resolved{level, start, end, estimate, unit, teamName}, raw}`; `raw` holds only the mapped fields' values, `resolved.estimate` is read as a sync reads it (`estimateOf`: two decimals half up, absent for a figure the observer drops). Nothing stored, no audit; the key must be in the connection's project keys; an upstream failure is `502 jira-upstream` carrying only the code (`respondJiraUpstream`).

Pinned by: `JiraMappingTest`, `JiraMappingDefaultsTest`.

## Bindings

A binding links ONE plan node (program, project or milestone) to ONE Jira issue by its numeric id; the key is for display and follows a move. The database holds both directions (`uq_jira_bindings_node_active`, `uq_jira_bindings_issue_active`); the lock makes the service's checks exact. `POST /integrations/jira/bindings {connectionId, level, nodeId, issueKey}` → `201`, in this order (guard order: `authorization.md` "Jira bindings and acknowledge"):

1. The body decodes; the node's chain is read (missing = `404`); `requireOwnerOrAdmin` (`403`); then validation (`400`).
2. **One Jira call, outside any transaction** (`observeForBind`): the connection active and enabled (`400`), its token readable (`409 jira-token-unreadable`), discovered (`409 jira-not-discovered`), its effective mapping valid (`409 jira-mapping-invalid`); the level mapped and the key in scope (`400`); the issue exists (`400 "Unknown Jira issue"`) at the hierarchy level the mapping gives that plan level (`400` naming both). Any `FetchException` is `502 jira-upstream (CODE)`, `BUSY` included.
3. The transaction: the advisory lock; the connection row `FOR SHARE` (a delete or edit waits, or has won: `400`); the scope re-checked; the node row `FOR SHARE` (`404` if deleted); the chain re-read and the guard re-run;
   the node's own active binding → `409 already-bound`; the issue's active bindings on this connection **or on another active connection of the same site** (`JiraConnectionService.siteConnectionIds(site)`) → `409 already-bound`, unless their node (or an ancestor) is deleted: then the old binding is **released** (soft-deleted; `jira.binding_released`, `reason=NODE_GONE`). Then the binding and its first `jira_observations` row are inserted; audit `jira.binding_created` after the commit.

- `DELETE …/bindings/{id}` soft-deletes (history stays) after the guard on the chain as last stored (a binding of a gone node is unbound by whoever passes it); `jira.binding_deleted`.
- Deleting a connection soft-deletes its bindings in the same transaction (the node index has no connection column, so they would block their nodes for good) and hard-deletes its runs. A program-level binding is made on a connection's page (ADMIN) only.

Pinned by: `JiraBindingTest`, `JiraBindingLifecycleTest`, `JiraBindingRaceTest`, `JiraBindBusyTest`.

## Observations and the run

Files: `jira/JiraObserver.kt`, `JiraObservation.kt`, `JiraRunStore.kt`, `JiraSearch.kt`, `JiraGoneProbe.kt`, `GoneProbeDamper.kt`.

`jira_observations` holds the LATEST observed state of a binding (a hard overwrite, one row per binding; the status category `new|indeterminate|done` reads `TODO|IN_PROGRESS|DONE`, else `UNKNOWN`). `JiraObservation.of` is pure and clamps every value to its column (a figure past `NUMERIC(12,2)` reads as null), so one odd issue cannot wedge every later run.

**Refresh now** (`POST /integrations/sync/runs`): `requireRunnable` (active and enabled, else `400`), the claim (`sync.md` "The run registry and the claim"), audit `jira.sync_requested`, `202`.
A run and an import are independent: they meet only on binding rows, in id order.
The scheduler's read of a connection is `JiraConnectionService.pollRows()` (`jira/JiraConnectionPolling.kt` over `pollRowsOf`): seven columns of the ACTIVE rows, never the token or the discovery.
Both connectors' runs go through `sync/RunEnvelope.kt` (`runWithTally`): the tally, the counters (`RunProgress`), the typed `RunProblem` and the failure text `"<Jira|Flow> fetch failed: CODE (status)"` (`fetchFailureDetail`) are defined once there.

### The order of a run

`JiraObserver.execute`:

1. Read the connection: gone → `CONNECTION_GONE`, disabled → `CONNECTION_DISABLED`. Release bindings of deleted nodes (`jira.binding_released`).
2. Token readable (`TOKEN_UNREADABLE`), discovery present (`NOT_DISCOVERED`), mapping usable (`MAPPING_UNREADABLE`, `MAPPING_INVALID`, the latter also when a mapped level has no issue type in the discovery snapshot). Take the active bindings; **none → the run succeeds having called nothing.**
3. `tenant_info` (persisting `cloud_id` when none is stored), then the read ("The read").
4. The **sweep**: `…issuetype in (…) ORDER BY id ASC`, `fields=id`. A bound id missing from it, not just read, whose last observed type is among the swept types, is `gone` as `OUT_OF_SCOPE` (a deletion, a move out of the keys and a lost permission look alike here); a flagged id seen again is cleared.
5. The **gone probe** ("The gone probe").
6. The **census** (`Coverage and roll-ups`).

- **Inside a read:** at most 200 pages (the read and the sweep each get 200) else `LIMIT_EXCEEDED`; `CURSOR_EXPIRED` restarts the query once, a second expiry fails the run; a `200` that is not a listing (no `issues`, or `isLast: false` with no token) is `INVALID_RESPONSE`, never an empty page; a cycling `nextPageToken` is refused.
- **Before every search page** the run asks `runnableState` (`sync/ConnectionRegistry.kt`'s `runnableStateOf`; the `RunnableState` enum is shared with Flow): a connection deleted or disabled meanwhile ends the run `FAILED` with `CONNECTION_GONE` / `CONNECTION_DISABLED` (a deleted connection's token is destroyed, so no copy may authenticate one more read).
- **The empty-sweep default:** an empty listing of a non-empty bound set still flags the bound issues of a swept type `gone` (a WARN with counts): a false flag only warns and heals on the next good sweep, while failing would wedge a site whose only bound item was really deleted.

### The read

- **Full** (`project in (…) AND issuetype in (<every mapped level's type ids>) ORDER BY id ASC`, with the observation `fields`; a bound issue of an unmapped type is not read by it and keeps its old observation) when no earlier run succeeded, a binding has no observation, `census_at` is null, or anything that decides what an unchanged issue reads as is newer than the last succeeded run's start. Otherwise **incremental** (`project in (…) AND updated >= "-Nm" ORDER BY updated ASC`, N = minutes since that start + `incrementalOverlapMinutes`, recomputed at every first-page request).
- Those inputs are `discovered_at` (re-discovery), `mapping_changed_at` and the connection's `updated_at` (any edit, e.g. a widened `projectKeys`; `storeCloudId` and a recorded Test connection leave it alone), so a rename, a token rotation and a PUT that changes only the poll interval each cost one extra full read.
- The incremental is NOT type-filtered: an unfiltered window is how a change of type is seen. One that hits `LIMIT_EXCEEDED` (a long gap on a busy site: the window only grows) restarts once as the typed full read.
- Every bound issue found is upserted in chunks of 100, one short transaction each.
- The census (`jira/JiraCensus.kt`) is filled by the same pass: the mapped levels are pruned after the reconcile and the child level is listed in full on a full read, else as an id sweep once per `jira.censusHours` (`JIRA_CENSUS_HOURS`). Then `census_at` is stamped, or cleared when a sweep listed an issue the mirror lacks, so the next run re-seeds. A failing children pass never fails the run; `calls` counts the child pages. No audit event: the run row and the INFO line are the record.

### The gone probe

`jira/JiraGoneProbe.kt`: each gone binding in the queue is read by id, `GET /issue/{issueId}?fields=id`, through the run's own guarded client (it counts in `calls=` and asks `runnableState` before each call).

- **404 → `DELETED`, 403 → `FORBIDDEN`, 200 → the column stays `OUT_OF_SCOPE`**. Jira answers the same 404 for an issue the account cannot see, so `DELETED` reads "deleted, or no longer visible". Every answer, the 200 too, stamps `gone_probed_at` (`JiraRunStore.recordProbe`, a short transaction as it arrives, so a cut run keeps every answer it had); any other failure leaves the row unstamped, so a later run probes it again. Every path that clears `gone` clears the stamp (`CHECK (gone_probed_at IS NULL OR gone)`).
- **The queue** (`goneProbeQueue`, pure) comes from the bindings the sweep judges gone, in three ranks: **0** newly flagged in this run; **1** `gone` with no `gone_probed_at` (a probe that failed, was cut or fell beyond the cap); **2** stored `OUT_OF_SCOPE` and answered with a 200, asked AGAIN as the issue may have been deleted since (every one on a MANUAL run; on a SCHEDULED run those whose answer is `jira.censusHours` or more old). A stored `DELETED` or `FORBIDDEN` is never asked again.
- **Order,** in four groups: rank 0; rank-1 then rank-2 rows with no failed read remembered; then every row whose read failed before, the least recently tried first; inside a group the oldest answer first, then binding id. At most 100 a run, so a row whose read keeps failing queues behind every binding not yet tried.
- **The key follows the issue.** A 200 keeps the issue KEY it carried (`jira_observations.gone_probed_key`), taken from the document's top-level `key` only when its `id` equals the probed id AND the key matches `ISSUE_KEY_PATTERN` (an outbound value is stored and rendered as a link), else NULL (the 200 still counts); a 404 or 403 writes NULL.
  The binding's `jira_issue_key` follows it in the same transaction, so every list, link, chip and audit shows the current key; `observation.issueKey` keeps the key the issue was last read under (the pages show "was OLD-1"; the row's `jira.previousKey` is derived on read).
  No audit event and no log line carries a key. `writeObservations`, `markGone` and `clearGone` reset the column, `recordProbe` sets it.
- **The API derives the reason** (`wireGoneReason(stored, probedAt, probedKey, projectKeys)`, against the connection's CURRENT keys, so a key edit needs no rewrite): `OUT_OF_SCOPE` with a `gone_probed_at` reads `MOVED_OUT` for a key outside the connection's `projectKeys` (or no key) and `NOT_LISTED` for a key inside them (Jira has it where the connection looks, but the listing no longer returns it: archived, a changed type, a false-empty sweep).
  `isInScope` (`JiraMappingRoutes.kt`) is the one scope rule. Two call sites apply the derivation, so they agree: `World.candidate` (the view, the flags, the acknowledge; `storedObservation()` keeps the raw stamp and key) and `responsesOf` → `toObservationResponse(projectKeys)` (the bindings list). A row not yet answered for keeps `OUT_OF_SCOPE`. The probe columns are server-internal. The deviation's `detail.jira` is the reason, so a change of reason (a re-ask turning a 200 into a 404) reopens an acknowledged `GONE` line: by design.
- **Circuit breaker:** after 3 failures in a row that say nothing about the issue (a 200 or a verdict resets the count) the probe stops and leaves the rest for the next run; the run still succeeds.
- **The damper** (`GoneProbeDamper`, in memory per connection). A run whose probe sent a read and got no answer is a *failing run*; one with an answer (200, 404, 403) an *answering run*; a run that sent nothing or was cut changes nothing. After 3 failing runs in a row (`GONE_PROBE_FAILING_RUNS`) a SCHEDULED run asks only rank 0 until `jira.censusHours` have passed since the last run allowed to retry.
  A MANUAL run always asks everything; without an answer it neither counts toward the streak nor restarts the clock, with one it ends the streak. A config change (a new token or account may read more) and a run that finds the connection deleted or with nothing bound drop it too. Log lines: `sync.md` "Log lines".

Pinned by: `JiraRunTest`, `JiraRunReadTest`, `JiraRunCensusTest`, `JiraGoneProbeRunTest`, `GoneProbeDamperTest`.

## Deviations

`GET /views/deviations` runs in one `READ ONLY REPEATABLE READ` snapshot, the plan revision first; unpaged, at most 2,000 items; it applies the pure `JiraDeviationKernels.deviations` to each binding. Dates compare in WORKING days (a start snaps to the next working day, an end to the previous one); a project's or program's derived span is compared, not stored dates. Without a usable mapping neither the level nor the estimate is compared and the connection reads `mappingOk: false`.

- **The document:** `{revision, asOf, connections[{…, status}], totals{warnings, infos, bindings, gone, stillInJira, acknowledged}, items, truncated}`. An item carries `fingerprint`, `can` and its `deviations` lines, each with its own `acknowledgement`; an item has none of its own.
- **`totals`** count before the cap: `warnings`/`infos` the OPEN LINES (a listed deviation without a current acknowledgement of its own); `gone` the open items (every reason); `stillInJira` the part of `gone` read `MOVED_OUT` or `NOT_LISTED`; `acknowledged` the items with a currently acknowledged listed line; `bindings` the list's length. `all=false` overrides the `all`-implying filters.
- **Items:** the default lists OPEN bindings (a listed line without a current acknowledgement), those with an open warning first; `all`, `projectId` or `teamId` also list clean and acknowledged ones. A **disabled** connection's bindings stay in the view with their last observation.
- **No validator:** the view answers no `ETag`/`304`: each connection's `status.nextPollAt` is the read's own instant while a poll is due (`planning-model.md` "View validators"); `GET /views/jira-links` does answer one.

| Kind | Levels | Rule | Severity |
|---|---|---|---|
| `GONE` | all | the observation is `gone`, alone; the detail is the reason: `DELETED` (the probe's 404), `FORBIDDEN` (its 403), `OUT_OF_SCOPE` (the sweep's, until a probe answers), `MOVED_OUT` (a probe's 200 whose key is outside the connection's keys, or none), `NOT_LISTED` (a 200 whose key is inside them) | WARNING |
| `LEVEL_MISMATCH` | all | the observed hierarchy level (or none) ≠ the mapping's level | WARNING |
| `PARENT_MISMATCH` | project, milestone | the observed parent issue is bound to a node that is NOT the plan parent (an unbound parent raises nothing); the plan parent is the nearest ancestor whose level the connection maps (a milestone's project, else its program when the project level is unmapped); none when no ancestor level is mapped or the mapping does not resolve | WARNING |
| `RENAMED` | all | summary ≠ name (trimmed, case-insensitive; a name cut at 100 compares as a prefix) | INFO |
| `START_DIFFERS`, `END_DIFFERS` | all | both dated and the working-day shift ≠ 0 (`days` positive = the plan is later) | WARNING when the plan's END is later than Jira's, else INFO |
| `TARGET_DIFFERS` | project | the target window vs Jira's dates differs in working days | INFO |
| `UNSCHEDULED_IN_PLAN`, `UNSCHEDULED_IN_JIRA` | milestone | Jira dated and the milestone not, or the reverse | INFO |
| `ESTIMATE_DIFFERS` | milestone | comparable (`DAYS`, or a factor) and `|jira × factor − estimateMd| ≥ 0.01` | INFO |
| `ESTIMATE_NOT_COMPARABLE` | milestone | an estimate with no factor, or read under a different unit than the mapping names now (listed only with `all=true` or `kind=`) | INFO |
| `PROGRESS_MISMATCH` | all | `DONE` while the plan's end is after today; `TODO` while the plan's start is past; `IN_PROGRESS` while it is ahead | INFO |
| `UNLINKED_IN_JIRA` | program, project | open (not DONE) Jira items under the bound issue, at the mapping's level for the child plan level, that no active binding covers (`jira` = their keys, at most 10, `count` = all; never a summary) | WARNING |
| `UNLINKED_IN_PLAN` | program, project | the bound node's direct plan children that have no binding (`plan` = their names, at most 10, `count` = all) | INFO |
| `CHILDREN_DONE` | milestone | the bound epic has children, all done (`jira` = `done/children`, `count` = children), the epic is not DONE (else `PROGRESS_MISMATCH` alone) and the plan's end is after today | INFO |
| `CHILDREN_OPEN` | milestone | the bound epic has children, some not done (`jira` = `open/children`, `count` = children), while the plan's end is BEFORE today; the epic's own status does not matter; never for an unscheduled milestone, no children, or no roll-up | INFO |

- The four coverage kinds are declared last, so they sort after the older ones within a severity. They come from two optional kernel inputs (`ChildRollup`, `UnlinkedChildren`; null = none) that the loaders fill from the census mirror (`DeviationCoverageRows.kt`; `Coverage and roll-ups`).
- `DeviationDetail.count` is null-defaulted, `@EncodeDefault(NEVER)` and omitted from a fingerprint while null (the pinned `Json` writes neither nulls nor defaults), so a binding that gains none of the coverage kinds keeps its acknowledgements. `CHILDREN_OPEN`'s fingerprint evidence is the `open/children` text, the plan's end and the children count.

Pinned by: `JiraDeviationKernelsTest`, `DeviationViewScopeTest`, `DeviationFingerprintTest`.

## The plan's links

`GET /views/jira-links` (`jira/JiraLinksView.kt`) is the narrow read behind the Plan page's "Import from Jira..." entries (the Deviations view would compute every deviation).

- One `READ ONLY REPEATABLE READ` snapshot, TWO statements whatever the plan's size (`loadConnections()`, `loadNodeLinks()`); no revision, no `can`, no parameter, no `404`; it answers a validator (`planning-model.md` "View validators").

## Import

Files: `jira/JiraImport*.kt`. Two routes, `POST /integrations/jira/connections/{id}/import-preview` and `…/import`, share one pure planner (`JiraImportKernels.plan`) and one scope: `{workStreamId, ownerPersonId, projectKeys?, defaults{programId?, projectId?, teamId?}?, copyDates, filter{excludeDone, updatedWithinDays}?, root?, matches?[{jiraId, nodeId}]}`.

The preview says what importing the connection's in-scope Jira items into ONE picked work stream WOULD do, per item: CREATE a program, project or milestone, BIND an existing unbound same-name node, or SKIP. The apply writes what the user ticked.

- **Nothing is written to Jira,** and the import is the one Jira-derived write to the plan. Work streams are never imported: the import picks one and creates only under it; an existing node is never updated.
- **Order of answers:** the `jira-import` bucket, the connection (`404`), the body, the named targets (`404`, then `403`), the shape (`400`), the connection enabled (`400`), its token / discovery / mapping (`409`, the bind's resolution), then the browse. Guards and the order are `authorization.md` "Jira import"; a caller refused by the up-front checks never makes the server decrypt (`JiraImportDecryptOrderTest`).
- **The shape `400`s** (after the up-front `403`s; the resolved-target `403` still comes after the browse): `projectKeys` a subset of the connection's keys; the owner an active person; `defaults.teamId` an active team; the defaults and the root under the picked stream; with a root, no `defaults.programId` and `defaults.projectId` only a project of the root program (none under a project root); last `filter.updatedWithinDays` a whole number 1..3,650.
- **More `400`s of the apply:** every `overrides.teamId` an active team, every `overrides.ownerPersonId` an active person. `matches` (more than 2,000 entries, a `jiraId` that is not a numeric Jira id so a `hidden-<n>` handle is refused, an id named twice) is refused after the `403`s.
- **An upstream failure** is `502` `urn:astrolabe:problem:jira-upstream` through `respondJiraUpstream` (`jira/JiraUpstream.kt`): the failure code only, never a URL, a body or a token. The active connections of a site are read by `JiraConnectionService.siteConnectionIds(site)`, in the caller's transaction.
- **Rate:** `jira-import` (`RateLimits.JIRA_IMPORT`, per verified user id) is ONE bucket of 5 calls a minute for preview and apply together (a confirmed suggested match is one more preview). It runs before the handler, so before the guard: a request that would be `404`, `403` or `400` spends a token and an over-limit caller gets `429` whatever it would have answered (`JiraImportPreviewErrorsTest`). Audit: bucket `jira-import`, `byUserId`.
- **Concurrency:** a call lasts up to 170 s while the bucket admits 5 per 60 s, so one account can hold 15 browses in flight (20 across a window edge). The bucket limits the rate, not the concurrency: every search page takes one of the process's `jira.maxConcurrentRequests` outbound permits (default 2, max 8; the pool the heap-fit check sized the heap on), so concurrent browses queue instead of adding load, each holding one parsed page. An administrator's Test connection can queue behind them (a preview, unlike the bind, sets no `PermitWait`).
- **By-id reads:** an active `filter` may add up to 200 `GET /issue/{id}` reads a call, one at a time, one permit each, inside the same deadline: about 1,000 per account per fixed window behind the bucket (5 x 200; a window edge can admit 2,000 in one sliding minute).
- **A query is never spliced.** A parent id passes `ISSUE_ID_PATTERN` before it joins a path or a query (`JiraJql.children`, `ImportRoot` and `HttpJiraClient.issue` refuse anything else) and no more than 50 name one query; a query is shaped only by the `projectKeys` subset picked (checked against the connection's own keys) and the bounded filter (sent as minutes); `matches` is only ever compared with the kernel's own suggestion and never reaches a query.
- **Entry points** (the server's guards are the authority): the connection page (ADMIN) with the stream a free pick; the Plan page's work-stream menu on every stream whose `can.edit` is true, the stream preset and read-only. That modal takes its connection from `GET /views/deviations?workStreamId=<id>` `connections[]` (any authenticated: the registry is ADMIN-only): the usable ones are `enabled` with `mappingOk`; `projectKeys` rides along (not secrets). A `403`/`409` from the server shows inline. The linked-node entries: "Import from a linked node".

### The preview

`import-preview` answers `{connectionId, workStreamId, revision, asOf, totals{items, create, bind, skip, truncated}, unmatchedTeams[], items[]}`, unpaged, at most 2,000 rows; `truncated` is reported only here (the apply refuses a truncated scope). It stores nothing and takes no lock. In order:

1. **One browse**, outside any transaction ("The browse and the filter").
2. **One snapshot** (`JiraImportService.read`, `READ ONLY REPEATABLE READ`, the plan revision first): the holiday calendar; the picked stream's active tree with each node's owner and whether it carries an active binding; ALL active program names (globally unique); the active bindings of the browsed issues AND of their Jira parents on every active connection of the same site (a holder is `live` when its node and every ancestor are active); the active teams and the teams the caller manages (ADMIN: every team).
3. **The pure kernel** (`JiraImportKernels.plan`, shared with the apply) plans the rows top-down (below).
4. **The resolved targets' guards**, then the redaction for a non-admin ("What a non-admin sees"), then `200`.

**The planner's rules** (`JiraImportKernelsTest`):

- **A child's parent** is the node bound to its direct Jira parent (under the stream), else the batch row of that parent, else the level's default parent, else `NO_PARENT`; a child of a skipped parent is `PARENT_SKIPPED`; a rooted import also skips, `OUTSIDE_ROOT`, a row whose parent resolves to an existing node outside the root's subtree.
- **Only the direct Jira parent counts** (`fields.parent` holds the immediate parent and nothing further). An item whose direct parent sits on a level the mapping skips has no parent at its own plan level: it goes under the default parent for its level, else `NO_PARENT`. Unmapped levels are not browsed (backlog).
- **Linking is by name.** An unlinked plan sibling with the same name is proposed as a BIND, anything else is a CREATE; program names compare against every active program, and a name taken is `NAME_TAKEN`. Names compare with `lowercase` only (accents count); the Jira summary is first cleaned by `importName` (control characters become spaces, inner whitespace collapsed, trimmed, cut at 100 characters), a plan name is not, so a plan name with a double space never matches.
- **A renamed, unlinked item previews as NEW** and importing it adds a second node, unless "Suggested matches" finds the pair. An already linked item is `ALREADY_BOUND` whatever it is called now. The user must read the preview.
- **Team** by folded name, then `defaults.teamId`, else `NO_TEAM`. Estimates convert only with a declared unit or factor (`ESTIMATE_NOT_CONVERTED`). A milestone's dates are copied only where the caller may schedule its team (`DATES_NOT_COPIED`) and are valid (`DATES_INVALID`, `NO_WORKING_DAY`).
- **A created project's target window** (`windowFor`) rides the `copyDates` switch: the dates the project level is mapped to (Target start / Target end by default, Start date / Due date on a site without Target fields; the fields `TARGET_DIFFERS` reads) become the window the project is CREATED with (`ImportRow.window`, written by `insertProjectRow`; no second write, no extra revision).
- **Both dates or neither:** one date, or an end before the start, gives no window and the info `TARGET_NOT_COPIED` (the row is created all the same); no dates says nothing (an unparseable date reads as missing, `isoDateOrNull`). The row's `startDate`/`endDate` show the window that WILL be written (the web labels it "Target window"). A BIND, an `ALREADY_BOUND` row, a program and a milestone carry none: a bound project's window is never overwritten.
- **Who may:** the guard of a target-window write is `requireTargetWindowEditorOrAdmin` (ADMIN, an owner ABOVE the project, or the roadmap-editor grant). A created project sits under a program (guarded up front and under the lock) or one created in the same batch (guarded through the stream), so every caller who passes the create guards is the stream's or the program's owner, or ADMIN: the check is met by construction and the kernel does not ask it (`PlanPermissionsTest` pins `canManage` on the program implies `canEditTargetWindow` on a project under it).
- **A stricter future guard** on the target window must add the check here.

### The browse and the filter

Files: `jira/JiraImportBrowse.kt`, `JiraImportFilter.kt`, `JiraImportParents.kt`.

- **The read:** `JiraJql.full(keys, sweepTypeIds)` (the run's typed full read) with the run's `fields` (the system fields and every mapped date, estimate and Team id), paged by the shared `searchPages` (`jira.pageSize`, at most 200 pages, `CURSOR_EXPIRED` restarted once). Each issue is read through the mapping at ITS OWN plan level and keeps the issue type of its direct Jira parent (`fields.parent.fields.issuetype`; its level through the discovery by type id when the object omits `hierarchyLevel`).
- **The cap:** paging stops at 2,000 issues (`MAX_IMPORT_ITEMS`); the first issue beyond it ends the read with `truncated: true` (a page exactly at the cap costs one more page to find out) and what is kept is the lowest ids. Before every page the connection's liveness is asked (`runnableState`): deleted meanwhile `404`, disabled meanwhile `400`, never a `500`.
- **The deadline:** 170 s for the whole browse (`IMPORT_BROWSE_DEADLINE_MILLIS`, `withTimeoutOrNull`, under the web client's 180 s abort); past it `502 jira-upstream (TIMEOUT)`. Only the browse's own deadline becomes that; a cancelled caller stays cancelled. The token is only the client's `Authorization` header: never a URL, log line, exception text or response (`JiraImportBrowseTest`, `JiraImportPreviewTest`).
- **The filter** (`filter{excludeDone, updatedWithinDays}`, per request, nothing stored; the dialog opens at "leave out done" and 365 days) exists because a project with more than 2,000 items at the mapped levels could not otherwise be imported. An absent or inactive filter (no member on, or both off) is the read above, request for request, and reads no parent by id.
- **An active filter** sends `JiraJql.importBrowse`: the typed read plus `AND statusCategory != Done` and/or `AND updated >= "-<days x 1440>m"` (a window in minutes; the day count is an `Int` 1..3,650 validated in the request AND in the builder), before `ORDER BY id ASC`, for EVERY mapped level.
- **The server's own rule** (`admits`: not done when `excludeDone`; `updated` within N days, the boundary kept; an unknown category is not done; an unreadable `updated` is admitted) is put to every entry as it streams: one not admitted is dropped and never counts toward the cap. The stub evaluates no clause, so on the stub this is what filters. The preview does not say how many items were left out.
- **Missing parents are read by id** (`GET /issue/{id}` with the search's `fields`) for each kept item that is not itself linked to a live node, sits at a mapped level below the top whose level above is mapped, and whose direct parent (`fields.parent.id`) is not already a row, not linked to a live node, has its key (when the child carries it) inside the import's keys and its level (when the child's `parent` type object tells) the wanted one.
- **Two rounds** (a milestone's project, then its program), ids ascending and distinct, one short read of the bindings per round (`liveHeldIssueIds`, between Jira calls). At most 200 reads a browse and at most 2,000 rows (search + parents): past either the browse is `truncated` (a search that itself passed the cap reads none). The liveness is asked before each read, all inside the 170 s deadline.
- **A fetched document** is used only if its `id` is the one asked for, its key is inside the keys and its level is the wanted one; it joins the rows as `keptAsParent` (info `KEPT_AS_PARENT`). A `404` (or a `200` of another id) flags the child `parentUnreadable`: the planner skips it `NO_PARENT` (never the default parent) with the info `PARENT_UNREADABLE` (stripped from a skipped row for a non-admin, who sees `NO_PARENT`), and what is under it is `PARENT_SKIPPED`.
- **A document outside the keys or at another level** is dropped (the child is then the orphan it would otherwise be). Any other failure is the `502`, a by-id `401`, `403` or `429` after the transport's retries included: the account's scope or rate, never a verdict on one issue.
- **Only the import reads through the filter.** A run reading through it would flag finished bound items `gone`, freeze their observations and empty the census mirror and the roll-ups. An item imported earlier that later becomes done stays linked, swept and observed; an open item the window left out is still in the mirror, so its bound parent lists it as `UNLINKED_IN_JIRA`; a done parent kept for an open child and imported reads `PROGRESS_MISMATCH` while the children are ahead.
- **The filter does not make an orphan importable** (give a default program or project). The apply re-browses and re-reads the parents under ITS request's `filter`.

### What a non-admin sees

Files: `jira/JiraImportRedaction.kt` (`redactForNonAdmin(plan, filterActive)`, pure, applied at the route). The guards and the disclosure rules are `authorization.md`'s; this is what the answers hold.

- **A skipped row other than `ALREADY_BOUND`** loses its summary, its name and its infos and shows its issue key as its name; `unmatchedTeams` counts the rows that would be CREATED only. With no active filter the key, `typeName`, `hierarchyLevel`, `reason` and the parent keys of a blanked skip row stay.
- **Under an active filter** (`isActive()`: `excludeDone` on or `updatedWithinDays` set) the filter is a probe the caller steers, so `issueKey` is null (nullable on the wire), `name` blank, `jiraId` is `hidden-<n>` (never a Jira id) and `parentJiraId`/`parentIssueKey` are null. The web row shows a "Hidden" placeholder in the key column and its reason.
- **The order of redacted rows:** after every visible row, by what they still show (level top-down, then reason, type name, hierarchy level), never by id; `<n>` numbers that final list, so two rows that show the same differ only by number and the ascending Jira id order is not observable.
- **An `ALREADY_BOUND` row** is decided before its parent is looked at, so it could name a redacted parent (or one the filtered browse never listed): it keeps `parentJiraId`/`parentIssueKey` ONLY when its parent is a visible row. A CREATE/BIND row never has a redacted parent (a child of a skipped parent is `PARENT_SKIPPED`) and keeps its parent (the apply compares it). `ALREADY_BOUND` rows keep their key and text (public through `GET /integrations/jira/bindings`).
- **No suggestion** rides a redacted row (`JiraImportRedactionTest`); an entry of `matches` naming a numeric id whose row is redacted changes nothing in the answer.
- **The apply's answers for withheld ids** follow the visible skips (row order, key and reason) in the order ticked, as `CHANGED` with no key: an id the same-scope preview redacts and an id the browse does not hold cannot be told apart. The withheld ids come from the same-scope kernel run with the SAME `matches` and no `overrides.teamId`. An ADMIN, or no active filter, gets the plain list.
- **What stays visible, honestly:** the caller picks which rows are visible through `defaults`, `projectKeys` and the filter, and a visible row shows in full, with its key, in the preview and in `skipped[]` (a resolved-target `403` names the first unowned visible row's key). That is the settled rule. A caller who previews without a filter and ticks the ids of rows visible there learns which the filter leaves out (what their own filtered preview shows by omission).
- **The residual:** the counts of redacted rows per filter and their level/type/reason mix are visible; a count is still a verdict when its group holds one issue (an issue alone in its level, reason and type has its filter verdict told by the group's count: `BACKLOG.md`). A rooted scope narrows the group a count speaks about; the done/open verdict of an unlinked child is already public through `UNLINKED_IN_JIRA`.

### Suggested matches

Files: `jira/JiraImportMatch.kt` (`ImportNameMatch`, pure, the rule), `ImportPlanner.settleMatches` (the per-level settle).

- **What it is.** A CREATE row that looks like an existing, UNLINKED plan item of its level under the same parent carries `suggestion {nodeId, nodeName}` (absent otherwise; `@EncodeDefault(NEVER)`). The user confirms it with `matches[{jiraId, nodeId}]` on the NEXT preview and, flat, on the apply (the web spreads it from the preview's scope).
- **Nothing is ever linked by a suggestion alone.** A confirmed row reads BIND with the info `MATCH_CONFIRMED` (the natural BIND's shape: no estimate, dates, team or window); what hangs under it lands under the EXISTING node and matches that node's children by name.
- **The rule is strict on purpose.** Names are folded (`JiraImportKernels.foldName`: lowercase `Locale.ROOT`, accents stripped, `ł ø ß`… mapped) and split into words on every run of non-letters and non-digits. Two names are `similar` when (1) both have a word; (2) their NUMBERING words are the same multiset; (3) every word of the name with fewer letters occurs in the other, as a multiset (the longer name only ADDS words); (4) `2 x letters(shorter) >= letters(longer)`, integers only.
- **Numbering words:** a word with a digit (any Unicode number, `\p{N}`: "x²" counts), a single character, or a Roman numeral `ii iii iv vi vii viii ix`. A numeral above `ix` is an ordinary word: "Phase" / "Phase XII" ARE similar, "Phase XII" / "Phase II" are not.
- **Matches:** "Checkout redesign" / "checkout  REDESIGN", "Płatności mobilne" / "Platnosci mobilne", "Customer portal" / "Portal: customer", "Mobile app" / "Mobile app rollout". **Does not match:** "Team A" / "Team B", "Phase 1" / "Phase 2", "Release" / "Release 2", "Billing revamp" / "Billing redesign" (a replaced word), "API" / "API gateway" (3 of 10 letters), "Custmer portal" (a typo), "Check-out" / "Checkout". A typo-tolerant version is a backlog item (Toadie's `levenshtein` was not ported: it would pair "Team A" / "Team B").
- **Unique both ways.** A suggestion needs exactly one free sibling similar to the row, and that sibling similar to no other would-be-created row of the scope; two candidates, or two rows for one candidate, propose nothing. An ambiguous pair gives nothing.
- **Work budget.** The matcher sums, per sibling scope, the nodes sharing a word with each row (`ImportNameMatch.MAX_MATCH_WORK`, 5,000,000); past it the scope gets no suggestion at all (deterministic, a function of the names), so thousands of siblings sharing many words with up to 2,000 rows cannot make a preview slow (`JiraImportMatchKernelTest`, an adversarial vector).
- **The settle.** Rows are planned level by level. After a level's name verdicts, per sibling scope (the CREATE rows landing under the same EXISTING node, parent kind `EXISTING` or `DEFAULT`, never `NEW_ROW`; or the picked stream's programs) the free siblings are the parent's children at that level with no active binding (any connection) that no exact-name BIND row claimed. Suggestions are computed on the level's natural state: a confirmation never changes another suggestion of the level.
- **Which entries count.** An entry of `matches` is honoured ONLY when it equals the kernel's own suggestion for that row, recomputed under the plan lock in an apply; any other (a linked or renamed node, another node, an id the browse does not hold, a row that is not a CREATE) is ignored.
- **A `NO_TEAM` milestone** gets none, judged on its NATURAL verdict, so an apply's `overrides.teamId` cannot honour a pair no preview showed nor break an honest one; a converted milestone's Jira team name leaves `unmatchedTeams`. A converted row's name stays in `takenNames`. `OUTSIDE_ROOT` and the other skips are decided first: a skipped row never has a suggestion.
- **Guards.** A confirmed BIND is guarded first as the CREATE it replaces, then as a BIND (`requireResolvedTargets`: every row in the preview, the ticked rows in the apply; `JiraImportMatchGuardTest`).
- **In the apply** both kernel runs (the preview run that finds a non-admin's withheld ids under a filter, and the ticked run) get the SAME `matches` and root. A confirmed row is a BIND (`expected {action: BIND, nodeId}`). If under the lock the node is no longer the kernel's unique suggestion (renamed, linked, deleted, a second candidate appeared) or the request left the entry out, the row plans as a CREATE, which is not what was expected: `CHANGED`, nothing created or bound, its children likewise. `jira.import_applied` carries `confirmedMatchBindingIds` (ascending, ids only).
- **What a user must know.** Under an active filter the preview does not see an item the filter left out, so a plan item whose own Jira item was left out looks free and may be proposed to a similarly named open one (the dialog says so; nothing is linked without the click).
- **A confirmation** costs one more preview (same bucket, same browse, no new Jira call); program, project and milestone confirmations in turn are four previews and an apply, and several rows can be confirmed before one "Preview again". The sample plan's renamed items ("Documentation (renamed)") are proposed where their plan item is the only candidate and are still CREATED unless confirmed.

### The apply

`POST …/import {…, matches?, items[1..2,000 of {jiraId, expected{action, level, parentJiraId?, nodeId?}, overrides{teamId?, ownerPersonId?}?}]}` writes what the user ticked, under the same rights as the preview. It runs the preview's checks and its browse again (the same `JiraJql.full` read, matched by id: a static stub cannot answer `id in (...)`), then:

1. **Before any write** a truncated browse is a `400` (a parent cut by the cap cannot be told from an orphan), as is a bad `overrides.*` (`requireShape`, again under the lock) or `matches` (`validateMatches`).
2. **ONE `withPlanWrite`** (`JiraImportService.apply`, `LockedApply.run`; the lock order is `persistence.md`'s): the plan lock, then the bind's advisory lock, the connection row, the caller's person; everything re-read and re-guarded under them. The connection's project keys, `mapping_changed_at` AND `discovered_at` are compared with what the browse used: keys `400`, mapping or discovery `409`. The dead holders to release are locked in one `ORDER BY id FOR NO KEY UPDATE` before the first bind (the run's sweep updates in id order).
3. **The kernel re-plans** over the rows read under the lock with the client's ticks. Decided in Kotlin under the lock, never by catching a `23505`:
   - a ticked row no longer exactly what the preview showed (`expected`: action, level, Jira parent, BIND node; for a CREATE the previewed LANDING `parent{kind, nodeId?}` so a row is never silently re-homed; for a milestone the previewed `teamId`, before any override) is skipped `CHANGED`. A BIND target bound meanwhile is `NAME_TAKEN`; one deleted turns the row into a CREATE: `CHANGED`. An `overrides.teamId` applies on top and is not compared;
   - an id the re-browse no longer finds is `CHANGED` without a key; a child of a row the client left out, or whose own row was skipped, is `PARENT_SKIPPED`; a name taken meanwhile is `NAME_TAKEN`;
   - a caller who may not schedule a milestone's team (`lockedIsActiveManager`) gets it created unscheduled.
4. **Inserts top-down** (a child's parent id is the one just returned), the dates of scheduled milestones through `writeSchedules` at `revision + 1`, then a binding and its first observation per written row through `insertBoundLocked`; a dead-node holder of the issue (this connection or another of the site) is released.
5. **Exactly one revision bump**, also when every item was skipped (a re-import answers `skipped[] = ALREADY_BOUND` and still moves the revision by one). The plan lock is held about 1 s at the plan's whole scale and about 2 s at the 2,000-item cap (`build-times.md`); the browse happens before it.
6. **After the commit:** `jira.binding_released` per released holder, then ONE `jira.import_applied` line (fields: `observability.md`). The answer is `{revision, created[{jiraId, issueKey, kind, id, bindingId, name, scheduled}], bound[…], skipped[{jiraId, issueKey?, reason}]}`: ids, keys and reasons only. `skipped[]` lists the visible skips first, in row order; a non-admin under an active filter gets the withheld ids after them ("What a non-admin sees"); the vanished ids come last.

**The per-row owner.** `overrides.ownerPersonId` names the owner of a PROGRAM or PROJECT the apply CREATES instead of `ownerPersonId` (`LockedApply.ownerOf`). It is ignored on a milestone, a BIND and a skipped row (not a `400`), as the team override is on a row it does not fit, and it is not part of `expected`. It adds NO guard: whoever may apply may name any active person per row, and the up-front `403`s still come first.
It is audited: `jira.import_applied` carries `ownerPersonId` and `ownerOverridePersonIds` (the distinct per-row owners applied, ascending: an ownership grant hands rights over a subtree); the team override is not logged.

### Import from a linked node

Files: `jira/JiraImportChildren.kt` (`browseChildren`, the query `JiraJql.children`), `JiraImportService.resolveRoot`, `ImportPlan.requireRootRow`, `ImportParentRule.lookupOf`/`isOutsideRoot`.

- **What it is.** Preview and apply take an optional `root {level: PROGRAM|PROJECT, nodeId}` (on `JiraImportScope` and, flat, on `JiraImportApplyRequest`; absent = the whole-scope import, request for request). With it they read ONLY what Jira lists under the root's Jira item and land it under the root's own node: a program root brings its projects and their milestones, a project root its milestones. `workStreamId` stays required and must be the root's own stream (`400`); a rooted import never creates a program; `items` are the root's descendants and the root is never a row.
- **The request cannot steer a row out of the subtree** (`400` after the guards, `JiraImportService.requireDefaultsUnderRoot`): with a root `defaults.programId` is refused, `defaults.projectId` must be a project of the root PROGRAM, a PROJECT root takes none. The apply repeats the `defaults.projectId` rule under the plan lock (a project moved to another program during the browse: the same `400`, nothing written).
- **Who may.** The root is ONE MORE NAMED TARGET of "ADMIN, or an owner of every target": the root's owner chain (a program root: the stream's or the program's owner; a project root: any of the three) or ADMIN, read first (`404`), guarded up front (`403`) before the token is decrypted and before any Jira call, and re-read and re-guarded under the plan lock. An import started from a linked item writes only under that item, for EVERY caller (ADMIN and the stream's owner included). `authorization.md` has the order and what a non-admin learns.
- **The order** adds to the whole-scope one: the root's chain `404` (`Program not found` / `Project not found`) and `403`; the root under the picked stream (`400`); then the root's ACTIVE link through THIS connection (`resolveRoot`: `jira_bindings` by level and node; none, or one held through another connection of the site, is `409 urn:astrolabe:problem:jira-root-unusable`); then the browse, snapshot and kernel; then the root's own row must read `ALREADY_BOUND` to the root node through the root's own connection (`requireRootRow`, else the same `409`: the link changed, preview again).
- **The apply repeats it** under the plan lock before the ticked-target guard: a `409` there is a rollback, nothing written, no bump.

#### The rooted browse

- **The read.** One `GET /issue/{id}` of the root by the STORED numeric id (the request never names an issue), then rounds top down: round one asks for the root's children at every mapped level below the root's (`project in (...) AND issuetype in (<ids>) AND parent in (<root id>) ORDER BY id ASC`); round two (a program root with the project level mapped) asks for the milestone level under every project round one held, ALL of them (admitted or not, linked or not), in chunks of 50 ids ascending.
- **What reaches a query:** every id passes `ISSUE_ID_PATTERN` first; the request shapes a query only through the picked project keys and the filter (`excludeDone`, the bounded day count): constant, safe clauses. The server's own verdict on every entry (a site that ignored a clause cannot widen the scope): it names one of the parents of THAT query, its key is inside the import's keys, its mapped level is one the round reads, it is not a repeat.
- **The root document** must be the id asked for, parse, have its key inside the connection's keys and sit at the Jira level the mapping gives the root's plan level; each miss is the `409`. A `404` on it is trusted as a verdict (the `409`: deleted or not visible); every other failure is the `502 jira-upstream`, a `403` (`FORBIDDEN_SCOPE`) included, whereas the gone probe records a `403` as `GONE_FORBIDDEN`: a rooted import has no use for a half-verdict.
- **The kernel is untouched:** the root is handed to it (`ImportInput.root`) as a browsed issue (its level from its own document, the row `ALREADY_BOUND`), so its children land `EXISTING` under the root node and round-two rows under their project's row; the import never depends on A10.
- **The filter under a root.** A round that reads a level with children to walk (the projects) is NOT narrowed at the source and is judged by the server's rule afterwards: an admitted project is kept; a done or quiet one is held only so its children can be read and is kept (`KEPT_AS_PARENT`) only when a kept item hangs under it, else dropped. The leaf level is narrowed in the query. No parent is read by id, so the 200-read bound does not apply.
- **Accepted:** every held row, a not-admitted project included, counts toward the 2,000 cap, so a root with very many done projects can read `truncated` although few rows would remain; narrow the filter or start from a project. An apply truncated at the cap answers its own sentence (`rootedImportTruncated`: narrow the filter, and under a PROGRAM root start from a project below it).
- **Bounds.** At most 2,000 rows (the root counts), the 170 s deadline, the `jira-import` bucket, the same guarded client and two endpoints (`search/jql`, `issue/{id}`). The whole rooted browse shares ONE page budget of 200 requests (`MAX_SEARCH_PAGES`; one `PageCeiling` passed to every `searchPages` call and spent once by the root read): past it `502` with `LIMIT_EXCEEDED`, so a site that ignores the parent clause stops at the budget, not the deadline.
- **Cost.** An honest site stays far below the budget WITHOUT a filter (a program root with 2,000 rows is at most 40 round-two queries, about 60 requests). Under a filter round one is unfiltered at the source (it lists the projects to walk), so the milestone-level children the filter drops there are read but never held, and only the budget bounds them.

#### Rules and disclosure

- **Rules worth knowing.** A milestone-level item straight under a root program follows the whole-scope rule (the default project, which the dialog offers from the root program's projects, else `NO_PARENT`). A level the mapping leaves out between the root and its children is not walked (backlog: browse unmapped intermediate levels).
- **`OUTSIDE_ROOT`.** A child project already linked to a plan project of ANOTHER program of the same stream stays `ALREADY_BOUND` (naming its holder) and what hangs under it is skipped `OUTSIDE_ROOT` in the preview and the apply, whoever asks: the preview never depends on who looks. The rule lives in ONE place, `ImportParentRule.lookupOf`/`isOutsideRoot`, whenever a row's parent resolves to an existing node: a project-level row must sit under the root program itself, a milestone-level row under a project of the root program or under the root project.
- **More on `OUTSIDE_ROOT`:** a parent that is a new row of the batch needs no check; a holder in another work stream still falls to the default project else `NO_PARENT`; a default project outside the root handed straight to the kernel is `OUTSIDE_ROOT`.
- **An apply re-plans** under the lock with the same root, so a project moved out of the root program meanwhile turns its ticked rows into `OUTSIDE_ROOT` skips, never a write outside the root. For a non-admin it is an ordinary redacted skip.
- **A ticked id** the rooted browse does not hold (outside the subtree) is `CHANGED` with no key. `requireResolvedTargets` stays as defence in depth.
- **Accepted races:** a root unlinked by someone else in the instant after the holders are read under the lock still gets its children created under the root NODE (no new lock); a root moved to another work stream meanwhile leaves every ticked row `NO_PARENT` (`CHANGED` where a default project is sent). Either way nothing is written to a wrong place.
- **Disclosure.** An owner who links their node to a Jira item (an audited bind) can preview the text of everything under that item in the connection's projects: the settled rule "rows on the caller's own target are shown in full", applied to a subtree. Each ANSWERED rooted preview leaves one `jira.import_previewed` audit line (ids and a count: `observability.md`), so a bind, a rooted preview and an unbind cannot read a subtree unseen; a refused preview emits none and a whole-scope preview is unaudited. The `409`s speak only about the caller's own link.
- **The residual (under an active filter).** `OUTSIDE_ROOT` rows are handle-free like every redacted skip, but their COUNT tells how many items under the child project linked elsewhere pass the filter; the `jira-import` bucket bounds the probing. Without a filter the rows themselves are listed (key, level, reason, no text). `jira.import_applied` carries `rootLevel` and `rootNodeId` (null for a whole-scope import).

Pinned by: `JiraImportChildrenTest` (the browse, the shared page budget), `JiraImportChildrenPreviewTest` (the `IMC` tables, the `jira.import_previewed` line), `JiraImportChildrenGuardsTest` (the caller matrix per root level, the order, the redaction), `JiraImportRootKernelTest`, `JiraImportChildrenErrorsTest` (every status, the five causes of the `409`), `JiraImportChildrenApplyTest` (the write, the two lock races), `JiraImportDecryptOrderTest`, `JiraImportWebBodyTest`.

## Coverage and roll-ups

Files: `jira/JiraCensus.kt`, `CensusLoopGuard.kt`, `JiraIssueStore.kt`, `DeviationCoverageRows.kt`, `JiraCoverage.kt`. Coverage finds what the plan misses (Jira children nobody planned, plan children Jira does not track) and shows an epic's story roll-up. The EXISTING run observes the whole in-scope census into the mirror `jira_issues` (`persistence.md` "The Jira census (V23)") in the same pass; nothing is fetched at request time and nothing is written to Jira. This section is the census half (what the run writes) and the two reads of it.

### The census

- **Terms.** *Mapped levels* = the effective mapping's hierarchy levels. *Child level* = `milestone.hierarchyLevel - 1` when that is not below 0 and the site has non-sub-task types there (`typeIdsAtLevel`, every id a valid JQL type id), else none: a milestone mapped to Jira level 0 has no roll-up, and sub-tasks never count. *Census levels* = mapped ∪ child.
- **Every page entry is observed.** The run's read, the typed full read or the untyped incremental, passes each entry to `JiraCensus.observe` BEFORE the bound-issue skip: a row is built by `CensusIssue.of` (fitted like an observation), kept when its level is a census level, buffered by id and flushed in `RUN_CHUNK`s through `JiraIssueStore.upsert` (one short transaction, no plan lock, no revision; the connection row is taken `FOR SHARE`, so a connection deleted meanwhile writes nothing). The incremental window already carries every story updated since.
- **What a row is.** Only issues of a type the run's sweeps ask for (the mapped types and the child types) at a census level are mirrored (an issue of any other type is invisible to the sweeps and would flap). The story-points marker (a plausible field id only) is added to the mapped read's `fields` too, so an incremental update of a story keeps its points whichever field the milestone's estimate is mapped to. Control characters in a summary become spaces.
- **After the reconcile** (`JiraCensus.complete`): flush; **prune the mapped levels** (rows at a mapped level in neither the sweep's listing nor the rows this run saw: the connection's `(issue_id, level)` index read once, deleted in `RUN_CHUNK` batches; an EMPTY listing prunes too, the sweep's WARN covers it and the next good sweep heals).
- **The children pass** follows: on a FULL read (the `LIMIT_EXCEEDED` fallback included) a typed full read (`JiraJql.full(keys, childTypeIds)` with `fields` = the system fields + the discovery's story-points marker) upserts every row and prunes child rows not read; otherwise, when `now - census_at >= jira.censusHours`, an id-only typed sweep (`JiraJql.sweep`, `fields=id`) prunes child rows neither listed nor seen this run. An empty children listing is normal (epics without stories) and logs no warning.
- **Self-healing.** On a FULL read the rows of a level that is no census level any more are deleted too. When an incremental run's sweep (mapped, or the due child sweep) lists an in-scope id the mirror lacks and the run did not read, `census_at` is CLEARED instead of stamped: the next run is full and re-seeds.
- **`census_at`** is stamped with the run's START after a full read (even with no child level, else it would stay null) or a completed child sweep, and `readPlan` reads in full whenever it is null. A connection with no bindings returns before any call: no census, no stamp.
- **Ceiling.** The children read shares the 200-page ceiling and `jira.pageSize`. Past a listing or response ceiling (`LIMIT_EXCEEDED` on the children listing ONLY; the mapped read keeps its rule and fails the run) the run keeps what it read, prunes nothing, still stamps (a big site is not re-read on every poll) and logs WARN `children census truncated at {n} pages after {n} child issue(s) (a listing or response ceiling): roll-ups may be incomplete` (A11).
- **Any other failure of the children pass** (a 5xx, a timeout, an invalid page) does NOT fail the run: the mapped work stands and the run SUCCEEDS, the pass keeps the rows it read, prunes nothing, does not stamp (so the next run is full and retries, until the loop guard trips and stamps instead) and logs WARN `children census failed: {code}`. Only a deleted or disabled connection ends the run (`runnableState` runs before every page: `CONNECTION_GONE` / `CONNECTION_DISABLED`, no further read, no stamp).
- **Cost.** The extra calls are the child level's pages: one typed read on a full run and one id sweep per `censusHours`; at the 1,000-milestone scale with 5,000 stories that is +50 field pages once per full read and +50 id pages a day.
- **Logging** (`ch.nokillswit.sync`, counts only, never a key, a summary or a URL): INFO `Sync run {id} census: issues={mapped rows written} children={child rows written} pruned={n} childPass={FULL|SWEEP|NONE}` and the WARNs above (`sync.md` "Log lines").

Pinned by: `JiraRunCensusTest` (MockEngine), `JiraRunReadTest` (a null `census_at` forces a full read), `JiraRunTest` (the `COV` roll-up figures and the day-2 prune against the stub), `JiraBootTest` (`jira.censusHours` 0 and 169 refuse boot).

### The loop guard

`jira/CensusLoopGuard.kt`. A census that can never converge (an in-scope issue that can never become a mirror row, or a children read that always fails) would heal or stay unstamped on every poll and read in full forever. The guard keeps TWO streaks per connection: the runs that CLEARED `census_at` (a heal) and the runs whose children pass FAILED.

- **Tripped.** Past `MAX_UNCONVERGED_RUNS` (3) a streak is tripped and its first run logs ONE WARN `Sync run {id} (connection {id}) census cannot converge after 3 runs in a row: {reason}; roll-ups may be incomplete` (reason: `a sweep keeps listing an issue the mirror lacks; ...` or `the children read keeps failing; ...`; ids and counts only), then DEBUG while it stays stuck; the warning re-arms when the streak ends.
- **Tripped heal:** the run leaves `census_at` ALONE (stamping it would push the child sweep's due time forward for ever and stale children would never be pruned), except when the child sweep is due (once per `jira.censusHours`): then it CLEARS once, one forced full read a day that may heal a later genuine gap, the streak held at the threshold so the next gap run trips again at once. **Tripped failure:** the run STAMPS `census_at`, so the retry cadence becomes the child sweep's, daily, not every poll.
- **What ends a streak.** A completed children FULL read ends the failure streak; a completed id SWEEP ends it only while it is not tripped (a working sweep says nothing of a typed full read that keeps failing). A conclusive incremental run (no gap, no failure, not truncated, and its child sweep ran or there is no child level) ends the heal streak. A `LIMIT_EXCEEDED`-truncated children listing neither counts nor resets the failure streak (a mapped-level gap in that run still counts as a heal). A run that is both a gap and a tripping failure warns for both.
- **A config change** that forces the full read (a re-discovery, a mapping change or an edit newer than the last succeeded run's start, the `readPlan` conditions) drops the entry, so a mapping fix untrips at once.
- **State** is IN MEMORY (`JiraObserver` holds one guard: a `ConcurrentHashMap` of a small record per connection id, updated atomically per key). The entry is removed when both streaks are empty, on a config change, or when a run finds its connection already deleted at its start (one deleted or disabled MID-run keeps a tiny entry until restart). A restart resets it, which costs at most one more round of full reads before it trips again: no migration.

Pinned by: `JiraRunCensusTest` (the heal loop and its reset, the tripped runs that leave the child sweep due, the daily forced full read, the failure streak, a working sweep that does not untrip, the config-change untrip, the truncated listing).

### The view reads the mirror

`jira/DeviationCoverageRows.kt`, called by `DeviationViewService.computeInTransaction` after `loadBoundTo`, inside the same snapshot; the acknowledge's `computeBindingInTransaction` goes through the same function, so an acknowledged coverage fingerprint equals the view's.

- **Three loaders**, one statement each (two for the plan side), scoped to the bindings in view. **`loadRollups`** (a bound MILESTONE's mirror rows at `milestone.hierarchyLevel - 1`, `GROUP BY (connection, parent)`: count, DONE count, points sum or null, newest `observed_at`; absent while there is no child).
- **`loadUnlinkedJira`** (the bound PROGRAM's or PROJECT's mirror children at the mapping's level for the child plan level, not DONE, with no ACTIVE binding of that issue id on an ACTIVE connection of the SAME `site_url`; keys ascending by numeric id).
- **`loadUnlinkedPlan`** (the node's direct ACTIVE plan children with no active binding on an active connection; names ascending by id).
- **No coverage** for a binding whose child plan level is unmapped or whose connection's mapping does not resolve. The inputs feed the kernel (`ChildRollup`, `UnlinkedChildren`) and the item carries the roll-up as `jira.rollup` (`DeviationRollup`, `JiraRollup` in the spec; always present, null = none; milestone bindings only).
- **Scope.** Coverage is computed for whatever bindings a scope reads, so a program binding's coverage shows on the Deviations page (the timeline fold asks for projects and milestones only). A disabled connection's items keep their last census. The view discloses the Jira KEYS of unbound issues, never summaries (`authorization.md`).

Pinned by: `DeviationCoverageTest` (the rows that count, the same-site rule, the unmapped level, scoped = full), `JiraAcknowledgeTest` (acknowledge and reopen on a new unbound epic).

### The connection's coverage summary

`GET /integrations/jira/connections/{id}/coverage` (`jira/JiraCoverage.kt`; ADMIN only, `requireAdmin` first, like the page it feeds). A separate route, not a member of `GET …/{id}`: that DTO is shared by the list, create and update, and a count read there would cost every list row a statement. No lock, no write, no Jira call, no migration.

- **What it counts,** per MAPPED plan level of the connection's current effective mapping (`loadConnections`, the Deviations view's resolution), over the census mirror's rows at that level's Jira hierarchy level: **in scope** (every mirror row of the connection at the level; the mirror is already scoped to the connection's keys), **linked** (an ACTIVE binding of an ACTIVE connection of the SAME site names the issue id: `bindingOnSameSite()`, the predicate `loadUnlinkedJira` uses) and **open and unlinked** (`status_category` not `DONE`, and not linked).
- **How:** one read-only REPEATABLE READ transaction, ONE grouped statement (`count` and two `CASE` sums over a LEFT JOIN to the DISTINCT set of the site's linked issue ids, `linkedIssueIdsOnSite`, so the verdict is computed once per row; two correlated `EXISTS` per row were measured slower).
- **`state`:** `NOT_SYNCED` (`census_at` null AND no mirror row; no counts); `MAPPING_UNUSABLE` (the mapping is missing, unreadable or no longer fits the discovery; no counts); `MAPPING_CHANGED` (`mapping_changed_at` later than the START of the last SUCCEEDED run, or a change and no success on record: the mirror was read under the old mapping; no counts until a run reads under the new one); else `READY` with `levels[]` top down (only the mapped ones; a level with no rows reads 0/0/0).
- **`readAt`** is the FINISH of the connection's last SUCCEEDED run (`SyncRunService.lastSucceededInTransaction`; null when none): the mapped levels are upserted and pruned on every run, so the counts are as of then, not `census_at`, which stamps only the child level.
- **Known limits.** A run of a connection with no bindings returns before any read (the mirror stays as the last run that had bindings left it, while `readAt` moves). `MAPPING_CHANGED` follows `mapping_changed_at` only, so a re-discovery that changes the DEFAULT mapping or an edit of the project keys is not flagged until the next run has read. The child level and unmapped levels never count; a disabled connection keeps its last census.
- **Counts only:** no key, name or summary (the keys of open unlinked items under a bound parent are on the Deviations page). The page shows it as the Coverage section (`web-internals.md` "Jira connections").

Pinned by: `JiraCoverageTest`, `jira-coverage.spec.ts`.

## Acknowledge

Files: `jira/JiraAcknowledgeRoutes.kt`, `JiraAcknowledgeService.kt`. A planner who has seen a deviation and accepts it acknowledges that LINE "until changed"; it then stops counting as open. `POST /integrations/jira/bindings/{id}/acknowledge {fingerprint, kind?}` and `DELETE …/{id}/acknowledge[?kind=]`. The order and the guard are `authorization.md`'s rows, the locks `persistence.md`'s, the audit `observability.md`'s; the shared vocabulary (the `409` URN, the 64-hex shape rule) is `sync/Acknowledge.kt` (`sync.md`).

- **What it keys on.** `fingerprintOf` (`jira/DeviationCompute.kt`, a delegate of the generic `fingerprintOf` in `infra/json/CanonicalJson.kt`, shared with the Flow capacity acknowledge): the SHA-256 of the canonical JSON of the binding's FULL kernel list (`[{kind, severity, detail}]`, `ESTIMATE_NOT_COMPARABLE` included even where the item hides it, so the value does not depend on the filter or the caller).
- **The pinned `Json`** writes neither nulls nor defaults, so a later additive nullable member of a deviation changes no hash (a null still differs from a value); `DeviationFingerprintTest` pins literal digests. A change on either side that alters a deviation (the plan date moved further, Jira's end moved, a new or vanished kind, a different count of days) gives another fingerprint: the stored acknowledgement reads `current = false`, "changed since", and the line is OPEN again. A change that alters no deviation keeps it.
- **Per line.** The stored fingerprint is that of ONE deviation (`fingerprintOf(Deviation)`, severity in the hash); the table `jira_deviation_acknowledgements` is keyed (binding, kind) because the kernel raises a kind at most once per binding (`JiraDeviationKernelsTest`), and a change reopens only the line it altered. The LIST fingerprint stays the token the client echoes (to acknowledge one line or all) and the compare that a view read is still current.
- **Stable details.** `PROGRESS_MISMATCH`'s detail is the contradicting plan date, so the fingerprint is stable day to day and a boundary crossed raises a NEW deviation, which correctly reopens the item. A release that changes a kernel rule un-acknowledges the lines whose fingerprints it alters: by design, stated in that release's notes.
- **The write:** ONE short transaction, no plan lock. The binding row is locked, the node's chain re-read and the guard run again, the deviations of THIS binding recomputed with `DeviationViewService.computeBindingInTransaction` (the view's own `computeInTransaction`, scoped by `DeviationScope(bindingId)`; a parent issue's own binding is looked up so `PARENT_MISMATCH` equals the view's), then the LIST fingerprint compared: different, an empty list, or a `kind` the full list does not hold now is `409 urn:astrolabe:problem:stale-deviations`, nothing written.
- **What is stamped.** With a `kind` that ONE line; without one, the lines without a current acknowledgement, or every line when each has one (a restamp). Each stamped line stores its OWN fingerprint, when and by whom: the target kinds' rows are deleted and the new ones inserted by one `insertRows` under the binding row lock (every writer of the table holds it; the unique index is the backstop). Nothing else is written: not `jira_bindings.updated_at`, no plan revision. Acknowledging the same state again restamps who and when.
- **`DELETE`** with `?kind=` removes that line's row (`404` when none); without it EVERY stored row of the binding, stale and retired kinds included (`404` when none). The parameter is parsed after the guard (`400` unknown, blank or repeated).
- **No pruning.** A row is never deleted because its line left the list: a line that disappears and returns identical reads acknowledged again with its original stamp; a stored kind this build does not know is ignored on read. The old `jira_bindings.ack_*` columns are dropped (V30); no earlier acknowledgement was backfilled.
- **What the view does with it.** Each listed line is a `DeviationLine` (`kind`, `severity`, `detail` and its own `acknowledgement{at, by, current}`, null until acknowledged); an item has no `acknowledgement` of its own, each line carries its own. A listed item shows EVERY line with its state, whatever the Status filter.
- **The default `GET /views/deviations`** lists OPEN items (at least one listed line without a current acknowledgement); `acknowledged=true` the items with at least one currently acknowledged LISTED line (a stamp on the hidden `ESTIMATE_NOT_COMPARABLE` line alone does not count: that item surfaces under `all=true` only), `=false` the open ones; `all` and the chips' implied `all` keep every state.
- **A kind or severity chip matches the lines of the selected Status:** the open lines by default and under `acknowledged=false`, the currently acknowledged ones under `acknowledged=true`, any listed line under `all` without a status (so Open + End differs omits an item whose End line is acknowledged; the item still shows every line).
- **Counting.** `warnings`, `infos`, `gone` and `acknowledged` share one basis, the items matching every filter but the acknowledgement state, and count its OPEN LINES (`warnings`, `infos`), its open items that are gone, and its items with a currently acknowledged listed line (so "N open" survives `acknowledged=true`); items order an OPEN warning line first; `bindings` is the number the list answers.
- **`ESTIMATE_NOT_COMPARABLE`.** An item whose only deviation is that kind is open, and counted, exactly where the kind is listed (`kind=ESTIMATE_NOT_COMPARABLE` or `all=true`); the default never lists it, so it is not open there. It can be acknowledged from such a listing (the kind-less call stamps it with the rest); the timeline fold ignores that kind.
- **Who.** The owner chain of the node or ADMIN, and, on a MILESTONE binding only, the ACTIVE manager of the milestone's STORED team, who may acknowledge and withdraw every deviation of it, whoever stamped it (`requireOwnerOrTeamManagerOrAdmin`, read first with `TeamService.isActiveManager`, again under the row lock with `lockedIsActiveManager`; `AckAudience` carries the chain and the stored team). A manager on a program or project binding, another team's manager, a roadmap editor and a stranger stay `403`; bind and unbind stay owners and ADMIN.
- **`can.acknowledge`** carries the verdict per item (`PlanPermissions.canAcknowledgeDeviations`, pinned against the guard; the view loads `activeManagedTeamIds` for a non-admin).

Pinned by: `JiraAcknowledgeTest`, `JiraAcknowledgeLinesTest` (one line, the kind-less form, refusals, withdrawals, a returning line, an unlinked manager), `JiraAcknowledgeRaceTest`, `JiraAcknowledgeRunTest` (a real `jira-day2` run opens the new GONE line only), `DeviationViewAckTest`, `DeviationFingerprintTest`, `JiraSchemaTest`.

## Timeline flags

The four timeline views (roadmap, programs, project, team) carry the Jira links and flags of the rows they answer (`planning-model.md` "Jira flags and links" is the contract, `timeline.md` "The Jira markers" the document shape and the measured cost). Files: `planning/ExternalFlags.kt`, `jira/JiraFlagSource.kt`.

- **The seam.** `planning` declares it (`ExternalFlagSource`, `ExternalFlagRequest`, `ExternalFlags`, `JiraLink`, `JiraSite`, `JiraSiteState`; the deviation vocabulary `Deviation`, `DeviationKind`, `DeviationSeverity`, `DeviationDetail` lives in `planning/Deviations.kt` under unchanged serialized names, so a stored fingerprint and the spec schemas did not move) and names no `jira` type.
- **The source.** `jira/JiraFlagSource.kt` implements it over `DeviationViewService.computeInTransaction(scope)`; `infra/db/Database.kt` wires it into the four view services through `CompositeExternalFlagSource`, beside `flow/FlowFlagSource`. It answers only the node half and returns early on `request.namesNoNode`. It runs INSIDE each view's `READ ONLY REPEATABLE READ` snapshot, after the calendar, with the calendar the view read and "today" from the deviations service's own clock, so a flag equals what the Deviations page lists as open for the same state.
- **The request's team half.** `ExternalFlagRequest.teamId` (the team view) and `everyTeam` (the roadmap loader: roadmap, programs, Home) are the two forms of Flow's half of the seam; the Jira source reads neither (`planning-model.md` "The roadmap view", `flow-sync.md` "The project rows' flag").
- **What raises a flag.** A binding of an ENABLED connection raises one `JIRA_DEVIATION` per OPEN LINE (a kernel deviation without a CURRENT acknowledgement of its own) at the deviation's severity, except `ESTIMATE_NOT_COMPARABLE` (a Deviations-page note, not a timeline warning). A stale acknowledgement (`current = false`) is open again. A project also gets ONE `JIRA_MILESTONES` roll-up over its milestones that raised a flag (`count`, the worst severity among the OPEN lines).
- **The flag's shape:** `{kind, severity}` plus only the members that apply: `deviation: {kind, detail}` on a `JIRA_DEVIATION` (no `severity` inside: it is the flag's own; the kernel's `Deviation` stays whole and is what the fingerprints hash), `count` on a `JIRA_MILESTONES`. A `detail`'s null members (`jira`, `plan`, `days`, `count`) are absent from the wire, on the flags and on the `GET /views/deviations` lines alike; no fingerprint moves (`DeviationFingerprintTest`).
- **What does not.** A DISABLED connection: its rows keep the `jira` link and its site with null dates, no flag, no bar and no roll-up contribution, so the page still sees the node as linked and can unlink it (its bindings also list on the Deviations page and still block their node). A fully acknowledged binding (it keeps its `jira` link so the bar stays), a clean binding, an unobserved one (link with null dates). A `gone` item raises `GONE` alone with null dates. Program and work-stream bindings are not folded in (the programs tree rolls up the projects' flags).
- **The scope.** `DeviationScope.levels` (the whole-plan ask reads project and milestone bindings only); a named node list matches a binding on ANY named node, a named EMPTY list names nothing. The roadmap and programs views ask for the whole plan, the project view for the project and ALL its milestones, the team view for no project and the team's milestones. The scoped computation equals the full one (`DeviationScopeNodesTest`, including a parent issue bound outside the scope).
- **The sites.** `JiraSite` is `{connectionId, siteUrl, state, mappingOk}`, built at ONE place (`JiraFlagSource`) from the connections the REFERENCED rows link through (`referencedConnectionsOnly`, then the rows that survived the liveness filter).
- **The site's state:** `state` is the connection's derived sync state (`JiraSiteState`, `planning`'s own enum with `SyncState`'s five names, converted by name and pinned equal by `JiraFlagSourceTest`; the fold calls `DeviationViewService.siteStatesInTransaction`); `mappingOk` is `levels != null`. Only the state and the mapping verdict, never the connection's name, project keys, `lastRun`, error code or any credential.
- **Honest limits.** `CURRENT` means the newest run succeeded and, for a polled connection, not long ago; a manual-only connection stays `CURRENT` after any success, however old (its `lastSucceededAt` is on the Deviations page).
- **One staleness rule:** the chips and the Deviations banner read ONE rule (`isStaleSource`, `web-internals.md`: the state is not `CURRENT`, or the mapping does not fit), so `STALE`, a first run in flight and a retry in flight after a failure raise the banner too; a DISABLED connection the chip counts and the banner skips. The Roadmap and Programs facts line says "Jira data may be out of date" while ANY site of the document is behind (the view cannot say which site a project's milestone roll-up links through).
- **Cost.** About 45 us a binding in service time; numbers and a profile are `timeline.md`'s "Measured figures". The lean projection is a backlog item.

Pinned by: `JiraFlagSourceTest` (each kind, the roll-up, acknowledged, partly acknowledged, stale, disabled, noise, gone, the request shapes), `DeviationScopeNodesTest`, `TimelineJiraFlagsTest` (the four views through HTTP on one bound world, additivity, the always-present members), `JiraFlagsScaleTest` (the sizes and the gates), `JiraSiteStateTest` (a site's state and mapping verdict equal the Deviations view's in every state).

## First real-site walk-through

Do this when a real site and token arrive, with an account and a scoped or classic API token that reads a handful of projects. Nothing in this doc records what a real site answered; record findings in the ledger below as assumptions confirmed or refuted, never as site data.

1. **Connect.** Administration → Jira → New connection: the site URL (`https://<name>.atlassian.net`), the account email, the token, auth scheme `BASIC` first (`BEARER` if the site demands it), a few project keys (≤ 50). **Test connection** and read the rows top to bottom; the FIRST failed row is the cause.
   - `tenant_info` failed (everything after reads `SKIPPED`): the site URL is wrong, or `BLOCKED_HOST` (not a tenant host), or a network/DNS block (`outbound.blocked` audit event).
   - `myself` 401: the token or the auth scheme. `myself` ok but another row 401: a missing scope; the row's hint names it (a missing scope is a 401, not a 403).
   - `search` 400 or `INVALID_RESPONSE`: A3 (issue-type ids in JQL). `projects` 400: A8 (50 `keys`). A scoped token is the likeliest remaining surprise.
   - `project:<KEY>` `PROJECT_NOT_VISIBLE`: the token cannot see that project. No `issue` row: the search returned nothing.
2. **Read the discovery report** (the Mapping section; it exists only once a Test connection has been RECORDED, so a stored-connection test comes first; mapping, Peek and bind answer `409` until then): the counts, which field matched "Target start"/"Target end" and with what `schema.custom` (A1), whether a legacy Parent Link exists (A2), the Team and Story-points fields (A7 if `fieldsTruncated`). Every "not found" is a decision for the mapping.
3. **Check the mapping defaults and save them** (or pick fields by hand); the levels list shows the type names per Jira level on this site. A site without Jira levels 2 and 3 (Initiative, Program need Premium) leaves the project and program levels unmapped: then only milestones can be linked until an admin maps levels that exist.
4. **Peek** one epic (and an initiative where the site has them): the type, hierarchy level, parent key, the dates as plain `YYYY-MM-DD` (A5: a datetime field is refused), the estimate, the Team name. `raw` shows what the site sent.
5. **Bind** one node per mapped level to known issues: "Link to Jira…" on the project page for a project or a milestone (an owner or ADMIN), "Link a node…" in the connection page's Bindings section for a program (ADMIN). A wrong level reads `400` naming both levels. Then **Refresh now** (ADMIN) and read the run row (`observed`, `calls`, the error code; `rateLimited` and `backoffMs` are in `GET /integrations/sync/runs` and the INFO log line). Compare the Deviations page with the Jira UI for those items.
6. **Import** (only after steps 1 to 5 read right). It creates real plan rows and nothing undoes it in one step; program names are globally unique. Use a throwaway work stream (with a throwaway owner) and a connection scoped to a small project, and review the mapping first (the import reads exactly the mapped levels, fields, unit and Team field).
   - Open **Import from Jira…**, pick the stream, an owner and a default team, **Preview** and read it: the totals, which rows are CREATE, BIND and SKIP and why. Renamed items preview as new unless a suggested match offers the link. **Assert the totals against what you expect** before pressing Import.
   - Many `NO_PARENT` rows: the items have no parent at the level above (give a default program or project) or the site's `search/jql` entries do not carry `parent.fields.issuetype` (A10). A preview that takes minutes is the browse itself (it stops at 170 s): keep the dialog's filter on (done items out, 365 days).
   - `502` with `INVALID_RESPONSE` means the site refused a clause (A16): switch "Leave out done items" off to tell which.
   - After **Import** read the outcome, open the project page, run **Refresh now** and compare the Deviations page. A second import must create nothing when everything was imported (`ALREADY_BOUND`).
7. **When something fails:** the run row's `errorCode` (the list: the spec's `SyncFailureCode`); the `ch.nokillswit.sync` log lines (counts and codes only); the `jira.connection_tested` / `jira.sync_requested` audit events; `502 BUSY` on a bind means the permit pool was occupied (retry, or raise `JIRA_MAX_CONCURRENT_REQUESTS`).
8. **Leave it running** for a day at the 15-minute default (after steps 1 to 7 read right). Watch the status (Administration → Jira, or the telemetry panel's Sync section): **Current**, "next poll in N min", **Scheduled** rows in the runs table; a token the site rejects must read **Failed** with its code and a doubling wait (one interval, then two, up to six hours), and a corrected token must poll at once. `RATE_LIMITED` run codes mean: lengthen the interval.
9. **Compare the flags:** the Jira flags on the roadmap and the project and team pages should name the same items the Deviations page lists as open; acknowledging one must silence its flag on all four pages; the "Jira dates" bar must sit where Jira's own dates are.
10. **Coverage and roll-ups** (with a bound program or project whose Jira item has children): compare the Deviations page's **Not in plan** (`UNLINKED_IN_JIRA`) and **Not in Jira** (`UNLINKED_IN_PLAN`) rows with the Jira board: every OPEN child that no binding covers is listed by key (done children are not), every unlinked plan child by name. Compare each epic chip's roll-up (`done/children · points pt`) with the epic's real counts and points; an epic whose children are all done must show **Children done** while the plan still runs.
11. **No roll-up anywhere:** the site's stories do not carry `fields.parent` (A12, the discovery's Epic Link marker) or sit past the page ceiling (A11, the `children census truncated` WARN). `done` stuck at 0: A13. Points missing: A14.
12. **The gone probe** (A15): bind a milestone to a throwaway issue, **Refresh now**, then delete it in Jira (and, separately, move another to a project outside the connection's keys) and run again. Expect "Deleted in Jira (or no longer visible to the connection's account)" and "Moved out of the connection's projects (Jira still has it)", with `observation.goneReason == "MOVED_OUT"` and the binding's `issueKey` and link showing the NEW key (the 200's `key`).
13. **The probe's cost:** `calls=` grows by one per gone binding in the queue. A verdict (`DELETED`, `FORBIDDEN`) is never asked again; the moved one is asked again by every Refresh now and by a scheduled run a day after its last answer (once deleted, that ask answers 404 and the row turns `DELETED`). A key still inside the connection's keys (archived, a changed type) reads `NOT_LISTED`. A moved issue that reads Deleted, a deleted one that reads Moved out, or a moved one that keeps its OLD key or reads "Not listed" means A15 is wrong: record it in the ledger.
14. **Import from a linked node** (A18, after steps 1 to 6): import from a linked program (Plan page) or project (its page) and compare the preview with Jira's own search for `parent = <the item's key>`. An empty preview against a non-empty search is A18 (`parent in (<numeric ids>)` above an epic) or A2 (the hierarchy lives elsewhere); `502 jira-upstream (INVALID_RESPONSE)` is a site refusing the query (A16, or A18). Import only what is wanted, then **Refresh now**: the imported rows read `ALREADY_BOUND` in a second preview.
