# Jira sync

Owns: the Jira connector (gateway, Test connection, discovery, mapping, bindings, the run, deviations, the plan's links; below the divider the import, coverage, acknowledge, timeline flags, the stub). Not here: runs, scheduler, status, failure codes, token life (`sync.md`); guard orders (`authorization.md`); audit events (`observability.md`); tables (`persistence.md` "Jira"); the outbound guard (`security.md` "The Jira consumer"); Flow (`flow-sync.md`); the pages (`web-internals.md`); the stub's data (`sample-data/jira/README.md`).

## Rules

- **Nothing is ever written to Jira.** The sync observes and warns; a correction is made in Astrolabe. The one Jira-derived write to the plan is the import (ADMIN or an owner of every target, under the plan lock).
- **A stored site URL never steers authenticated traffic.** Every authenticated call goes to `https://api.atlassian.com/ex/jira/{cloudId}/rest/api/3/...`; only the unauthenticated `GET https://<site>/_edge/tenant_info` goes to the site and supplies the `cloudId` (`HttpJiraClient.resolveCloudId`; validated as a UUID before it is stored or spliced into a path). One guarded client serves the app.
- **The registry is ADMIN only on every operation, reads included, `requireAdmin` before the body.** Its token is write-only (`sync.md` "A stored token's life"). Test connection never answers 502: every outcome is a row of a `200`.
- **A binding is 1:1** per plan node and per Jira issue, across the active connections of a site. Binds serialize on `BIND_LOCK_KEY`; the one Jira call of a bind is outside any transaction; a binding is not plan state (no plan lock, no revision bump).
- **A run observes and holds no plan lock,** never keeps a transaction across a Jira call and writes whole chunks (at most 100 bindings) in short transactions. The views read only the database.
- **The mapping is the connection's state.** A mapping a later discovery outgrew is reported (`problems[]`), never rewritten; a stale one is `409 jira-mapping-invalid` on a bind and Peek and a `FAILED` run with `MAPPING_INVALID`.
- **A bound issue that leaves the listing is probed by id until Jira answers.** A verdict (404 `DELETED`, 403 `FORBIDDEN`) is final and never asked again; a probe never fails the run; a connection that never answers is backed off.
- **Deviations only warn.** The kernel is pure; dates compare in working days; nothing is moved.
- **Disclosure.** Every reader of the Deviations view, the bindings list and the timeline chips sees a moved item's current key (it may name a project outside the connection's keys) and the Jira keys (never a summary) of unbound items; never a connection's email, token or mapping.

## The transport and the gateway

Files: `jira/Jira.kt`, `JiraHttp.kt`, `JiraClient.kt`, `infra/fetch/`.

- A site URL that no longer has the genuine tenant shape is refused (`BLOCKED_HOST`) before any client exists (`infra/outbound/AtlassianSites.kt`).
- `authScheme` per connection: `BASIC` (`base64(email:token)`) or `BEARER`. Which one a site and token need is NOT verified (Assumptions ledger). A scoped token missing a scope answers **401, not 403**; the probe rows carry the scope hint for that reason.
- The transport is `infra/fetch/` (Flow's: retry, per-tenant pause, `X-RateLimit-NearLimit` = a 1 s sleep, byte, node and page ceilings); its codes are `FetchCodes` plus `JiraRunCodes.CURSOR_EXPIRED` (`sync.md` "Failure codes").
- One outbound permit pool (`jira.maxConcurrentRequests`) serves the run, the probes, Peek, the import and the binds. A bind queues for a permit at most `jira.bindPermitWaitMillis`, then answers `502 BUSY`, so binds never hold a Test connection behind them.
- `search/jql` returns only `id` unless `fields` is named; the run names every field it reads (timestamps: `JiraTime`).
- **Development only:** `jira.stubBaseUrl` (`JIRA_STUB_BASE_URL`) reroutes BOTH hosts of a `stub-` site, and no other, to the stub; a non-blank value outside development mode refuses boot naming the key.
- **Boot configuration** (`jira.*`, env `JIRA_*`, boot-validated; the first five via `infra/fetch/TransportConfig.kt`), default and bounds: `requestTimeoutSeconds` 30 (5..120); `requestDeadlineSeconds` 180 (10..600); `maxResponseBytes` 4 MiB (64 KiB..16 MiB); `maxConcurrentRequests` 2 (1..8); `maxRetries` 4 (0..8); `bindPermitWaitMillis` 5000 (100..60000); `pageSize` 100 (1..500); `incrementalOverlapMinutes` 10 (0..1440); `censusHours` 24 (1..168; also the hours between two scheduled re-asks of a readable gone item).

## Test connection and the probes

`JiraConnector.testConnection` runs the probes in sequence (10 s each, 30 s in all, never throwing); every row is required. In this order, with the scope each needs:

1. `tenant_info`: `GET /_edge/tenant_info`, unauthenticated; supplies the `cloudId`.
2. `myself` (`read:jira-user`).
3. `issuetype` (`read:issue-type:jira`): supplies the type ids the search narrows by.
4. `search` (`read:jql:jira`): `GET /search/jql`, `maxResults=1`, `fields=id`; the JQL is the connection's scope AND `issuetype in (<ids at the mapped milestone level, else Epic level 1, else level 0>)`.
5. `field` (`read:field:jira`).
6. `projects` (`read:project:jira`): `GET /project/search?keys=…` with exactly the configured keys; then one `project:<KEY>` row per key (a key the token cannot see fails `PROJECT_NOT_VISIBLE`).
7. `issue` (`read:issue-details:jira`): `GET /issue/{id}` on the first id the search returned; no row at all when the search returned nothing.

- **When `tenant_info` fails** the gateway rows (`myself` to `projects`) read `SKIPPED` (`ok: false`, no status, no scope hint; `gatewayProbe`, `ProbeRun.skip` in `infra/fetch/ConnectionProbes.kt`, shared with Flow): there is no gateway to call. They count as failed required rows; the UI shows a gray "Skipped" and counts only the real failure. No `project:<KEY>` or `issue` row appears.
- **Other row codes,** by object: `FetchCodes` `SKIPPED`, `BLOCKED_HOST`, `TIMEOUT`, `INVALID_RESPONSE` (a malformed body); `SyncErrorCodes.TOKEN_UNREADABLE` (one `stored_token` row, nothing called); `JiraRunCodes.PROJECT_NOT_VISIBLE`.
- `POST …/connections/test` is ad hoc (carries the token, stores nothing). `POST …/{id}/test` uses the stored token and records `last_tested_at/ok`, `cloud_id` (only when resolved) and **the discovery whenever both `field` and `issuetype` answered, even if another probe failed**, so a failing first test still leaves the report that diagnoses it; only if the row was not edited meanwhile (`recorded`); audited `jira.connection_tested`, never with the token.

Pinned by: `JiraTestConnectionTest`, `JiraConnectionTest`, `JiraBootTest`.

## Discovery

`GET …/{id}/discovery` answers the stored snapshot (`409 jira-not-discovered` before the first recorded test).

- `fieldCount`/`issueTypeCount` as the site reported them; the usable fields (`date`, `datetime`, `number`, the customs `atlassian-team`, `gh-epic-link`, `jpo-custom-field-parent`), capped at 2,000, markers first (`fieldsTruncated`); the issue types (cap 500); `levels[{level, typeNames}]` (non-sub-task types by `hierarchyLevel`).
- The **markers** the report prints: `targetStart`/`targetEnd` (a **date** field named "Target start"/"Target end", else `schema.custom` `jpo-custom-field-baseline-start`/`-end`), `startDate` ("Start date"), `dueDate` (`duedate`), `storyPoints` (the first `number` field named like "story point"), `team` (`atlassian-team`), `legacyEpicLink`, `legacyParentLink`.

## Mapping

Files: `jira/JiraMapping*.kt`, `JiraPeek.kt`. One canonical JSONB document per connection (`jira_connections.mapping`): `levels.{program,project,milestone}` = `{hierarchyLevel, fields{start, end, estimate}}` (program and project optional, milestone required), `estimate{unit POINTS|HOURS|DAYS, manDaysPerUnit|null}`, `teamFieldId`.

- `PUT …/{id}/mapping` (204) checks the shape before any database read (levels ≥ 0 and strictly decreasing program > project > milestone, field ids of the Jira shape, factor `0 < x ≤ 1000` with at most two decimals), then under the row lock against the discovery: every named level has a non-sub-task type, start/end are `date` fields (a `datetime` is refused: time zones), the estimate is a `number`, the Team field is the site's `atlassian-team` one; `409 jira-not-discovered` with no discovery.
- `jira.mapping_changed` audits the before/after SHA-256 of every accepted PUT; one that changes the document sets `mapping_changed_at` (the next run reads in full). `GET` answers `{stored, defaults, effective, discoveredAt, problems[]}`.
- **Defaults** (pure `JiraMappingDefaults.resolve(discovery)`, used until a mapping is saved): milestone = Jira level 1 (Epic) if the site has a non-sub-task type there, else level 0; project = level 2, program = level 3 when present; start = "Target start", else "Start date"; end = "Target end", else `duedate` (`date` fields only); estimate = the story-points field **on the milestone only**, unit `POINTS`, no factor (shown, never compared); `teamFieldId` = the `atlassian-team` field.
- The bind, the import and the run share one resolution (`resolveEffectiveMapping`): stored-or-defaults, re-validated against the CURRENT discovery; an undecodable document is `MAPPING_UNREADABLE`.
- **Peek** (`GET …/{id}/peek?key=ABC-12`, `jira-test` bucket): one `GET /issue/{key}`, answered as `{issue, resolved{level, start, end, estimate, unit, teamName}, raw}`; `raw` holds only the mapped fields' values, `resolved.estimate` is read as a sync reads it (`estimateOf`: two decimals half up, absent for a figure the observer drops). Nothing stored, no audit; the key must be in the connection's project keys; an upstream failure is `502 jira-upstream` carrying only the code (`respondJiraUpstream`).

Pinned by: `JiraMappingTest`, `JiraMappingDefaultsTest`.

## Bindings

A binding links ONE plan node (program, project or milestone) to ONE Jira issue by its numeric id; the key is for display and follows a move. The database holds both directions (`uq_jira_bindings_node_active`, `uq_jira_bindings_issue_active`); the lock makes the service's checks exact. `POST /integrations/jira/bindings {connectionId, level, nodeId, issueKey}` → `201`, in this order (guard order: `authorization.md` "Jira bindings and acknowledge"):

1. The body decodes; the node's chain is read (missing = `404`); `requireOwnerOrAdmin` (`403`); then validation (`400`).
2. **One Jira call, outside any transaction** (`observeForBind`): the connection active and enabled (`400`), its token readable (`409 jira-token-unreadable`), discovered (`409 jira-not-discovered`), its effective mapping valid (`409 jira-mapping-invalid`); the level mapped and the key in scope (`400`); the issue exists (`400 "Unknown Jira issue"`) at the hierarchy level the mapping gives that plan level (`400` naming both). Any `FetchException` is `502 jira-upstream (CODE)`, `BUSY` included.
3. The transaction: the advisory lock; the connection row `FOR SHARE` (a delete or edit waits, or has won: `400`); the scope re-checked; the node row `FOR SHARE` (`404` if deleted); the chain re-read and the guard re-run;
   the node's own active binding → `409 already-bound`; the issue's active bindings on this connection **or on another active connection of the same site** (`JiraConnectionService.siteConnectionIds(site)`) → `409 already-bound`, unless their node (or an ancestor) is deleted: then the old binding is **released** (soft-deleted; `jira.binding_released`, `reason=NODE_GONE`). Then the binding and its first `jira_observations` row are inserted; audit `jira.binding_created` after the commit.

- `DELETE …/bindings/{id}` soft-deletes (history stays) after the guard on the chain as last stored (a binding of a gone node is unbound by whoever passes it); `jira.binding_deleted`.
- Deleting a connection soft-deletes its bindings in the same transaction (the node index has no connection column, so they would block their nodes for good) and hard-deletes its runs. A program-level binding is made on a connection's page (ADMIN) only.

Pinned by: `JiraBindingTest`, `JiraBindingLifecycleTest`, `JiraBindingRaceTest`, `JiraBindBusyTest`.

## Observations and the run

Files: `jira/JiraObserver.kt`, `JiraObservation.kt`, `JiraRunStore.kt`, `JiraSearch.kt`, `JiraGoneProbe.kt`, `GoneProbeDamper.kt`.

`jira_observations` holds the LATEST observed state of a binding (a hard overwrite, one row per binding; the status category `new|indeterminate|done` reads `TODO|IN_PROGRESS|DONE`, else `UNKNOWN`). `JiraObservation.of` is pure and clamps every value to its column (a figure past `NUMERIC(12,2)` reads as null), so one odd issue cannot wedge every later run.

**Refresh now** (`POST /integrations/sync/runs`): `requireRunnable` (active and enabled, else `400`), the claim (`sync.md` "The run registry and the claim"), audit `jira.sync_requested`, `202`.
A run and an import are independent: they meet only on binding rows, in id order.
The scheduler's read of a connection is `JiraConnectionService.pollRows()` (`jira/JiraConnectionPolling.kt` over `pollRowsOf`): seven columns of the ACTIVE rows, never the token or the discovery.
Both connectors' runs go through `sync/RunEnvelope.kt` (`runWithTally`): the tally, the counters (`RunProgress`), the typed `RunProblem` and the failure text `"<Jira|Flow> fetch failed: CODE (status)"` (`fetchFailureDetail`) are defined once there.

### The order of a run

`JiraObserver.execute`:

1. Read the connection: gone → `CONNECTION_GONE`, disabled → `CONNECTION_DISABLED`. Release bindings of deleted nodes (`jira.binding_released`).
2. Token readable (`TOKEN_UNREADABLE`), discovery present (`NOT_DISCOVERED`), mapping usable (`MAPPING_UNREADABLE`, `MAPPING_INVALID`, the latter also when a mapped level has no issue type in the discovery snapshot). Take the active bindings; **none → the run succeeds having called nothing.**
3. `tenant_info` (persisting `cloud_id` when none is stored), then the read ("The read").
4. The **sweep**: `…issuetype in (…) ORDER BY id ASC`, `fields=id`. A bound id missing from it, not just read, whose last observed type is among the swept types, is `gone` as `OUT_OF_SCOPE` (a deletion, a move out of the keys and a lost permission look alike here); a flagged id seen again is cleared.
5. The **gone probe** ("The gone probe").
6. The **census** (`Coverage and roll-ups`).

- **Inside a read:** at most 200 pages (the read and the sweep each get 200) else `LIMIT_EXCEEDED`; `CURSOR_EXPIRED` restarts the query once, a second expiry fails the run; a `200` that is not a listing (no `issues`, or `isLast: false` with no token) is `INVALID_RESPONSE`, never an empty page; a cycling `nextPageToken` is refused.
- **Before every search page** the run asks `runnableState` (`sync/ConnectionRegistry.kt`'s `runnableStateOf`; the `RunnableState` enum is shared with Flow): a connection deleted or disabled meanwhile ends the run `FAILED` with `CONNECTION_GONE` / `CONNECTION_DISABLED` (a deleted connection's token is destroyed, so no copy may authenticate one more read).
- **The empty-sweep default:** an empty listing of a non-empty bound set still flags the bound issues of a swept type `gone` (a WARN with counts): a false flag only warns and heals on the next good sweep, while failing would wedge a site whose only bound item was really deleted.

### The read

- **Full** (`project in (…) AND issuetype in (<every mapped level's type ids>) ORDER BY id ASC`, with the observation `fields`; a bound issue of an unmapped type is not read by it and keeps its old observation) when no earlier run succeeded, a binding has no observation, `census_at` is null, or anything that decides what an unchanged issue reads as is newer than the last succeeded run's start. Otherwise **incremental** (`project in (…) AND updated >= "-Nm" ORDER BY updated ASC`, N = minutes since that start + `incrementalOverlapMinutes`, recomputed at every first-page request).
- Those inputs are `discovered_at` (re-discovery), `mapping_changed_at` and the connection's `updated_at` (any edit, e.g. a widened `projectKeys`; `storeCloudId` and a recorded Test connection leave it alone), so a rename, a token rotation and a PUT that changes only the poll interval each cost one extra full read.
- The incremental is NOT type-filtered: an unfiltered window is how a change of type is seen. One that hits `LIMIT_EXCEEDED` (a long gap on a busy site: the window only grows) restarts once as the typed full read.
- Every bound issue found is upserted in chunks of 100, one short transaction each.
- The census (`jira/JiraCensus.kt`) is filled by the same pass: the mapped levels are pruned after the reconcile and the child level is listed in full on a full read, else as an id sweep once per `jira.censusHours` (`JIRA_CENSUS_HOURS`). Then `census_at` is stamped, or cleared when a sweep listed an issue the mirror lacks, so the next run re-seeds. A failing children pass never fails the run; `calls` counts the child pages. No audit event: the run row and the INFO line are the record.

### The gone probe

`jira/JiraGoneProbe.kt`: each gone binding in the queue is read by id, `GET /issue/{issueId}?fields=id`, through the run's own guarded client (it counts in `calls=` and asks `runnableState` before each call).

- **404 → `DELETED`, 403 → `FORBIDDEN`, 200 → the column stays `OUT_OF_SCOPE`**. Jira answers the same 404 for an issue the account cannot see, so `DELETED` reads "deleted, or no longer visible". Every answer, the 200 too, stamps `gone_probed_at` (`JiraRunStore.recordProbe`, a short transaction as it arrives, so a cut run keeps every answer it had); any other failure leaves the row unstamped, so a later run probes it again. Every path that clears `gone` clears the stamp (`CHECK (gone_probed_at IS NULL OR gone)`).
- **The queue** (`goneProbeQueue`, pure) comes from the bindings the sweep judges gone, in three ranks: **0** newly flagged in this run; **1** `gone` with no `gone_probed_at` (a probe that failed, was cut or fell beyond the cap); **2** stored `OUT_OF_SCOPE` and answered with a 200, asked AGAIN as the issue may have been deleted since (every one on a MANUAL run; on a SCHEDULED run those whose answer is `jira.censusHours` or more old). A stored `DELETED` or `FORBIDDEN` is never asked again.
- **Order,** in four groups: rank 0; rank-1 then rank-2 rows with no failed read remembered; then every row whose read failed before, the least recently tried first; inside a group the oldest answer first, then binding id. At most 100 a run, so a row whose read keeps failing queues behind every binding not yet tried.
- **The key follows the issue.** A 200 keeps the issue KEY it carried (`jira_observations.gone_probed_key`), taken from the document's top-level `key` only when its `id` equals the probed id AND the key matches `ISSUE_KEY_PATTERN` (an outbound value is stored and rendered as a link), else NULL (the 200 still counts); a 404 or 403 writes NULL.
  The binding's `jira_issue_key` follows it in the same transaction, so every list, link, chip and audit shows the current key; `observation.issueKey` keeps the key the issue was last read under (the pages show "was OLD-1"; the row's `jira.previousKey` is derived on read).
  No audit event and no log line carries a key. `writeObservations`, `markGone` and `clearGone` reset the column, `recordProbe` sets it.
- **The API derives the reason** (`wireGoneReason(stored, probedAt, probedKey, projectKeys)`, against the connection's CURRENT keys, so a key edit needs no rewrite): `OUT_OF_SCOPE` with a `gone_probed_at` reads `MOVED_OUT` for a key outside the connection's `projectKeys` (or no key) and `NOT_LISTED` for a key inside them (Jira has it where the connection looks, but the listing no longer returns it: archived, a changed type, a false-empty sweep).
  `isInScope` (`JiraMappingRoutes.kt`) is the one scope rule. Two call sites apply the derivation, so they agree: `World.candidate` (the view, the flags, the acknowledge; `storedObservation()` keeps the raw stamp and key) and `responsesOf` → `toObservationResponse(projectKeys)` (the bindings list). A row not yet answered for keeps `OUT_OF_SCOPE`. The probe columns are server-internal. The deviation's `detail.jira` is the reason, so a change of reason (a re-ask turning a 200 into a 404) reopens an acknowledged `GONE` line: by design.
- **Circuit breaker:** after 3 failures in a row that say nothing about the issue (a 200 or a verdict resets the count) the probe stops and leaves the rest for the next run; the run still succeeds.
- **The damper** (`GoneProbeDamper`, in memory per connection). A run whose probe sent a read and got no answer is a *failing run*; one with an answer (200, 404, 403) an *answering run*; a run that sent nothing or was cut changes nothing. After 3 failing runs in a row (`GONE_PROBE_FAILING_RUNS`) a SCHEDULED run asks only rank 0 until `jira.censusHours` have passed since the last run allowed to retry.
  A MANUAL run always asks everything; without an answer it neither counts toward the streak nor restarts the clock, with one it ends the streak. A config change (a new token or account may read more) and a run that finds the connection deleted or with nothing bound drop it too. Log lines: `sync.md` "Log lines".

Pinned by: `JiraRunTest`, `JiraRunReadTest`, `JiraRunCensusTest`, `JiraGoneProbeRunTest`, `GoneProbeDamperTest`.

## Deviations

`GET /views/deviations` runs in one `READ ONLY REPEATABLE READ` snapshot, the plan revision first; unpaged, at most 2,000 items; it applies the pure `JiraDeviationKernels.deviations` to each binding. Dates compare in WORKING days (a start snaps to the next working day, an end to the previous one); a project's or program's derived span is compared, not stored dates. Without a usable mapping neither the level nor the estimate is compared and the connection reads `mappingOk: false`.

- **The document:** `{revision, asOf, connections[{…, status}], totals{warnings, infos, bindings, gone, stillInJira, acknowledged}, items, truncated}`. An item carries `fingerprint`, `can` and its `deviations` lines, each with its own `acknowledgement`; an item has none of its own.
- **`totals`** count before the cap: `warnings`/`infos` the OPEN LINES (a listed deviation without a current acknowledgement of its own); `gone` the open items (every reason); `stillInJira` the part of `gone` read `MOVED_OUT` or `NOT_LISTED`; `acknowledged` the items with a currently acknowledged listed line; `bindings` the list's length. `all=false` overrides the `all`-implying filters.
- **Items:** the default lists OPEN bindings (a listed line without a current acknowledgement), those with an open warning first; `all`, `projectId` or `teamId` also list clean and acknowledged ones. A **disabled** connection's bindings stay in the view with their last observation.
- **No validator:** the view answers no `ETag`/`304`: each connection's `status.nextPollAt` is the read's own instant while a poll is due (`planning-model.md` "View validators"); `GET /views/jira-links` does answer one.

| Kind | Levels | Rule | Severity |
|---|---|---|---|
| `GONE` | all | the observation is `gone`, alone; the detail is the reason: `DELETED` (the probe's 404), `FORBIDDEN` (its 403), `OUT_OF_SCOPE` (the sweep's, until a probe answers), `MOVED_OUT` (a probe's 200 whose key is outside the connection's keys, or none), `NOT_LISTED` (a 200 whose key is inside them) | WARNING |
| `LEVEL_MISMATCH` | all | the observed hierarchy level (or none) ≠ the mapping's level | WARNING |
| `PARENT_MISMATCH` | project, milestone | the observed parent issue is bound to a node that is NOT the plan parent (an unbound parent raises nothing); the plan parent is the nearest ancestor whose level the connection maps (a milestone's project, else its program when the project level is unmapped); none when no ancestor level is mapped or the mapping does not resolve | WARNING |
| `RENAMED` | all | summary ≠ name (trimmed, case-insensitive; a name cut at 100 compares as a prefix) | INFO |
| `START_DIFFERS`, `END_DIFFERS` | all | both dated and the working-day shift ≠ 0 (`days` positive = the plan is later) | WARNING when the plan's END is later than Jira's, else INFO |
| `TARGET_DIFFERS` | project | the target window vs Jira's dates differs in working days | INFO |
| `UNSCHEDULED_IN_PLAN`, `UNSCHEDULED_IN_JIRA` | milestone | Jira dated and the milestone not, or the reverse | INFO |
| `ESTIMATE_DIFFERS` | milestone | comparable (`DAYS`, or a factor) and `|jira × factor − estimateMd| ≥ 0.01` | INFO |
| `ESTIMATE_NOT_COMPARABLE` | milestone | an estimate with no factor, or read under a different unit than the mapping names now (listed only with `all=true` or `kind=`) | INFO |
| `PROGRESS_MISMATCH` | all | `DONE` while the plan's end is after today; `TODO` while the plan's start is past; `IN_PROGRESS` while it is ahead | INFO |
| `UNLINKED_IN_JIRA` | program, project | open (not DONE) Jira items under the bound issue, at the mapping's level for the child plan level, that no active binding covers (`jira` = their keys, at most 10, `count` = all; never a summary) | WARNING |
| `UNLINKED_IN_PLAN` | program, project | the bound node's direct plan children that have no binding (`plan` = their names, at most 10, `count` = all) | INFO |
| `CHILDREN_DONE` | milestone | the bound epic has children, all done (`jira` = `done/children`, `count` = children), the epic is not DONE (else `PROGRESS_MISMATCH` alone) and the plan's end is after today | INFO |
| `CHILDREN_OPEN` | milestone | the bound epic has children, some not done (`jira` = `open/children`, `count` = children), while the plan's end is BEFORE today; the epic's own status does not matter; never for an unscheduled milestone, no children, or no roll-up | INFO |

- The four coverage kinds are declared last, so they sort after the older ones within a severity. They come from two optional kernel inputs (`ChildRollup`, `UnlinkedChildren`; null = none) that the loaders fill from the census mirror (`DeviationCoverageRows.kt`; `Coverage and roll-ups`).
- `DeviationDetail.count` is null-defaulted, `@EncodeDefault(NEVER)` and omitted from a fingerprint while null (the pinned `Json` writes neither nulls nor defaults), so a binding that gains none of the coverage kinds keeps its acknowledgements. `CHILDREN_OPEN`'s fingerprint evidence is the `open/children` text, the plan's end and the children count.

Pinned by: `JiraDeviationKernelsTest`, `DeviationViewScopeTest`, `DeviationFingerprintTest`.

## The plan's links

`GET /views/jira-links` (`jira/JiraLinksView.kt`) is the narrow read behind the Plan page's "Import from Jira..." entries (the Deviations view would compute every deviation).

- One `READ ONLY REPEATABLE READ` snapshot, TWO statements whatever the plan's size (`loadConnections()`, `loadNodeLinks()`); no revision, no `can`, no parameter, no `404`; it answers a validator (`planning-model.md` "View validators").

### Suggested matches (1.15)

**What it is.** A CREATE row that looks like an existing, UNLINKED plan item of its level under the same parent carries `suggestion {nodeId, nodeName}` (absent otherwise; `@EncodeDefault(NEVER)`); the user confirms it with `matches[{jiraId, nodeId}]` on the NEXT preview (and, flat, on the apply, which the web spreads from the preview's scope). **Nothing is ever linked by a suggestion alone.** A confirmed row reads BIND with the info `MATCH_CONFIRMED` (the natural BIND's shape: no estimate, dates, team or window), and what hangs under it lands under the EXISTING node and matches that node's children by name. `jira/JiraImportMatch.kt` (`ImportNameMatch`, pure) holds the rule; `ImportPlanner.settleMatches` the per-level settle.

**The rule (strict on purpose; the user's answer Q2).** Names are folded (`JiraImportKernels.foldName`: lowercase `Locale.ROOT`, accents stripped, `ł ø ß`... mapped) and split into words on every run of non-letters and non-digits. Two names are `similar` when (1) both have a word; (2) their NUMBERING words - a word with a digit, a single character, or a Roman numeral `ii iii iv vi vii viii ix` - are the same multiset; (3) every word of the name with fewer letters occurs in the other, as a multiset (the longer name may only ADD words); (4) `2 x letters(shorter) >= letters(longer)`, integers only. So "Checkout redesign" / "checkout  REDESIGN", "Płatności mobilne" / "Platnosci mobilne", "Customer portal" / "Portal: customer", "Documentation" / "Documentation (renamed)" and "Mobile app" / "Mobile app rollout" match; "Team A" / "Team B", "Phase 1" / "Phase 2", "Release" / "Release 2", "Billing revamp" / "Billing redesign" (a replaced word), "API" / "API gateway" (3 of 10 letters), "Custmer portal" (a typo) and "Check-out" / "Checkout" do not. A suggestion needs the pair to be UNIQUE BOTH WAYS inside the sibling scope: exactly one free sibling is similar to the row, and that sibling is similar to no other would-be-created row of the scope (two candidates, or two rows for one candidate: nothing is proposed). A Roman numeral above `ix` is an ordinary word: "Phase" / "Phase XII" ARE similar, "Phase XII" / "Phase II" are not; a digit means any Unicode number (`\p{N}`, so "x²" is numbering). **Work budget:** the matcher sums, per sibling scope, the nodes sharing a word with each row (`ImportNameMatch.MAX_MATCH_WORK`, 5,000,000); past it the scope gets no suggestion at all (deterministic, a function of the names), measured worst case in `JiraImportMatchKernelTest`: 1,100 rows against 2,600 siblings drawn from ten shared words (4.8M of the 5M, the adversarial shape) settle in about 110 ms on the dev machine, and a refused scope answers in about 15 ms; the plan-sized 2,000 x 1,000 vector takes about 150 ms. Toadie's `levenshtein` was NOT ported (it answers "which identifier did you mistype", and would pair "Team A" / "Team B"); a typo-tolerant version is a backlog item.

**The settle.** Rows are planned level by level (the order of the answer is unchanged). After a level's name verdicts, per sibling scope - the CREATE rows landing under the same EXISTING node (the parent kind `EXISTING` or `DEFAULT`, never a `NEW_ROW`), or the programs of the picked stream - the free siblings are the parent's children at that level with no active binding (any connection) that no exact-name BIND row claimed. Suggestions are computed on the level's natural state: a confirmation never changes another suggestion of the level. An entry of `matches` is honoured ONLY when it equals the kernel's own suggestion for that row; any other (a node that is linked, renamed, another one, an id the browse does not hold, a row that is not a CREATE) is ignored. A `NO_TEAM` milestone gets none (it is not a CREATE) - judged on the NATURAL verdict, so an apply's `overrides.teamId` that turns such a row into a CREATE does not enter the scope's competition and cannot honour a pair no preview showed or break an honest one; a converted milestone no longer needs a team, so its Jira team name leaves `unmatchedTeams`. A converted row's name stays in `takenNames` (conservative: a later same-name row of the level is `NAME_TAKEN`, decided before the settle). A confirmed BIND is guarded first as the CREATE it replaces, then as a BIND (`authorization.md`). `OUTSIDE_ROOT` and the other skips are decided first; a skipped row never has a suggestion.

**The apply.** Both kernel runs (the preview run that finds the withheld ids of a non-admin under a filter, and the ticked run) get the SAME `matches` and root. A confirmed row is a BIND like any other (`expected {action: BIND, nodeId}`; its target guarded by `requireResolvedTargets` over the ticked rows). If under the plan lock the node is no longer the kernel's unique suggestion (renamed, linked, deleted, a second candidate appeared), or the request left the entry out, the row is planned as a CREATE, which is not what was expected: `CHANGED`, nothing created, nothing bound (its children likewise). `jira.import_applied` gains `confirmedMatchBindingIds` (the bindings made through a confirmed match, ascending, ids only).

**What the user must know.** Under an active filter the preview does not see an item the filter left out, so a plan item whose own Jira item was left out looks free and may be proposed to a similarly named open one (the dialog says so under a filter; nothing is linked without the click). A confirmation costs one more preview (the same bucket, the same browse, no new Jira call); program, then project, then milestone confirmations in turn are four previews and an apply, and several rows can be confirmed before one "Preview again". The sample plan's deliberately renamed items ("Documentation (renamed)") are now proposed as links where their plan item is the only candidate, and are still CREATED when the proposal is not confirmed. Proven by `JiraImportNameMatchTest` (the rule's vectors, the pairing, determinism), `JiraImportMatchKernelTest` (the planner: the scopes, the confirmation, the children, the stale cases, the root, a scale vector), `JiraImportSuggestionsTest` (HTTP, the `IMC` stub: the two previews, the apply, the audit line, `CHANGED`, the `400`s after the `403`s, a non-admin under a filter), `JiraImportRedactionTest` (no suggestion on a redacted row) and `JiraImportWebBodyTest` (the literal bodies).

## Import from a linked node (1.14)

**What it is.** The preview and the apply take an optional `root {level: PROGRAM|PROJECT, nodeId}` (on `JiraImportScope` and, flat, on `JiraImportApplyRequest`; absent = the whole-scope import above, request for request). With it they read ONLY what Jira lists under the root's Jira item and land it under the root's own node: a program root brings its projects and their milestones, a project root its milestones; `workStreamId` stays required and must be the root's own stream (`400`); a rooted import never creates a program; `items` are the root's descendants and the root is never a row. **The request cannot steer a row out of the root's subtree (a `400` after the guards, `JiraImportService.requireDefaultsUnderRoot`):** with a root `defaults.programId` is refused, `defaults.projectId` must be a project of the root PROGRAM, and a PROJECT root takes none (the web never sends either). The apply repeats the `defaults.projectId` rule under the plan lock (a project moved to another program during the browse is the same `400`, nothing written). The dialogs that start one are the web's (C4/C5); the server's rules are these.

**Who may.** The root is ONE MORE NAMED TARGET of today's rule "ADMIN, or an owner of every target": the root's owner chain (a program root: the stream's or the program's owner; a project root: any of the three) or ADMIN, read first (`404`), guarded up front (`403`) - before the token is decrypted and before any Jira call - and re-read and re-guarded under the plan lock. What a rooted import creates lands under the root's own node (the defaults are held to it, above), so the resolved-target guards pass for the root's owner. Since 1.15 there is no exception: **an import started from a linked item writes only under that item, for every caller** (ADMIN and the stream's owner included) - the kernel gets the root (`ImportInput.root`) and a row whose resolved parent is an EXISTING plan node outside the root's subtree is skipped `OUTSIDE_ROOT` (under "Rules worth knowing"). `authorization.md` has the order and what a non-admin learns.

**The order** (both routes; new steps in bold): bucket `429` -> connection `404` -> body `400` -> named chains `404` (**the root: `Program not found` / `Project not found`**) -> `403` for a login that owns no plan node, the guard on each named default **and on the root's chain** -> token decrypt -> shape `400` (**the root lies under the picked work stream**) -> connection enabled `400`, token / discovery / mapping `409` -> **the root's ACTIVE link through THIS connection (`JiraImportService.resolveRoot`: `jira_bindings` by level and node; none, or one held through another connection of the site, is `409 urn:astrolabe:problem:jira-root-unusable`)** -> the browse -> snapshot -> kernel -> **the root's own row must read `ALREADY_BOUND` to the root node THROUGH the root's own connection (`ImportPlan.requireRootRow`, else the same `409`: the link changed, preview again)** -> resolved-target guards `403` -> redaction -> `200`. The apply repeats it, the root row's verdict under the plan lock before the ticked-target guard (a rollback: nothing written, no bump).

**The browse** (`jira/JiraImportChildren.kt`, `browseChildren`; the query `JiraJql.children`). One `GET /issue/{id}` of the root by the STORED numeric id (the request never names an issue), then rounds top down: round one asks for the root's children at every mapped level below the root's (`project in (...) AND issuetype in (<ids>) AND parent in (<root id>) ORDER BY id ASC`), round two (a program root with the project level mapped) for the milestone level under every project round one held, ALL of them (admitted or not, linked or not), in chunks of 50 ids ascending. Every id passes `ISSUE_ID_PATTERN` before it joins a query; the request shapes a query only through the project keys it picked (a subset of the connection's own, validated before) and the filter (`excludeDone`, and the bounded day count) - both safe, constant clauses. The server's own verdict on every entry (a site that ignored a clause cannot widen the scope): it names one of the parents of THAT query, its key is inside the import's keys, its mapped level is one the round reads, it is not a repeat. The root document must be the id asked for, parse, have its key inside the connection's keys and sit at the Jira level the mapping gives the root's plan level; each miss is the `409`. **The root read's failures:** a `404` is trusted as a verdict about that issue (the `409`: deleted or not visible); every other failure is the `502 jira-upstream`, a `403` included (`FORBIDDEN_SCOPE`: the account's scope), whereas the gone probe records a `403` as `GONE_FORBIDDEN` - a deliberate difference, because a rooted import has no use for a half-verdict. The kernel is untouched: the root is handed to it as a browsed issue (its level from its own document, the row `ALREADY_BOUND`), so its children land `EXISTING` under the root node, round-two rows under their project's row, and the import never depends on A10.

**The filter under a root.** A round that reads a level with children to walk (the projects) is NOT narrowed at the source and is judged by the server's rule afterwards: an admitted project is kept; a done or quiet one is held only so its children can be read and is kept (`KEPT_AS_PARENT`) only when a kept item hangs under it, else dropped (after the walk, also when the read was truncated). The leaf level is narrowed in the query as today. No parent is read by id, so the 200-read bound does not apply. **Accepted:** every held row, a not-admitted project before the pruning included, counts toward the 2,000 cap, so a root with very many done projects can read `truncated` although few rows would remain; the user narrows the filter or starts from a project.

**Bounds.** At most 2,000 rows (the root counts), the 170 s deadline, the `jira-import` bucket (5 a minute per user, preview and apply together), the same guarded client and the same two endpoints (`search/jql`, `issue/{id}`): one by-id read, typically two searches. **The whole rooted browse shares ONE page budget of 200 requests** (`MAX_SEARCH_PAGES`, the whole-scope browse's own ceiling; one `PageCeiling` passed to every `searchPages` call and spent once by the root read): past it the `502` with code `LIMIT_EXCEEDED`, so a site that ignores the parent clause and pages on stops at the budget, not at the deadline. An honest site stays far below it WITHOUT a filter (a program root with 2,000 rows is at most 40 round-two queries, about 60 requests); under a filter round one is unfiltered at the source (it lists the projects to walk), so the milestone-level children the filter drops there are read but never held, and only the budget bounds them. `security.md` has the figure.

**Rules worth knowing.** A milestone-level item straight under a root program follows today's rule (the default project, the dialog offers the root program's projects, else `NO_PARENT`). A level the mapping leaves out between the root and its children is not walked (an item under it is not listed: the "Browse unmapped intermediate levels" backlog item stays). **OUTSIDE_ROOT (1.15).** A child project already linked to a plan project of ANOTHER program of the same stream stays `ALREADY_BOUND` (naming its holder), and what hangs under it - the milestones that would land under, or bind to, that other program's project - is skipped `OUTSIDE_ROOT` in the preview and the apply, whoever asks: the preview stays whole and never depends on who looks (the 1.14 `403` is gone, and so is the re-homing for ADMIN and the stream's owner; they import those milestones from that project: its page, or a whole-scope import). The rule lives in ONE place, `ImportPlanner.lookupOf`/`isOutsideRoot`, whenever a row's parent resolves to an existing node: a project-level row must sit under the root program itself, a milestone-level row under a project of the root program (program root) or under the root project (project root); a parent that is a new row of the batch needs no check, a holder in another work stream still falls to the default project else `NO_PARENT`, and a default project outside the root handed straight to the kernel is `OUTSIDE_ROOT`. An apply re-plans under the lock with the same root, so a project moved out of the root program between the preview and the apply turns its ticked rows into `OUTSIDE_ROOT` skips (`skipped[]`, the kernel's reason), never a write outside the root. `OUTSIDE_ROOT` is an ordinary redacted skip for a non-admin (no summary; under a filter no key). `requireResolvedTargets` is unchanged and stays as defence in depth. **Accepted:** a root unlinked by someone else in the instant after the holders are read under the lock still gets its children created under the root NODE (no new lock); a root moved to another work stream meanwhile leaves every ticked row `NO_PARENT` (`CHANGED` where a default project is sent: the row would then land under that default, not where the preview showed); either way nothing is written. **A disclosure, stated plainly:** an owner who links their node to a Jira item (an audited bind) can then preview the text of everything under that item in the connection's projects - the settled rule "rows on the caller's own target are shown in full" applied to a subtree. Since 1.14 each ANSWERED rooted preview leaves one `jira.import_previewed` audit line (`byUserId`, `connectionId`, `rootLevel`, `rootNodeId`, `rowCount`: ids and a count, never a key, name or summary), so a bind, a rooted preview and an unbind cannot read a subtree unseen; a refused preview emits none, and a whole-scope preview is still unaudited. The redaction (LOW-1, key-free under a filter) is unchanged and the `409`s speak only about the caller's own link. `jira.import_applied` carries `rootLevel` and `rootNodeId` (null for a whole-scope import). An apply truncated at the cap answers its own sentence under a root (`rootedImportTruncated`: narrow the filter, and under a PROGRAM root also start from a project below it - no `projectKeys` lever, no parent reads).

**Proven by** `JiraImportChildrenTest` (the browse over a scripted site, the shared page budget, the helpers), `JiraImportChildrenPreviewTest` (the `IMC` tables, the requests, the landing, the `jira.import_previewed` line), `JiraImportChildrenGuardsTest` (the caller matrix per root level, the order, the redaction, the token's absence from the logs, `OUTSIDE_ROOT` for the root's owner and ADMIN, and that no caller who passes the root's guard meets the resolved-target `403`), `JiraImportRootKernelTest` (the root rule as pure vectors), `JiraImportChildrenErrorsTest` (every status, the five causes of the `409`, the defaults' `400`s), `JiraImportChildrenApplyTest` (the write, a re-import, an ADMIN's ticks under another program's project skipped `OUTSIDE_ROOT`, the two lock races, the under-lock root re-guard, a non-admin under a filter, no `jira.import_applied` on a refusal), `JiraImportDecryptOrderTest` and `JiraImportWebBodyTest`. Proven against the built-in Jira stub (the `IMC` children family); **not yet tested against a real Jira site** (A18).

## Coverage and roll-ups (1.4)

1.4 finds what the plan misses (Jira children nobody planned, plan children Jira does not track) and shows an epic's story roll-up. **Where the data comes from:** the EXISTING run observes the whole in-scope census into the mirror `jira_issues` (V23, `persistence.md` "The Jira census (V23)") in the same pass; nothing is fetched at request time and nothing is written to Jira. This section is the CENSUS half (what the run writes); the deviation kinds and the roll-up on the views are described here as their commits land.

- **Terms.** *Mapped levels* = the effective mapping's hierarchy levels. *Child level* = `milestone.hierarchyLevel - 1` when that is not below 0 and the site has non-sub-task types there (`typeIdsAtLevel`, every id a valid JQL type id), else none: a milestone mapped to Jira level 0 has no roll-up, and sub-tasks never count. *Census levels* = mapped ∪ child.
- **Every page entry is observed.** The run's read - the typed full read or the untyped incremental - passes each entry to `JiraCensus.observe` BEFORE the bound-issue skip: a row is built by `CensusIssue.of` (fitted like an observation), kept when its level is a census level, buffered by id and flushed in `RUN_CHUNK`s through `JiraIssueStore.upsert` (one short transaction, no plan lock, no revision; the connection row is taken `FOR SHARE`, so a connection deleted meanwhile writes nothing). The incremental window already carries every story updated since, so a changed or new story reaches the mirror at no extra call.
- **What a row is.** Only issues of a type the run's sweeps ask for (the mapped types and the child types) at a census level are mirrored (an issue of any other type is invisible to the sweeps and would flap); the story-points marker (a plausible field id only) is added to the mapped read's `fields` too, so an incremental update of a story keeps its points whichever field the milestone's estimate is mapped to; control characters in a summary become spaces.
- **After the reconcile** (`JiraCensus.complete`): flush; **prune the mapped levels** - rows at a mapped level that are in neither the sweep's listing nor the rows this run saw (in Kotlin: the connection's `(issue_id, level)` index once, deleted in `RUN_CHUNK` batches; an EMPTY listing prunes too, the sweep's WARN covers it and the next good sweep heals); then the **children pass**: a typed full read (`JiraJql.full(keys, childTypeIds)` with `fields` = the system fields + the discovery's story-points marker) on a FULL read (the `LIMIT_EXCEEDED` fallback included), upserting every row and pruning child rows not read; otherwise, when `now - census_at >= jira.censusHours`, an id-only typed sweep (`JiraJql.sweep`, `fields=id`) that prunes child rows neither listed nor seen this run. An empty children listing is normal (epics without stories) and logs no warning.
- **Self-healing.** On a FULL read the rows of a level that is no census level any more are deleted too. When an incremental run's sweep (mapped, or the due child sweep) lists an in-scope id the mirror lacks and the run did not read (rows lost to an earlier false-empty or partial listing), `census_at` is CLEARED instead of stamped: the next run is full and re-seeds.
- **The loop guard** (`jira/CensusLoopGuard.kt`). A census that can never converge (an in-scope issue that can never become a mirror row - a type or level the census refuses - or a children read that always fails) would heal or stay unstamped on every poll and read in full forever. The guard keeps TWO streaks per connection, so "in a row" is true of each: the runs that CLEARED `census_at` (a heal) and the runs whose children pass FAILED. Past `MAX_UNCONVERGED_RUNS` (3) a streak is **tripped**, and its first run logs ONE WARN `Sync run {id} (connection {id}) census cannot converge after 3 runs in a row: {reason}; roll-ups may be incomplete` (reason: `a sweep keeps listing an issue the mirror lacks; ...` or `the children read keeps failing; ...`; ids and counts only), then DEBUG while it stays stuck (the warning re-arms when the streak ends). **Tripped heal:** the run leaves `census_at` ALONE (never stamps it - that would push the child sweep's due time forward for ever and stale children would never be pruned), except when the child sweep is due (once per `jira.censusHours`): then it CLEARS once, one forced full read a day that may heal a later genuine gap, with the streak held at the threshold so the next gap run trips again at once. **Tripped failure:** the run STAMPS `census_at` (instead of leaving it null), so the retry cadence becomes the child sweep's, daily, not every poll. **What ends a streak:** a completed children FULL read ends the failure streak, and a completed id SWEEP ends it only while it is not tripped (the sweep working says nothing of a typed full read that keeps failing; resetting on it would let each daily forced full read cost a fresh run of ~4 failing full reads, instead of one); a conclusive incremental run (no gap, no failure, not truncated, and its child sweep ran or there is no child level) ends the heal streak - a full read cannot see a gap (it re-seeds), and a run whose child sweep is not due has not looked at the child level. A `LIMIT_EXCEEDED`-truncated children listing neither counts nor resets the FAILURE streak and gives no child-level verdict (it does not end the heal streak either); a mapped-level gap in that same run still counts as a heal. A run that is both a gap and a tripping children failure warns for both streaks. And a **config change** that forces the full read (a re-discovery, a mapping change or an edit newer than the last succeeded run's start, the `readPlan` conditions) drops the entry, so a mapping fix untrips at once. The state is IN MEMORY (`JiraObserver` holds one `CensusLoopGuard`, a `ConcurrentHashMap` of a small record per connection id, updated atomically per key so concurrent runs of different connections are safe; the entry is removed when both streaks are empty, on a config change, or when a run finds its connection already deleted at its start - a connection deleted or disabled MID-run keeps a tiny entry until restart), so a restart resets it, which costs at most one more round of full reads before it trips again - no migration. Proven by `JiraRunCensusTest` (the heal loop and its reset, the tripped runs that leave the child sweep due, the daily forced full read, the failure streak and its reset by a completed full read, a tripped failure's daily retry, a working sweep that does not untrip, a gap plus a tripping failure in one run, the config-change untrip, the truncated listing).
- **`census_at`** is stamped with the run's START after a full read (even with no child level, else it would stay null) or a completed child sweep, and `readPlan` reads **in full whenever it is null**: the first run after the 1.4 upgrade seeds the mirror for every existing connection (a full read plus the child read, once, within a poll tick); a fresh connection's first run was full anyway. A connection with no bindings still returns before any call: no census, no stamp.
- **Ceiling.** The children read shares the 200-page ceiling and `jira.pageSize`. Past a listing or response ceiling (`LIMIT_EXCEEDED` on the children listing ONLY; the mapped read keeps its rule and fails the run) the run keeps what it read, **prunes nothing**, still stamps (a big site is not re-read on every poll) and logs WARN `children census truncated at {n} pages after {n} child issue(s) (a listing or response ceiling): roll-ups may be incomplete` (A11). **Any other failure of the children pass** (a 5xx, a timeout, an invalid page) does NOT fail the run: the mapped work of 1.3 stands, the run SUCCEEDS, the pass keeps the rows it read, prunes nothing, does not stamp (so the next run is full and retries - until the loop guard trips after 3 such runs in a row and stamps instead, so the retry is daily) and logs WARN `children census failed: {code}`; only a deleted or disabled connection still ends the run. `runnableState` runs before every page, so a connection deleted or disabled mid-census ends the run `CONNECTION_GONE` / `CONNECTION_DISABLED` with no further read and no stamp.
- **Cost.** The extra calls are the child level's pages: one typed read on a full run (the stub's sample scope: +6 on 25, `expected.json` `search.sample/fulltypes/s/started`; the E2E scope: +1 on 3) and one id sweep per `censusHours` otherwise. At the 1,000-milestone scale with 5,000 stories: +50 field pages once per full read, +50 id pages a day (about +2 calls per 15-minute poll on average).
- **Logging** (`ch.nokillswit.sync`, counts only - never a key, a summary or a URL): INFO `Sync run {id} census: issues={mapped rows written} children={child rows written} pruned={n} childPass={FULL|SWEEP|NONE}` and the WARN above (`sync.md` "Log lines").
- **The view reads the mirror** (`jira/DeviationCoverageRows.kt`, called by `DeviationViewService.computeInTransaction` after `loadBoundTo`, inside the same snapshot; the acknowledge's `computeBindingInTransaction` goes through the same function, so an acknowledged coverage fingerprint equals the view's). Three loaders, one statement each (two for the plan side), scoped to the bindings in view: `loadRollups` (a bound MILESTONE's mirror rows at `milestone.hierarchyLevel - 1`, `GROUP BY (connection, parent)`: count, DONE count, points sum or null, newest `observed_at`; absent while there is no child), `loadUnlinkedJira` (the bound PROGRAM's or PROJECT's mirror children at the mapping's level for the child plan level, not DONE, with no ACTIVE binding of that issue id on an ACTIVE connection of the SAME `site_url` - D1; node liveness of that binding is not re-checked; keys ascending by numeric id) and `loadUnlinkedPlan` (the node's direct ACTIVE plan children - a program's projects, a project's milestones - with no active binding on an active connection; names ascending by id). A binding whose child plan level is unmapped, or whose connection's mapping does not resolve, has no coverage. The inputs feed the kernel (`ChildRollup`, `UnlinkedChildren`) and the item carries the roll-up as `jira.rollup` (`DeviationRollup`, `JiraRollup` in the spec; always present, null = none; milestone bindings only). Coverage is computed for whatever bindings a scope reads, so a program binding's coverage shows on the Deviations page (the timeline fold asks for projects and milestones only). A disabled connection's items keep their last census. The view discloses the Jira KEYS of unbound issues, never summaries (`authorization.md`). Tests: `DeviationCoverageTest` (the rows that count, D1, the unmapped level, scoped = full), `JiraAcknowledgeTest` (acknowledge and reopen on a new unbound epic).
- **The connection's coverage summary (1.14, `jira/JiraCoverage.kt`).** `GET /integrations/jira/connections/{id}/coverage` (ADMIN only, `requireAdmin` first, like the page it feeds) counts, per MAPPED plan level of the connection's current effective mapping (`loadConnections`, the Deviations view's resolution), the census mirror's rows at that level's Jira hierarchy level: **in scope** (every mirror row of the connection at the level; the mirror is already scoped to the connection's project keys), **linked** (an ACTIVE binding of an ACTIVE connection of the SAME site names the issue id: `bindingOnSameSite()`, the very predicate `loadUnlinkedJira` uses, D1) and **open and unlinked** (`status_category` not `DONE` - the `CHILDREN_DONE` / `UNLINKED_IN_JIRA` notion - and not linked). One read-only REPEATABLE READ transaction, ONE grouped statement (`count` and two `CASE` sums over a LEFT JOIN to the DISTINCT set of the site's linked issue ids, `linkedIssueIdsOnSite`, so the verdict is computed once per row; the first version's two correlated `EXISTS` per row cost about 8 ms against about 1.1 ms for 3,000 mirror rows and 2,000 bindings, EXPLAIN ANALYZE on a throwaway Postgres), no lock, no write, no Jira call, NO migration. `state`: `NOT_SYNCED` (`census_at` null AND no mirror row: nothing was ever censused; no counts), `MAPPING_UNUSABLE` (the mapping is missing, unreadable or no longer fits the discovery, so the mapped levels are unknown; no counts), `MAPPING_CHANGED` (`mapping_changed_at` is later than the START of the last SUCCEEDED run, or there is a change and no success on record: the mirror was read under the old mapping, so a newly mapped level would read a false 0/0/0; no counts until a run reads under the new mapping), else `READY` with `levels[]` top down (program, project, milestone, only the mapped ones; a level with no rows reads 0/0/0). `readAt` is the FINISH of the connection's last SUCCEEDED run (`SyncRunService.lastSucceededInTransaction`; null when none is on record): the mapped levels are upserted and pruned on every run, so the counts are as of then - not `census_at`, which stamps only the CHILD level's census. Known limits: a run of a connection with no bindings returns before any read (the mirror then stays as the last run that had bindings left it, while `readAt` moves); `MAPPING_CHANGED` follows `mapping_changed_at` only, so a re-discovery that changes the DEFAULT mapping or an edit of the project keys is not flagged until the next run has read. The child level (stories) and unmapped levels never count; a disabled connection keeps its last census. Counts only - no key, name or summary (the Deviations view's disclosure rule; the keys of the open unlinked items under a bound parent are on the Deviations page). A separate route, not a member of `GET …/{id}`: that DTO is shared by the list, create and update, and a count read there would cost every list row a statement. The page shows it as the Coverage section (`web-internals.md` "Jira connections"). Tests: `JiraCoverageTest`, `jira-coverage.spec.ts`.
- **Proven by** `JiraRunCensusTest` (MockEngine), `JiraRunReadTest` (a null `census_at` forces a full read), `JiraRunTest` (the `COV` roll-up figures and the day-2 prune against the stub), `JiraBootTest` (`jira.censusHours` 0 and 169 refuse boot).

## Acknowledge (1.3)

A planner who has seen a deviation and accepts it acknowledges that LINE ("until changed", per deviation since 1.12; 1.3 acknowledged the whole list); it then stops counting as open. `POST /integrations/jira/bindings/{id}/acknowledge {fingerprint, kind?}` and `DELETE …/{id}/acknowledge[?kind=]` (`jira/JiraAcknowledgeRoutes.kt`, `JiraAcknowledgeService.kt`; the order and the guard are the `authorization.md` rows, the locks `persistence.md`, the audit `observability.md`).

- **What it keys on.** `fingerprintOf` (`jira/DeviationCompute.kt`, a delegate of `infra/json/CanonicalJson.kt`'s generic `fingerprintOf` since 1.9, shared with the Flow capacity acknowledge; the 409 URN and the 64-hex shape rule live in `sync/Acknowledge.kt`): the SHA-256 of the canonical JSON of the binding's FULL kernel list (`[{kind, severity, detail}]`, `ESTIMATE_NOT_COMPARABLE` included even where the item hides it, so the value does not depend on the filter or the caller). It is rendered with a pinned `Json` that writes neither nulls nor defaults, so a later additive nullable member of a deviation changes no hash (a null still differs from a value); `DeviationFingerprintTest` pins a literal digest. Any change on either side that alters a deviation - the plan date moved further, Jira's end moved, a new or vanished kind, a different count of days - gives another fingerprint, and the stored acknowledgement reads `current = false`: acknowledged on D by X, **changed since**, and the item is OPEN again. A change that alters no deviation (a plan field the kernel does not compare) keeps it. **Per line since 1.12:** the stored fingerprint is that of ONE deviation (`fingerprintOf(Deviation)`, severity in the hash), the table is keyed (binding, kind) because the kernel raises a kind at most once per binding (`JiraDeviationKernelsTest` pins it), and a change reopens only the line it altered; the LIST fingerprint above stays the token the client echoes (to acknowledge one line or all) and the compare that a view read is still current. `PROGRESS_MISMATCH`'s detail is the contradicting plan date, so the fingerprint is stable day to day and a boundary crossed raises a NEW deviation, which correctly reopens the item. **A later release that changes a kernel rule changes the fingerprints it alters and so un-acknowledges those lines: by design, stated in that release's notes.**
- **The write.** ONE short transaction, no plan lock: the binding row locked, the node's chain re-read and the guard run again, the deviations of THIS binding recomputed with `DeviationViewService.computeBindingInTransaction` (the same `computeInTransaction` the view runs, scoped by `DeviationScope(bindingId)`; a parent issue's own binding is looked up so `PARENT_MISMATCH` equals the view's), then the LIST fingerprint compared: different, an empty list, or a `kind` the full list does not hold now is `409 urn:astrolabe:problem:stale-deviations` and nothing is written. With a `kind` that ONE line is stamped; without one (every pre-1.12 request) the lines without a current acknowledgement (D3), or every line when each has one (a restamp, as before). Each stamped line stores its OWN fingerprint, when and by whom in `jira_deviation_acknowledgements` (V28): the target kinds' rows are deleted and the new ones inserted by one `insertRows`, under the binding row lock (every writer of the table holds it, so the unique index is only the backstop); nothing else is written - not `jira_bindings.updated_at`, no plan revision. Acknowledging the same state again restamps who and when. `DELETE` with `?kind=` removes that line's row (`404` when none), without it EVERY stored row of the binding, stale and retired kinds included (`404` when none); the parameter is parsed after the guard (`400` unknown, blank or repeated). **No pruning (Q5):** a row is never deleted because its line left the list, so a line that disappears and returns identical reads acknowledged again with its original stamp; a stored kind this build does not know is ignored on read. 1.3's three `jira_bindings.ack_*` columns were unread and unwritten since 1.12 (Q3: no backfill, every earlier acknowledgement stopped applying) and are dropped by V30 (1.13; a build older than 1.12 can no longer run on the schema).
- **What the view does with it.** Each listed line is a `DeviationLine` (`kind`, `severity`, `detail` and its own `acknowledgement{at, by, current}`, null until acknowledged; a listed item shows EVERY line with its state, whatever the Status filter, D5); an item has no `acknowledgement` of its own: only its lines carry one (the item-level summary left `/api/v1` by the user's decision, product.md "The Jira sync"). The default `GET /views/deviations` lists OPEN items (at least one listed line without a current acknowledgement); `acknowledged=true` the items with at least one currently acknowledged LISTED line (a stamp on the hidden `ESTIMATE_NOT_COMPARABLE` line alone does not count: that item surfaces under `all=true` only), `=false` the open ones; **a kind or severity chip matches the lines of the selected Status (D11)**: the open lines by default and under `acknowledged=false`, the currently acknowledged ones under `acknowledged=true`, any listed line under `all` without a status (so Open + End differs omits an item whose End line is acknowledged; the item still shows every line, and the totals count the open lines of the whole scope); `all` and the chips' implied `all` keep every state. `warnings`, `infos`, `gone` and `acknowledged` share one basis - the items matching every filter but the acknowledgement state - and count its OPEN LINES (`warnings`, `infos`), its open items that are gone, and its items with a currently acknowledged listed line (so "N open" survives `acknowledged=true`); items order an OPEN warning line first; `bindings` is the number the list answers. An item whose only deviation is `ESTIMATE_NOT_COMPARABLE` is open, and counted, exactly where that kind is listed (`kind=ESTIMATE_NOT_COMPARABLE` or `all=true`); the default never lists it, so it is not open there. It can be acknowledged from such a listing (the kind-less call stamps it with the rest); the timeline fold ignores that kind.
- **Who.** The owner chain of the node or ADMIN (Q4a), and since 1.12 (Q4b) - on a MILESTONE binding only - the ACTIVE manager of the milestone's STORED team, who may acknowledge and withdraw every deviation of it, whoever stamped it (`requireOwnerOrTeamManagerOrAdmin`, read first with `TeamService.isActiveManager`, again under the binding's row lock with `lockedIsActiveManager`; `AckAudience` carries the chain and the stored team). A manager on a program or project binding, another team's manager, a roadmap editor and a stranger stay 403; bind and unbind are unchanged (owners and ADMIN). `can.acknowledge` carries the verdict per item (`PlanPermissions.canAcknowledgeDeviations`, pinned against the guard; the view loads `activeManagedTeamIds` for a non-admin).
- **Proven by** `JiraAcknowledgeTest`, `JiraAcknowledgeLinesTest` (one line, the kind-less form, the pre-1.12 body, refusals, withdrawals, a returning line, an unlinked manager), `JiraAcknowledgeRaceTest`, `JiraAcknowledgeRunTest` (a real `jira-day2` run opens the new GONE line only and the first stamps read current again on return), `DeviationViewAckTest`, `DeviationFingerprintTest`, `JiraSchemaTest` (V28).

## Timeline flags (1.3)

The four timeline views (roadmap, programs, project, team) carry the Jira links and flags of the rows they answer (`planning-model.md` "Jira flags and links" is the contract, `timeline.md` "The Jira markers" the document shape and the measured cost). **How it is built.** `planning` declares the seam (`planning/ExternalFlags.kt`: `ExternalFlagSource`, `ExternalFlagRequest`, `ExternalFlags`, `JiraLink`, `JiraSite`, `JiraSiteState`; the deviation vocabulary `Deviation`, `DeviationKind`, `DeviationSeverity`, `DeviationDetail` moved to `planning/Deviations.kt` with unchanged serialized names, so a stored fingerprint and the spec schemas did not move) and names no `jira` type; `jira/JiraFlagSource.kt` implements it over `DeviationViewService.computeInTransaction(scope)` and `infra/db/Database.kt` wires it into the four view services (since 1.9 through `CompositeExternalFlagSource`, beside `flow/FlowFlagSource`: the request gained `teamId` and the answer `teams`, the team view's half; `JiraFlagSource` answers only the node half and returns early on `request.namesNoNode`). The source runs INSIDE each view's `READ ONLY REPEATABLE READ` snapshot, after the calendar, with the calendar the view read and "today" from the deviations service's own clock, so a flag equals what the Deviations page lists as open for the same state.

- **What raises a flag.** A binding of an ENABLED connection raises one `JIRA_DEVIATION` per OPEN LINE (1.12: a kernel deviation without a CURRENT acknowledgement of its own; an acknowledged line of the same binding raises nothing) at the deviation's severity, except `ESTIMATE_NOT_COMPARABLE` (the kernel's "a figure exists and cannot be compared" is a Deviations-page note, not a timeline warning). A stale line acknowledgement (`current = false`) is open again. A project also gets ONE `JIRA_MILESTONES` roll-up over its milestones that raised a flag (`count`, the worst severity among the OPEN lines). `PlanFlag` and `JiraLink` gained no member for this. **The flag's shape (1.15):** `{kind, severity}` plus only the members that apply - `deviation: {kind, detail}` on a `JIRA_DEVIATION` (no `severity` inside: it is the flag's own; the kernel's `Deviation` stays whole and is what the fingerprints hash), `count` on a `JIRA_MILESTONES`; a `detail`'s null members (`jira`, `plan`, `days`, `count`) are absent from the wire, on the flags and on the `GET /views/deviations` lines alike. No fingerprint moves: the pinned `Json` writes neither nulls nor defaults, so what it hashes is the same bytes as before (`DeviationFingerprintTest`'s literal digests, unchanged, one with `days` and one with `count`).
- **What does not.** A DISABLED connection (Q8a: its rows keep the `jira` link and its site with null dates, no flag, no bar and no roll-up contribution, so the page still sees the node as linked and can unlink it; its bindings also list on the Deviations page and still block their node), a fully acknowledged binding (it keeps its `jira` link so the bar stays), a clean binding, an unobserved one (link with null dates). A `gone` item raises `GONE` alone with null dates. Program and work-stream bindings are not folded in 1.3 (the programs tree rolls up the projects' flags).
- **The request's team half (1.23).** `ExternalFlagRequest.teamId` (the team view) and `everyTeam` (the roadmap loader: roadmap, programs, Home) are the two forms of Flow's half of the seam; the Jira source reads neither and answers the node half exactly as before (`planning-model.md` "The roadmap view", `flow-sync.md` "The project rows' flag (1.23)").
- **The scope.** `DeviationScope` gained `levels` (the whole-plan ask reads project and milestone bindings only); a named node list matches a binding on ANY named node, a named EMPTY list names nothing. The roadmap and programs views ask for the whole plan, the project view for the project and ALL its milestones, the team view for no project and the team's milestones. The scoped computation equals the full one (`DeviationScopeNodesTest` pins it, including a parent issue bound outside the scope).
- **The sites (1.16).** `JiraSite` is `{connectionId, siteUrl, state, mappingOk}`, built at ONE place (`JiraFlagSource`) from the connections the REFERENCED rows link through (`referencedConnectionsOnly`, then the rows that survived the liveness filter): `state` is the connection's derived sync state (`JiraSiteState`, `planning`'s own enum with `SyncState`'s five names, converted by name and pinned equal by `JiraFlagSourceTest`; the fold calls `DeviationViewService.siteStatesInTransaction`) and `mappingOk` is `levels != null`, the Deviations view's member. Only the state and the mapping verdict, never the connection's name, project keys, `lastRun`, error code or any credential. The web turns them into the chips' "may be out of date" (`web-internals.md`). **Honest limits:** `CURRENT` means the newest run succeeded and, for a polled connection, not long ago; a manual-only connection stays `CURRENT` after any success, however old (its `lastSucceededAt` is on the Deviations page); the chips and the Deviations banner read ONE rule since 1.17 (`isStaleSource`, `web-internals.md`: the state is not `CURRENT`, or the mapping does not fit), so `STALE`, a first run in flight and a retry in flight after a failure raise the banner too; the only difference is a DISABLED connection, which the chip counts and the banner skips (its own row says so); the Roadmap and Programs pages' facts line says "Jira data may be out of date" while ANY site of the document is behind (plan-wide: the view cannot say which site a project's milestone roll-up links through).
- **Cost.** About 45 us a binding in service time (the roadmap over 1,100 bindings: +50 ms; the team view over 301: +16 ms); numbers and a profile in `timeline.md` "Measured figures"; the lean projection is a backlog item.
- **Proven by** `JiraFlagSourceTest` (the table: each kind, the roll-up, acknowledged, partly acknowledged, stale, disabled, noise, gone, the request shapes), `DeviationScopeNodesTest`, `TimelineJiraFlagsTest` (the four views through HTTP on one bound world, the overlay's additivity, the always-present members), `JiraFlagsScaleTest` (the sizes and the gates), `JiraSiteStateTest` (1.16: a site's state and mapping verdict equal the Deviations view's in every state - no run, a good run, a failed one, a mapping that stopped fitting, a disabled switch, `STALE` through an injected clock - two connections give two sites, and an unbound plan reads no `sync_runs`).

## First real-site walk-through

Do this when a real site and token arrive. Use an account and a scoped or classic API token with read access to a handful of projects.

1. **Connect.** Administration → Jira → New connection: the real site URL (`https://<name>.atlassian.net`), the account email, the token, auth scheme `BASIC` first (`BEARER` if the site demands it), a few project
   keys (≤ 50). **Test connection** and read the rows top to bottom; the FIRST failed row is the cause.
   - `tenant_info` failed (everything after reads `SKIPPED`): the site URL is wrong, or `BLOCKED_HOST` (not a tenant host), or a network/DNS block (`outbound.blocked` audit event).
   - `myself` 401: the token or the auth scheme. `myself` ok but another row 401: a missing scope; the row's hint names it (a missing scope is a 401, not a 403).
   - `search` 400 or `INVALID_RESPONSE`: **A3** (issue-type ids in JQL); `projects` 400: **A8** (50 `keys`). Both were confirmed by hand on a real site (not yet through Astrolabe's probes); the likeliest remaining surprise is a scoped token (unverified).
   - `project:<KEY>` `PROJECT_NOT_VISIBLE`: the token cannot see that project. No `issue` row: the search returned nothing.
2. **Read the discovery report** (the Mapping section; it exists only once a Test connection has been RECORDED, so a stored-connection test comes first, and mapping, Peek and bind all answer `409` until then): the counts, which field matched "Target start"/"Target end" and with what `schema.custom` (**A1**), whether a legacy Parent Link exists (**A2**), the
   Team and Story-points fields (**A7** if `fieldsTruncated`). Every "not found" is a decision for the mapping.
3. **Check the mapping defaults and save them** (or pick fields by hand); the levels list shows the type names per Jira level on this site. A site without Jira levels 2 and 3 (Initiative, Program need Premium) leaves the project and program levels unmapped by default: then only milestones can be linked until an admin maps them to levels that exist.
4. **Peek** one real epic (and, where the site has them, an initiative): the type, hierarchy level, parent key, the dates as plain `YYYY-MM-DD` (**A5**: a datetime field is refused), the estimate, the Team name. `raw` shows what the site sent.
5. **Bind** one node per mapped level to known issues: "Link to Jira…" on the project page for a project or a milestone (an owner or ADMIN), "Link a node…" in the connection page's Bindings section for a program (ADMIN). A wrong level reads `400` naming both levels. Then **Refresh now** (ADMIN) and read the run row: `observed`, `calls`, the error code; `rateLimited` and `backoffMs` are in `GET /integrations/sync/runs` and in the INFO log line, not in the table.
   Compare the Deviations page with the Jira UI for those items.
6. **Import** (only after steps 1 to 5 read right). A real import creates real plan rows, and nothing undoes it in one step (each node is deleted by hand), and program names are globally unique, so:
   - **Use a throwaway work stream** the first time (create one, with a throwaway owner), and a connection scoped to a small project (`projectKeys` narrows a larger connection); never a work stream with real data.
   - **Review the mapping first** (step 3): the import reads exactly the mapped levels, fields, unit and Team field, and a wrong level or no declared factor (a unit other than `DAYS` with no man-days per unit) shows up in the preview (rows skipped, a milestone's `ESTIMATE_NOT_CONVERTED`).
   - Administration → Jira → the connection → Bindings → **Import from Jira…** (or, as a work stream's owner, Plan → the stream's Operations → **Import from Jira…**, with the stream preset and the connection preselected or picked); pick the stream, an owner and, say, a default team; then **Preview** and read it before anything else: the totals, which rows are CREATE, BIND and SKIP and why. Expect renamed items to preview as new (above).
     Tick only what you want. **Assert the totals against what you expect** (how many Jira items at each level) before pressing Import; do not import on a hunch.
   - A lot of `NO_PARENT` rows: either the items have no parent at the level above (give a default program or project) or the site's `search/jql` entries do not carry `parent.fields.issuetype` (**A10**); a preview that takes minutes is the browse itself (pages of `jira.pageSize`, retries on 429; it stops at 170 s). On a project with long history keep the dialog's filter on (1.13.2: done items out, 365 days); a "too large" preview means fewer Jira projects or a shorter window, and "Jira could not be reached or refused the request" with `INVALID_RESPONSE` means the site refused a clause (A16): switch "Leave out done items" off to tell which.
   - After **Import**, read the outcome (created, linked, skipped with reasons), open the project page (milestones dated, or created unscheduled where you do not manage the team), run **Refresh now** and compare the Deviations page. A second import must create nothing when everything was imported (`ALREADY_BOUND`; items left out, or whose plan item was deleted since, are offered again).
7. **When something fails:** the run row's `errorCode` (`FORBIDDEN_SCOPE`, `INVALID_RESPONSE`, `LIMIT_EXCEEDED`, `MAPPING_INVALID`, `TOKEN_UNREADABLE`, …); the `ch.nokillswit.sync` log lines (counts and codes
   only); the `jira.connection_tested` / `jira.sync_requested` audit events; `502 BUSY` on a bind means the permit pool was occupied (retry, or raise `JIRA_MAX_CONCURRENT_REQUESTS`).

8. **Leave it running** (1.3, after steps 1 to 7 read right): keep the connection at its 15-minute default for a day. Watch the status (Administration → Jira, or the telemetry panel's Sync section): **Current**, "next poll in N min", and the runs table gaining **Scheduled** rows with no one's name behind them; a token the site rejects must read **Failed** with its code and a doubling wait (one interval, then two, up to six hours), and a corrected token must poll at once. Then read the flags: the Jira flags on the roadmap and the project and team pages should name the same items the Deviations page lists as open, acknowledging one must silence its flag on all four pages, and the "Jira dates" bar must sit where Jira's own dates are. Compare the polled data with the Jira UI at the end of the day; a site's rate limits show as `RATE_LIMITED` run codes, in which case lengthen the interval.

9. **Coverage** (1.4, after steps 1 to 8 read right, with at least one bound program or project whose Jira item has children): after a day, compare the Deviations page's **Not in plan** (`UNLINKED_IN_JIRA`) and **Not in Jira** (`UNLINKED_IN_PLAN`) rows with the Jira board: every OPEN child of the bound issue that no binding covers must be listed by key (done children are not), every unlinked plan child by name. Then compare each epic chip's roll-up (`done/children · points pt`) with the epic's real child count, done count and story points in Jira, and open an epic whose children are all done: the **Children done** row must be there while the plan still runs. If no roll-up shows anywhere, the site's stories do not carry `fields.parent` (**A12**, look at the discovery's Epic Link marker) or sit past the page ceiling (**A11**, the `children census truncated` WARN); if `done` stays 0, **A13**; if points are missing, **A14**. The first run after the upgrade (or after the first bind) is a full read plus the children, and the child list is re-read once a day (`jira.censusHours`).

10. **The gone probe** (A15, after steps 1 to 5 read right): bind a milestone to a throwaway issue on the real site, run **Refresh now**, then delete that issue in Jira (and, separately, move one to a project outside the connection's keys) and run again. Expect the Deviations row to read "Deleted in Jira (or no longer visible to the connection's account)" for the deleted one and "Moved out of the connection's projects (Jira still has it)" (badge "Moved out of scope"; the wide "No longer readable in Jira: deleted, moved out of the connection's projects, or no longer visible to its account" is what a row Jira has not yet answered for reads) for the moved one, with `observation.goneReason == "MOVED_OUT"` on its binding **and (1.13) its binding's `issueKey` and link now showing the NEW key** (the 200's `key`; `observation.issueKey` still holds the old one), and `calls=` of the run to grow by one per gone binding in the probe's queue (a verdict - `DELETED`, `FORBIDDEN` - is never asked again; the moved one is asked again by every Refresh now and by a scheduled run a day after its last answer, and once the issue is deleted in Jira that ask answers 404 and the row turns `DELETED`). If the moved issue reads Deleted too (Jira answered 404 by id), or a deleted one reads Moved out (200), A15 is wrong: record it in the ledger. Since 1.13 "Moved out" is checked against the key the 200 carried: an issue whose key is still inside the connection's keys (archived, a changed type, a false-empty sweep) reads "Not listed by Jira" (`NOT_LISTED`: "Still in the connection's projects, but Jira no longer lists it (archived, or its type changed)"). If a moved issue keeps its OLD key on the real site, or reads "Not listed", A15's key assumption is wrong: record it in the ledger.

11. **Import from a linked node** (1.14, A18; after steps 1 to 6 read right): open the import from a linked program (Plan page, the program's menu) or a linked project (its page) and compare the preview with what Jira's own search lists for `parent = <the item's key>` (its direct children at the mapped levels, and for a program the milestones under those). An empty preview against a non-empty search is A18 (`parent in (<numeric ids>)` for the levels above an epic) or A2 (the discovery report's legacy Parent Link marker: the site keeps its hierarchy elsewhere); `502 jira-upstream (INVALID_RESPONSE)` is a site refusing the query (A16's clauses, or A18). Import only what is wanted, into a program whose plan children are understood, and run **Refresh now** afterwards: the imported rows read `ALREADY_BOUND` in a second preview.

## To place (from security.md)

Moved out of `security.md` "The Jira import bucket" (D10); D18 places them under "Import".

- **A rooted call (`root`)** costs one by-id read of the root plus the `parent in (...)` searches: a program root asks one query for its children and one per 50 of the projects it found (at most 40 round-two queries at the 2,000-row cap), so about 60 requests a call on an honest site WITHOUT a filter; under a filter round one is unfiltered at the source (it lists the projects to walk), so the milestone-level children it drops there are read and never held, and the 60 does not bound them. The whole rooted browse shares ONE budget of 200 requests (`MAX_SEARCH_PAGES`, one `PageCeiling` shared by all the `searchPages` calls).
- **What reaches a query or a path:** the root's issue id is the STORED binding's and every other parent id comes from Jira's own answers; each passes `ISSUE_ID_PATTERN` before it joins a path or a query (`JiraJql.children`, `ImportRoot` and `HttpJiraClient.issue` refuse anything else) and no more than 50 name one query. A fetched document is used only when its `id` is the one asked for, its key is inside the import's project keys and its level is the wanted one. A query is shaped only by the `projectKeys` subset picked (checked against the connection's own keys before) and the filter (`excludeDone` and the bounded day count: `JiraJql.importBrowse`, `updatedWithinDays` 1..3,650, validated in the request and again in the builder, sent as minutes) - safe, constant clauses, never a spliced string.

## To place (from authorization.md)

Moved out of `authorization.md` "Jira import" (D11/D12); D18 places them under "Import". The guard order, the who-may-do-what and the disclosure rules stay in `authorization.md`; these are what the preview and the apply hold.

- **The preview's shape `400`s** (after the up-front `403`s, as the shape reaches a query; the resolved-target `403` still comes after the browse): `projectKeys` a subset of the connection's keys; the owner person active; `defaults.teamId` an active team; the defaults and the root under the picked stream, with a root: no `defaults.programId`, and `defaults.projectId` only a project of the root program (none under a project root); and last `filter.updatedWithinDays` a whole number 1..3,650. The apply's shape `400`s add every `overrides.teamId` (an active team) and every `overrides.ownerPersonId` (an active person; no guard beyond the dialog-level owner's, which is none).
- **A filtered browse reads the missing direct parents by id** (at most 200, with one short read of the bindings per round between the Jira calls). A fetched parent is an in-scope issue of a mapped level that an unfiltered preview of the same scope lists anyway; a by-id `404` marks that parent unreadable; any other failure (a `403` included) is the `502`, never a per-issue verdict. The unreadable-parent outcome is observable to a non-admin as `NO_PARENT` (the `PARENT_UNREADABLE` info itself is stripped from a skipped row).
- **The redaction, in detail** (`redactForNonAdmin`, pure, applied at the route). With no active filter the key, `typeName`, `hierarchyLevel`, `reason` and the parent keys of a blanked skip row stay; under an active filter (`isActive()`: `excludeDone` on or `updatedWithinDays` set) `issueKey` is null, `name` blank, `jiraId` is `hidden-<n>` (never a Jira id) and the row's `parentJiraId`/`parentIssueKey` are null (`redactForNonAdmin(plan, filterActive)`).
- **The order of the redacted rows:** they come AFTER every visible row, ordered by what they still show (level top-down, then reason, type name, hierarchy level), never by id; `<n>` numbers that final list. Two redacted rows that show the same are identical but for their number, so the order the plan lists them in (ascending Jira id) is not observable.
- **An `ALREADY_BOUND` row** is decided before its parent is looked at, so it can name a redacted parent, or one the filtered browse never listed (it does not read the parent of a linked child), a handle to an item the caller may not see: it keeps `parentJiraId`/`parentIssueKey` ONLY when its parent is a VISIBLE row. A CREATE/BIND row never has a redacted parent (a child of a skipped parent is itself `PARENT_SKIPPED`) and keeps its parent (the apply compares it). The `ALREADY_BOUND` rows keep their own key and text (public through `GET /integrations/jira/bindings`); ADMIN and a preview with no or an inactive filter are unchanged.
- **The apply's answers for withheld ids** follow the visible skips (row order, with key and reason) in the order the caller ticked them, so a withheld id and an id the browse does not hold cannot be told apart; the withheld ids are computed by the same-scope kernel run with the SAME `matches` and no `overrides.teamId`.
- **What remains visible, honestly:** the caller chooses which rows are VISIBLE through `defaults` (`teamId`, `programId`, `projectId`), `projectKeys` and the filter, and a visible row shows in full, with its key, in the preview and in the apply's `skipped[]` (a resolved-target `403` names the first unowned visible row's key). That is the settled rule, not a leak of the redacted ones; a caller who previews without a filter and ticks the ids of rows that were visible there under a filter learns which of them the filter leaves out (the same fact their own filtered preview shows by omission). The counts of redacted rows per filter and their level/type/reason mix are visible; a count is still a verdict when its group holds one issue: an issue alone in its level, reason and type in an unfiltered preview has its filter verdict told by that group's count under the filter (the remaining residual, `BACKLOG.md`).
- **The rooted import's query.** The query's parent is the root's issue id from the STORED binding and then ids from Jira's own answers; the request shapes a query only through the `projectKeys` subset (validated against the connection's own keys) and `excludeDone` / the bounded day count: safe, constant clauses; nothing else of it reaches a query. What a rooted import creates lands under the root's own node (the defaults are held to it, `400`), the one exception being the planner's re-homing.
- **A rooted import writes only under its root, for EVERY caller (ADMIN and the stream's owner included).** A child project whose Jira item is already linked to a plan project of ANOTHER program of the same stream stays `ALREADY_BOUND` (naming its holder, a plan node anyone reads) and what hangs under it is skipped `OUTSIDE_ROOT` by the kernel (`ImportInput.root`), in the preview and in the apply's re-plan under the lock; a project moved out of the root program meanwhile is an `OUTSIDE_ROOT` skip, never a write. What a caller learns from such a row is what any redacted skip tells (level, type, reason; the key only without a filter); the resolved-target `403` it replaced named the other project and the first key, and the holder of its Jira parent was already named by the parent's own `ALREADY_BOUND` row.
- **The rooted residual** (the LOW-1 class, inside the root's own Jira subtree): under an active filter the `OUTSIDE_ROOT` rows are handle-free like every redacted skip, but their COUNT tells how many items under the child project linked elsewhere pass the filter; the `jira-import` bucket (5 a minute) bounds the probing; without a filter the rows themselves are listed (key, level, reason, no text). A rooted scope narrows the group a redacted count speaks about; the done / open verdict of an unlinked child is already public through `UNLINKED_IN_JIRA`.
- **Suggested matches, mechanically.** `matches[{jiraId, nodeId}]` rides the preview and the apply bodies. An entry is honoured only when it equals the kernel's own suggestion for that row under that parent, recomputed under the plan lock in an apply; any other entry is ignored (in an apply the ticked row is `CHANGED`). The guard over a BIND made through a confirmed match runs over every row in the preview and over the ticked rows in the apply (`requireResolvedTargets`; `JiraImportMatchGuardTest`). The `matches` shape `400`s (more than 2,000 entries, a `jiraId` that is not a numeric Jira id, so a `hidden-<n>` handle is refused, an id named twice) come after the up-front `403`s; an entry naming a numeric id whose row is redacted changes nothing in the answer. `JiraImportRedactionTest` pins that a redacted row never carries a suggestion.
