### The Jira sync (v1.1.0 to 1.4.0; connection verified on a real site in 1.5.1)

Read before touching `jira/`, `sync/`, `infra/fetch/` or the Jira pages. **What it is:** Astrolabe reads Jira Cloud and compares it with the plan; **nothing is ever written to Jira**
and corrections are made in Astrolabe. 1.1.0 is the connection, the mapping, 1:1 bindings, a manual Refresh and the Deviations page; 1.2.0 adds the import (preview, then apply); 1.3.0 adds polling, the connection status, acknowledge and the timeline markers; 1.4.0 adds coverage and roll-ups from a census mirror (V23); the connection stores its `pollIntervalMinutes` (V22: default 15, 5..1440, `null` = manual only), which the in-process scheduler reads ("Polling (1.3)", "Status (1.3)", "Acknowledge (1.3)" below). **The sync, import, deviations and the gone-reason probe are proven against the built-in Jira stub only; the connect path (Test connection) was verified on a real Jira Cloud site in 1.5.1** (`product.md` "v1.5.1 - what shipped"; ledger rows A3 and A8 were settled by hand with direct GETs on a real site on 2026-11-08; the walk-through below still covers the rest). Flow is a separate connector (`flow-sync.md`). Coverage and roll-ups (1.4, V23: the mirror `jira_issues` and `jira_connections.census_at`): "Coverage and roll-ups (1.4)" below and `persistence.md` "The Jira census (V23)".
Related: schema `persistence.md` "The Jira sync tables (V21)"; outbound guard `security.md` "Outbound HTTP calls"; audit events and the run log lines `observability.md`; per-route guards
`authorization.md`; the web pages `web-internals.md` "Jira connections" and "Deviations"; the stub's dataset `sample-data/jira/README.md`.

## The transport and the gateway

- Every authenticated call goes to `https://api.atlassian.com/ex/jira/{cloudId}/rest/api/3/...`; only the unauthenticated `GET https://<site>/_edge/tenant_info` goes to the site, and it supplies
  the `cloudId`, validated as a UUID before it is stored or spliced into a path (`HttpJiraClient.resolveCloudId`). A stored site URL can therefore never redirect authenticated traffic
  elsewhere. A site URL that no longer has the genuine tenant shape is refused (`BLOCKED_HOST`) before any client exists.
- `authScheme` per connection: `BASIC` (`base64(email:token)`) or `BEARER`. Which one a given site and token need is NOT verified (see the ledger).
- A scoped token missing a scope answers **401, not 403** (Flow's finding); the probe rows carry the scope hint for that reason.
- One guarded `HttpClient(OkHttp)` for the whole app (`configureJira`), the allow-list being the general tenant-host shape (`infra/outbound/AtlassianSites.kt`), never a stored site. Config
  (`jira.*`, each boot-validated, env `JIRA_*`): `requestTimeoutSeconds` 30 (5..120), `requestDeadlineSeconds` **180** (10..600), `bindPermitWaitMillis` 5000 (100..60000),
  `maxResponseBytes` 4 MiB, `maxConcurrentRequests` 2 (1..8, the permit pool), `maxRetries` 4 (0..8), `pageSize` 100 (1..500), `incrementalOverlapMinutes` 10 (0..1440), `censusHours` 24 (1..168, 1.4); `sync.maxRunMinutes` 10 (1..60).
- The transport (`infra/fetch/`, Flow's): retry with jittered backoff on 429/5xx/IO errors, `Retry-After` clamped, a per-tenant pause, `X-RateLimit-NearLimit` = a 1 s sleep, a response byte cap and
  node ceiling (`LIMIT_EXCEEDED`), a page ceiling. Failure codes: `AUTHENTICATION_FAILED FORBIDDEN_SCOPE NOT_FOUND RATE_LIMITED UPSTREAM_UNAVAILABLE TIMEOUT INVALID_RESPONSE LIMIT_EXCEEDED
  BLOCKED_HOST REDIRECT CURSOR_EXPIRED BUSY`. `SourceHttp.kt` is at the 400-line cap: the next edit splits it.
- `search/jql` returns only `id` unless `fields` is named; the run names every field it reads. Timestamps are `yyyy-MM-dd'T'HH:mm:ss.SSS+0000` (`JiraTime`).
- **Development only:** `jira.stubBaseUrl` (`JIRA_STUB_BASE_URL`) reroutes BOTH hosts of a `stub-` site (and no other site: `JiraStubRouting`, `jira/JiraStubRouting.kt`) to the stub; a non-blank value outside development mode refuses boot naming the key.

## Test connection and the probes

`JiraConnector.testConnection` runs the probes in sequence (10 s each, 30 s in all, never throwing; every outcome is a row, **never a 502**). All rows are required; a result passes when every row
is ok. In this order: `tenant_info` (unauthenticated), `myself` (`read:jira-user`), `issuetype` (`read:issue-type:jira`; supplies the type ids the search narrows by), `search`
(`GET /search/jql`, `maxResults=1`, `fields=id`, the JQL = the connection's scope AND `issuetype in (<ids at the mapped milestone level, else Epic level 1, else level 0>)`;
`read:jql:jira`), `field` (`read:field:jira`), `projects` (`GET /project/search?keys=…` with exactly the configured keys; `read:project:jira`), one `project:<KEY>` per key (a key the token cannot
see is a failed row, code `PROJECT_NOT_VISIBLE`), and `issue` (`GET /issue/{id}` on the first id the search returned; `read:issue-details:jira`; **no row at all** when the search returned nothing).
Other typed row codes: `SKIPPED` (not run: `tenant_info` failed), `TOKEN_UNREADABLE` (the stored token cannot be decrypted: a wrong or rotated `DATA_ENCRYPTION_KEY`; one `stored_token` row, nothing called), `BLOCKED_HOST`, `TIMEOUT`,
`INVALID_RESPONSE` (a malformed body or an `IllegalArgumentException`).

**When `tenant_info` fails the later rows read `SKIPPED`**: there is no gateway to call, so `myself`, `issuetype`, `search`, `field` and `projects` are not run and each answers `ok: false`, code `SKIPPED` (no status, no scope hint; `JiraConnector.probe`'s `gatewayProbe`, `ProbeRun.skip`; the harness lives in `infra/fetch/ConnectionProbes.kt`, shared with Flow's Test connection). They still count as failed REQUIRED rows for `passed` (so does `tenant_info` itself), but the UI shows them as a gray "Skipped" and counts only the real failure. No `project:<KEY>` or `issue` rows appear. Read the first failed row.

`POST …/connections/test` is ad hoc (carries the token, stores nothing); `POST …/{id}/test` uses the stored token, records `last_tested_at/ok`, `cloud_id` and **the discovery whenever both `field`
and `issuetype` answered, even if another probe failed (D3)** so a failing first test still leaves the report that diagnoses it. A result is recorded only if the row was not edited meanwhile
(`recorded`). Audited `jira.connection_tested` (host, ok, failed probe names, `recorded`, `stub`; never the token).

## Discovery

`GET …/{id}/discovery` answers the stored snapshot (`409 jira-not-discovered` before the first recorded test): `fieldCount`/`issueTypeCount` as the site reported them, the usable fields (types
`date`, `datetime`, `number`, plus the recognised customs `atlassian-team`, `gh-epic-link`, `jpo-custom-field-parent`; capped at 2,000, markers kept first, `fieldsTruncated` says when it bit),
the issue types (cap 500), `levels[{level, typeNames}]` (non-sub-task types by Jira `hierarchyLevel`) and the **markers** the report prints (a null is an amber "not found" line): `targetStart`/`targetEnd`
(a **date** field named "Target start"/"Target end", else a field whose `schema.custom` contains `jpo-custom-field-baseline-start`/`-end`), `startDate` ("Start date", a date), `dueDate` (`duedate`),
`storyPoints` (the first `number` field whose name contains "story point"), `team` (`schema.custom` contains `atlassian-team`), `legacyEpicLink`, `legacyParentLink`.

## Mapping

One canonical JSONB document per connection (`jira_connections.mapping`): `levels.{program,project,milestone}` = `{hierarchyLevel, fields{start, end, estimate}}` (program and project optional, milestone
required), `estimate{unit POINTS|HOURS|DAYS, manDaysPerUnit|null}`, `teamFieldId`. `PUT …/{id}/mapping` (204) checks the shape before any database read (levels ≥ 0 and strictly decreasing program > project >
milestone, field ids of the Jira shape, factor `0 < x ≤ 1000` with two decimals), then under the row lock against the discovery: every named level has a non-sub-task type, start/end are `date` fields
(a `datetime` is refused: the date depends on a time zone), the estimate is a `number`, the Team field is the site's `atlassian-team` one; `409 jira-not-discovered` with no discovery. `jira.mapping_changed`
audits the before/after SHA-256 on every accepted PUT; a PUT that changes the document sets `mapping_changed_at` (the next run reads in full). `GET` answers `{stored, defaults, effective, discoveredAt, problems[]}`;
`problems[]` lists what a LATER discovery outgrew in a stored mapping (nothing is ever rewritten).

**Defaults** (pure `JiraMappingDefaults.resolve(discovery)`, used until a mapping is saved): milestone = Jira level 1 (Epic) if the site has a non-sub-task type there, else level 0; project = level 2 and
program = level 3 when present; start = "Target start", else "Start date"; end = "Target end", else `duedate` (only `date` fields qualify); estimate = the story-points field **on the milestone only**,
unit `POINTS`, no factor (nothing assumes points convert; the figure is shown beside the plan's, never compared); `teamFieldId` = the `atlassian-team` field.
The bind and the run share one resolution (`resolveEffectiveMapping`): stored-or-defaults, re-validated against the CURRENT discovery; a stale one is `409 jira-mapping-invalid` on a bind/Peek and a `FAILED`
run with `MAPPING_INVALID`; an undecodable document is `MAPPING_UNREADABLE`.

**Peek** (`GET …/{id}/peek?key=ABC-12`, `jira-test` bucket): one `GET /issue/{key}` for the mapped and system fields, answered as `{issue, resolved{level, start, end, estimate, unit, teamName}, raw}` where `raw`
holds only the mapped fields' values. Nothing stored, no audit; the key must be in the connection's project keys; an upstream failure is a `502 jira-upstream` carrying only the code.

## Bindings (1:1)

A binding links ONE plan node (program, project or milestone) to ONE Jira issue (by its numeric id; the key is stored for display and survives a rename). The database holds both directions
(`uq_jira_bindings_node_active`, `uq_jira_bindings_issue_active`); the service makes the checks exact with one **global transaction advisory lock `BIND_LOCK_KEY`** taken first (binds are human clicks).
`POST /integrations/jira/bindings {connectionId, level, nodeId, issueKey}` → `201`, in this order:

1. the body decodes; the node's chain is read (missing = `404`); `requireOwnerOrAdmin` (`403`); then validation (`400`).
2. **One Jira call, outside any transaction** (`observeForBind`): the connection must be active and enabled (`400`), its token readable (`409 jira-token-unreadable`), discovered (`409 jira-not-discovered`),
   its effective mapping valid (`409 jira-mapping-invalid`); the level must be mapped and the key's project in scope (`400`); the issue must exist (`400 "Unknown Jira issue"`) and sit at the hierarchy level
   the mapping gives that plan level (`400` naming both). The call queues for an outbound permit at most `jira.bindPermitWaitMillis`, then answers **`502` with code `BUSY`**, so a burst of binds never holds
   an administrator's Test connection behind it; any other `FetchException` is `502 jira-upstream (CODE)`.
3. The transaction: the advisory lock; the connection row `FOR SHARE` (a delete/edit waits, or has won and this is `400`); the scope re-checked; the node row `FOR SHARE` (`404` if it was deleted); the chain
   re-read and the guard re-run; the node's own active binding → `409 already-bound` ("Project X is already linked to ABC-9"); the issue's active bindings on this connection **or on another active
   connection of the same site (D1)** → `409 already-bound`, unless their node (or an ancestor) is deleted, in which case it is **released** (soft-deleted, audited `jira.binding_released reason=NODE_GONE`).
   Then the binding and its first `jira_observations` row (from the fetched issue) are inserted. No plan lock, no revision bump (a binding is not plan state). Audit `jira.binding_created` after the commit.

`DELETE …/bindings/{id}` soft-deletes (history stays) after the guard on the chain as last stored (a binding whose node is gone is unbound by whoever passes the guard on that chain); `jira.binding_deleted`.
Deleting a connection soft-deletes its bindings in the same transaction (**D2**) and hard-deletes its runs. A program-level binding can only be made on a connection's page (ADMIN), the plan having no program page.

## Observations and the run

`jira_observations` holds the LATEST observed state of a binding (a hard overwrite, one row per binding): summary, type, hierarchy level, status and status category (`new|indeterminate|done` →
`TODO|IN_PROGRESS|DONE`, anything else `UNKNOWN`), parent id/key, start, end, estimate and unit, team name, `gone`. `JiraObservation.of` is pure and clamps every value to its column (a figure
that cannot fit `NUMERIC(12,2)` reads as null) so one odd issue cannot fail a chunk and wedge every later run.

**Refresh now** → `POST /integrations/sync/runs`: `requireRunnable` (the connection is active and enabled, else `400`), `SyncRunService.claim` (in ONE transaction: lock the connection row `FOR SHARE` through `Connector.lockActiveInTransaction` - a delete racing the claim serializes with it, and a claim that meets a deleted connection is a `400` that writes nothing, so no orphan `sync_runs` row outlives its connection, which the delete otherwise purges; abandon any unfinished run of the connection older than
`sync.maxRunMinutes`, prune the finished ones to 50, INSERT the unfinished row; a `23505` on **`uq_sync_runs_running`** is `409 run-in-progress`: the claim IS the unique index, so replicas cannot double-run),
audit `jira.sync_requested`, `202`, and the run executes on the application's background scope (`SyncRunner`). The page polls `GET /integrations/sync/runs?kind=JIRA&connectionId=` (≤ 50, newest first).
Outcomes are `SUCCEEDED|FAILED|ABANDONED`; a run's own deadline is `maxRunMinutes − 1` (never under 30 s) → `FAILED/RUN_DEADLINE`, so a live run is never abandoned under itself.
In order (`JiraObserver.execute`):

1. Read the connection: gone → `CONNECTION_GONE`, disabled → `CONNECTION_DISABLED`. Release bindings whose node (or an ancestor) was deleted (`jira.binding_released`).
2. Token readable (`TOKEN_UNREADABLE`), discovery present (`NOT_DISCOVERED`), mapping usable (`MAPPING_UNREADABLE|MAPPING_INVALID`; also `MAPPING_INVALID` when a mapped level has no usable type id). Take the
   connection's active bindings; **none → the run succeeds having called nothing.**
3. `tenant_info` (persisting `cloud_id` when none is stored), then the read. **Full** (`project in (…) AND issuetype in (<every mapped level's type ids>) ORDER BY id ASC`) when no earlier run
   succeeded, a binding has no observation, or anything that decides what an unchanged issue reads as is newer than the last succeeded run's start (`discovered_at`, `mapping_changed_at`, the connection's
   `updated_at`); otherwise **incremental** (`project in (…) AND updated >= "-Nm" ORDER BY updated ASC`, N = minutes since that start + `incrementalOverlapMinutes`, recomputed from the clock at every
   first-page request, not type-filtered). Every bound issue found is upserted in chunks of 100, one short transaction each, never a transaction across an HTTP call and never the plan lock.
4. The **sweep**: `…issuetype in (…) ORDER BY id ASC` with `fields=id`: a bound id missing from it, and not just read, whose last observed type is among the swept types, is `gone` (`OUT_OF_SCOPE`: a
   deletion, a move out of the keys and a lost permission look the same here); a flagged id seen again is cleared.
4b. The **probe** (since 1.10, `jira/JiraGoneProbe.kt`): each gone binding Jira has not yet ANSWERED for is read by id, `GET /issue/{issueId}?fields=id`, through the run's own guarded client (it counts in `calls=` and runs `runnableState` before each call). The queue is the bindings the sweep judges gone that were **newly flagged in this run, plus those already `gone` with no `gone_probed_at`** (V27), at most 100 a run, **the newly flagged first, then the retries, each by binding id** (so a few retries whose read keeps failing cannot trip the breaker ahead of a new vanish: that is probed in the run that flags it). **404 → `DELETED`, 403 → `FORBIDDEN`, 200 → the column stays `OUT_OF_SCOPE`** (readable elsewhere: moved out of the keys). **Since 1.12 the API reads that answered 200 as `MOVED_OUT`** (`wireGoneReason(stored, probedAt)` in `JiraGoneProbe.kt`: `OUT_OF_SCOPE` with a non-null `gone_probed_at` is `MOVED_OUT`; applied where the stored observation is read, `DeviationViewRows.storedObservation()` for the view, the flags and the acknowledge recompute, and `toObservationResponse()` for the bindings list), so nothing stored changes and `gone_probed_at` stays server-internal; the row not yet answered for keeps the wide `OUT_OF_SCOPE` phrase. **Known limit:** a 200 proves only "Jira has it, readable by id, absent from the scope listing", which also holds after a type change during a full read and after a false-empty sweep (the empty-sweep default below), so "moved out" can over-claim in those rare cases. Because `detail.jira` is the reason, an acknowledged `GONE` of an already-answered 200 reopens ONCE on the 1.12 upgrade (`OUT_OF_SCOPE` → `MOVED_OUT` changes its fingerprint), and one acknowledged while its probe was still unanswered reopens when a retry answers 200 (as a 404 or 403 already did); **every answer, the 200 too, stamps `gone_probed_at`**, in `JiraRunStore.recordProbe` (one short transaction when it is obtained, `WHERE gone`, so a run cut or stopped part-way keeps every answer it already had). Any other failure is logged (WARN `Sync run {id} probe of issue {issueId} failed: {code}`) and leaves the row **unstamped**, so a later run probes it again. **The run never fails on a probe** (only a `FetchException` is caught, never a cancellation; a stop for a deleted or disabled connection still ends the run). **Retried until Jira answers (D2-D4 of 1.10):** a probe that failed, was cut by a stop or the breaker, or fell beyond the 100-a-run cap is retried by every later run while the sweep still judges the binding gone (the breaker counts per run); an answer is final for that vanish (a 200 is not probed again), and a clear (the issue is back in scope or was re-read) or a new vanish probes afresh, because every path that clears `gone` clears the stamp (`CHECK (gone_probed_at IS NULL OR gone)`). **No backfill:** a row flagged gone before 1.10 has no stamp, so the first 1.10 run classifies it (up to 100 extra by-id reads a run until the backlog is drained), and an acknowledged `GONE` whose reason flips reopens once. The column is server-internal, in no API. **Circuit breaker:** after 3 failures in a row that say nothing about the issue (a 200 or a verdict resets the count) the probe stops, logs once (WARN `Sync run {id} probe stopped after 3 failures in a row: {n} binding(s) left unprobed`; `{n}` counts the rest of THIS run's queue, not the whole backlog) and leaves the rest for the next run; the run still succeeds. A probe that keeps failing therefore logs on every run (at most 3 + 1 WARN lines). Jira answers the same 404 for an issue the connection's account cannot see, so `DELETED` reads "deleted, or no longer visible". Because the deviation's `detail.jira` is the reason, a probed row's fingerprint flips once (`OUT_OF_SCOPE` → `DELETED`) and an acknowledged `GONE` reopens then, which is the acknowledge idiom's intent. **Proven against the built-in Jira stub; not yet compared with a real Jira.**
5. The **census** (1.4, `jira/JiraCensus.kt`): every entry of the read above, bound or not, was also buffered into the mirror; after the reconcile the run prunes, reads the child level and stamps (`## Coverage and roll-ups (1.4)`).

Rules inside the read: at most 200 pages **per read** (the read and the sweep each get 200) else `LIMIT_EXCEEDED`; an incremental hitting `LIMIT_EXCEEDED` restarts once as the full read; `CURSOR_EXPIRED`
restarts the query once from its first page, a second expiry fails the run; a `200` that is not a listing (no `issues`, or `isLast: false` with no token) is `INVALID_RESPONSE`, never an empty page; a cycling
`nextPageToken` is refused. **Before every search page the run asks `runnableState`** (`JiraConnectionService.runnableState` delegating to `sync/ConnectionRegistry.kt`'s `runnableStateOf`; the `RunnableState` enum is `sync/`'s, shared with Flow): a connection deleted or disabled meanwhile ends the run `FAILED` with `CONNECTION_GONE` / `CONNECTION_DISABLED`
(a deleted connection's token is destroyed, so a copy in memory must not authenticate one more read). A run cut by its deadline or a shutdown (`SHUTDOWN`) keeps the counts it had.
**The empty-sweep default:** a genuinely empty listing of a non-empty bound set still flags the bound issues of a swept type that this run did not just read `gone` (a WARN log with counts), because a false flag only warns and heals on the next good sweep,
while failing would wedge a site whose only bound item was really deleted.

## Deviations

`GET /views/deviations` (one `READ ONLY REPEATABLE READ` snapshot, the plan revision first, unpaged, ≤ 2,000 items, `totals` before the cap; the document is `{revision, asOf, connections[{…, status}], totals{warnings, infos, bindings, gone, acknowledged}, items[≤ 2,000], truncated}`, the `totals` counting before the cap; `warnings` and `infos` count OPEN LINES (1.12: a listed deviation without a current acknowledgement of its own) and `gone` open items (it also counts moved-out ones: the label stays "N gone from Jira"); `all=false` overrides the `all`-implying filters) applies the pure `JiraDeviationKernels.deviations` to each
binding. Dates compare in WORKING days on the plan's holiday calendar (a start snaps to the next working day, an end to the previous one); a derived span (project, program) is compared, not stored dates.
A `gone` issue raises `GONE` alone. Default: OPEN bindings (at least one listed line without a current acknowledgement, 1.3; per line since 1.12), those with an open warning first; `all`, `projectId` or `teamId` also list clean and acknowledged ones. A **disabled** connection's bindings stay in the view with their last
observation (they still block their nodes).

| Kind | Levels | Rule | Severity |
|---|---|---|---|
| `GONE` | all | the observation is `gone`; the phrase names the reason: `DELETED` (the probe's 404: deleted, or no longer visible), `FORBIDDEN` (its 403), `OUT_OF_SCOPE` (the sweep's, until a probe answers), `MOVED_OUT` (1.12: what a probe's 200 reads on the wire, see 4b) | WARNING |
| `LEVEL_MISMATCH` | all | the observed hierarchy level (or none) ≠ the mapping's level | WARNING |
| `PARENT_MISMATCH` | project, milestone | the observed parent issue is bound to a node that is NOT the plan parent (an unbound parent raises nothing) | WARNING |
| `RENAMED` | all | summary ≠ name (trimmed, case-insensitive; a name cut at 100 compares as a prefix) | INFO |
| `START_DIFFERS`, `END_DIFFERS` | all | both dated and the working-day shift ≠ 0 (`days` positive = the plan is later) | WARNING when the plan's END is later than Jira's, else INFO |
| `TARGET_DIFFERS` | project | the target window vs Jira's dates differs in working days | INFO |
| `UNSCHEDULED_IN_PLAN`, `UNSCHEDULED_IN_JIRA` | milestone | Jira dated and the milestone not, or the reverse | INFO |
| `ESTIMATE_DIFFERS` | milestone | comparable (`DAYS`, or a factor) and `|jira × factor − estimateMd| ≥ 0.01` | INFO |
| `ESTIMATE_NOT_COMPARABLE` | milestone | an estimate with no factor, or one read under a different unit than the mapping names now (listed only with `all=true` or `kind=`) | INFO |
| `PROGRESS_MISMATCH` | all | `DONE` while the plan's end is after today; `TODO` while the plan's start is past; `IN_PROGRESS` while it is ahead | INFO |
| `UNLINKED_IN_JIRA` (1.4) | program, project | open (not DONE) Jira items under the bound issue, at the mapping's level for the child plan level, that no active binding covers (`jira` = their keys, at most 10, `count` = all; never a summary) | WARNING |
| `UNLINKED_IN_PLAN` (1.4) | program, project | the bound node's direct plan children that have no binding (`plan` = their names, at most 10, `count` = all) | INFO |
| `CHILDREN_DONE` (1.4) | milestone | the bound epic has children, all done (`jira` = `done/children`, `count` = children), while the epic is not DONE (else `PROGRESS_MISMATCH` alone) and the plan's end is after today | INFO |

The three 1.4 kinds are declared last, so they sort after the older ones within a severity; they come from two optional kernel inputs (`ChildRollup`, `UnlinkedChildren`; null = none) that the view's loaders fill from the census mirror (`DeviationCoverageRows.kt`, "Coverage and roll-ups (1.4)"). `DeviationDetail.count` has no default and is omitted from a fingerprint while null, so a binding that gains none of the new kinds keeps its acknowledgement; one that gains one reopens.

Without a usable mapping (no discovery, stale, unreadable) neither the level nor the estimate comparison is made and the connection reads `mappingOk: false`.

## Import (1.2): the preview and the apply

`POST …/connections/{id}/import-preview {workStreamId, ownerPersonId, projectKeys?, defaults{programId?, projectId?, teamId?}?, copyDates}` answers what importing the connection's scope into ONE picked work
stream WOULD do, per Jira item: CREATE a program / project / milestone, BIND an existing unbound same-name node, or SKIP. It stores nothing and takes no lock. Work streams are never imported; the
import PICKS one, and an item is created only under it. Checks in order (`authorization.md` has the guards): the `jira-import` bucket, the connection (`404`), the body, the named targets (`404`, then

**What a user must know about the preview** (the planner's rules, pinned by `JiraImportKernelsTest`):

- **Linking is by name.** An unlinked plan sibling with the same name (compared with `lowercase` only: accents count; the Jira summary is first cleaned by `importName` - control characters become spaces, inner whitespace is collapsed, it is trimmed and cut at 100 characters - while a plan name is not, so a plan name with a double space never matches) is proposed as a BIND; anything else is a CREATE. So **an item renamed in Jira, and not yet linked, does not match its plan
  item and previews as a NEW one**: importing it would add a second node. The user must read the preview (an already linked item is `ALREADY_BOUND` whatever it is called now). Matching renamed items is a backlog item.
- **Only the direct Jira parent counts** (`fields.parent` holds the immediate parent and nothing further, and the browse reads only the mapped levels' types). An item whose direct parent sits on a level the mapping skips (an epic under an unmapped
  initiative under a mapped program) has no parent at its own plan level: it goes under the default parent for its level, else it is skipped `NO_PARENT`. Browsing the unmapped levels too is a backlog item.
- **A non-admin sees less.** A skipped row other than `ALREADY_BOUND` shows no summary, its issue key as its name and no infos, and the unmatched Jira team names come from the rows that would be created only (`JiraImportRedaction.kt`); the web table renders the key.

The **Plan page's work-stream menu** offers "Import from Jira…" on every stream whose `can.edit` is true (its owner chain or ADMIN: the actor the server admits for a stream-level import); the modal then opens with that stream preset and read-only. A 403/409 from the server (an owner who owns the stream but not a program named as the default, say) is shown inline by the modal.

`POST …/connections/{id}/import {workStreamId, ownerPersonId, projectKeys?, defaults?, copyDates, items[1..2,000 of {jiraId, expected{action, level, parentJiraId?, nodeId?}, overrides{teamId?}?}]}` writes what the user ticked in the

   re-guarded under them. ## Coverage and roll-ups (1.4)

1.4 finds what the plan misses (Jira children nobody planned, plan children Jira does not track) and shows an epic's story roll-up. **Where the data comes from:** the EXISTING run observes the whole in-scope census into the mirror `jira_issues` (V23, `persistence.md` "The Jira census (V23)") in the same pass; nothing is fetched at request time and nothing is written to Jira. This section is the CENSUS half (what the run writes); the deviation kinds and the roll-up on the views are described here as their commits land.

- **Terms.** *Mapped levels* = the effective mapping's hierarchy levels. *Child level* = `milestone.hierarchyLevel - 1` when that is not below 0 and the site has non-sub-task types there (`typeIdsAtLevel`, every id a valid JQL type id), else none: a milestone mapped to Jira level 0 has no roll-up, and sub-tasks never count. *Census levels* = mapped ∪ child.
- **Every page entry is observed.** The run's read - the typed full read or the untyped incremental - passes each entry to `JiraCensus.observe` BEFORE the bound-issue skip: a row is built by `CensusIssue.of` (fitted like an observation), kept when its level is a census level, buffered by id and flushed in `RUN_CHUNK`s through `JiraIssueStore.upsert` (one short transaction, no plan lock, no revision; the connection row is taken `FOR SHARE`, so a connection deleted meanwhile writes nothing). The incremental window already carries every story updated since, so a changed or new story reaches the mirror at no extra call.
- **What a row is.** Only issues of a type the run's sweeps ask for (the mapped types and the child types) at a census level are mirrored (an issue of any other type is invisible to the sweeps and would flap); the story-points marker (a plausible field id only) is added to the mapped read's `fields` too, so an incremental update of a story keeps its points whichever field the milestone's estimate is mapped to; control characters in a summary become spaces.
- **After the reconcile** (`JiraCensus.complete`): flush; **prune the mapped levels** - rows at a mapped level that are in neither the sweep's listing nor the rows this run saw (in Kotlin: the connection's `(issue_id, level)` index once, deleted in `RUN_CHUNK` batches; an EMPTY listing prunes too, the sweep's WARN covers it and the next good sweep heals); then the **children pass**: a typed full read (`JiraJql.full(keys, childTypeIds)` with `fields` = the system fields + the discovery's story-points marker) on a FULL read (the `LIMIT_EXCEEDED` fallback included), upserting every row and pruning child rows not read; otherwise, when `now - census_at >= jira.censusHours`, an id-only typed sweep (`JiraJql.sweep`, `fields=id`) that prunes child rows neither listed nor seen this run. An empty children listing is normal (epics without stories) and logs no warning.
- **Self-healing.** On a FULL read the rows of a level that is no census level any more are deleted too. When an incremental run's sweep (mapped, or the due child sweep) lists an in-scope id the mirror lacks and the run did not read (rows lost to an earlier false-empty or partial listing), `census_at` is CLEARED instead of stamped: the next run is full and re-seeds.
- **The loop guard** (`jira/CensusLoopGuard.kt`). A census that can never converge (an in-scope issue that can never become a mirror row - a type or level the census refuses - or a children read that always fails) would heal or stay unstamped on every poll and read in full forever. The guard keeps TWO streaks per connection, so "in a row" is true of each: the runs that CLEARED `census_at` (a heal) and the runs whose children pass FAILED. Past `MAX_UNCONVERGED_RUNS` (3) a streak is **tripped**, and its first run logs ONE WARN `Sync run {id} (connection {id}) census cannot converge after 3 runs in a row: {reason}; roll-ups may be incomplete` (reason: `a sweep keeps listing an issue the mirror lacks; ...` or `the children read keeps failing; ...`; ids and counts only), then DEBUG while it stays stuck (the warning re-arms when the streak ends). **Tripped heal:** the run leaves `census_at` ALONE (never stamps it - that would push the child sweep's due time forward for ever and stale children would never be pruned), except when the child sweep is due (once per `jira.censusHours`): then it CLEARS once, one forced full read a day that may heal a later genuine gap, with the streak held at the threshold so the next gap run trips again at once. **Tripped failure:** the run STAMPS `census_at` (instead of leaving it null), so the retry cadence becomes the child sweep's, daily, not every poll. **What ends a streak:** a completed children FULL read ends the failure streak, and a completed id SWEEP ends it only while it is not tripped (the sweep working says nothing of a typed full read that keeps failing; resetting on it would let each daily forced full read cost a fresh run of ~4 failing full reads, instead of one); a conclusive incremental run (no gap, no failure, not truncated, and its child sweep ran or there is no child level) ends the heal streak - a full read cannot see a gap (it re-seeds), and a run whose child sweep is not due has not looked at the child level. A `LIMIT_EXCEEDED`-truncated children listing neither counts nor resets the FAILURE streak and gives no child-level verdict (it does not end the heal streak either); a mapped-level gap in that same run still counts as a heal. A run that is both a gap and a tripping children failure warns for both streaks. And a **config change** that forces the full read (a re-discovery, a mapping change or an edit newer than the last succeeded run's start, the `readPlan` conditions) drops the entry, so a mapping fix untrips at once. The state is IN MEMORY (`JiraObserver` holds one `CensusLoopGuard`, a `ConcurrentHashMap` of a small record per connection id, updated atomically per key so concurrent runs of different connections are safe; the entry is removed when both streaks are empty, on a config change, or when a run finds its connection already deleted at its start - a connection deleted or disabled MID-run keeps a tiny entry until restart), so a restart resets it, which costs at most one more round of full reads before it trips again - no migration. Proven by `JiraRunCensusTest` (the heal loop and its reset, the tripped runs that leave the child sweep due, the daily forced full read, the failure streak and its reset by a completed full read, a tripped failure's daily retry, a working sweep that does not untrip, a gap plus a tripping failure in one run, the config-change untrip, the truncated listing).
- **`census_at`** is stamped with the run's START after a full read (even with no child level, else it would stay null) or a completed child sweep, and `readPlan` reads **in full whenever it is null**: the first run after the 1.4 upgrade seeds the mirror for every existing connection (a full read plus the child read, once, within a poll tick); a fresh connection's first run was full anyway. A connection with no bindings still returns before any call: no census, no stamp.
- **Ceiling.** The children read shares the 200-page ceiling and `jira.pageSize`. Past a listing or response ceiling (`LIMIT_EXCEEDED` on the children listing ONLY; the mapped read keeps its rule and fails the run) the run keeps what it read, **prunes nothing**, still stamps (a big site is not re-read on every poll) and logs WARN `children census truncated at {n} pages after {n} child issue(s) (a listing or response ceiling): roll-ups may be incomplete` (A11). **Any other failure of the children pass** (a 5xx, a timeout, an invalid page) does NOT fail the run: the mapped work of 1.3 stands, the run SUCCEEDS, the pass keeps the rows it read, prunes nothing, does not stamp (so the next run is full and retries - until the loop guard trips after 3 such runs in a row and stamps instead, so the retry is daily) and logs WARN `children census failed: {code}`; only a deleted or disabled connection still ends the run. `runnableState` runs before every page, so a connection deleted or disabled mid-census ends the run `CONNECTION_GONE` / `CONNECTION_DISABLED` with no further read and no stamp.
- **Cost.** The extra calls are the child level's pages: one typed read on a full run (the stub's sample scope: +6 on 25, `expected.json` `search.sample/fulltypes/s/started`; the E2E scope: +1 on 3) and one id sweep per `censusHours` otherwise. At the 1,000-milestone scale with 5,000 stories: +50 field pages once per full read, +50 id pages a day (about +2 calls per 15-minute poll on average).
- **Logging** (`ch.nokillswit.sync`, counts only - never a key, a summary or a URL): INFO `Sync run {id} census: issues={mapped rows written} children={child rows written} pruned={n} childPass={FULL|SWEEP|NONE}` and the WARN above (`observability.md` "Sync runs").
- **The view reads the mirror** (`jira/DeviationCoverageRows.kt`, called by `DeviationViewService.computeInTransaction` after `loadBoundTo`, inside the same snapshot; the acknowledge's `computeBindingInTransaction` goes through the same function, so an acknowledged coverage fingerprint equals the view's). Three loaders, one statement each (two for the plan side), scoped to the bindings in view: `loadRollups` (a bound MILESTONE's mirror rows at `milestone.hierarchyLevel - 1`, `GROUP BY (connection, parent)`: count, DONE count, points sum or null, newest `observed_at`; absent while there is no child), `loadUnlinkedJira` (the bound PROGRAM's or PROJECT's mirror children at the mapping's level for the child plan level, not DONE, with no ACTIVE binding of that issue id on an ACTIVE connection of the SAME `site_url` - D1; node liveness of that binding is not re-checked; keys ascending by numeric id) and `loadUnlinkedPlan` (the node's direct ACTIVE plan children - a program's projects, a project's milestones - with no active binding on an active connection; names ascending by id). A binding whose child plan level is unmapped, or whose connection's mapping does not resolve, has no coverage. The inputs feed the kernel (`ChildRollup`, `UnlinkedChildren`) and the item carries the roll-up as `jira.rollup` (`DeviationRollup`, `JiraRollup` in the spec; always present, null = none; milestone bindings only). Coverage is computed for whatever bindings a scope reads, so a program binding's coverage shows on the Deviations page (the timeline fold asks for projects and milestones only). A disabled connection's items keep their last census. The view discloses the Jira KEYS of unbound issues, never summaries (`authorization.md`). Tests: `DeviationCoverageTest` (the rows that count, D1, the unmapped level, scoped = full), `JiraAcknowledgeTest` (acknowledge and reopen on a new unbound epic).
- **Proven by** `JiraRunCensusTest` (MockEngine), `JiraRunReadTest` (a null `census_at` forces a full read), `JiraRunTest` (the `COV` roll-up figures and the day-2 prune against the stub), `JiraBootTest` (`jira.censusHours` 0 and 169 refuse boot).

## Polling (1.3)

An in-process scheduler (`sync/SyncScheduler.kt`, `observability.md` "Sync runs") claims a run per connection every `pollIntervalMinutes` (5..1440; **omitted = 15, an explicit `null` = manual only**, "Refresh now" still works). It starts nothing the manual route would refuse and reads no secret: its only Jira-side read is `JiraConnectionService.pollRows()` (`jira/JiraConnectionPolling.kt` maps the row, the read is `sync/ConnectionRegistry.kt`'s `pollRowsOf`; seven columns of the ACTIVE rows: id, name, enabled, interval, `discovered_at`, `mapping_changed_at`, `updated_at` - never the token, never the discovery), and the run it starts is the ordinary `JiraObserver.run`, which decrypts the token through `readForBind` exactly as a manual run does.

- **Who is polled:** enabled, tested (a stored discovery: an untested connection could only fail `NOT_DISCOVERED` and back off, so it is never polled) and with an interval. A disabled connection is never polled; its bindings stay visible on the Deviations page with their last observation.
- **When:** the pure `decide` (`sync/SchedulePolicy.kt`) over the newest 50 `sync_runs` of the connection: no run = due at once (a freshly tested connection polls at the next tick, at most `sync.tickSeconds` = 60 s); otherwise newest finish + the interval, doubled per further consecutive failure (`ABANDONED` counts) up to six hours, **plus a jitter after a failure** (below), a success resets; **an edit to the connection, a real mapping change or a new discovery makes it due at once** (an administrator who fixes a token is not left waiting out a back-off); a run in flight (younger than `sync.maxRunMinutes`) is waited for, one older is a crash and the claim abandons it. A manual refresh is simply the newest run, so it resets the cadence by itself. A PUT that changes ONLY the interval also moves `updated_at` and so costs one full read (accepted).
- **Jitter after an outage.** When the site or the database comes back every connection has failed in the same tick and would retry in the same tick, on the two shared outbound permits. A failed connection's wait is therefore the back-off PLUS `fraction x min(backoff / 2, interval / 2, 1 h)` (`failureJitterMillis`; the back-off is never below the interval, so in practice up to half an interval: 2.5 minutes at the 5-minute floor, 7.5 at the default 15, capped at one hour for the long intervals). The fraction is NOT a random draw: it is a hash of the connection id and the newest run's id (`failureJitterFraction`, the splitmix64 finalizer), because the schedule is never stored - a draw per read would make `nextPollAt` flicker and two replicas disagree. The same two ids always give the same offset, so the scheduler, every replica and the status agree to the millisecond; connections that failed together have different ids and spread, and the next failure (a new run id) draws a new offset. A success is never jittered, and a change to the connection stays "due at once". `decide` and `SyncScheduler` take the fraction as a parameter (`JitterFraction`, `NO_JITTER` for the tests that pin the back-off table). Not covered: connections that merely come due DURING a database outage (nothing failed, so nothing is spread) all claim on the first tick after it - the shared permits queue them, which is today's behaviour.
- **A poll of a connection with no bindings** succeeds having called nothing: one database read per interval.
- **Concurrency:** a scheduled run and a manual one are the same claim (the loser of the unique index is a `409` on the route, a "claimed elsewhere" INFO in the scheduler); a poll never takes the plan lock and is independent of an import (they meet only on binding rows, in id order). Outbound permits (2) are shared with binds: a bind during a poll may queue up to `jira.bindPermitWaitMillis` and then answer `502 BUSY`.
- **Scheduled runs** are ordinary rows of the run list with `trigger` `SCHEDULED` and `requestedByUserId` null, and write no `jira.sync_requested` audit line.
- **Proven by** `SchedulePolicyTest` (the table, the jitter bounds and spread), `SyncSchedulerTest` (the jitter to the millisecond and equal to the status's `nextPollAt`, a real registry, a fake connector, an injected clock, two instances, a throwing connector, the tick budget, the shutdown), `SyncBootTest` and `JiraRunTest` "a scheduled run observes the bound issues like a refresh" (the stub). The e2e harness and the compose demo: the API-seeded e2e connections are manual-only (`pollIntervalMinutes: null`); the one the SPA modal creates in "admin creates a Jira connection, tests it…" (`jira-sync.spec.ts`) polls at the editor's default 15 minutes (the form always sends the member) - it has no bindings, so its run calls nothing; the compose stack polls its demo connection every 15 minutes. `jira-polling.spec.ts` owns the one exception: its own polled connection (5 minutes, tested, no bindings), whose scheduled run, edit-makes-it-due and Sync-section row it proves against the stack's real scheduler.

## Status (1.3)

Every connection answers a derived `status` (`SyncStatus`, `sync/SyncStatus.kt`; the rule and its three readers are in `observability.md` "Sync runs"): `state` NEVER_SYNCED | CURRENT | STALE | FAILED | DISABLED, `lastRun`, `lastSucceededAt`, `consecutiveFailures`, `nextPollAt`. Nothing is stored: `JiraConnectionService.read`/`list` compute it inside their own transaction from the connection row and `SyncRunService.recentRunsInTransaction` (the rows go through `toConnectorConnection` in `jira/JiraConnectionPolling.kt` and `SyncRunService.statusesInTransaction(SyncKind.JIRA, …)` in `sync/SyncStatus.kt`, the one copy both connectors call), and `GET /views/deviations` computes `connections[].status` from the snapshot's own reads (`DeviationViewRows.loadConnections` carries the poll facts, `DeviationViewService` derives against the view's clock). The top-level `lastRun` of both is `status.lastRun` (kept for existing readers).

- **FAILED** is the newest FINISHED run failing or being abandoned, with its machine `errorCode` on `lastRun` (never the detail); a run in flight on top does not clear it. An INTERRUPTED newest row (unfinished, older than `sync.maxRunMinutes`, no claim has abandoned it yet - a crash on a manual-only connection stays that way) counts like an abandonment: FAILED, one more in `consecutiveFailures`, `lastRun` showing it with `running` false and `finishedAt` null; `nextPollAt` is still `decide`'s (due for a polled connection, null for a manual-only one). It recovers by the next success, and an edit that makes the connection due at once (a fixed token) lets that happen without waiting out the back-off.
- **`nextPollAt`** is the scheduler's `decide` verbatim, so a failed connection shows the doubling wait plus its jitter (one interval after the first failure, two after the second, six hours at most, each up to half an interval later) and a freshly tested one "now". An untested connection has none (it is never polled); the SPA's hint "Test the connection first" comes from `discoveredAt == null`.
- **`lastSucceededAt`** is the START of the newest successful run (the incremental watermark: the data is as of then), which is also what STALE measures.
- **Proven by** `SyncStatusKernelsTest` (every state, STALE at exactly 3 intervals, manual-only, the streak, `nextPollAt` equal to `decide`), `JiraConnectionStatusTest` (a real run against the stub NEVER_SYNCED to CURRENT, FAILED with its code and the doubling wait, DISABLED after a PUT, STALE with rows and with the injected clock), `DeviationViewScopeTest` (the view's block and clock) and `TelemetryRoutesTest` (the telemetry block).

## Acknowledge (1.3)

A planner who has seen a deviation and accepts it acknowledges that LINE ("until changed", per deviation since 1.12; 1.3 acknowledged the whole list); it then stops counting as open. `POST /integrations/jira/bindings/{id}/acknowledge {fingerprint, kind?}` and `DELETE …/{id}/acknowledge[?kind=]` (`jira/JiraAcknowledgeRoutes.kt`, `JiraAcknowledgeService.kt`; the order and the guard are the `authorization.md` rows, the locks `persistence.md`, the audit `observability.md`).

- **What it keys on.** `fingerprintOf` (`jira/DeviationCompute.kt`, a delegate of `infra/json/CanonicalJson.kt`'s generic `fingerprintOf` since 1.9, shared with the Flow capacity acknowledge; the 409 URN and the 64-hex shape rule live in `sync/Acknowledge.kt`): the SHA-256 of the canonical JSON of the binding's FULL kernel list (`[{kind, severity, detail}]`, `ESTIMATE_NOT_COMPARABLE` included even where the item hides it, so the value does not depend on the filter or the caller). It is rendered with a pinned `Json` that writes neither nulls nor defaults, so a later additive nullable member of a deviation changes no hash (a null still differs from a value); `DeviationFingerprintTest` pins a literal digest. Any change on either side that alters a deviation - the plan date moved further, Jira's end moved, a new or vanished kind, a different count of days - gives another fingerprint, and the stored acknowledgement reads `current = false`: acknowledged on D by X, **changed since**, and the item is OPEN again. A change that alters no deviation (a plan field the kernel does not compare) keeps it. **Per line since 1.12:** the stored fingerprint is that of ONE deviation (`fingerprintOf(Deviation)`, severity in the hash), the table is keyed (binding, kind) because the kernel raises a kind at most once per binding (`JiraDeviationKernelsTest` pins it), and a change reopens only the line it altered; the LIST fingerprint above stays the token the client echoes (to acknowledge one line or all) and the compare that a view read is still current. `PROGRESS_MISMATCH`'s detail is the contradicting plan date, so the fingerprint is stable day to day and a boundary crossed raises a NEW deviation, which correctly reopens the item. **A later release that changes a kernel rule changes the fingerprints it alters and so un-acknowledges those lines: by design, stated in that release's notes.**
- **The write.** ONE short transaction, no plan lock: the binding row locked, the node's chain re-read and the guard run again, the deviations of THIS binding recomputed with `DeviationViewService.computeBindingInTransaction` (the same `computeInTransaction` the view runs, scoped by `DeviationScope(bindingId)`; a parent issue's own binding is looked up so `PARENT_MISMATCH` equals the view's), then the LIST fingerprint compared: different, an empty list, or a `kind` the full list does not hold now is `409 urn:astrolabe:problem:stale-deviations` and nothing is written. With a `kind` that ONE line is stamped; without one (every pre-1.12 request) the lines without a current acknowledgement (D3), or every line when each has one (a restamp, as before). Each stamped line stores its OWN fingerprint, when and by whom in `jira_deviation_acknowledgements` (V28): the target kinds' rows are deleted and the new ones inserted by one `insertRows`, under the binding row lock (every writer of the table holds it, so the unique index is only the backstop); nothing else is written - not `jira_bindings.updated_at`, no plan revision. Acknowledging the same state again restamps who and when. `DELETE` with `?kind=` removes that line's row (`404` when none), without it EVERY stored row of the binding, stale and retired kinds included (`404` when none); the parameter is parsed after the guard (`400` unknown, blank or repeated). **No pruning (Q5):** a row is never deleted because its line left the list, so a line that disappears and returns identical reads acknowledged again with its original stamp; a stored kind this build does not know is ignored on read. 1.3's three `jira_bindings.ack_*` columns are legacy since 1.12: unread, unwritten (Q3: no backfill, every earlier acknowledgement stopped applying).
- **What the view does with it.** Each listed line is a `DeviationLine` (`kind`, `severity`, `detail` and its own `acknowledgement{at, by, current}`, null until acknowledged; a listed item shows EVERY line with its state, whatever the Status filter, D5); the item-level `acknowledgement` is DEPRECATED, a summary over the listed lines (null when none is stamped, else the newest stamp with `current` = every listed line current) for the web UI until it renders lines. The default `GET /views/deviations` lists OPEN items (at least one listed line without a current acknowledgement); `acknowledged=true` the items with at least one currently acknowledged LISTED line (a stamp on the hidden `ESTIMATE_NOT_COMPARABLE` line alone does not count: that item surfaces under `all=true` only), `=false` the open ones; **a kind or severity chip matches the lines of the selected Status (D11)**: the open lines by default and under `acknowledged=false`, the currently acknowledged ones under `acknowledged=true`, any listed line under `all` without a status (so Open + End differs omits an item whose End line is acknowledged; the item still shows every line, and the totals count the open lines of the whole scope); `all` and the chips' implied `all` keep every state. `warnings`, `infos`, `gone` and `acknowledged` share one basis - the items matching every filter but the acknowledgement state - and count its OPEN LINES (`warnings`, `infos`), its open items that are gone, and its items with a currently acknowledged listed line (so "N open" survives `acknowledged=true`); items order an OPEN warning line first; `bindings` is the number the list answers. An item whose only deviation is `ESTIMATE_NOT_COMPARABLE` is open, and counted, exactly where that kind is listed (`kind=ESTIMATE_NOT_COMPARABLE` or `all=true`); the default never lists it, so it is not open there. It can be acknowledged from such a listing (the kind-less call stamps it with the rest); the timeline fold ignores that kind.
- **Who.** The owner chain of the node or ADMIN (Q4a), and since 1.12 (Q4b) - on a MILESTONE binding only - the ACTIVE manager of the milestone's STORED team, who may acknowledge and withdraw every deviation of it, whoever stamped it (`requireOwnerOrTeamManagerOrAdmin`, read first with `TeamService.isActiveManager`, again under the binding's row lock with `lockedIsActiveManager`; `AckAudience` carries the chain and the stored team). A manager on a program or project binding, another team's manager, a roadmap editor and a stranger stay 403; bind and unbind are unchanged (owners and ADMIN). `can.acknowledge` carries the verdict per item (`PlanPermissions.canAcknowledgeDeviations`, pinned against the guard; the view loads `activeManagedTeamIds` for a non-admin).
- **Proven by** `JiraAcknowledgeTest`, `JiraAcknowledgeLinesTest` (one line, the kind-less form, the pre-1.12 body, refusals, withdrawals, a returning line, an unlinked manager), `JiraAcknowledgeRaceTest`, `JiraAcknowledgeRunTest` (a real `jira-day2` run opens the new GONE line only and the first stamps read current again on return), `DeviationViewAckTest`, `DeviationFingerprintTest`, `JiraSchemaTest` (V28).

## Timeline flags (1.3)

The four timeline views (roadmap, programs, project, team) carry the Jira links and flags of the rows they answer (`planning-model.md` "Jira flags and links" is the contract, `timeline.md` "The Jira markers (1.3)" the document shape and the measured cost). **How it is built.** `planning` declares the seam (`planning/ExternalFlags.kt`: `ExternalFlagSource`, `ExternalFlagRequest`, `ExternalFlags`, `JiraLink`, `JiraSite`; the deviation vocabulary `Deviation`, `DeviationKind`, `DeviationSeverity`, `DeviationDetail` moved to `planning/Deviations.kt` with unchanged serialized names, so a stored fingerprint and the spec schemas did not move) and names no `jira` type; `jira/JiraFlagSource.kt` implements it over `DeviationViewService.computeInTransaction(scope)` and `infra/db/Database.kt` wires it into the four view services (since 1.9 through `CompositeExternalFlagSource`, beside `flow/FlowFlagSource`: the request gained `teamId` and the answer `teams`, the team view's half; `JiraFlagSource` answers only the node half and returns early on `request.namesNoNode`). The source runs INSIDE each view's `READ ONLY REPEATABLE READ` snapshot, after the calendar, with the calendar the view read and "today" from the deviations service's own clock, so a flag equals what the Deviations page lists as open for the same state.

- **What raises a flag.** A binding of an ENABLED connection raises one `JIRA_DEVIATION` per OPEN LINE (1.12: a kernel deviation without a CURRENT acknowledgement of its own; an acknowledged line of the same binding raises nothing) at the deviation's severity, except `ESTIMATE_NOT_COMPARABLE` (the kernel's "a figure exists and cannot be compared" is a Deviations-page note, not a timeline warning). A stale line acknowledgement (`current = false`) is open again. A project also gets ONE `JIRA_MILESTONES` roll-up over its milestones that raised a flag (`count`, the worst severity among the OPEN lines). `PlanFlag` and `JiraLink` gained no member for this.
- **What does not.** A DISABLED connection (Q8a: its rows keep the `jira` link and its site with null dates, no flag, no bar and no roll-up contribution, so the page still sees the node as linked and can unlink it; its bindings also list on the Deviations page and still block their node), a fully acknowledged binding (it keeps its `jira` link so the bar stays), a clean binding, an unobserved one (link with null dates). A `gone` item raises `GONE` alone with null dates. Program and work-stream bindings are not folded in 1.3 (the programs tree rolls up the projects' flags).
- **The scope.** `DeviationScope` gained `levels` (the whole-plan ask reads project and milestone bindings only); a named node list matches a binding on ANY named node, a named EMPTY list names nothing. The roadmap and programs views ask for the whole plan, the project view for the project and ALL its milestones, the team view for no project and the team's milestones. The scoped computation equals the full one (`DeviationScopeNodesTest` pins it, including a parent issue bound outside the scope).
- **Cost.** About 45 us a binding in service time (the roadmap over 1,100 bindings: +50 ms; the team view over 301: +16 ms); numbers and a profile in `timeline.md` "Measured figures (1.3)"; the lean projection is a backlog item.
- **Proven by** `JiraFlagSourceTest` (the table: each kind, the roll-up, acknowledged, partly acknowledged, stale, disabled, noise, gone, the request shapes), `DeviationScopeNodesTest`, `TimelineJiraFlagsTest` (the four views through HTTP on one bound world, the overlay's additivity, the always-present members), `JiraFlagsScaleTest` (the sizes and the gates).

## The token's life

Encrypted at write (`FieldCipher`, `enc:v1:` envelope, a fresh nonce), write-only on the wire (`hasApiToken`), masked in every `toString` (`SecretToStringTest`) and absent from audit lines, logs and run
rows (`error_detail` is built URL-free - `Jira fetch failed: {code} ({status})`, as Flow's - and `clampErrorDetail` clamps it as the backstop). It is decrypted in memory only by three methods of `JiraConnectionService` (`readForTest` for the Test connection, `readForPeek` for Peek, `readForBind` for the bind; the two import routes and the run are further callers of `readForBind`, not further readers; the decrypt-or-null rule itself is `infra/crypto/UnreadableToken.kt`). `JiraTestRecorder` and `JiraMappingStore` (the Test result and the mapping document) never select or see it. A `PUT` with a
token rotates it, and a changed token, email, auth scheme or project-key set clears `last_tested_at/ok` (the last test judged the old ones); a blank token keeps the stored one; the site cannot be changed (`409`). At boot `EncryptedAtRest` wraps any legacy plaintext, and with
`DATA_ENCRYPTION_KEY_PREVIOUS` set re-encrypts every row (soft-deleted ones too; NULLs skipped), audited `crypto.reencrypted`. `docker compose up` and `:server:run` use different keys over one Postgres, so a
row may be unreadable: that is `TOKEN_UNREADABLE`, never a 500. **Deleting a connection sets the column to NULL** (the V21 CHECK allows that on a deleted row only).

## First real-site walk-through

Do this when a real site and token arrive. Use an account and a scoped or classic API token with read access to a handful of projects.

1. **Connect.** Administration → Jira → New connection: the real site URL (`https://<name>.atlassian.net`), the account email, the token, auth scheme `BASIC` first (`BEARER` if the site demands it), a few project
   keys (≤ 50). **Test connection** and read the rows top to bottom; the FIRST failed row is the cause.
   - `tenant_info` failed (everything after reads `SKIPPED`): the site URL is wrong, or `BLOCKED_HOST` (not a tenant host), or a network/DNS block (`outbound.blocked` audit event).
   - `myself` 401: the token or the auth scheme. `myself` ok but another row 401: a missing scope; the row's hint names it (a missing scope is a 401, not a 403).
   - `search` 400 or `INVALID_RESPONSE`: **A3** (issue-type ids in JQL); `projects` 400: **A8** (50 `keys`). Both were confirmed by hand on a real site (2026-11-08; not yet through Astrolabe's probes); the likeliest remaining surprise is a scoped token (unverified).
   - `project:<KEY>` `PROJECT_NOT_VISIBLE`: the token cannot see that project. No `issue` row: the search returned nothing.
2. **Read the discovery report** (the Mapping section; it exists only once a Test connection has been RECORDED, so a stored-connection test comes first, and mapping, Peek and bind all answer `409` until then): the counts, which field matched "Target start"/"Target end" and with what `schema.custom` (**A1**), whether a legacy Parent Link exists (**A2**), the
   Team and Story-points fields (**A7** if `fieldsTruncated`). Every "not found" is a decision for the mapping.
3. **Check the mapping defaults and save them** (or pick fields by hand); the levels list shows the type names per Jira level on this site. A site without Jira levels 2 and 3 (Initiative, Program need Premium) leaves the project and program levels unmapped by default: then only milestones can be linked until an admin maps them to levels that exist.
4. **Peek** one real epic (and, where the site has them, an initiative): the type, hierarchy level, parent key, the dates as plain `YYYY-MM-DD` (**A5**: a datetime field is refused), the estimate, the Team name. `raw` shows what the site sent.
5. **Bind** one node per mapped level to known issues: "Link to Jira…" on the project page for a project or a milestone (an owner or ADMIN), "Link a node…" in the connection page's Bindings section for a program (ADMIN). A wrong level reads `400` naming both levels. Then **Refresh now** (ADMIN) and read the run row: `observed`, `calls`, the error code; `rateLimited` and `backoffMs` are in `GET /integrations/sync/runs` and in the INFO log line, not in the table.
   Compare the Deviations page with the Jira UI for those items.
6. **Import** (only after steps 1 to 5 read right). A real import creates real plan rows, and nothing undoes it in one step (each node is deleted by hand), and program names are globally unique, so:
   - **Use a throwaway work stream** the first time (create one, with a throwaway owner), and a connection scoped to a small project (`projectKeys` narrows a larger connection); never a work stream with real data.
   - **Review the mapping first** (step 3): the import reads exactly the mapped levels, fields, unit and Team field, and a wrong level or no declared factor (a unit other than `DAYS` with no man-days per unit) shows up in the preview (rows skipped, a milestone's `ESTIMATE_NOT_CONVERTED`).
   - Administration → Jira → the connection → Bindings → **Import from Jira…** (or, as a work stream's owner, Plan → the stream's Operations → **Import from Jira…**, with the stream preset and the connection preselected or picked); pick the stream, an owner and, say, a default team; then **Preview** and read it before anything else: the totals, which rows are CREATE, BIND and SKIP and why. Expect renamed items to preview as new (above).
     Tick only what you want. **Assert the totals against what you expect** (how many Jira items at each level) before pressing Import; do not import on a hunch.
   - A lot of `NO_PARENT` rows: either the items have no parent at the level above (give a default program or project) or the site's `search/jql` entries do not carry `parent.fields.issuetype` (**A10**); a preview that takes minutes is the browse itself (pages of `jira.pageSize`, retries on 429; it stops at 170 s).
   - After **Import**, read the outcome (created, linked, skipped with reasons), open the project page (milestones dated, or created unscheduled where you do not manage the team), run **Refresh now** and compare the Deviations page. A second import must create nothing when everything was imported (`ALREADY_BOUND`; items left out, or whose plan item was deleted since, are offered again).
7. **When something fails:** the run row's `errorCode` (`FORBIDDEN_SCOPE`, `INVALID_RESPONSE`, `LIMIT_EXCEEDED`, `MAPPING_INVALID`, `TOKEN_UNREADABLE`, …); the `ch.nokillswit.sync` log lines (counts and codes
   only); the `jira.connection_tested` / `jira.sync_requested` audit events; `502 BUSY` on a bind means the permit pool was occupied (retry, or raise `JIRA_MAX_CONCURRENT_REQUESTS`).

8. **Leave it running** (1.3, after steps 1 to 7 read right): keep the connection at its 15-minute default for a day. Watch the status (Administration → Jira, or the telemetry panel's Sync section): **Current**, "next poll in N min", and the runs table gaining **Scheduled** rows with no one's name behind them; a token the site rejects must read **Failed** with its code and a doubling wait (one interval, then two, up to six hours), and a corrected token must poll at once. Then read the flags: the Jira flags on the roadmap and the project and team pages should name the same items the Deviations page lists as open, acknowledging one must silence its flag on all four pages, and the "Jira dates" bar must sit where Jira's own dates are. Compare the polled data with the Jira UI at the end of the day; a site's rate limits show as `RATE_LIMITED` run codes, in which case lengthen the interval.

9. **Coverage** (1.4, after steps 1 to 8 read right, with at least one bound program or project whose Jira item has children): after a day, compare the Deviations page's **Not in plan** (`UNLINKED_IN_JIRA`) and **Not in Jira** (`UNLINKED_IN_PLAN`) rows with the Jira board: every OPEN child of the bound issue that no binding covers must be listed by key (done children are not), every unlinked plan child by name. Then compare each epic chip's roll-up (`done/children · points pt`) with the epic's real child count, done count and story points in Jira, and open an epic whose children are all done: the **Children done** row must be there while the plan still runs. If no roll-up shows anywhere, the site's stories do not carry `fields.parent` (**A12**, look at the discovery's Epic Link marker) or sit past the page ceiling (**A11**, the `children census truncated` WARN); if `done` stays 0, **A13**; if points are missing, **A14**. The first run after the upgrade (or after the first bind) is a full read plus the children, and the child list is re-read once a day (`jira.censusHours`).

10. **The gone probe** (A15, after steps 1 to 5 read right): bind a milestone to a throwaway issue on the real site, run **Refresh now**, then delete that issue in Jira (and, separately, move one to a project outside the connection's keys) and run again. Expect the Deviations row to read "Deleted in Jira (or no longer visible to the connection's account)" for the deleted one and "Moved out of the connection's projects (Jira still has it)" (badge "Moved out of scope"; the wide "No longer readable in Jira: deleted, moved out of the connection's projects, or no longer visible to its account" is what a row Jira has not yet answered for reads) for the moved one, with `observation.goneReason == "MOVED_OUT"` on its binding, and `calls=` of the run to grow by one per gone binding Jira has not yet answered for (later runs send no probe for an answered one: `gone_probed_at` is set). If the moved issue reads Deleted too (Jira answered 404 by id), or a deleted one reads Moved out (200), A15 is wrong: record it in the ledger. "Moved out" is derived from the 200 alone (Jira has it, readable by id, absent from the scope listing), so an issue whose type changed during a full read, or one flagged by a false-empty sweep, can read "Moved out" too.

## Decisions on the overnight defaults

Proposed on 2026-11-06 and **kept by the user on 2026-11-07**; each is a one-place change if overturned: **D1** one Jira issue stays 1:1 across connections of the same site (the V21 index is per
