### Planning model

The binding reference for the planning domain as it is built (v0.2.0: people, permissions and dates, the plan structure, the roadmap ranking; v0.3.0: milestones; v0.4.0: dependencies; v0.5.0: team capacity periods, the team milestone order; the views, calendar, proposal and baselines follow in their sections below). The product intent and the user's domain
decisions are in `product.md`; the closing section keeps the standing design notes of the original sketch (everything in it is built).

## Conventions every planning table follows

SERIAL ids (unsigned `UIntIdTable` in Kotlin), epoch-millis `BIGINT` `created_at`/`updated_at`, `SoftDeletable` (`marked_as_deleted`), partial unique indexes over ACTIVE rows, one migration + checksum
pin per change (`persistence.md`, `conventions.md`), `DATE` columns through `infra/db/LocalDateColumn.kt`, wire dates ISO `YYYY-MM-DD` strings. Names are trimmed single-line text (control characters are
a 400), 1-100 characters; descriptions optional, at most 500.

## People (built — V10, v0.2.0)

- **Table `people`** (`people/PersonService.kt`, `SoftDeletable`): `id SERIAL`, `name VARCHAR(100) NOT NULL`, `email VARCHAR(254) NULL`, `user_id BIGINT NULL REFERENCES users(id)`,
  epoch-millis `created_at`/`updated_at`, `marked_as_deleted`. A person is NOT a login: `user_id` links the optional account (an external owner has none).
- **Constraints** (partial, active rows only, the V6 shape): `uq_people_email_active ON (LOWER(email)) WHERE email IS NOT NULL` (an optional email, unique when set) and
  `uq_people_user_id_active ON (user_id) WHERE user_id IS NOT NULL` (one active person per login). Names are NOT unique (two real "Anna Nowak"s). `409` wording lives in `ErrorHandling.kt`.
- **The link** (§ person-to-user): set by an ADMIN through `userId` on the person create/update bodies; must be an ACTIVE user (`400`), not linked to another active person (`409`). A soft-deleted
  user leaves the person and the link in place, inert (reads resolve the login through ACTIVE users and show it as unlinked; the caller's person is `people.user_id = caller AND people.active()`).
  Name and email edits never cascade between the user and the person — they are separate records, and the person's name is the display name on the plan. `person.link_changed` is audited only on change.
- **Teams**: `teams.manager_person_id` replaced `manager_user_id` (V10 backfilled one person per ACTIVE user managing an ACTIVE team, linked to that user; a soft-deleted manager stayed unset).
  `isActiveManager(teamId, userId)` = an active team whose manager is an active person with `user_id = userId`.
- **Delete**: `409` ("Person is still an owner or a team manager") while the person manages an ACTIVE team OR owns an ACTIVE work stream, program or project (V12): reassign first, so every active node's
  owner stays a valid active person. Reads are open to every authenticated user, emails included (the owner pickers need them); writes are ADMIN only (`authorization.md`).
- **Tests**: `PersonTest` (incl. the owner 409), `PersonMigrationTest` (V10's backfill on V9-era data in a scratch database), `TeamTest`, `TestPeople` (the fixture).

## Permissions and dates (built — V11 and the DATE column, v0.2.0)

- **`user_permissions`** (V11, `users/UserService.kt`): the GRANT set `(user_id, permission)`; `Permission { ROADMAP_EDITOR }` is the Kotlin whitelist (`users/User.kt`).
  `ROADMAP_EDITOR` lets its holder edit the global project rank (V13) and set ANY project's target window (the owners above a project may set the window without it).
  Set wholesale by `PUT /users/{id}/permissions` (ADMIN, audited `user.permissions_changed`), read per request by `UserService.hasPermission` — never a JWT claim, never cached
  (`authorization.md` "Roles vs permissions").
- **Dates**: Postgres `DATE`, day precision, through `infra/db/LocalDateColumn.kt` (`localDate(name)` → `Column<java.time.LocalDate>`; no date module dependency; the column type overrides Exposed's default-zone
  `java.sql.Date` write path so the calendar date is bound as-is — `persistence.md` "The DATE column idiom"). Wire format ISO `YYYY-MM-DD` strings; `infra/validation/Dates.kt` (`parseIsoDate` — years 1900–2999 —
  and `requireDateOrder`) is the one parser/validator, a migration `CHECK` the backstop. `LocalDateColumnTest` pins insert, update and WHERE under swapped JVM zones and the historical traps.

## The plan structure (built — V12, v0.2.0; `planning/`)

Hierarchy **work stream → program → project**; every node has an OWNER, a person of the people directory, REQUIRED (`owner_person_id NOT NULL`: ownership-scoped rights need an owner). A node's parent
is set at create and its update body carries none; it changes only through the two **move** endpoints (v0.3.0, below). Milestones hang under a project since V14 (below).

### The `plan_state` lock protocol and the 409 contract (`planning/PlanState.kt`)

`R2dbcDatabase.withPlanWrite { revision -> … }` = one transaction: `SELECT revision FROM plan_state WHERE id = 1 FOR UPDATE`, run the block, `UPDATE plan_state SET revision = revision + 1`. **Every
mutation of `work_streams`, `programs`, `projects`, `roadmap_entries` (V13), `milestones` (V14), `team_milestone_orders` / `team_order_state` (V17), `public_holidays` (V19) and the `baselines` registry with its frozen rows (V20) runs inside it** — people and teams are not plan state. (The Jira import's apply (1.2) is such a writer too: the ONE Jira write that takes `withPlanWrite`, after every HTTP call; it also takes the bind's advisory lock right after the plan lock — `persistence.md`.) A block that throws (404/409/400 found after the lock) rolls
back the bump with everything else, so a rejected write never moves the revision; a no-op PUT still bumps (conservative). Consequences the code relies on:

- **"Count the children, then delete" is race-free**: the delete counts ACTIVE children under the plan lock, so a concurrent child create (which holds the same lock) either commits first and the
  delete sees it (409) or waits. A parent-row `FOR UPDATE` would NOT do it — a child INSERT's FK check takes only `FOR KEY SHARE` (`persistence.md` "Row locks vs. FK locks").
- **Plain `FOR UPDATE` is justified** on `plan_state`: nothing references it by a foreign key and its key is never changed.
- **Owner validity is not covered by the plan lock** (people are not plan state): `requireActiveOwner` locks the owner's person row `FOR SHARE`, which conflicts with `PersonService.delete`'s `FOR NO KEY UPDATE`
  — a delete racing a node write either commits first (the write is a 400) or waits and then sees the node (409). Both halves are pinned in `PlanStateTest`.
- **Guard outside for ordering, re-guarded under the lock.** Read-before-guard resolves the chain and guards BEFORE `call.receive` (the 404 → 403 → 400 ordering), but a request can be held open after
  that (Netty's read timeout is only an idle-gap bound, `security.md` "Slow requests"), so the verdict is not trusted: inside `withPlanWrite` every node write re-reads the chain (`workStreamChain`/`programChain`/`projectChain`; missing = 404, nothing written),
  re-resolves the caller's person (`PersonService.lockedActivePersonIdOf`, `FOR SHARE` — a re-link or delete of that person waits) and re-runs `requireOwnerOrAdmin` /
  `requireTargetWindowEditorOrAdmin` (re-reading the `ROADMAP_EDITOR` grant in the same transaction); ADMIN short-circuits. A `ForbiddenException` there rolls back with no revision bump and is audited
  centrally as `authz.denied`. No lock cycle: person and team writers never take `plan_state`. `PlanStateTest` pins owner change, person re-link and grant revocation mid-request.
- **Views read the revision FIRST, then the rows, in one transaction** (no `REPEATABLE READ`): a row newer than the revision only makes a client PUT carrying that revision answer a conservative 409.
- The wholesale ranking PUT (V13) compares `expectedRevision` under the lock against the RANKING's own revision (`plan_state.ranking_revision`, V18 — not the plan revision) and answers `409` with `type = urn:astrolabe:problem:stale-revision` (below, "The global project rank"). Like a milestone's `schedule_revision` and a team's `team_order_state.revision` (V17), it is stamped with the new plan revision by the writes that change the thing it guards, so a plan write elsewhere never stales it; the plan revision stays the upper bound of each (a value above it is a view from the future).

**Designed, not built (v0.3 view ETags).** A view's validator must cover everything in its body, so it is `W/"p<plan revision>-n<max(people.updated_at, teams.updated_at)>-c<hash of the
caller's can-flags>"` (people/team renames change owner names without a plan revision; the flags make the validator per-caller). v0.2 offers no ETag. (Baselines, which record the `revision` they were taken at —
monotonic, so any later state orders against them — are built since V20, "Baselines" below.)

`POST /work-streams`; `GET/PUT/DELETE /work-streams/{id}`; `POST /work-streams/{id}/programs`; `GET/PUT/DELETE /programs/{id}`; `POST /programs/{id}/projects`; `GET/PUT/DELETE /projects/{id}`;
`PUT /projects/{id}/target-window`; `POST /projects/{id}/move`; `POST /programs/{id}/move`; `GET /views/plan`; `GET /views/programs`; and the ranking (below): `GET /views/roadmap`, `PUT /roadmap/ranking`. PUTs are full replaces (omitted optional = unset; `204`); creates answer `201` + `Location` + the record. **No paged lists** for
work streams/programs (the plan view is the read surface); `GET /projects` is the paged picker list since v0.4 (see "The picker lists" below). `WorkStreamResponse` etc. carry `ownerPersonId` +
`ownerName`; a project also carries `workStreamId`.

**The plan view** (`GET /views/plan`, any authenticated user; the documented view-endpoint shape exception of `list-endpoints.md`, bounded by the scale ≈5 streams / 20 programs / 100 projects):
`{revision, can{createWorkStream}, workStreams[]{…, can{edit, delete, createProgram}, programs[]{…, can{edit, delete, createProject, move}, projects[]{…, can{edit, delete, editTargetWindow, move, createMilestone}}}}}`, open work streams
first then closed ones, each level by name (case-insensitive, then id).

**Moves** (v0.3.0; `ProjectService.move`, `ProgramService.move`, bodies `{programId}` / `{workStreamId}`, `204`): a node changes parent only here. The caller must be ADMIN or own something ABOVE the node (its program's / stream's
owner — the node's own owner alone may not take it out of where it is) AND own something on the TARGET chain (the right to create a child there); both guards re-run under the plan lock against chains re-read there. A missing or
deleted target is a `400` on the body field, never a `404`. The write is one `UPDATE … SET program_id / work_stream_id` plus `updated_at` in a `withPlanWrite` (revision +1): a project's name must be free in the target program (the
partial index's `409`, "A project with this name already exists in this program"); program names are global, so a program move cannot clash. Milestones ride along (their FK is the project), the global ranking is untouched (it is by
project, not by place), and the program span / project view / roadmap are derived by joins, so every chain-derived read (`projectChainRow`, the guards, `GET /views/project/{id}`, the plan view) follows at once. A move to the current
parent is a no-op `204` for a caller who passes both guards: no `UPDATE`, no audit (the plan revision still bumps — the conservative rule). No `expectedRevision`: it sets a parent, it does not merge a client's view, and the guards
re-check the target anyway. The plan view carries `can.move` on every program and project (`PlanPermissions.canMove` = the source guard) and the SPA pairs it with the candidate's `can.createProject` / `can.createProgram`. A closed
work stream still takes children, so it is a valid target (`PlanMoveTest`).
A closed work stream still takes children, so it is a valid target.

### Authorization (the matrix in `authorization.md`)

ADMIN everything; ownership cascades down (an owner at ANY level of a node's chain acts on the node); a project's own owner edits the project but does NOT set its target window (ADMIN, an owner above
it, or a `ROADMAP_EDITOR` do); reads open to every authenticated user; creating a work stream is ADMIN only. Plan routes are **read-before-guard**: chain → 404 → guard 403 → body 400 → validate 400 → write.
Any owner on the chain, the node's own included, may reassign the node's owner (a hand-over; the ancestors can always take it back). The `can:{}` flags come from the pure kernel
`planning/PlanPermissions.kt`, which uses the SAME arithmetic as the guards (`authz/Guards.kt`); `PlanPermissionsTest` pins the agreement table-driven.

### Audit events (`observability.md`)

`work_stream.created/updated/deleted`, `work_stream.owner_changed`, `work_stream.closed` / `work_stream.reopened` (end-date transitions), `program.created/updated/owner_changed/deleted`,
`project.created/updated/owner_changed/deleted`, `project.target_window_changed` (start/end from/to), `project.moved` / `program.moved` (from/to parent; a no-op move emits nothing). Owner changes and window changes are their own trail lines (rights paths). The ranking adds `roadmap.ranked` (below).

## The global project rank (built — V13, v0.2.0; `planning/RoadmapService.kt`, `RoadmapRoutes.kt`)

One rank over ALL projects, not per program or work stream. **Table `roadmap_entries`** (`project_id INTEGER PRIMARY KEY REFERENCES projects(id)`, `position INTEGER NOT NULL CHECK (position >= 1)`,
`CONSTRAINT uq_roadmap_entries_position UNIQUE (position) DEFERRABLE INITIALLY DEFERRED`): one row per RANKED project, positions **dense 1..n**; a project with no row is **unranked**. It is a
**hard-delete table** (a pure position join rewritten wholesale — `persistence.md` "Soft delete"), so a project that leaves the rank leaves no row behind. `DEFERRABLE` is load-bearing: a swap of two
positions, and the renumber sweep below, are single statements an immediate unique check can reject mid-statement depending on physical row order; deferred, uniqueness is checked once at commit
(`RoadmapRankingTest` pins the swap, the sweep, the commit-time duplicate and the `CHECK`).

- **Ranking** (`PUT /roadmap/ranking`, body `{expectedRevision, projectIds[]}`; `200 {revision}`): **wholesale** — the listed projects get positions 1..n in the given order, every other project becomes
  unranked (omit one to unrank it). The SPA's "Rank" appends an unranked project at the END of the list (the user's choice; it is then moved like any other row) — to the server that is just a list one longer.
  Inside `withPlanWrite`, in this order: the grant re-check (`requireRoadmapEditorOrAdmin` again, the same TOCTOU rule as the owner guards: a revocation that landed while the request waited at the lock is a
  `403` with no bump) -> `expectedRevision` must not be below the RANKING's revision read under the lock (`plan_state.ranking_revision`, V18) nor above the current plan revision (**`409`**, `type = urn:astrolabe:problem:stale-revision`, nothing written; checked BEFORE the ids so a stale list
  that names a since-deleted RANKED project is the reload signal, not a `400` — an unranked project deleted under a held view moves no revision, so ranking it later is a `400`, which the web maps to a reload) -> every id must name an ACTIVE project (`400` "Unknown or deleted project ids: …") -> `DELETE FROM roadmap_entries` + one
  `insertRows`. Before the lock: `400` for a duplicated id ("projectIds must be distinct") or more than 1000 ids. **Every accepted PUT bumps the plan revision, even one that keeps the order** (a no-op PUT is
  still a plan write, the conservative rule of the lock protocol) **and stamps `ranking_revision` with the new plan revision** — which is also the `revision` the PUT answers. Concurrent PUTs carrying the same `expectedRevision`: the lock serializes them, the first wins and the second sees the stamped ranking revision —
  exactly one `200`, one `409` (`RoadmapRankingTest`, deterministic with the lock barrier). A plan write that does not touch `roadmap_entries` (a milestone, a dependency, a rename, a new project) moves only the plan revision: a held roadmap view stays current for the PUT.
- **Project delete keeps the rank dense**: `ProjectService.delete` calls `removeFromRanking(id, revision + 1)` in the SAME locked transaction as the soft delete — the project's entry is hard-deleted and
  `UPDATE roadmap_entries SET position = position - 1 WHERE position > ?` closes the gap (one statement, which is why the constraint is deferred) and stamps `ranking_revision` with the delete's plan revision (positions moved: a roadmap view held across the delete is stale). An unranked project is a no-op, no stamp. Work stream and
  program deletes need no hook: they are refused (`409`) while an ACTIVE project exists.
- **The view** (`GET /views/roadmap`, any authenticated user; the view-endpoint shape exception, bounded by ~100 projects): `ranked[]{position, project}` by position, `unranked[]` by name (case-insensitive, then id). `revision` is the RANKING's revision (V18), read
  FIRST, then the rows, in one transaction (the plan view's protocol); a plan write elsewhere does not move it. `can.editRank` comes from `PlanPermissions.canEditRank` (ADMIN or a `ROADMAP_EDITOR` holder, the same arithmetic as the guard;
  `PlanPermissionsTest` pins it, `RoadmapRankingTest` checks it against the real PUT). Since v0.6.0 the project rows and the document carry more: the next section.
- **Authorization**: guard-before-read (the route addresses no node) — `requireRoadmapEditorOrAdmin` runs FIRST, before the body, so every other caller (an owner without the grant included) gets a uniform
  `403` even for a malformed body; `authorization.md`.
- **Audit**: `roadmap.ranked` (byUserId/revisionFrom/revisionTo/orderFrom/orderTo — the ranked project ids as comma-joined text, before and after) on every accepted PUT; a rejected PUT (`409`, `400`) emits nothing,
  a `403` is the central `authz.denied`.
- **Tests**: `RoadmapRankingTest` (guard matrix, revocation under the lock, stale `409`, the `400`s, permutations -> dense rows, delete first/middle/last, the deferrable constraint, the same-revision race, the
  view, `can.editRank` vs. the guard, audit; since V18: a plan write elsewhere — rename, create, schedule, dependency — does not stale a ranking PUT, a ranking write or a ranked project's delete does, an unranked delete does not, a revision above the plan's is stale, and a PUT queued behind a plan write at the lock still passes).

## The roadmap view (built, v0.6.0; `planning/RoadmapKernels.kt`, `RoadmapViewRows.kt`, `RoadmapViewService.kt`)

`GET /views/roadmap` is `{revision, can{editRank}, teams[], ranked[]{position, project}, unranked[], links[]}`; no migration (every figure is derived per request, nothing is stored). The service is ONE read-only REPEATABLE READ
transaction (`SNAPSHOT`): the ranking revision first, then four row sets (the active projects with their program, work stream and the three owner ids of their chain; `roadmap_entries`; the active milestones with their team; the active links), then
the pure `RoadmapKernels` ONCE. A **project row** adds to the old fields: `ownerPersonId`, `rankPosition` (null = unranked), `teamIds` (the distinct teams of ALL its active milestones, scheduled or not, ascending), `span` (the derived span, `SpanKernels.derivedSpan`
over its scheduled milestones; null when none), `drift` (`SpanKernels.drift` against the target window), `flags[]` and `can{editTargetWindow}` (`PlanPermissions.canEditTargetWindow` on the chain read in the same statement as the row; `RoadmapViewTest` checks it
against the real `PUT /projects/{id}/target-window` for every kind of caller). `teams[]` = the active teams with a milestone in the plan, by name (the team filter's options).

- **Flags** (`PlanFlag{kind, severity, days, teamId, otherProjectId}`, raised ON a project, WARNING first, then kind, team, other project). Drift: the end later than the target end = `DRIFT_END_LATE` WARNING (`days` = the delay); a start later than the target start =
  `DRIFT_START_LATE` INFO; an end ahead of the target = `DRIFT_END_EARLY` INFO; an early start or an on-target edge raises nothing; no window or no span, no drift flags.
- **Jira flags and links (1.3; `ExternalFlags.kt`, `Deviations.kt`).** `PlanFlag` gains `deviation: Deviation|null` and `count: int|null` (both always present), `FlagKind` gains `JIRA_DEVIATION` and `JIRA_MILESTONES` (declared last, after the calendar kind `NO_WORKING_DAY`, a milestone row's own flag, see "The calendar" decision D2; so they sort after the existing kinds within a severity; `FLAG_ORDER` breaks the remaining tie by the deviation's kind, the kernel's own order). A project row gains `jira: JiraLink|null` (`{bindingId, connectionId, issueKey, start, end, rollup}`: the observed dates, null when never observed or `gone`; `rollup` (1.4, always present) is `JiraRollup {children, done, points|null, observedAt}`, a live milestone link's census figure from the deviations view's own loader, null on a project link, through a DISABLED connection, beside a `gone` issue and with no mirrored child) and each of the four views `jiraSites[]` (`{connectionId, siteUrl}` once per document: the client builds `siteUrl + "/browse/" + issueKey`). The two kinds, both raised by an OPEN binding only: **`JIRA_DEVIATION`**, ON the node the binding sits on, one per deviation of the kernel's list at the deviation's severity, carrying the `deviation` (a project's on its roadmap row and in `ProjectView.project.flags`, a milestone's on its row of the project and team views; `days`, `teamId` and `otherProjectId` stay null, the detail holds the days), and **`JIRA_MILESTONES`**, ON a project, ONE roll-up over its milestones that raised at least one flag: `count` = how many such milestones, severity = the worst among them. Never one flag per milestone on the roadmap; the detail lives on the project view's rows. **(1.9) the team half:** `ExternalFlagRequest.teamId`, `ExternalFlags.teams` (`TeamExternal{flags, ranges}`, `FlaggedRange{start, end, severity}`), `CompositeExternalFlagSource` merging the Jira and Flow sources (per node the first link and every source's flags in `FLAG_ORDER`; per team the flags and ranges; the sites distinct), `FlagKind.FLOW_CAPACITY` and `flow/FlowFlagSource` (the open capacity rows of an ENABLED connection: ONE roll-up flag and one day range per row; `flow-sync.md` "Deviations"); only the team view asks (`teamId`), so the other three views are byte-identical.
  **The fold rule** (`JiraFlagSource`, the Jira implementation of `planning`'s `ExternalFlagSource`, wired by `infra/db/Database.kt`; `planning` names no `jira` package): a binding raises one flag per OPEN LINE - a kernel deviation whose own acknowledgement is not CURRENT (1.12, per line: an acknowledgement that went stale raises again, an acknowledged line of the same binding raises nothing; `PlanFlag` and `JiraLink` gained no member); `ESTIMATE_NOT_COMPARABLE` never raises a flag; a binding through a DISABLED connection keeps its link and its site with null dates but raises no flag and adds nothing to a roll-up (the node still reads as linked, so it can be unlinked and never gets a second link; the Deviations page lists it too); a `gone` item raises its `GONE` WARNING alone and its dates are null; an unbound plan answers `jira: null`, `flags` without the Jira kinds and `jiraSites: []`. A fully acknowledged binding keeps its `jira` link (the bar), it only stops raising flags. The source is asked INSIDE each view's `READ ONLY REPEATABLE READ` snapshot, right after the calendar (the roadmap and programs views through `loadRoadmapSnapshot`, which the baseline capture and comparison call WITHOUT a source), and runs the deviations view's own `computeInTransaction` scoped to the requested nodes, so the flags equal the Deviations page's open lines for the same state. The project and team views name their milestones (`ExternalFlagRequest`: the project view the project and ALL its milestones, the team view no project and the team's milestones; a project's roll-up is exact only when all its milestones are named, so the team view carries none). The `?baseline=` overlay stays additive (the new members are in both documents).
  **1.4 kinds.** `DeviationKind` gains `UNLINKED_IN_JIRA` (WARNING), `UNLINKED_IN_PLAN` and `CHILDREN_DONE` (INFO) and `DeviationDetail` gains `count: int|null`; they fold into `JIRA_DEVIATION` flags like every other kind (`jira-sync.md` "Deviations").
- **Rank inversion (user decision, 2026-11-01: adjacent pairs per team).** Only RANKED projects carry it, and the flag lives on the LOWER-ranked project B (`otherProjectId` = the higher-ranked A). `startOn(T, p)` = the earliest STORED `start_date` over p's
  scheduled milestones on team T (calendar days, not working days). For each team T, order the ranked projects with scheduled work on T by rank; flag B against its immediate predecessor A on T when `startOn(T, B) < startOn(T, A)`: a `RANK_INVERSION` WARNING
  with `teamId = T`, `days = startOn(T, A) - startOn(T, B)`. A tie is no inversion; a project without scheduled work on T is not on T's list (it neither carries a flag nor separates a pair); a chain A > B > C all inverted reads as two flags (B against A, C against B),
  so every inversion is reported once per (pair, team) without the all-pairs flood (184 warnings on the 80-project sample plan, against 1,038 for all pairs). The INFO variant is the same rule over the OVERALL rank order: each pair of adjacent ranked projects
  (among those that have a derived span) that shares NO team with scheduled work and whose B span starts strictly before A's is a `RANK_INVERSION` INFO (`teamId` null, `days` between the span starts). An unranked project never carries an inversion flag (no rank to invert).
- **Links.** `links[]` rolls the ACTIVE dependencies up per ORDERED pair (predecessor project, successor project), ordered by that pair. Each end resolves to its project (a milestone's own, a project itself) and span (the milestone's dates, the project's derived span);
  a link inside one project is skipped. The pair's `direct` is its PROJECT-to-PROJECT link (`{id, type, lagDays, check}`, at most one per ordered pair by the partial unique index), every other link (a milestone on either end) counts in
  `milestoneLinks{count, violated, unscheduled}`; each is checked like the project view's (`DependencyKernels.check`, working days). Both directions between two projects are two entries.
- **The chain toward a picked project (1.7; `RoadmapCriticalPath.kt`).** `GET /views/roadmap?criticalPath=N` adds `criticalPath{projectId, projects[], pairs[]}` (`@EncodeDefault(NEVER)`: the document is byte-identical without the parameter, `RoadmapViewTest` compares it with the parameter's document minus the key). N names an ACTIVE project of the snapshot, else a plain `400` "Unknown or deleted project id: N" (a repeated or malformed value is a plain `400` too, a blank one means absent, and with `?baseline=` the baseline's own errors, the typed `unknown-baseline` included, are answered first; ids are no secret, the page clears its own pick). `loadRoadmapSnapshot` keeps the milestone and link rows it read (`RoadmapSnapshot.facts`/`linkFacts`) and `CriticalPathKernels.analyse(N, …)` runs on those very rows: no second read, no new statement, the project page's rule over the whole graph on the planned dates (the roadmap's root and rows also require the program and the work stream active, which cannot differ from the project page's on a live database: a program delete is refused with 409 while it has active projects and a work stream delete while it has active programs, so an active project always has an active program and stream). The pure `RoadmapCriticalPathKernels.rollUp` folds the result to the roadmap's grain: `projects[]` = the OTHER projects with an upstream milestone or a linked project entity (N is implied: critical, slack 0), each with the least `slackDays`, `critical` when any entity is, the fewest `hops`, ordered by hops, slack, id; `pairs[]` = the ordered (predecessor, successor) project pairs holding at least one link of `criticalDependencies` (a link inside one project yields none; a pair with a direct link and several milestone links is critical when ANY is: the per-link truth stays on the project page; the web marks the pair's direct AND bundle arrows). A target with nothing scheduled answers both lists empty; the parameter combines with `?baseline=` (independent blocks) and `RoadmapCriticalPathTest` (pure) pins the roll-up.
- **Roll-up.** `RoadmapKernels.flagCounts` (warnings, infos over a set of flags) is the kernel half of the program/work-stream roll-up of the programs view (below); since 1.3 a program's and stream's counts include the projects' Jira flags (a `JIRA_DEVIATION` counts once per deviation, a `JIRA_MILESTONES` once).
- **Tests.** `RoadmapKernelsTest` (pure: the drift table, the inversion rule incl. chains, ties, unranked, two teams, the INFO; the link aggregates; the counts), `RoadmapViewTest` (the wire, a flag of each kind, teams, direct/rolled-up links, the deletion, `can` vs. the real PUT, the 401, `?criticalPath=`).

## Milestones (built — V14, v0.3.0; `planning/Milestone*.kt`)

The fourth level, under a project: a **name**, an optional **description**, **exactly one team** and a **man-day estimate**, **no owner**, and an optional inclusive **start/end** (null = *unscheduled*, the Unscheduled tray).

- **Table `milestones`** (`MilestoneService.Milestones`, `SoftDeletable`): `id SERIAL`, `project_id → projects`, `team_id → teams` (neither with an `ON DELETE` rule: projects and teams are only soft-deleted), `name VARCHAR(100)`, `description VARCHAR(500)`,
  `estimate_md NUMERIC(8,2) NOT NULL CHECK (>= 0)` (`persistence.md` "The NUMERIC column idiom"), `start_date`/`end_date DATE NULL` (`ck_milestones_schedule`: both or neither; `ck_milestones_schedule_order`: end ≥ start),
  `pinned BOOLEAN NOT NULL DEFAULT FALSE` (V25, on the wire; `ck_milestones_pinned_scheduled`: a pin needs dates), `schedule_revision BIGINT NOT NULL` (internal, never on the wire), epoch-millis `created_at`/`updated_at`, `marked_as_deleted`. Names are unique per project among ACTIVE rows, case-insensitively
  (`uq_milestones_project_name_active`, 409 "A milestone with this name already exists in this project"; "Discovery" recurs across projects).
- **Two audiences, two routes.** The **plan fields** (name, description, team, estimate) are written by the owner chain of the project — the project's own owner included — or ADMIN (`POST /projects/{id}/milestones`,
  `PUT`/`DELETE /milestones/{id}`; a team manager who owns nothing on the chain gets 403). The **dates** are written ONLY by `PUT /milestones/{id}/schedule` (and, with the same manager rule, the batch accept, the cross-team accept (1.8) and, since 1.2, the Jira import's apply), whose guard is `requireTeamManagerOrAdmin` against the milestone's STORED
  team: the manager of that team or ADMIN — **never the project's owner** (the product rule of this increment; `MilestoneScheduleTest` "the project owner cannot schedule"). Reads (`GET /milestones/{id}`) are open to every authenticated
  user and 404 when the milestone or any ancestor is gone. Everything is read-before-guard and the guard is re-run under the plan lock (`authorization.md`); the schedule PUT's full order is **404 → 403 → body/validation 400 → lock → 404 (re-read) → 403 (re-guard) → 409 stale**.
- **A new milestone is ALWAYS unscheduled**: the create body carries no dates, for every caller including ADMIN (one shape, one matrix; dates enter only through the schedule PUT, the batch accept or the Jira import's apply, which inserts the milestone unscheduled and dates it in the same plan write only where the caller manages its team).
- **Estimate**: a JSON number (`estimateMd: Double`, `type: number, format: double, minimum: 0`), validated server-side: finite, `0 <= x < 1_000_000`, at most two decimals — 400 "Estimate must be a non-negative man-day figure with at
  most two decimals" — so the stored value is exactly the sent one. Zero is allowed (a zero-effort checkpoint). No `multipleOf` in the spec (float `multipleOf` is unreliable in validators).
- **Dates** are inclusive: `[start, end]`, end ≥ start, a one-day milestone has `start == end` (the rule every dated record follows, `Dates.kt`). The schedule body is `{expectedRevision, startDate, endDate}` with both dates nullable,
  **both or neither** (400 otherwise); **the null pair unschedules** (same guard — there is no separate unschedule operation). The span must contain at least one Monday–Friday day (400 "A milestone must cover at least one working
  day"; `WorkingCalendar.containsWorkingDay`, `infra/time/WorkingCalendar.kt`). **Two checks, one message (v0.7 C3, decision D2):** `validateSchedule` (route, before any lock) keeps the calendar-free weekend-only rule; `MilestoneService.schedule` then re-checks the span against the CURRENT holiday calendar (`loadWorkingCalendar()`, read under the plan lock), **after the guard re-run and before the stale check**, so a span of only holidays (and weekend days) is a 400 with the same message. The order stays 404 → 403 → 400 → lock → 404 → 403 → **400 (holiday-only)** → 409 stale. The null pair (unschedule) has no span to check. A milestone that LATER loses its last working day to a new holiday keeps its dates (a holiday write never touches a milestone): it stays scheduled in every view, covers no working day (no load, no WIP, a zero-length point in the dependency check), and cannot be written back to the same span. **Since 1.10 the project and team views mark it:** each SCHEDULED milestone row carries a `NO_WORKING_DAY` WARNING flag (`FlagKind`, declared after `RANK_INVERSION`; every other `PlanFlag` member null) raised by the pure `MilestoneFlagKernels.noWorkingDay(span, calendar)` from the view's OWN `WorkingCalendar` inside its snapshot (nothing stored, no migration; the roadmap and programs views, the tray and the weeks strip carry nothing); `withExternal` merges the row's own flags with the external ones in `FLAG_ORDER` instead of replacing them.
- **Per-milestone optimistic concurrency** (`schedule_revision`). It holds the plan revision at which THIS milestone's schedule was last written (`revision + 1` inside `withPlanWrite`, which hands the block the OLD revision; also set at
  create). The schedule PUT, under the lock, in this order: the chain is re-read (missing = 404, nothing written) → the guard against the stored team (a manager revoked meanwhile is a **403, not a 409**) →
  `stored.schedule_revision > expectedRevision`, or `expectedRevision` above the current plan revision (a view from the future), is a **409** `type = urn:astrolabe:problem:stale-revision` (nothing written, no bump) → the write. A negative `expectedRevision` is a 400 before the lock. The client sends the view's `revision` and adopts the `revision` the PUT answers
  (`ScheduleResponse{revision}`). So a 409 happens only when THIS milestone moved after the client's view was read; unrelated plan writes (another team's drags, a rename elsewhere, a plan-field edit or team change of this milestone)
  never stale a drag. Every accepted PUT bumps the plan revision, even a no-op one (the conservative rule); the batch schedule (built, v0.8; below) reuses the same per-milestone check.
- **The batch schedule (built, v0.8.0 C3; `TeamSchedule.kt`, `TeamScheduleService.kt`, `TeamScheduleRoutes.kt`).** `POST /teams/{id}/milestone-schedules`, body `{expectedRevision, items: [{milestoneId, startDate, endDate}], scopeHash?}` (the scope check: "The auto-proposal"): each item is the single PUT's body (both dates or neither, the null pair unschedules, inclusive, end ≥ start, a working day inside) and the batch is "N schedule PUTs in ONE plan write under the TEAM's guard" — the accept of an auto-proposal. A `POST`, not a `PUT`: unlisted milestones keep their dates. `200 {revision, accepted: [id…], skipped: [{milestoneId, reason}]}` in request order, `reason ∈ STALE | GONE | NOT_ON_TEAM | NO_WORKING_DAY` (Flow's preview-then-apply `{created, skipped}` idiom, user answer Q4: a stale item is skipped and the rest are written).
  The order, verbatim from the order PUT then the schedule PUT per item: team active ?: 404 → `requireTeamManagerOrAdmin` 403 → body → **whole-batch 400s before the lock, for client bugs** (negative `expectedRevision`, no items, more than 1000, a milestone twice, an item failing `validateSchedule`: one date only, shape, order, a weekend-only span; the message names `items[i]`) → `withPlanWrite`: team re-read + locked `FOR SHARE` (404) → the manager guard again (403, nothing written, no bump) → `expectedRevision` above the plan revision → **409 `stale-revision` for the WHOLE batch** (a view from the future is never a state the server produced) → only with a `scopeHash`: **409 `stale-scope` for the WHOLE batch** (v0.9 C4; a changed holiday dictionary refuses only when it changes an accepted date, 1.13.1: "The scope check") → the working calendar read once → per item in body order the FIRST of: no ACTIVE milestone with the id — in `milestoneChain`'s sense, its project, program and work stream active too — (`GONE`; an id that never existed too) → the milestone's STORED team is not the path's team (`NOT_ON_TEAM`: a team change keeps `schedule_revision`, so it is not caught by the revision, and a milestone moved to another team is no longer this manager's to schedule) → a span without a working day of the CURRENT holiday calendar (`NO_WORKING_DAY`, decision D2: a holiday added since the proposal; the unschedule pair is exempt) → `schedule_revision > expectedRevision` (`STALE`: THIS milestone was written after the view; unrelated plan writes never stale an item) → the accepted items are then written together by multi-row `UPDATE start_date, end_date, schedule_revision = revision + 1, updated_at … FROM (VALUES …)` statements.
  **ONE bump for the batch**, whatever was skipped — an all-skipped batch bumps too (the lock was taken and the write ran, the conservative rule of a no-op single PUT); the answered `revision` is `revision + 1` and is every written item's new `schedule_revision`, so it is the next `expectedRevision` of a single PUT or a second batch. A skipped item never rolls the others back. An item equal to its stored span is accepted (and stamped) but audits no `milestone.scheduled`. No cycle check, no order change, no `team_order_state` touch. Audit: `milestone.scheduled` per changed item + one `team.schedule_batch_applied` (`observability.md`). Tests: `TeamScheduleBatchTest`, `PlanStateTest` ("a batch schedule bumps…"), `TeamViewTest` (`can.schedule` vs the batch POST), `MilestoneScheduleTest` ("a single PUT after a batch…").
- **The pin (built, V25, 1.7 C6; `MilestoneService.pin`, `MilestoneRoutes.kt`).** "Keep this one": a pinned milestone is FIXED for the team's auto-proposal (its dates stand, its load is booked, its dates bound its successors; "The auto-proposal" below). The user's answers: stored (Q4a), advice and not a lock (Q5a), the schedule write's audience (Q6a). `PUT /milestones/{id}/pin` `{pinned: boolean}` → `200 {revision}` (`ScheduleResponse`), the order of the schedule PUT: milestone chain ?: **404** → `requireTeamManagerOrAdmin` against the STORED team **403** (the project's owner is not enough; **no new `can` flag**: `can.schedule` governs it) → body **400** (`pinned` required) → `withPlanWrite` → chain re-read 404 → the guard again with `lockedIsActiveManager` 403 → pinning a milestone **without dates** is a **409** `urn:astrolabe:problem:milestone-unscheduled` (`MILESTONE_UNSCHEDULED_PROBLEM`; unpinning one is a harmless no-op) → `UPDATE pinned, updated_at`. **No `expectedRevision`** (an idempotent flag; what guards an accept against a pin flipped meanwhile is the proposal's `scopeHash`), **`schedule_revision` untouched** (a pin never stales a drag), the plan revision bumps ONCE like any plan write, a no-op included. A drag or the schedule dialog still moves a pinned milestone and **a reschedule keeps the pin**; **an unschedule clears it in the same write** — in EVERY writer of the dates: `MilestoneService.schedule` (the null pair sets `pinned = FALSE`), `writeSchedules` (the batch accept's and the Jira import's multi-row `UPDATE`: `pinned = pinned AND v.s IS NOT NULL`; the import only dates milestones it just inserted, so it never clears one) and the insert (dates NULL, unpinned); the CHECK turns a missed writer into a 500, never a pinned unscheduled row. A team change and a plan-field edit keep the pin with the dates. `pinned` rides `MilestoneResponse`, `MilestoneListItem`, `ProjectMilestone` and `TeamMilestone` (required). Audit: `milestone.pinned` / `milestone.unpinned` on a change only; the clear is `milestone.unpinned` with `reason = UNSCHEDULED` (`observability.md`). Tests: `MilestonePinTest` (the guard matrix, 404 → 403 → 400/409 order, idempotence, no stale, clear-on-unschedule through the PUT, the batch and the shared writer, the CHECK, the held-request re-guards), plus the clear cases in `MilestoneScheduleTest` / `TeamScheduleBatchTest`, `PlanStateTest` (a pin bumps by one) and `TeamScheduleScopeTest`.
- **The re-guard locks.** `TeamService.lockedIsActiveManager` takes `FOR SHARE OF teams, people` (not the user row), so a manager change or a re-link of the manager's person either commits first (403) or waits (`persistence.md`).
  The team id the guard checks is the milestone's STORED team re-read under the lock (`milestoneChain`), never a body field.
- **A team change keeps the dates.** `PUT /milestones/{id}` with another `teamId` (an ACTIVE team, else 400 "Unknown or deleted team ids: N", locked `FOR SHARE`) leaves `start_date`/`end_date`/`schedule_revision` untouched: the new team's
  manager inherits the bar and may move or unschedule it — nothing but the manager/ADMIN ever moves a bar. It is its own audit line (`milestone.team_changed`: it changes WHO may schedule — a rights path).
- **Deletes.** A milestone delete is a soft delete under the plan lock (the name is freed). **A project delete cascades**: its ACTIVE milestones are soft-deleted in the same locked transaction (`project.deleted` carries
  `milestoneCount`), so a project with milestones deletes without a 409 (it has no children with their OWN owners). **A team delete is 409 "Team still has milestones"** while an ACTIVE milestone names it (counted under the team row lock).
- **API** (tag `plan`): `POST /projects/{id}/milestones` → 201 + `Location`; `GET`/`PUT`/`DELETE /milestones/{id}`; `PUT /milestones/{id}/schedule` → `200 {revision}`; `PUT /milestones/{id}/pin` → `200 {revision}` (V25, above); `POST /teams/{id}/milestone-schedules` → `200 {revision, accepted, skipped}` (the batch, v0.8); `GET /views/project/{id}` (below); `GET /milestones` is the paged picker list since v0.4 ("The picker lists" below). ## Dependencies (built — V15, v0.4.0; `planning/Dependency*.kt`, `Problems.kt`)

A link between two time points of the plan, each end a **milestone or a project**, within or across projects. Built on the recommended defaults of the v0.4 plan's open questions (the user reviews them; `product.md`).

- **Table `dependencies`** (`DependencyService.Dependencies`, `SoftDeletable`): `pred_milestone_id | pred_project_id` and `succ_milestone_id | succ_project_id` — real nullable FKs, `num_nonnulls = 1` per side (`ck_dependencies_pred/succ`) —
  `type VARCHAR(2)` (`ck_dependencies_type`: FS/SS/FF/SF), `lag_days INTEGER` (`ck_dependencies_lag`: -365..365 **working days**, negative = a lead), epoch-millis `created_at`/`updated_at`, `marked_as_deleted`. `ck_dependencies_not_self` forbids the same id on
  both sides (a NULL comparison passes a CHECK, so the mixed milestone-to-project cases pass). **`uq_dependencies_pair_active`**: one ACTIVE link per ORDERED pair of endpoints, whatever its type (`NULLS NOT DISTINCT` — the unused id column of each side is NULL
  and must still collide — and partial over ACTIVE rows, so a deleted link frees the pair); the 409 wording "These two endpoints are already linked" is in `UNIQUE_CONSTRAINT_DETAILS`. The service widens it to **at most one ACTIVE link per UNORDERED pair** (an index cannot: it is over the ordered columns): under the plan lock, before the insert, an active link on (successor, predecessor) answers the same 409 (see the cycle rule). A link's TYPE and LAG are edited in place (`PUT /dependencies/{id}`, below); its ENDS never are (another end = delete + add).
  No `ON DELETE` rules: milestones and projects are soft-deleted only and their deletes cascade here in the same transaction.
- **The successor is the constrained party.** In all four types the SUCCESSOR is the side the constraint binds (FS: it starts after the predecessor ends; SS: starts after it starts; FF: ends after it ends; SF: ends after it starts), so the link is a plan field of
  the successor and **the SUCCESSOR's project chain authorizes it** (`authorization.md`): `POST /projects/{id}/dependencies` (the successor must be project `{id}` itself or one of its ACTIVE milestones, else 400), `PUT /dependencies/{id}` and `DELETE /dependencies/{id}`. The predecessor must
  merely be an ACTIVE milestone or project (400 "Unknown or deleted milestone ids: N" / "… project ids: N" on the body); its owner is asked nothing — a link never moves a date. A team manager as such has no say. Reads are open to every authenticated user.
- **Cycle rule (`DependencyGraph.kt`, pure).** The graph's nodes are `START(x)` and `END(x)` of every milestone and project; edges are `START(x) → END(x)`, containment `START(project) → START(milestone)` and `END(milestone) → END(project)`, and one edge per
  dependency (`X(pred) → Y(succ)`: FS `END→START`, SS `START→START`, FF `END→END`, SF `START→END`). Without dependency edges it is a DAG, so a new edge `u → v` closes a cycle **iff `v` already reaches `u`**: the create loads every active milestone's containment
  and every active dependency (two statements, bounded by the plan's scale) and runs one iterative DFS with parent links, **under the plan lock** (two racing inserts cannot both pass). **ANY** directed cycle is refused, lags ignored: the reverse of an existing
  pair whenever the two links close a loop (FS/FS, SS/SS, ...), a zero-lag SS/SS pair, `m FS p` and `p FS m` for `m` inside `p`, a three-entity loop across projects (a link between two PROJECTS also forbids any milestone-level link the other way across them). `p SS m` / `m FF p` inside one project are redundant with containment and
  allowed (and some redundant containment links, `p SS m` with a positive lag when `m` is `p`'s earliest milestone, `m FF p` likewise for its latest, are accepted but can never be satisfied: the check will always show them violated). A reverse pair that closes NO
  loop (`a SS b` + `b FF a`, `a SF b` + `b SF a`) is not a cycle, but the one-link-per-unordered-pair rule refuses it with the plain "already linked" 409. A self-link is a 400, not a cycle. The invariant "every active row set is acyclic" is what the v0.7 critical path (built: `CriticalPathKernels` reuses this time-point vocabulary and adds the values and offsets, see "The critical path") and the v0.8 scheduler rely on.
- **The 409 names the cycle as data.** `type = urn:astrolabe:problem:dependency-cycle` (`DEPENDENCY_CYCLE_PROBLEM`, beside `STALE_REVISION_PROBLEM` in `Problems.kt`), `detail` "Adding this dependency would close a cycle: A → B → A", and an RFC 7807 extension member
  **`cycle`**: `[{kind: MILESTONE|PROJECT, id, name}, …]` — consecutive time points of one entity collapsed, the NEW link's predecessor first and repeated last. `ConflictException.cycle` carries it, `ProblemDetail.cycle` serializes it (omitted when null, so every other
  problem is unchanged). The SPA renders the path in the UI language instead of sniffing text. A duplicate ordered pair is the plain index 409. A refused write leaves no row and no revision bump.
- **Editing a link in place (`PUT /dependencies/{id}`, `DependencyService.update`).** Body `DependencyUpdateRequest{type, lagDays}`, **both required** (a PUT replaces the editable part, like every other PUT of the plan — `PUT /projects/{id}`, the target window; a missing field is a 400, there is no partial body) with the create's lag bounds (`validateDependencyUpdate`, shared `requireLagInRange`, -365..365). The ENDS are not editable. Answers **204** with no body (the precedent of the plan's metadata PUTs; the SPA refetches the view, whose `check` is the answer). **Cycle:** only a changed TYPE moves an edge (a lag-only edit skips the check), so then the time-point graph is loaded **without this link's old edge** (`loadTimePointGraph(excludingDependency = id)`) and the new edge `DependencyEdge(pred, succ, newType)` is checked with the same `cycleClosedBy` under the same lock: `409 urn:astrolabe:problem:dependency-cycle`, `cycle` as data (predecessor first, repeated last), detail "**Changing** this dependency would close a cycle: …" (the create says "Adding"), nothing written, no bump. Example: `p SS m` (redundant with containment, allowed) → `p FS m` loops through `m` inside `p`. No duplicate/reverse-pair check: the unordered pair is already this link's alone. **Revision:** every accepted PUT bumps the plan revision once, a no-op (same type and lag) included — the conservative rule; a no-op writes no row (`updated_at` stays) and emits no audit. **Write order:** route `dependencyChain` 404 → `requireOwnerOrAdmin` 403 → body 400 → `update`: pure validation again → under the lock the chain re-read (404) and the guard again (403) → stored row read → cycle (409, type change only) → `UPDATE`.
- **Endpoints on the wire** (`DependencyResponse`, `resolveEndpoints` in `DependencyEndpoints.kt`): both ends resolved to `{kind, id, name, projectId, projectName, teamId?, teamName?, startDate?, endDate?}`; a milestone carries its own project and team, a project
  (`projectId` = its own id, no team) carries its **derived span** — `SpanKernels.derivedSpan` over its scheduled ACTIVE milestones, null while none is scheduled — never its target window.
- **Working days.** `infra/time/WorkingCalendar.kt` is the pure working-day calendar (Flow's `WorkingDayIndex` ported over the closed-form Monday–Friday arithmetic): `isWorkingDay`, `workingDayIndex`, `workingDayOfIndex`, `nextWorkingDayOnOrAfter`, `previousWorkingDayOnOrBefore`, `plusWorkingDays`, `containsWorkingDay`, `workingDaysBetween`, `holidayName`. The index is monotone, flat over a weekend AND a holiday (both collapse onto the working day before), Friday→Monday = +1. The
  holidays are a constructor parameter (date → name), never read from the database by the kernel; `WorkingCalendar.MON_FRI` is the calendar without holidays (kernel tests and pure vectors). **Loading (v0.7 C3):** every consumer takes a `calendar` parameter, and `loadWorkingCalendar()` (`planning/PublicHolidayService.kt`: one `SELECT` of the whole dictionary inside the caller's open transaction) builds it ONCE per request — right after `readPlanRevision()` in `ProjectViewService.view`, `TeamViewService.view` and `loadRoadmapSnapshot` (so the roadmap AND programs views share one read), and under the lock in `MilestoneService.schedule` — so the revision, the rows and the calendar are one REPEATABLE READ snapshot. Never from a route, never cached across requests. The violation check of a link (`DependencyKernels`, below) and the load kernels are built on it. `WorkingCalendarTest` pins the identities.
- **Deletes.** A milestone delete soft-deletes every ACTIVE link with either end at it (`deleteDependenciesOf`, same locked transaction; `milestone.deleted` carries `dependencyCount`). A project delete soft-deletes the links at the project AND at its milestones, both ends,

A project move changes no id, so links survive; a team change and an unschedule keep them too (an unscheduled end simply has no dates). Dependency writes bump the plan revision
  and never a milestone's `schedule_revision` — a drag is never staled by someone adding a link.
- **Write order** (`DependencyService.create`, in `withPlanWrite`): project chain re-read (404) → `ownerGuard` re-run with the caller's person `FOR SHARE` (403) → successor in the project (400) → predecessor active (400) → cycle (409) → insert (pair 409). The route's outer order is

### The project view's dependencies (built, v0.4.0 C3; `DependencyKernels.kt`, `ProjectViewDependencies.kt`)

`GET /views/project/{id}` carries `dependencies[]`: every ACTIVE link with an end in the project (the project itself or one of its active milestones) — including a link whose OTHER end is in another project, which is how the page draws its ghost rows. One read in the view's transaction, no
lock. Each item is `{id, predecessor, successor, type, lagDays, check, can{edit, delete}}`:

- **Ends** are the `DependencyEndpoint` of `resolveEndpoints` (batched; a milestone: its own `projectId`/`projectName`, `teamId`/`teamName`, dates; a project: `projectId` = its own id, no team, its DERIVED span — never its target window — null while nothing in it is scheduled). The SPA derives the ghost rows from the ends whose `projectId` is not the viewed project; there is no separate `external[]`.
- **`check`** (`DependencyCheck{status, shortfallDays, slackDays, requiredDate, actualDate}`) comes from the pure kernel `DependencyKernels.check(type, lagDays, predecessorSpan, successorSpan, calendar)` (no I/O; `DependencyKernelsTest` is table-driven, every figure counted by hand on the 2027 calendar, 2027-02-01 a Monday). With `W` the calendar's working-day index (`infra/time/WorkingCalendar.kt`, Monday–Friday minus holidays, flat over a weekend and a holiday), a span's EFFECTIVE start the first working day on or after
  `start`, its EFFECTIVE end the last working day on or before `end`, `A` the predecessor, `B` the successor and `lag` in working days (negative = a lead):

  | Type | required | actual |
  |---|---|---|
  | FS | `W(A.effEnd) + 1 + lag` | `W(B.effStart)` |
  | SS | `W(A.effStart) + lag` | `W(B.effStart)` |
  | FF | `W(A.effEnd) + lag` | `W(B.effEnd)` |
  | SF | `W(A.effStart) − 1 + lag` | `W(B.effEnd)` |

  Spans are half-open working intervals `[W(effStart), W(effEnd)+1)`, so SF mirrors FS: a successor ending the working day BEFORE the predecessor starts is `OK` at lag 0 (A = 2027-02-01..05, B = 2027-01-25..29, SF → `OK`).

  `shortfallDays = required − actual`; `VIOLATED` when positive (then `shortfallDays` ≥ 1, else null), `OK` otherwise; **`slackDays = actual − required` (1.7: the link's OWN float in working days — 0 or more when `OK`, `−shortfallDays` when `VIOLATED`, null when `UNSCHEDULED`; not the critical path's slack toward a project's end)**; `requiredDate` = the working day with index `required`, `actualDate` = B's effective start/end, both answered for OK and VIOLATED. An end without dates (a tray milestone, a project with nothing scheduled) makes the link `UNSCHEDULED` (question 3a of the v0.4 plan): no dates, no shortfall, no warning, no arrow. Example: A = 2027-02-01..05, B moved to 2027-01-25..29, FS lag 0 → `VIOLATED`, 10 working days short, "needs 2027-02-08 · is 2027-01-25". A violation changes nothing but the view: no write, no 409, no audit.
- **Order**: `VIOLATED` first (the largest shortfall first), then `OK`, then `UNSCHEDULED`; within a group by the successor's name, the predecessor's name (case-insensitive) and the id — the top of the list IS the conflict list.
- **Flags**: `project.can.createDependency` = `canCreateDependency(projectChain)`; a link's `can.edit` = `canEditDependency` and `can.delete` = `canDeleteDependency`, both on the chain of the project that holds its SUCCESSOR (`authorization.md`; two flags, one arithmetic today). Each equals the arithmetic of the real `PUT`/`DELETE`, `createDependency` that of the `POST`.
- **Tests**: `DependencyKernelsTest` (pure), `ProjectViewDependenciesTest` (the first vector per type over HTTP, both projects of a cross-project link, the order, derived-span and unscheduled ends, deleted and unrelated links absent, the three flags against the real writes for ten kinds of caller), `PlanPermissionsTest` (the three flags against the guards).

## Team capacity periods (built — V16, v0.5.0; `teams/TeamCapacity*.kt`)

A team's **man-days per week** and an optional **work-in-progress (WIP) limit**, in effective-from periods. **Team data, not plan state**: written by the team's manager or ADMIN in a transaction of its own, so a capacity write takes **no plan lock and never bumps the plan
revision** (`PlanStateTest` "a capacity write is team data"). The weekly load, overload and WIP verdicts that read these periods arrive with the team view (C3 of v0.5.0); this section is the stored model and its rules.

- **Table `team_capacity_periods`** (`TeamCapacityService.CapacityPeriods`, `SoftDeletable`; the service lives in `teams/`, beside the team it belongs to): `id SERIAL`, `team_id → teams` (no `ON DELETE` rule: teams are only soft-deleted), `effective_from DATE`
  (through `LocalDateColumn.kt`), `md_per_week NUMERIC(8,2) NOT NULL` (`ck_team_capacity_periods_md`: `>= 0`; zero = on hold), `wip_limit INTEGER NULL` (`ck_team_capacity_periods_wip`: NULL or `BETWEEN 1 AND 99`), epoch-millis
  `created_at`/`updated_at`, `marked_as_deleted`. **`uq_team_capacity_periods_team_from_active`**: one ACTIVE period per team and start date (409 "A capacity period already starts on this date for this team"; a deleted period frees its date) — the partial index also serves every per-team read of active rows, so there is no separate `team_id` index.
- **Provenance (V24, 1.5.0)**: `source VARCHAR(10) NOT NULL DEFAULT 'MANUAL'` (`ck_team_capacity_periods_source`: `MANUAL` or `FLOW`), `flow_sprint_id BIGINT NULL`, `flow_sprint_name VARCHAR(255) NULL`. A hand-entered period is `MANUAL` (so is every period that existed before V24); a `FLOW` one is written by the capacity import for the named Flow sprint. **A PUT on a `FLOW` period makes it `MANUAL`** and clears the sprint columns (the manager took it over: the import never updates or removes a `MANUAL` period), even when the figures are equal; the audit carries `sourceFrom`/`sourceTo`. `CapacityPeriodResponse` always carries `source` and `flowSprintName` (null on a manual one); the team view's `capacity.periods` are the same schema. The kernels read neither column: a Flow-sourced period weighs like any other. **The capacity import** (`flow/CapacityImportKernels.kt`, `flow-sync.md` "The capacity import") writes `FLOW` periods from a sprint's man-days over its working days: `mdPerWeek = round2(5 x flowMd / workingDays)`, so `weekCapacity` over the sprint adds up to the sprint's man-days within rounding (the divisor 5 holds on a holiday week; a sprint that shares its first day with the previous one holds from the day after, `flow-sync.md`); a hand-entered period is never changed or removed by it. Its preview (`POST /integrations/flow/team-bindings/{id}/capacity-preview`) only reads the periods; its apply (`…/capacity-import`, `TeamCapacityService.applyImport`, step C8) writes them in ONE team-locked transaction - creates a `FLOW` period per CREATE row, rewrites the figure, sprint id and sprint name of the sprint's existing `FLOW` period for an UPDATE (its WIP limit is kept), soft-deletes the ticked removals - and never touches a `MANUAL` one (`flow-sync.md`). A period the import wrote is shown with its `source`/`flowSprintName` like any other and feeds `weekCapacity` unchanged (`TeamViewTest` "imported periods feed the weekly capacity").
- **The rules below are the kernel's, not the schema's** (V16's comments carry schema facts only, and point here): the proration and the WIP count read the calendar's working-day predicate (`WorkingCalendar.isWorkingDay`), so the holiday calendar (v0.7, loaded per request) changes the covered days of the proration (the divisor stays 5) and a holiday runs no WIP, without a migration.
- **A period starts on ANY date** (the user's decision, Q1c): there is no weekday CHECK and no weekday rule anywhere; the date is `parseIsoDate`'s alone (`YYYY-MM-DD`, years 1900-2999, `Dates.kt`). A period is in force from `effective_from` until the next ACTIVE period of
  the same team; a weekend date is in force from that date, which simply counts from the next working day. Periods in the past are allowed (history). The weeks before a team's first period have **no capacity and no limit** — "no capacity", never zero, never flagged.
- **The week a period starts in is prorated by working days** (applied by the team view's kernel): a week's capacity is the sum over its working days (the calendar's) of the capacity in force THAT day, divided by 5 (fixed - a holiday week keeps the divisor) (10 MD/week through Wednesday and 20 from Thursday = 3/5 x 10 + 2/5 x 20 = 14);
  `md_per_week` is validated to two decimals so the stored value is exactly the sent one. A period that is the team's first and starts mid-week covers only the days from its start (the uncovered working days contribute 0; a week with no covered day has no capacity).
- **The WIP limit** is per period and optional (`wipLimit` null or 1..99 on the wire, 400 "wipLimit must be between 1 and 99"; the CHECK is the backstop). It is checked **per working day** against the team's scheduled milestones whose effective span covers that day, and a limit that changes
  mid-week applies to each day's own count; a period with a capacity and no limit simply never warns. Both overload and too much WIP only ever **warn** (orange); nothing moves.
- **Writes** (`TeamCapacityService`): ONE transaction that first locks the team row (`Teams.lockActiveForWrite`, `FOR NO KEY UPDATE` — a team delete racing it either commits first and the write is a 404, or waits and then cascades the new period too), then re-runs the manager guard
  with `TeamService.lockedIsActiveManager` (`FOR SHARE OF teams, people`; the guard runs twice, `authorization.md`), then writes. `PUT /capacity-periods/{id}` is a full replace (an absent or null `wipLimit` CLEARS the limit); a PUT that changes nothing is 204 and writes nothing.
  The man-day figure uses `validateManDays(value, field)` (`planning/Milestone.kt`, the milestone estimate's rule with the field named: finite, `0 <= x < 1_000_000`, at most two decimals). **A team delete soft-deletes the team's ACTIVE periods** in its own locked transaction (`deleteCapacityPeriodsOf`, after the
  "Team still has milestones" 409, so a refused delete changes nothing); `team.deleted` carries `capacityPeriodCount`.
- **API** (tag `teams`; `documentation.yaml`): `GET /teams/{id}/capacity` → `200 {items: CapacityPeriodResponse[]}` in `effectiveFrom` order (the bounded `{items}` wrapper of `list-endpoints.md` — a handful of periods per team per year, not paged); `POST /teams/{id}/capacity` → 201 + `Location`;
  `GET`/`PUT`/`DELETE /capacity-periods/{id}` (200 / 204 / 204). Reads: any authenticated user; 404 when the team (or the period, or the period's team) is deleted. Writes: **read-before-guard** (the team or the period's team resolved first — 404 for every caller — then `requireTeamManagerOrAdmin`
  403, then the body, a forbidden caller's malformed body staying 403, then validation 400), the guard again under the lock. The project's owner, the other teams' managers and every other caller are 403.
- **Audit** (`observability.md`): `team.capacity_period_created`, `team.capacity_period_updated` (from/to values, only on an actual change), `team.capacity_period_deleted`; `team.deleted` += `capacityPeriodCount`.
- **Tests**: `TeamCapacityTest` (the caller matrix incl. the project owner and the other team's manager, read-before-guard, any date, the 400s, the optional limit, the stored `::text`, the 409s, the audit), `TeamCapacityLifecycleTest` (the guard re-run under the team row lock — a manager cleared or the team deleted while the
  request was held —, the team-delete cascade, the CHECK and index backstops), `PlanStateTest` (no plan-revision bump), `MigrationChecksumTest`.

## The team milestone order (built — V17, v0.5.0; `planning/TeamOrder*.kt`)

**Two ranks, two meanings (the user's decision "A").** The PROJECT rank (`/roadmap/ranking`, one global list) is the top-down SUGGESTION of the order in which projects should be delivered. The MILESTONE order is the order of ACTUAL EXECUTION and belongs to the
TEAM: each team's manager orders their own team's milestones, and a lower-ranked project's milestone may come before a higher-ranked project's. The project rank is only the DEFAULT of a team's order — used until the team overrides it, and again after a Reset.
**A manager's override is never reshuffled by a later project-rank change**: the stored positions are the team's own and absolute (`replaceRanking` touches `roadmap_entries` only); only milestones the team did not list (newly created, or moved onto the team) slot in after the
listed ones, in project-rank order. The v0.6 rank-vs-time inversion (a WARNING per team, an INFO where no team is shared; built, "The roadmap view (built, v0.6.0)" above) only flags, never reorders.

- **The client's list is the FULL list (the interleaving rule, pinned).** The PUT is wholesale and positions cover scheduled and unscheduled milestones alike, so a manager's order is never reshuffled by the page either: a milestone the manager placed and later unscheduled keeps its stored place. `GET /views/team/{id}` therefore exposes the stored order as `order.milestoneIds` (the team's ACTIVE milestones currently on that team that are listed, scheduled or not, in stored position order, read in the view's own snapshot; empty when `custom` is false). The list the SPA PUTs is `order.milestoneIds` followed by the scheduled rows it does not list, in their displayed order; a reorder of the scheduled rows (a permutation `S'` of the displayed scheduled ids) keeps every unscheduled listed id at its INDEX in that full list and fills the other slots, in order, with `S'` (`web/src/utils/teamOrderList.ts`). Example: stored `[A,B,M,C]`, M unscheduled, Move C to top -> `S'=[C,A,B]` -> PUT `[C,A,M,B]`. Unlisted unscheduled milestones stay unlisted; only the unlisted newcomers (scheduled ones the write lists at the bottom of the full list, by their displayed = project-rank order) slot in at the bottom; Reset still sends `[]`.
- **Tables** (`TeamOrderService.TeamMilestoneOrders`, `TeamOrderState`): `team_milestone_orders (milestone_id INTEGER PRIMARY KEY → milestones, team_id → teams, position INTEGER NOT NULL CHECK (position >= 1), UNIQUE (team_id, position) DEFERRABLE INITIALLY DEFERRED)` — one row per LISTED
  milestone, positions dense 1..n per team; a **hard-delete position join** like `roadmap_entries` (`persistence.md` "Soft delete"); and `team_order_state (team_id PRIMARY KEY → teams, revision BIGINT, updated_at)` — per team, the plan revision at which its order was last written (created
  by the first write, never removed, inert for a deleted team). No `ON DELETE` rules: milestones and teams are only soft-deleted, so the writers remove rows themselves.
- **Write** (`PUT /teams/{id}/milestone-order`, body `{expectedRevision, milestoneIds[]}`, `200 {revision}`): **wholesale** — the listed milestones get positions 1..n, every other milestone of the team is unlisted; **`[]` is the reset** (every row removed, the state revision still
  bumped, so a stale list cannot undo it; there is no `DELETE`). Route order is read-before-guard: team active ?: 404 -> `requireTeamManagerOrAdmin` (the team's ACTIVE manager or ADMIN; the project's owner and every other caller are 403) -> body (a forbidden caller's malformed body stays 403) ->
  pure validation 400 (`expectedRevision` negative, more than 1000 ids, an id twice). Inside `withPlanWrite`, in this order: the team re-read (404; its row locked `FOR SHARE` for EVERY caller, ADMIN included, so a team delete cannot slip in before the state row is stamped) -> the guard again (`lockedIsActiveManager`, 403, no bump) -> **the stale check** (409 `urn:astrolabe:problem:stale-revision`) -> every id an
  ACTIVE milestone OF THIS TEAM (400 "Unknown, deleted or other-team milestone ids: …") -> `DELETE … WHERE team_id = ?` + one `insertRows` -> the state row set to the plan revision the write leaves behind. Every accepted PUT bumps the plan revision, a no-op one included. Positions cover any milestone of the team, scheduled or not.
- **The revision is the team's own.** The stale check is `stored order revision > expectedRevision` or `expectedRevision >` the plan revision under the lock (a view from the future); a team never written has no stored revision, so its first write passes with any valid `expectedRevision`. So only THIS team's order write
  (or its reset) stales a reorder — another team's reorder, a schedule drag, a rename or any other plan write does not, and the order write does not stale a schedule PUT (that one compares the milestone's own `schedule_revision`). The answer `{revision}` is the new order revision.
- **Hooks keep the positions dense**, each in the same plan-locked transaction (`removeFromTeamOrder`, `removeFromTeamOrders`; `persistence.md`): a milestone's team change (`MilestoneService.update`, `teamFrom != teamTo`), its delete, and its project's delete (all the project's milestones, one compaction per touched team) delete the row and close the gap with
  `UPDATE … SET position = position - 1 WHERE team_id = ? AND position > ?` (the single statements the deferred constraint exists for). A removal never bumps the team's order revision: the manager's list is still the manager's list. A milestone that LEAVES a team is unlisted in the new one.
- **The effective order** (`TeamOrderKernels.kt`, pure; `TeamOrderKernelsTest`): the stored custom position first (an unlisted milestone after every listed one), then the project's global rank (unranked projects after ranked ones), then project name (case-insensitive), project id, then the project view's tuple (start, end, name
  case-insensitive, id; a milestone WITHOUT dates sorts after the dated work of its project — undated work follows dated work in an execution order, so the tray's milestones sit last within their project). With no override a team sees its work in the roadmap's order, project by project; with one, the listed rows come first exactly as listed and only the unlisted tail follows the rank. The team view (v0.5.0 C3) is the first reader of it; the stored positions are read through `positionsOf(teamId)`.
- **Audit** (`observability.md`): `team.milestone_order_changed` (byUserId/teamId/revisionFrom/revisionTo/orderFrom/orderTo — the plan revisions around the write and the listed ids before and after as comma-joined text, "" = the default order) on EVERY accepted PUT; a 409/400 emits nothing, a 403 is the central `authz.denied`.
  The server does not know whether a list came from a menu or a drag: both are the same PUT.
- **Tests**: `TeamOrderTest` (the caller matrix incl. ## The team view (built, v0.5.0 C3; `planning/LoadKernels.kt`, `TeamView*.kt`)

`GET /api/v1/views/team/{id}` (tag `plan`; any authenticated user; 404 when the team is deleted, for every caller; **no audit** — a read) answers ONE document, the view-endpoint shape exception of `list-endpoints.md`:
`{revision, team{…TeamResponse fields, can{schedule, editCapacity, editOrder}, flags[]}, order{custom, revision, milestoneIds[]}, capacity{periods[]}, weeks[], weeksTruncated, scheduled[], unscheduled[], dependencies[], idleGaps[]}`. `TeamViewService` runs ONE READ ONLY REPEATABLE READ transaction (`ProjectViewService`'s snapshot):
the plan revision FIRST, then the team ⋈ its manager's name, the team's ACTIVE milestones ⋈ project ⋈ program ⋈ work stream ⋈ `roadmap_entries` (left: `rankPosition`; `TeamViewRows.kt`), the order positions (`positionsOf`, looked up FROM the active milestones — never by iterating the order table) and the order revision, the capacity periods and the links;
then the pure kernels. `order.revision` is the TEAM's order revision (0 when never written; the `expectedRevision` of `PUT /teams/{id}/milestone-order`), `revision` the PLAN revision (the schedule PUT's). A `TeamMilestone` is `MilestoneResponse` + `projectName`, `programName`, `workStreamName`, `rankPosition` (null = unranked) and, since 1.7, `slackDays` (null while unscheduled) and `critical` ("The critical path"); no per-milestone `can` —
the three team-level flags apply to every bar. Bound: one team's milestones (about 100), their links and at most 520 weeks.

- **The `can` flags: three names, one arithmetic.** `canSchedule`, `canEditCapacity` and `canEditTeamOrder` (`PlanPermissions`) are all "ADMIN, or the caller is the ACTIVE manager of THIS team" (`requireTeamManagerOrAdmin`; the actor's managed teams resolved once, `withManagedTeams = true`). Three flags so a later version may split the rights without a wire change. `PlanPermissionsTest` pins each against the guard;
  `TeamViewTest` checks each against the real write (the schedule PUT, the capacity POST, the order PUT) for every kind of caller.
- **Order** (`effectiveOrder`, see "The team milestone order"): `scheduled[]` and `unscheduled[]` are the team's milestones in the effective order — the team's own override first, the global project rank as the default of the unlisted tail. Positions come from the team's ACTIVE milestones.
- **Weeks and working days.** A week is an ISO week keyed by its Monday (`weekStart`); its working days are the calendar's (`WorkingCalendar.isWorkingDay`: Monday–Friday minus the holidays). The capacity divisor stays **5** in a holiday week: the holiday is an uncovered day, so a 10 MD/week team has 8.00 in the week of 2027-01-04 (Epiphany, Wednesday 01-06) and a 10 MD milestone dated 01-04..01-08, spread over the four remaining days, loads 10.00 — overloaded by +2.00 (the table below; `LoadKernelsTest`). `weeks[]` runs from the Monday of the earliest scheduled start to the Sunday of
  the latest scheduled end (`loadWindow`; empty while nothing is scheduled), capped at **520 weeks** counted from the start (`MAX_LOAD_WEEKS`; `weeksTruncated` then true). - **The Flow capacity flag (1.9).** `team.flags[]` carries at most ONE flag, `FLOW_CAPACITY` (`count` = the team's OPEN Flow capacity deviation rows, the worst severity among them; empty without a Flow link, with a disabled connection or when every row is acknowledged), and a `weeks[]` row gains `flowCapacity: WARNING|INFO` when the held days `[effectiveFrom, end]` of an open row meet the week `weekStart..weekStart+6` (the worst severity among the rows that meet it; absent otherwise, and always absent on the proposal's and the check's weeks: `@EncodeDefault(NEVER)`). - **The spread (load).** A scheduled milestone's estimate `E` is spread evenly over its `n = calendar.workingDaysBetween(start, end)` working days (`W(prevWorkingDayOnOrBefore(end)) − W(nextWorkingDayOnOrAfter(start)) + 1`, `W` the index of `WorkingCalendar.kt`): a milestone's share of a week is the EXACT fraction `E × (its working days inside the week) / n` (never divided first — no digit is lost); a week's `load` = the shares of
  every milestone summed exactly (as a fraction over a common denominator) and rounded ONCE to two decimals `HALF_UP` (7.25 MD over six working days loads 3.63 into each of two weeks, 3 days apiece; two 0.01 MD milestones Friday → Monday load 0.01 into the first week, not 0.02). A weekend inside a span costs nothing. 10 MD Wednesday → next Tuesday (5 working days) loads 6.00 into the first week and 4.00 into the second; 10 MD over Friday + Monday + Tuesday loads 3.33 and 6.67.

## Idle gaps (built, v0.7.0 C5; `planning/IdleGapKernels.kt`)

`idleGaps[{start, end, workingDays}]` on `GET /views/project/{id}` and `GET /views/team/{id}` (spec schema `IdleGap`, by start; empty when there are none). An **idle gap** is a maximal run of at least **3** working days (`MIN_IDLE_GAP_DAYS`, the user's threshold of 2026-11-01) inside the derived span on which nothing is in progress; weekends and public holidays neither count nor break a run, and nothing before the first start or after the last end is reported (the gaps are inside the work).

- **Team**: working days on which the team has NO scheduled milestone in progress, inside the span of the team's scheduled milestones that hold a working day (`SpanKernels.derivedSpan`, not the 520-week load window, so no truncation flag). Only the team's own milestones count. **Project**: working days inside the span of the project's milestones that hold a working day (`span` unless an end milestone is holiday-only) on which none of its OWN milestones is in progress (another project's work of the same team fills nothing).
- **In progress** is the WIP rule of the team view: a scheduled milestone covers the working days of its EFFECTIVE span, first working day on or after its start to the last on or before its end; a weekend-only or holiday-only span covers nothing (a milestone whose only day later became a holiday keeps its dates and stops splitting a hole).
- **The kernel** (`idleGaps(spans, within, calendar, minWorkingDays = 3)`, pure; the calendar is a parameter): spans to working-day-index intervals, sorted, swept with a cursor (`max`, so a nested span never pulls it back); a run closes at the next start or at the end of `within`; a gap answers its FIRST and LAST working day (ISO dates, never a weekend or holiday) and its length. `idleGapViewsOf(spans, calendar)` derives `within` from the spans that hold a working day (`containsWorkingDay`: a milestone on a single day that later became a holiday keeps its dates, is no work and opens no leading or trailing gap) and is what both services call. O(n log n).
- **Hand-counted** (`IdleGapKernelsTest`, 2027-02-01 a Monday): milestones Mon 02-01 and Tue 02-09 leave Tue 02-02..Mon 02-08 = **5** working days (the weekend between uncounted); Mon 01 and Fri 05 leave Tue..Thu = 3 (a gap) but with Wed 03 a holiday only 2 (none); Mon..Tue and Fri 02-12 leave Wed 03..Thu 11 = 7, with Wed 03 and Thu 11 holidays Thu 04..Wed 10 = 5; Thu..Tue over a weekend = 4, Fri..Mon = 2.
- **Tests**: `IdleGapKernelsTest` (pure), `ProjectViewTest` and `TeamViewTest` (a 5-day hole through the wire, a holiday-shortened hole absent via `TestHolidays.with`, own-milestones-only scoping). The web bands and the "Idle gaps" tables are C8.

## The critical path (built, v0.7.0 C4; `planning/CriticalPathKernels.kt`, `CriticalPathView.kt`)

Per PROJECT, on the PLANNED dates, nothing moves (the user's answers 5-8 of 2026-11-01; **D5: the whole chain** — the path follows the driving chain through every project it passes). It rides `GET /views/project/{id}`, (1.7) `GET /views/roadmap?criticalPath=N` (below) and (1.7) `GET /views/team/{id}`, which asks the question per milestone toward its OWN project's end: each `TeamMilestone` carries the SAME `slackDays`/`critical` the project page gives that milestone (pinned by `TeamViewTest`), and a link is `critical` when it lies on the chain of a project one of the team's milestones belongs to (the union over those projects; a link that drives only a project none of them belongs to is not marked, its own project's page marks it). `TeamViewService` loads the graph once (`loadCriticalPaths`, `analyseAll`: one edge build, one walk per project of the team, milliseconds) inside its snapshot. The roadmap asks it for ONE picked project (`RoadmapCriticalPath.kt`, "The roadmap view"). No migration.

- **Inputs, one snapshot.** `ProjectViewService` loads, inside its REPEATABLE READ transaction right after the calendar, the WHOLE active graph with the roadmap's shared loaders (`milestoneFacts`/`linkFacts`/`activeProjectNames` in `RoadmapViewRows.kt`, made `internal`: every active milestone with its name, every link, every project name — ≈1,000 + 300 + 100 rows on the sample plan; `persistence.md`), then runs the pure `CriticalPathKernels.analyse(projectId, milestones, links, calendar)` once. A milestone whose project is not an active row is left out (only a hand-edited database has one).
- **Values and edges** (reuse `DependencyGraph.kt`'s `TimePoint`/`TimeSide` and `DependencyEdge.from`/`to`). A scheduled milestone has the half-open working-day values `S = W(first working day on or after start)`, `E = W(last working day on or before end) + 1` (exactly `DependencyKernels`' table); a project has `min S`/`max E` over its scheduled milestones. An edge `from -> to` with `offset` has slack `value(to) - value(from) - offset`: a **milestone's** `S -> E` (offset = its length, slack 0: the whole bar slips together), containment `S(project) -> S(milestone)` and `E(milestone) -> E(project)` (offset 0), and a link `X(pred) -> Y(succ)` with offset `lagDays` for all four types — so **a link's slack equals `actual - required` of `DependencyKernels.check`** (pinned for every type, several lags and a holiday calendar). **A PROJECT has no start-to-end edge** (the v0.7 plan's sketch gave it one; its span is derived from its milestones, and the edge would make every link into a project's START zero-slack through its END). Excluded: a link with an unscheduled end (no values) and a VIOLATED link (negative slack, D4): never driving, caps nothing, and upstream it ENDS the chain (that project's page shows it red).
- **The upstream set and the float.** Walk the included edges backwards from `E(p)` (p = the viewed project); the points that reach it are the upstream set U (downstream-only and unconnected points have no slack toward this project: `null` / absent). `float(E(p)) = 0` and `float(u) = min(slack(u -> v) + float(v))` over the edges into U, in the reverse topological order of U (Kahn; the acyclicity invariant of the cycle rule makes it terminate, a leftover is `error("the active plan graph holds a cycle")`, a 500-grade invariant violation; a zero-slack cycle such as two milestones SS-linked both ways is the test input). A milestone's `slackDays = float(S)`: the working days it could slip — with everything downstream of it allowed to slip too — before THIS project's end moves. Internal milestones are always finite (containment reaches `E(p)`); an external milestone's slack is finite exactly when it is upstream, through any number of projects; a link from this project into another project caps nothing unless its path returns to `E(p)`.
- **Critical** = zero float (every point with a zero-slack edge to a critical point is critical, which is the same thing). Ties: every milestone ending on the project's end is critical and parallel zero-slack chains are all critical (a critical network). A milestone is critical when either point is, a link when its slack is 0 and its `to` point is critical, a project entity when either of its points is (it reports the minimum over its points in U). **hops** = the fewest LINK edges from one of its points to the viewed project (containment and a milestone's own start-to-end cost nothing; a direct neighbour is 1). An unscheduled milestone has `slackDays: null`, `critical: false`.
- **The wire** (`list-endpoints.md`): each `ProjectMilestone` adds `slackDays` (`null` while unscheduled) and `critical`; each `ProjectDependency` adds `critical`; the view adds `criticalPath{upstream[], upstreamTruncated}` — `UpstreamEntity{kind, id, name, projectId, projectName, startDate, endDate, slackDays, critical, hops}` for every milestone or project of ANOTHER project in U (a PROJECT only when an included link names it — it is the point the link uses; a project that merely contains upstream milestones is not listed). `orderUpstream` (pure, tested) puts the CRITICAL entries first, read from the chain's origin (start date, end date, name case-insensitively, kind, id), then the rest by slack ascending (then the same keys); the critical ones are never cut, the non-critical are capped at **100** (`upstreamTruncated`). `hops` counts links only (containment is free), so every milestone of a project that a link names is at hops 1 and `hops` is NOT a ghost-row filter: the page's "Critical chain" list is `criticalPath.upstream` minus the ends already shown in `dependencies[]` (matched by kind + id).
- **Cost.** The kernel is three linear passes over ≈2,000 points and ≈3,000 edges (hash maps), well under 1 ms; the extra reads are the roadmap's milestone/link statements plus one 100-row name read. Budget (the C10 gate): `GET /views/project/{id}` on the sample plan, warm, p50 ≤ 30 ms and p95 ≤ 45 ms, largest response ≤ 120 KB; the fallback if it fails is to trim the milestone statement to the kernel's columns and read names only for U.
- **Tests.** `CriticalPathKernelsTest` (pure, hand-counted on 2027-02: one milestone, back-to-back, parallel, gaps and lags, SS/FF/SF at zero and positive slack, two-hop chains across three projects, a chain through a project entity, links into a project's start, violated/unscheduled/downstream-only/returning paths, ties, the link-slack equality matrix, a holiday between two milestones, an all-holiday milestone, the cyclic input, the ordering and the cap), `ProjectViewTest` (a three-project chain through the wire, scoped to its own ids because the container holds other classes' milestones), `ProjectViewDependenciesTest` (`critical` on a driving link, asymmetric between the two projects), `TeamViewTest` (the team view's figures and the asymmetry, 1.7), `RoadmapViewTest` (`?criticalPath=`, 1.7), `ProgramsViewTest` unchanged (the shared loaders).

## The auto-proposal (v0.8.0; `planning/ScheduleKernels.kt`, `ScheduleLedger.kt`, `ScheduleConstraints.kt`)

The scheduling kernel (v0.8 C1; pure — no I/O, no clock, no randomness: the calendar, the clock date `asOf` and every row are parameters). It places ONE team's not-started milestones and answers a PROPOSAL; nothing moves. The endpoint, the batch accept and the page are C2–C5 (the v0.8.0 plan); this section is the kernel's contract. The user's binding answers (2026-11-01/02): every not-started milestone is re-planned from the earliest day (Q1a); a link into another team's fixed milestone is placed anyway and reported (Q2a); a day without capacity or on hold is unusable (Q3a); a 0 MD milestone takes one working day and counts for WIP (Q5a); the target window is NOT a constraint (Q6a). Q4a (a stale item is skipped, the rest land) is the batch's (C3).

- **API.** `ScheduleKernels.propose(ScheduleInputs): ScheduleProposalResult` and `ScheduleKernels.postCheck(inputs, result): ScheduleProposalCheck`. `ScheduleInputs(asOf, teamId, team: List<TeamScheduleItem>, periods, plan: Collection<PlanMilestoneFact>, links: Collection<PlanLinkFact>, calendar, horizonWeeks = 520)`; `TeamScheduleItem(id, projectId, span: DaySpan?, estimateMd, key: OrderKey, pinned = false)`; `Placement(milestoneId, from: DaySpan?, to: DaySpan)` (`to == from` = it stays); `Unplaced(milestoneId, reason: NO_CAPACITY | NO_ROOM)`; `ScheduleProposalResult(placements, unplaced, spansAfter)`; `ScheduleProposalCheck(weeks: List<WeekLoad>, weeksTruncated, links: List<ScheduleLinkCheck(linkId, before: DependencyStatus, after: DependencyCheck)>)`. `Fraction` (`LoadKernels.kt`, the exact rational, now `internal`, with `minus` and `compareTo`) and `DependencyKernels.requiredIndex` (now `internal`) are the shared arithmetic; neither changes behaviour.
- **Movable / fixed.** MOVABLE = the team's milestones with no dates or a start AFTER `asOf`; FIXED = every other milestone: the other teams' always, this team's with `start <= asOf` (in progress or past; a weekend-dated start counts by its date) **and, since V25, this team's PINNED dated milestones whatever their start** (`Pass.isFixed`, the one predicate a pin touches: `span != null && (start <= asOf || pinned || id in held)`; the pin only widens it, no placement arithmetic changes). A pinned milestone's dates stand, its load is booked in the ledger at the even rate, its dates feed the link values (an FS successor starts after it, exactly like another team's milestone), it is in `spansAfter` and it is in NO placement and NO `unplaced` list. The word "pinned" has two meanings in this section: the manager's pin (V25, stored) and the fixpoint's "held" set below (a scheduled movable milestone that found no room keeps its dates; internal, per run). The ledger starts with this team's fixed milestones only (their effective working days, the even rate `E/n`); a movable milestone's current dates are forgotten until it is placed (they survive as the order tiebreak only).
- **Order and hoisting.** Movable milestones sorted by `effectiveOrder`. The PLACEMENT order hoists, depth-first in link-id order, the movable milestones of this team a milestone must wait for: the predecessor of a link INTO it (any type), the movable milestones of a predecessor PROJECT, and the same for a START-bound link (FS/SS) into its project (containment). An END-bound link (FF/SF) into a PROJECT binds the project's derived end, which no single milestone owns: no bound, no hoist; the post-check reports it. `placements` and `unplaced` are listed in the TEAM order. The hoisting relation can close a loop on valid data (`a FF b` + `b SS a`: the cycle rule is on time points, the hoist is on entities): an entity met again on the walk's stack is skipped, never an error (the bound it would have given is then missing, and only the post-check reports a link it leaves violated); a real cycle of the time-point graph (every link, containment) fails closed first with `error("the active plan graph holds a cycle")`.
- **The ledger** (per working day from the team's first USABLE day — a working day in a period with capacity above zero and a WIP limit above zero — to `horizonWeeks` weeks later): `dailyCap = mdPerWeek / 5` (the fixed divisor of `weekCapacity`), `share = dailyCap / (wipLimit ?: 1)`, `wip` and `used` (exact `Fraction`s) booked by the fixed milestones and every placement.
- **Earliest start.** The later of the first working day after `asOf` and every START-bound lower bound: `requiredIndex` of each binding link whose predecessor has dates now (fixed, or placed in this run; a project predecessor = min start / max end over its dated milestones). A predecessor without dates (an unscheduled milestone of another team, an unplaced one, a project with nothing scheduled) binds nothing. END-bound links into the MILESTONE (FF/SF) demand the span's last working-day index be `>= required`, tested per candidate. All four types are lower bounds, so no link makes a milestone impossible, only later. A link between two fixed ends is not the scheduler's business.
- **Duration.** From a candidate start `s`, `n` = the smallest number of consecutive usable working days `d1..dn` with `E <= n × min(share(d1..dn))` (`E = 0` → `n = 1`). For a constant share this is exactly `ceil(E / share)`; when a period lowers the share inside the span the span stretches so the even rate `E/n` never exceeds the share of ANY of its days. A holiday inside a span costs a calendar day, not a working day. An unusable day ends the candidate.
- **The candidate loop (per DAY — stricter than the view's week rule, and it implies it).** The first start that fits: every day has WIP place (`wip + 1 <= limit` when a limit is in force that day) and room for the rate (`rate <= dailyCap − used`, exact), and the END-bound links hold. A conflict moves the start by ONE working day (the span length, hence the rate, depends on the start). Two exact shortcuts only: the first day alone (WIP full, or `used >= dailyCap` for `E > 0`) rejects every span starting there; and a start from which even every remaining day of its usable run at the run's best share cannot carry `E` skips the whole run (a later start has fewer days and a no greater share) — so a stretch without capacity costs one jump per run, never a walk. **Two levels.** The per-day test alone does not imply the view's week rule when FIXED load overbooks a day (3 MD on a 2/day day) or sits on a day without capacity or before the first candidate day: summing `used <= dailyCap` over the days only bounds the PROPOSED load. So the ledger also keeps, per ISO week, the exact `weekCap` (`Σ mdPerWeek/5` over ALL the week's working days, the view's `weekCapacity` unrounded) and the exact `weekUsed` (every booking's rate on every working day of the week, the days before the first candidate day and any unusable day included — a fixed booking is not clipped at the first usable day), and a candidate fits only if for every week it touches `weekUsed + rate × (its days there) <= weekCap`, plus the per-day test (O(weeks touched) per candidate; a 0 MD estimate skips both load tests, WIP still applies). With both levels the proposal never adds load to a week the view would show overloaded (`HALF_UP` rounding is monotone, so exact `load <= capacity` keeps the rounded comparison false); a dense 200-milestone team is pinned. The fixed milestones' own excess (an overbooked in-progress milestone) stays and is shown, never added to. Example: F 3 MD on Mon 02-01 (`asOf` = 02-01), X 8 MD (4 days at 2): from 02-02 the week would load 3 + 8 = 11 of 10, so X starts Wed 02-03 (3 + 6 = 9; 02-08 loads 2).
- **Reasons.** `NO_CAPACITY`: no usable day exists at or after the milestone's earliest start (no period, or on hold from there on). `NO_ROOM`: usable days exist but no span fits before the horizon (`horizonWeeks` weeks counted from the team's FIRST USABLE day, not from `asOf`: a team whose capacity starts years away is placed there). An unplaced milestone with NO dates needs nothing and is absent from `spansAfter`. A SCHEDULED movable milestone that ends unplaced keeps its stored dates when the proposal is accepted, so its load is real: it is PINNED — treated as fixed at its stored dates (booked in the ledger, its dates feed link values) — and the run repeats to a fixpoint (the pinned set only grows: at most `|movable| + 1` passes). It stays listed in `unplaced` with its reason and is present in `spansAfter` at its stored dates, so the post-check's strip and links are honest. Example: capacity on hold from 02-15, A 18 MD first in order, U 4 MD stored 02-08..02-09: A alone would take 02-01..02-11 and leave U no room, but accepting would overload week 02-08 with U's kept dates, so U is pinned and A finds no nine free days either (both `NO_ROOM`; the week reads U's 4.00).
- **The post-check.** `weeks` = the view's own `weeklyLoad` over the team's spans AFTER the run (fixed + placed), so it is the strip the team page shows after accepting everything; `links` = `DependencyKernels.check` before (stored spans) and after for every link with a MILESTONE end among the team's milestones plus every link with a PROJECT end whose derived span changed, violated-after first, then by link id.
- **The endpoint (built, v0.8.0 C2; `ScheduleProposalService.kt`, `ScheduleProposalAssembly.kt`, `TeamScheduleRoutes.kt`).** `POST /teams/{id}/schedule-proposal`, body `{asOf}`: ONE read-only REPEATABLE READ snapshot (the plan revision first, then the calendar and the rows: the team's milestones with their order keys, its capacity periods, EVERY active milestone and link) feeds `propose` and `postCheck`; nothing is stored, locked, bumped or audited. The answer's `revision` is the snapshot's plan revision (the batch's `expectedRevision`). `moves` = the placements whose span differs from the stored one (`from` null = unscheduled, `workingDays`, `shiftDays` in working days between the effective starts, null when newly scheduled), `unchanged` = the placements that land on their stored dates, `unplaced` = the kernel's verdicts with names (a scheduled milestone the fixpoint held at its stored dates is listed ONLY there), **`pinned` (V25) = the team's pinned milestones that start after `asOf` (fixed by their pin; some would have stayed anyway, and a pinned one already in progress is fixed regardless and not listed), in the team's effective order, in neither `moves` nor `unchanged`: the page says "N kept by a pin"**, `weeks`/`weeksTruncated` = the post-check's, `dependencies` = only the post-check's links whose verdict is VIOLATED before or after (a link fine both times, or unscheduled then fine, is dropped - the page prints nothing for it; the kernel still checks every touching link), each end slimmed to `{kind, id, name, projectName|null}` (`projectName` null for a project end; no dates, no team: the full `check` carries `requiredDate`/`actualDate` after the moves, and `before` sits beside it); ≈ 290 B a row instead of 541 B (Platform: 170,731 B → 88,214 B; `timeline.md` "Measured figures (v0.8)"). The batch accept, when its body carries that `scopeHash` (OPTIONAL: absent = the v0.8 contract, no check), recomputes it UNDER THE PLAN LOCK from the same function over the same row shape (`loadScheduleSnapshot` -> `ScheduleSnapshot.scopeDigests`, the proposal's own loader) and refuses the WHOLE batch with `409 stale-scope` (nothing written, no bump, no audit) on a different STRUCTURE part (any 64 hex of the 1.13 layout lands here too: a proposal open across the upgrade is refused once and proposed again by the page), or when another milestone of the team that the batch does not name has `schedule_revision > expectedRevision` (the team sweep). The kernel's inputs, one by one: the team's milestone set with each one's project, estimate and **pin** (V25: the kernel reads the pin, so a pin flipped after the proposal is a `409 stale-scope`; every open proposal's hash changed once at the upgrade, harmless: proposals are ephemeral) - IN the hash; the team's effective ORDER (stored positions, the projects' global rank, project and milestone names, ids), with the milestones' own start/end taken OUT of its tiebreak - IN (as the id sequence, so an absolute rank shift that reorders nothing is not a change); the capacity periods (`effectiveFrom`, man-days, WIP) - IN; every link with an end that is a team milestone or a project holding one, each end carrying the span of its FOREIGN part (a foreign milestone's own span; a project's derived span over its milestones of OTHER teams) - IN; the Monday-Friday holidays (`WorkingCalendar.offDayDates()`; a weekend holiday changes no count) - OUT of the structure, in their own digest (below); the team's OWN milestones' spans (fixed or movable, scheduled or not) - OUT of the hash, covered by `schedule_revision` (a batch item is the per-item `STALE`; any other team milestone is the sweep) - so a colleague dragging a batch item skips that item and the rest land (v0.8 Q4), and the team's own accepted moves never stale a later accept; the horizon - not state. A change of the other teams' milestones that no link of the team touches changes nothing the kernel reads and does not flip it. **The look-again (1.13.1, user answer Q1a).** When the structure and the sweep pass and ONLY the holidays part differs, the accept does not refuse: it decodes `asOf` from the token (a day past `LATEST_AS_OF`, or any other undecodable part: `409 stale-scope`), runs the kernel ONCE on the very snapshot the check just loaded (`ScheduleKernels.propose(snapshot.inputs(teamId, asOf))`, `proposeMany` for a run; `ScheduleSnapshot.freshSpans`) and goes through only when EVERY item of the batch carries both dates and equals the fresh `spansAfter` of its milestone (`acceptsOnlyFreshDates`: another date, an unschedule pair, a milestone the fresh run does not place are all the same `409 stale-scope`: nothing written, no bump). What is then written is exactly what a proposal computed now, on the current dictionary, would propose for those milestones - the page's own "propose again, accept the same ticks" without the round trip - so no reasoning about which holidays the kernel read is needed (a far-off holiday and a near one that moves nothing accepted pass; a holiday inside an accepted span, or on a day that moves one, refuses). The rare path is conservative: a colleague's drag of a batch item together with a holiday change refuses the batch instead of skipping the item. With unchanged holidays the check is the digests only and runs NO kernel (the `asOf` part is not even decoded). Cost: two digests on the normal path; on the look-again path one kernel run under the plan lock (about 40 ms for a team of 1,000 milestones, about 300 ms for a 15-team run: `timeline.md` "Measured figures (1.13.1)" and "(1.8)"). ## The cross-team run (1.8.0; `planning/CrossTeamKernels.kt`)

The v0.8 proposal places ONE team with every other team's dates fixed, and accepting every team in turn never reaches a global fixed point (Platform moved 213 of 275 milestones again after the other 14 teams were accepted). The cross-team run is that proposal over a SET of teams: the user's answer Q9a (2026-11-09). Pure, like the kernel it is built on (no I/O, no clock); this section is the kernel's contract (C1), then the run endpoint and the runnable teams (C2), then the accept (C3) - the check is added by the commit that builds it. Nothing moves; a run stores nothing.

- **API.** `ScheduleKernels.proposeMany(MultiTeamInputs): MultiTeamResult` (extension functions on the `ScheduleKernels` object, so call sites read `ScheduleKernels.proposeMany(...)`). `MultiTeamInputs(asOf, teams: List<TeamRun>, plan, links, calendar, horizonWeeks = 520, maxPasses = MAX_CROSS_TEAM_PASSES)`; `TeamRun(teamId, name, team: List<TeamScheduleItem>, periods)` (`name` is only the team order's tiebreak); `MultiTeamResult(order, passes, settled, byTeam: Map<teamId, ScheduleProposalResult>)` (`byTeam` iterates in `order`; each value is the team's result of the LAST pass, the very `ScheduleProposalResult` of the per-team kernel). `MAX_CROSS_TEAM_PASSES = 5`, a separate constant from the per-team fixpoint's (that one is internal to each team's run and unchanged: the "held" set). `propose` itself is `requireAcyclicPlan` + `proposeUnchecked`; the run calls `proposeUnchecked` per team and pass and checks the plan ONCE (containment over `plan` and every run team's rows, all links) - the check is ≈ 300 DFS over ≈ 2,200 points, 75 of them would be the whole cost.
- **Each team is placed by today's kernel**, with the teams placed so far as FIXED facts: the other teams enter a team's run only through `inputs.plan`, so the run keeps a working copy of the plan facts and, after a team, replaces that team's facts by the spans it ended on (a milestone with no span after the run - unscheduled and unplaced - gets `null`). The team's own facts are ignored by teamId, so its `TeamScheduleItem.span` stays the STORED span (the `from` of a move, the fixed test, the order tiebreak). Before the first pass every run team's facts are its stored rows. **Pinned milestones (V25) are fixed everywhere**: fixed in their own team's run, in its `spansAfter` at the stored dates, and so the stored dates in every other team's facts, in no placement list.
- **The team order.** A team graph over the run's teams: an edge `a -> b` per link with an end on `a` and the other on a different team `b` (a MILESTONE end is its plan fact's team, a PROJECT end every run team holding one of its milestones; teams outside the run add no edge - their dates never change). Influence between teams flows only along links (`ScheduleConstraints.bounds` reads link predecessors; a project's span is derived from its valued milestones), so the graph captures every path by which one team's placement can change another's. **Kahn's algorithm**, picking among the READY teams (no incoming edge from a remaining team) by ONE comparator: **the most movable milestones first** (`span == null || (start > asOf && !pinned)` at the stored dates, the complement of the kernel's fixed test), then the **name case-insensitively**, then the **id**. When a cycle leaves no team ready the same comparator picks among the teams of the SOURCE strongly connected components of what remains (a team is eligible when every remaining team that reaches it is also reachable from it; closure per round over ≤ 50 teams), so a team merely downstream of a cycle is never placed before that cycle (the cycle break). An edge whose source is placed after its target is a **back edge** (only a cyclic team graph has any): the target read the source's dates of the PREVIOUS pass.
- **The passes and `settled`.** Every pass places every team in `order` once. A team is **changed** in a pass when its `spansAfter` differs from its previous result's (pass 1: from its stored spans). After a pass, **`settled`** = no team changed in it is the SOURCE of a back edge: a change read only by later-placed teams was already seen in this very pass, so a next pass would reproduce every result (the kernel is deterministic); then the run stops with `passes` = the passes made. After `maxPasses` without settling: `settled = false` and the last pass's results stand (each team's dates are self-consistent; the cross-team links that still fail are what the post-check reports). Consequences, all pinned: **an acyclic team graph settles in ONE pass**; a single team always does and equals `propose`; teams with no link between them each equal their own `propose`; a request order never matters (the order is computed); shuffled `teams`/`plan`/`links`/rows give the identical result.
- **`checkMany(inputs, afterByTeam)` and `postCheckMany(inputs, result)`.** `before` = every plan fact's stored span (the run teams' from their rows); `after` = the stored spans of the teams OUTSIDE the run plus `afterByTeam` (team -> milestone -> span, an id absent = no dates); a run team with no entry fails closed with `NoSuchElementException`. Per team: `weeks` = the view's `weeklyLoad` over its after-spans (`ScheduleKernels.proposedWeeks`, also `postCheck`'s) and `links` = `teamLinkChecks`: a link with a MILESTONE end among the team's, or a PROJECT end that holds one of the team's milestones AND whose derived span changed. So a link between two run teams is in BOTH lists, and a project link whose projects hold only B's milestones is in B's list and not A's. For ONE team the holding clause is implied and `postCheck` is unchanged (`ScheduleKernelsTest` stays green untouched). `postCheckMany` is `checkMany` over the run's own final spans; the check endpoint calls `checkMany` with the stored spans overlaid by the ticked moves (its input type `CheckInputs` has no `asOf` or horizon).
- **Cost.** 15 teams x up to 5 passes = up to 75 `proposeUnchecked` calls plus one acyclicity check. Measured (`ScheduleKernelsScaleTest`, NON-BINDING, this machine; 15 teams in the sample's sizes, 1,000 milestones, 300 links of which 30 % cross teams in both directions, a capacity cliff on a third of the teams, WIP limits on half, a few pinned): 4 passes, settled, ≈ 285 ms per run, ≈ 15 ms for `postCheckMany`; tripwire 20 s. The fallback if a real plan measures slow is a per-pass worklist (re-run only the teams whose incoming facts changed) - not built.
- **The run endpoint and the runnable teams (built, 1.8.0 C2; `CrossTeamSchedule.kt`, `CrossTeamProposalService.kt`, `CrossTeamScheduleRoutes.kt`, `ScheduleSnapshot.kt`, `ScheduleScope.kt`).** `POST /api/v1/schedule-proposals`, body `{asOf, teamIds[1..50]}` -> `{revision, asOf, passes, settled, teams[], scopeHash}`; a COMPUTATION like the per-team proposal (`200`, no lock, no bump, no audit event, nothing stored). `teams[]` is in PLACEMENT order (`MultiTeamResult.order`; one list, no separate `order[]`), each block the per-team proposal's shape without the run-level fields: `{teamId, name, moves, unchanged, unplaced, pinned, weeks, weeksTruncated, dependencies}` (`proposalLists` and `proposalLinks`, shared with the per-team service through `ScheduleProposalAssembly.kt`); `dependencies` are the links touching THAT team, violated before or after over the WHOLE run's final dates (`postCheckMany`; a link between two run teams is in both blocks). **The order of the checks** differs from the per-team route only because the team SET is in the body: the body decodes first (a malformed body is a `400` even for a caller the guard would refuse - there is nothing to guard before it), `validateTeamIds` `400` (1..50, none twice; the guard needs well-formed ids), then `PlanRouteDeps.requireTeamManagers`: every team ACTIVE else `404` for EVERY caller (`TeamService.activeNamesAmong`, one query; the message names the missing ids - ids are no secret), then `requireTeamManagerOfAllOrAdmin` (ADMIN, or one `activeManagedTeamIds` query and every listed team in it, else `403` with the single-team guard's words), then `asOf` `400` (`validateAsOf`; a forbidden caller's malformed `asOf` stays `403`). **One snapshot, no lock:** `CrossTeamProposalService.propose` is ONE read-only REPEATABLE READ transaction whose FIRST statement is the plan revision, then the teams' names, the calendar, per team `teamMilestoneRows` / `positionsOf` / `teamCapacityRows`, and the plan-wide `milestoneFacts` / `linkFacts` read ONCE (`loadCrossTeamSnapshot` -> `CrossTeamSnapshot`), so `revision`, every block, the link verdicts and `scopeHash` describe one plan; a team deleted between the guard and the snapshot is the same `404`. **`scopeHash`** = the same three-part token as the per-team proposal's (the structure digest is over `ScheduleRunScope`, the holidays digest and `asOf` as there; ## Baselines (built — V20, v0.9.0 C5-C7; `planning/Baseline*.kt`, `*BaselineOverlay.kt`)

A **baseline** is a named, immutable copy of the plan's DATED STRUCTURE taken at one plan revision (the user's v0.9 answers, `product.md`): every ACTIVE milestone (name, project, team, estimate, dates) and every ACTIVE project (name, program, work stream, target window, rank position, derived span) — everything the timelines draw. Links, capacity periods, holidays and team orders are NOT copied (they do not "move"; the comparison is about dates). Plan-wide only: one object at one revision, which every page filters to its own rows. Nothing is edited inside a baseline; baselines are not scenarios (one live plan).

- **Tables** (`persistence.md` "The baselines (V20)"): `baselines` (the header; soft-deleted; `uq_baselines_name_active` over `LOWER(name)`; `plan_revision`, `milestone_count`, `project_count`, `created_by_user_id`), and the two FROZEN row tables `baseline_projects` / `baseline_milestones` (no FK to a live row; a `BEFORE UPDATE OR DELETE` trigger and a `BEFORE TRUNCATE` one refuse every change — Flow's `metrics.forbid_snapshot_change` ported without its purge bypass; the header has its own triggers: never hard-deleted, and `id`, `plan_revision`, `created_by_user_id`, the counts and `created_at` never change — only name, description, `updated_at` and the soft-delete flag do). Typed rows rather than a JSON document: the `DATE`/`NUMERIC` idioms, CHECKs, indexed per-team and per-project reads, and a 50-row overlay never parses 1,000 entries.
- **The create** (`BaselineService.create`, one `withPlanWrite`): the grant is re-read under the lock (`requireRoadmapEditorOrAdmin`, the ranking's TOCTOU rule) → the cap (`MAX_ACTIVE_BASELINES` = 100 active; 409 `urn:astrolabe:problem:baseline-limit`, "The limit of 100 baselines is reached: delete one first") → the facts: `loadRoadmapSnapshot` (the roadmap's loaders and ONE `RoadmapKernels` run, so a baseline project's span, rank and target are exactly what the roadmap showed at that moment) plus `baselineMilestoneFacts` (the active milestones with name and estimate) → the header (a name clash is the unique index's 23505 → 409, before the bulk rows) → one `insertRows` per frozen table → the audit. The plan lock makes the copy the plan at ONE revision (no plan writer can interleave); the create bumps the revision like any plan write and stales no client write (`schedule_revision`, the ranking's and the team orders' revisions are untouched, like a holiday write). **`plan_revision` = `revision + 1`** (the revision the create LEFT BEHIND: `withPlanWrite` hands the block the old one), so the plan at that revision equals the baseline exactly: a view whose `revision` equals it shows zero movement; any later state orders against it.
- **Rename and delete** run under `withPlanWrite` too (one lock discipline, as the holidays): `PUT` re-guards, locks the ACTIVE row `FOR NO KEY UPDATE` (gone = 404), updates name and description (audit only on a change; a no-op still bumps the revision); `DELETE` re-guards and flips `marked_as_deleted` (the name frees; the frozen rows stay as history). Both 404 for a gone id. A deleted baseline reads as 404 everywhere.
- **API** (tag `plan`, `authorization.md` for the guards): `POST /baselines` `{name, description?}` → `201` + `Location` + `Baseline`; `GET /baselines` → `{items, can{manage}}`, the ACTIVE baselines newest first (`created_at` then `id`, descending) — a bounded set (≤ 100 by the cap), not paged; `GET /baselines/{id}`; `PUT /baselines/{id}` → `204`; `DELETE /baselines/{id}` → `204`. `Baseline {id, name, description|null, planRevision, createdAt (epoch millis), createdBy {userId, name}|null, milestoneCount, projectCount}`; `createdBy.name` is the login's linked ACTIVE person's name, else its display name (`users.name`) - NEVER its email, which would reach every reader (a person-less login's email is not public, and an email on a lockout-prone account is a targeting aid) - and `createdBy` is null once the login is gone. Name and description follow the registry rules (trimmed single-line name 1..100, description ≤ 500).
- **Audit** (`observability.md`): `baseline.created`, `baseline.updated` (only on a change), `baseline.deleted`.
- **Loaders for the views** (`BaselineRows.kt`, one indexed select each, inside the view's snapshot after `readPlanRevision()`): `activeBaseline(id)`, `frozenProjects(id)` / `frozenProject(id, projectId)`, `frozenMilestonesOfProject(id, projectId)`, `frozenMilestonesOfTeam(id, teamId)`, `frozenMilestonesById(id, ids)`, `frozenMilestones(id)`, plus `teamNames(ids)` (any team, active or not) and `liveTeamsOfMilestones(ids)`.

- **The comparison view** (`GET /views/baseline/{id}`, any authenticated; `BaselineView.kt`, `BaselineViewService.kt`, pure `BaselineComparison.kt`): `{revision, baseline (the registry's Baseline), totals{milestones, projects}, projects[{projectId, name, programName, workStreamName, rankThen, rankNow, baselineSpan, span, movement, counts}], milestones[{milestoneId, name, projectId, teamId, teamName, frozen{start, end, estimateMd}|null, live|null, movement}]}`. Bounded by the plan's scale (≤ 100 project rows, ≤ 1,000 milestone rows). **Two baselines (1.7 C8):** `?against=N` (`optionalUInt`) swaps the "now" side from the live plan to baseline N's frozen rows: the path id is "then", N is "now", `against` (a `BaselineResponse`, ABSENT without the parameter so the plain document is byte-identical) names it, and the fields named `live`/`rankNow`/`span` read N (`BaselineComparison` is side-neutral over `CompareProject` and `MilestoneCapture`; `FrozenProjectRow.toCompare()`, `FrozenMilestoneRow.toCapture()`, `RoadmapProject.toCompare()`). Every ordinary resource list keeps the envelope; **projects and milestones have a paged list** (`GET /projects` rows add `programName`/`workStreamName`, `GET /milestones` rows add `projectName`; sortable `id, name, createdAt, updatedAt`, one `name` filter), work streams and programs have NONE (the plan view is theirs).

**Batch commands.** `POST /teams/{id}/milestone-schedules` takes `{expectedRevision, items[1..1000], scopeHash?}` and answers `{revision, accepted[], skipped[{milestoneId, reason}]}`: unpaged; a per-item failure is data in `200`. `…/schedule-proposal`, `POST /schedule-proposals` (`{asOf, teamIds[1..50]}`, `teams[]` ≤ 50), `…/import-preview` and `…/import` (`items[1..2,000]`) answer one unpaged document each. `POST /schedule-proposals/accept` takes `{expectedRevision, scopeHash, teamIds, items[1..2,000]}` and answers the batch's `{revision, accepted[], skipped[]}`; `…/check` takes `{teamIds, items}` and answers per team `{weeks, dependencies}`.

The `planning/` package at a glance (moved from `CLAUDE.md` "Package layout"): work streams, programs, projects (V12), milestones (V14: dates only by the team's manager/ADMIN), dependencies (V15: the SUCCESSOR's chain writes, cycle-checked), `GET /views/plan`, `GET /views/project/{id}` (derived span + drift, `criticalPath` + slack: pure `CriticalPathKernels`), `GET /views/team/{id}` (weekly load vs capacity and WIP: pure `LoadKernels`); both views' `idleGaps` (pure `IdleGapKernels`), the global project rank (V13, `/roadmap/ranking`; `GET /views/roadmap` and `/views/programs`: pure `RoadmapKernels`), the team milestone order (V17, `PUT /teams/{id}/milestone-order`: the team's own execution order), the v0.8 auto-proposal (`POST /teams/{id}/schedule-proposal`: pure `ScheduleKernels`, nothing stored; `POST …/milestone-schedules`: the batch accept, per-milestone stale + scope checks, one revision bump), the 1.8 cross-team run (`/schedule-proposals`: propose, accept, check — pure `proposeMany`), the public-holiday dictionary (V19, `/public-holidays`: ADMIN registry + Polish preset, read once per view into the `WorkingCalendar`), the baselines (V20, `/baselines` by ADMIN or `ROADMAP_EDITOR`: frozen rows; the views' `?baseline=` and `GET /views/baseline/{id}`: movement in working days, pure `BaselineKernels`): owner-scoped writes under the `plan_state` lock; pure `PlanPermissions` kernel.

## Standing design notes (the v0.2 sketch, all built since)

- Derived spans, drift (built for the project view, `SpanKernels.kt`) and load (built, `LoadKernels.kt`) are computed at request time in pure kernels (`planning/`, Flow's `CapacityKernels.kt` idiom, ported), with shared JSON test vectors for Kotlin and vitest (deferred to the first
  kernel that needs them; `PlanPermissions` is the first pure kernel and is tested against the guards instead).
- More view endpoints (`/views/plan`, `/views/roadmap`, `/views/programs`, `/views/project/{id}` and `/views/team/{id}` are built), each one document with `can:{…}` flags and a revision, like Flow's `/reports/home`.
