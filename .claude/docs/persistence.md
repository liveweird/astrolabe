# Persistence

Owns: the database stack (Flyway, Exposed + R2DBC, the pool), the migrations list, the cross-feature read/write matrix with its lock protocols, the soft-delete and column idioms, and what each table's DDL does not say. Not here: the DDL (the migration files are the source), the plan lock's contract (`planning-model.md` "The lock protocol"), the guard order (`authorization.md`), the sync runs and the token's life (`sync.md`, `jira-sync.md`, `flow-sync.md`).

## Rules

- PostgreSQL is the only database. Runtime access is Exposed over R2DBC; the `org.postgresql:postgresql` JDBC driver is on the classpath solely for Flyway. Migrations are the single source of the schema: never call `SchemaUtils.create`; Exposed table objects are for queries only, never DDL.
- **An applied migration's bytes are immutable, comments included.** Flyway validates stored checksums at startup, so any edit to an existing `V*.sql` makes every long-lived database refuse to boot (a failure no fresh-container CI run can see). `MigrationChecksumTest` pins every file's checksum; a new migration adds one manifest line; a red pin means REVERT the edit (clarifications go into this doc), never update the pinned value. V1 to V35 today.
- Exposed table `object`s are nested in their service (`UserService.Users`). Each service lives next to its feature and is published into `Application.attributes` by `infra/db/Database.kt`, the one composition root. Route handlers never touch tables; services only.
- Ids are `UIntIdTable`, unsigned end to end (the spec declares `minimum: 0`; `ErrorHandling.kt` 400s a negative path segment before it could wrap).
- **The matrix is the permission.** A service may query or write another feature's table when the operation must run inside its own transaction (a join, an atomic snapshot, a soft delete that must also close a dependent row). A new cross-feature read or write adds its matrix cell and its protocol line in the same commit; the Migrations table, the soft-delete list and the matrix grow in the same commit as each migration.
- **Soft delete is the default.** Every business entity is flagged, never removed; every read filters `active()` (the ONE predicate of `infra/db/SoftDelete.kt`); `delete` flips the flag and the route maps `0 rows` to `404`. A hard-delete table needs a documented justification in "Soft delete"; FROZEN rows are never changed. A foreign key from a business entity to a soft-deleted table carries no `ON DELETE` rule (the hard-delete join tables of `users` cascade, inertly: "Per-user permissions (V11)").
- A value freed by a delete is a partial unique index over the ACTIVE rows (`WHERE NOT marked_as_deleted`), its 409 wording registered in `UNIQUE_CONSTRAINT_DETAILS` (unless it is a pure backstop under a lock).
- A paged list counts, reads its page and resolves page projections in ONE read-only REPEATABLE READ transaction (`infra.paging.pagedRead`, `list-endpoints.md`). Every substring filter is `containsNormalized` (`infra/db/Sql.kt`). A create route receives its response DTO from the service's write transaction; audit and the `201` response happen only after that transaction commits, with no post-commit read-back window.
- **Locks.** Lock a row `FOR NO KEY UPDATE` unless the write changes its key (an FK check's `FOR KEY SHARE` must not stall it). A plain `FOR UPDATE` on an FK-referenced row needs its justification in a comment; `plan_state` is the one deliberate plain `FOR UPDATE` on a lock row; `UserAdminGuard.lockedActiveAdminCount` is the justified FK-referenced one ("Row locks vs. FK locks"). Every plan write runs in `withPlanWrite`. A lock order written below is never inverted.
- **Statement timeouts.** ONLY the transaction's `queryTimeout` and the pool's default of it (`postgres.statementTimeoutSeconds`, 15 s) set the statement timeout. Never `SET` or `SET LOCAL statement_timeout`, `set_config`, `RESET` or `DISCARD` on a pooled connection.
- **No transaction spans an outbound HTTP call or a mail send.** `idle_in_transaction_session_timeout` is the backstop, not the design.
- Exposed connects through ONE bounded r2dbc-pool pool built by `connectPooledDatabase`, never a raw `r2dbc:postgresql://` connect. Size it `maxSize × replicas + 1` (Flyway's short-lived JDBC connection) well under the server's `max_connections`; the acquire deadline is in effect about twice its setting.
- A persisted enum value is never renamed or removed (`sync_runs.kind` stores the `SyncKind` name).
- Dates are `DATE` through `infra/db/LocalDateColumn.kt`; estimates are `NUMERIC` via `decimal(…)`; `jsonb` goes through `infra/db/Jsonb.kt` and `canonicalJson` (U+0000 becomes U+FFFD before hashing).
- An encrypted column (`api_token`) holds a `FieldCipher` envelope, is decrypted only by its service's named readers, is never selected on a read path and is registered with the boot backfill (`security.md` "Encryption at rest").
- Pure operational history with no reader once old may be pruned by a fixed, documented retention window; regenerated samples are hard-deleted, never soft-deleted.

## The stack

Connection settings come from the `postgres:` block of `application.yaml` (env-overridable: `POSTGRES_JDBC_URL`, `POSTGRES_R2DBC_URL`, `POSTGRES_USER`, `POSTGRES_PASSWORD`). Defaults match `docker compose up postgres` (host port **5437**; the sibling repos occupy 5432-5436, table in `ci.md`; in-network consumers use `postgres:5432`).

- **Flyway** (`infra/db/Flyway.kt`) runs `db/migration/` at startup through the Java API on a short-lived JDBC connection.
- **Exposed + R2DBC** (`infra/db/Database.kt` and `ConnectionPool.kt`). `Database.kt` constructs the services and publishes them as `Application.attributes` keys (`UserServiceKey`, `PersonServiceKey`, …), wired by concern in this order, a later group taking what an earlier one answers: `wireRegistries`, `wirePlan`, `wireSync`, `wireJira`, `wireFlow`, `wirePlanViews`, `wireAuth`.
- **Schemas.** `public` holds every table but the telemetry; `ops` holds the telemetry (V9: numbers and labels only, never project data). Flyway's history table stays in `public` (`flyway.schemas` is at its default). A schema-qualified table is declared by passing the dotted name to `Table(...)` (`object Samples : Table("ops.telemetry_samples")`); no Exposed `Schema` object and no `search_path` override. `CREATE SCHEMA IF NOT EXISTS` runs in the first migration that needs the schema, never in a standalone "create schemas" migration.
- **Id widths.** `users.id` is `BIGSERIAL` (V1), `teams` and the planning tables `SERIAL`: harmless at this scale, kept so nobody "fixes" one to match the other without a migration (an `INTEGER` FK column may reference the `BIGINT` id); user-referencing columns (`created_by_user_id`, `ack_by_user_id`) are `BIGINT`.

## Connection pool

Applies when touching the connect call of `infra/db/ConnectionPool.kt`, the `postgres.pool.*` configuration, or reasoning about how many PostgreSQL backends one instance can hold.

### Bounds

Exposed connects through ONE bounded `io.r2dbc:r2dbc-pool` `ConnectionPool` (ported from Lettuce via Flow) wrapping the plain PostgreSQL R2DBC factory, built by the one shared `connectPooledDatabase` (the test harness's `sharedDatabaseForTests()` uses it too, with a small pool of its own).
A raw `r2dbc:postgresql://` connect opens one backend per `suspendTransaction` with nothing capping concurrency (Lettuce measured 120 parallel requests taking ALL 100 backends of PostgreSQL's default `max_connections`, and the JWT validation's blocklist read failed and surfaced as an invalid token), so a throwing blocklist lookup answers the catch-all's 500, never 401 (`security.md` "JWT model").

Every bound is boot-validated (startup fails outside the range, through `infra/config/` `requireConfigInt`/`requireConfigLong`):

| Setting | Env | Default | Range |
|---|---|---|---|
| `postgres.pool.maxSize` | `POSTGRES_POOL_MAX_SIZE` | 20 | 1..1000 |
| `postgres.pool.initialSize` | `POSTGRES_POOL_INITIAL_SIZE` | 2 | 0..`maxSize` |
| `postgres.pool.maxAcquireTimeSeconds` | `POSTGRES_POOL_MAX_ACQUIRE_SECONDS` | 10 | 1..600 |
| `postgres.pool.maxIdleTimeSeconds` | `POSTGRES_POOL_MAX_IDLE_SECONDS` | 600 | 1..86400 |
| `postgres.pool.idleInTransactionTimeoutSeconds` | `POSTGRES_POOL_IDLE_IN_TRANSACTION_TIMEOUT_SECONDS` | 300 (0 = off) | 0..86400 |
| `postgres.statementTimeoutSeconds` | `POSTGRES_STATEMENT_TIMEOUT_SECONDS` | 15 (0 = off) | 0..300 |

- `initialSize` is the floor the pool fills up to on its FIRST acquire, not at construction: r2dbc-pool warms up lazily and `warmup()` is deliberately not called.
- Every pooled connection carries `application_name = astrolabe` (`postgres.pool.applicationName`, a test-only override), so an operator counts this instance's backends with `SELECT count(*) FROM pg_stat_activity WHERE application_name = 'astrolabe'`.
- **The acquire deadline is per attempt, and the effective bound is about 2× the setting.** r2dbc-pool 1.0.2 builds `create()` as `Mono.defer { acquire.flatMap(…).timeout(maxAcquireTime) }.retry(acquireRetry)` with the builder default `acquireRetry = 1`: the timeout is an ordinary error to `retry`, so a timed-out waiter is re-queued at the BACK of the acquire queue for a second full deadline.
  Astrolabe keeps the default on purpose: the same retry transparently replaces a connection that fails `LOCAL` validation (`prepareConnection` invalidates it and the outer retry acquires another), so a connection closed from the driver side (a Postgres or pod restart, a FIN/RST on an idle socket) costs no request, whereas `acquireRetry(0)` would fail one per stale connection. The healing has a limit: after a Postgres restart every idle connection is stale, and an acquire that draws more than one in a row (`acquireRetry = 1`) still fails its request. `ConnectionPoolTest` pins the ~2×.
- A caller that waits past the acquire deadline fails with the pool's timeout exception, which the catch-all of `plugins/ErrorHandling.kt` renders as a logged `500`: deliberately NOT a declared status (the conformance gate would need it on every operation).
- The pool is disposed on `ApplicationStopped`, so every `testApplication` releases its connections. Exposed's `R2dbcDatabase.connect(connectionFactory, databaseConfig)` derives the dialect from `databaseConfig.connectionFactoryOptions` alone, so the parsed options (still `driver=postgresql`) are threaded into the config unchanged while traffic goes through the pool. The same config pins `defaultMaxAttempts = 1`: Exposed would otherwise retry ANY `R2dbcException` three times, and a saturated pool would cost 3 × the acquire budget per request.
- **Prepared statements.** The driver's per-connection cache is bounded (`PREPARED_STATEMENT_CACHE_QUERIES` = 256, applied in `connectPooledDatabase`, so the test pool has it too); r2dbc-postgresql's default is unbounded and every cached text stays a named server-side statement for the connection's life. It matters because `MultiRowInsert.kt`'s SQL text varies with the row count (quantized to a handful of sizes per table).
- **A multi-row statement is bounded in payload as well as in bind parameters.** `MultiRowInsert.kt` splits a batch so one statement binds at most `MAX_PAYLOAD_CHARS` (1 MiB) of `String` values (a lone heavier row goes alone, never refused there). `insertRows` and `insertRowsIgnoringConflicts` build each row (run the caller's body) lazily, only while the statement that carries it is assembled, so the rows in flight are one statement's cap and each body runs exactly once; `upsertRows` builds them all first (its collapse of repeated keys needs every key).
  Exposed lists every statement a transaction ran until it ends (parsed SQL and encoded parameters included): `insertRows` clears the list after each statement.
- **Reactor alignment.** r2dbc-pool declares an older reactor-pool than the reactor-core Astrolabe resolves, so `server/build.gradle.kts` imports the Reactor BOM as a platform (the rationale and the coupling to the `netty` pin: the `reactor-bom` comment in `gradle/libs.versions.toml`), and `:server:checkDependencyAlignment` fails when any reactor module resolves to another version.
- **Liveness exception.** The pool runs r2dbc-pool's defaults for liveness (`ValidationDepth.LOCAL`, no `maxLifeTime`): a connection killed server-side between uses is handed out once and fails that request with a 500, accepted until a deployment introduces an idle killer or proxy.

Pinned by: `ConnectionPoolTest` (bounded concurrency, a saturated pool's acquire timeout and its ~2× deadline, disposal on `ApplicationStopped` and on a later module's failed startup, the config range checks), `checkDependencyAlignment`'s Reactor guard.

### Statement timeouts

**Use the transaction's `queryTimeout` and the pool's default of it, nothing else.** Exposed's R2DBC executor *requests* the transaction's `queryTimeout` (whole seconds, never null) from the driver before EVERY statement.

- **The pool's default.** `connectPooledDatabase(…, statementTimeoutSeconds)` hands `postgres.statementTimeoutSeconds` (15 s) to Exposed as `defaultQueryTimeout` (beside `defaultMaxAttempts = 1`), so every statement of every transaction that does not assign its own `queryTimeout` is limited: the views, the lists, the previews, the sync runs and a save waiting for the plan lock (a lock wait included: `FOR UPDATE` on `plan_state`, a row lock, a unique-index wait). The default is the same for every transaction, so the cache below never has to switch it (no extra round trip).
  The parameter comes last with a default of 0, so `sharedDatabaseForTests()` and a test's own pool keep no limit; the harness boots the app with 60 s (`TestEnvironment.kt`).
- **Why 15 s.** Above the longest measured wait (the plan lock held by the 2,000-item Jira import apply, about 2.1 s; `planning-model.md` "Measured figures") and under the browser's 30 s, so the server's answer arrives first.
- **What it does not bound:** the wait for a pooled connection (`maxAcquireTimeSeconds`), a whole request (the limit is per statement), a frozen server (a frozen backend never runs the cancel; Toadie's client-side deadline is not ported) and Flyway's own JDBC connection.
- **A cancelled statement** (SQLSTATE `57014`) aborts its transaction, Exposed rolls it back and the connection stays valid. That transaction wrote nothing, moved no revision and emitted no audit event (routes audit after the service returns). The request answers the existing `500` with `type: urn:astrolabe:problem:database-timeout` (`plugins/ErrorHandling.kt`, `observability.md`).
- **Own budgets win.** A transaction that assigns a `queryTimeout` keeps it (the telemetry reads, 5 s, "Telemetry (V9)"). An explicit `queryTimeout = 0` would switch the pool's limit OFF for that transaction, so the two `sync` readers that take a budget as a parameter (`pollRowsOf`, `SyncRunService.recentRuns`; default 0, the telemetry read API passes its own) assign it only when positive: 0 there means "the pool's own".

**The per-connection cache** (`infra/db/StatementTimeoutCache.kt`). r2dbc-postgresql answers each request with its own `SET STATEMENT_TIMEOUT` simple query that Exposed awaits, a large share of all round trips. `connectPooledDatabase` therefore wraps the RAW connection factory (below the pool) in `StatementTimeoutCachingConnectionFactory`: each physical connection remembers the value the server last confirmed, and the driver call is *sent* only when the requested value differs from it.
No reset on release is needed: Exposed requests its value before every statement, so the borrower after a 30 s budget sees `0 != 30` and sends it, which is also why a budget never leaks to the next borrower.

- **The hazard.** PostgreSQL reverts a session-level `SET` issued inside a transaction when that transaction rolls back, and a statement cancelled by the timeout aborts its transaction; a naive cache would believe the budget is still set and run the next query unbudgeted. The remembered value is therefore forgotten on every rollback (also to a savepoint), on a failed commit and on `setAutoCommit(true)`, forgotten before a SET is sent, remembered only once it completed under an unchanged generation, and kept across a successful commit.
- **Why nothing else may set it.** A `SET LOCAL statement_timeout` may stay in force for the rest of its transaction (the cache no longer sends a request that matches its remembered value, so nothing overwrites it), and a session-level `SET`, `set_config(…, false)`, `RESET` or `DISCARD` on a pooled connection desyncs the cache from the backend.
- Deployment assumption: one client connection is one server session. A transaction-mode PgBouncer in front of Postgres would break the cache (none today).

Pinned by: `StatementTimeoutCacheTest` (own one-connection pool: convergence, the rolled-back SET, the aborted-transaction canary, a budget enforced again after a cancelled statement, the skip with its limit); `ConnectionPoolTest` (the server reports the default, a long statement is cancelled and the connection survives it and a rollback, the range check, the shipped 15); `StatementTimeoutAnswerTest` (a view and a save cut by a lock held in a second session, the log line, the own-budget rules).

### Pool hygiene

Two defences against a backend left holding its transaction, both on every pooled connection (built in `connectPooledDatabase`, so the test pool has them too), and one against a pooled connection pinning a finished request.

- **`infra/db/LeakedSocketGuard.kt`.** r2dbc-postgresql 1.1.3 never closes the socket after a protocol-level connection error ("Response queue is full"); the backend then keeps its transaction and locks for the life of the process (`idle in transaction`, or `active` in `ClientWrite`, which no server timeout ends). A decorator on the RAW factory (below the pool, beside the statement-timeout cache) disposes the netty channel after the driver's close when the client is closed but the channel is open;
  the pool's release validation (`LOCAL`) then fails such a connection at once and destroys it. It reads two private driver fields by reflection; `LeakedSocketGuardTest` pins them AND the driver bug on an unguarded connection (red after an upgrade = the upstream fix landed: delete the guard).
- **`idle_in_transaction_session_timeout`**, sent as a startup parameter (`postgres.pool.idleInTransactionTimeoutSeconds`, default 300; an operator's own `options=` key in the URL wins): the server ends any pooled session idle inside a transaction for longer, the backstop for a client that stopped talking with a transaction open (a coroutine stuck mid-transaction). It is a different setting from the statement timeout, so the "only `queryTimeout`" rule is untouched. `LeakedSocketGuardTest` pins both.
- **A pooled connection must not pin the frame that created it.** reactor-netty keeps the subscriber chain of the `create()` that opened a channel on the channel (`ChannelOperations.listener`) for its whole life; through r2dbc-pool and Exposed's `awaitOne` that chain reached the continuation of the coroutine that triggered the creation, so a finished request's frame stayed reachable from the netty selector for minutes.
  `infra/db/DetachingConnectionFactory.kt` ends the chain at a bridge: it subscribes to the real `create()` with a `DetachingBridge`, forwards the one connection, error or completion to the pool and then DROPS the pool's subscriber, and it offers the driver an EMPTY Reactor context (reactor-netty copies the subscriber context into the observer at connect time). It is the OUTERMOST decorator of the raw factory, so a connection it closes is the decorated one (the close reaches the socket guard).
  It honours demand, delivers exactly once and CLOSES a connection nobody owns (it arrived after a cancel): never a leaked socket.

Pinned by: `PooledConnectionPinTest` (weak references on a fresh pool: a 16 MiB array held across the query, the connection idle, `System.gc()` must clear it; its callers run on `Dispatchers.IO`, since a query on the `runBlocking` thread keeps a stale reference on that thread's own stack), `DetachingConnectionFactoryTest` (the contract without a database).

## Cross-feature table reads and writes

A feature service MAY query, or WRITE, another feature's Exposed table objects directly when the operation must run **inside its own transaction** (a join, an atomic snapshot, a soft delete that must also close a dependent row; Exposed reuses an enclosing transaction for nested `suspendTransaction` calls on the same database). Route handlers never touch tables.

*Owner* is the service whose Exposed object declares the table (a cell or a note may write the object bare, `Projects` for `ProjectService.Projects`, `Programs`, `WorkStreams`, `RoadmapEntries`, `People`, `Teams`); `Bindings`, `Connections` and `Acknowledgements` are the section connector's own object. *Also read by* and *Also written by* name every other service that touches it, inside or outside its package (a bare package name means every service of that package that needs it; the owner's `###` below names them and holds the reasons, the locks and the order);
a write through the owner's exported function (`deleteCapacityPeriodsOf`, `removeFromRanking`, …) counts as the caller's. *Protocol* names the `###` that holds the notes.

### People

Files: `people/PersonService.kt`.

- `PersonService` reads `UserService.Users` (the linked login: the active-user check on create AND update, the login's email on read and list through ACTIVE users) and `TeamService.Teams` (the delete 409 while the person manages an ACTIVE team). `planning/OwnerChains.kt`'s `ownsActivePlanNode` extends the delete refusal to an ACTIVE work stream, program or project the person owns.
- `people.user_id` has no `ON DELETE` rule: users are only soft-deleted and the link stays INERT while the user is deleted (a deleted login never passes the access verdict). A future hard purge of users must clear it first; a future user RESTORE must re-audit the link (the partial unique index refuses a clash if the person was re-linked meanwhile). No row lock and no `plan_state` (the new user row is the transaction's own, so the person's FK check waits on nothing); a failure anywhere, an email clash on the person side included, rolls back both.

### Teams

Files: `teams/TeamService.kt`, `teams/TeamCapacityService.kt`, `teams/TeamCapacityImportStore.kt` (the import's reads and writes behind the service's delegates), `teams/TeamCapacityListeners.kt`.

- `TeamService` reads `PersonService.People` for the manager: the active manager's name (one batched lookup per page); the manager id check on create AND update, which locks the person row `FOR SHARE` (a delete racing an assignment either commits first and the assignment is a 400, or waits and then sees the team and answers 409); and `isActiveManager`'s `Teams` ⋈ `People` ⋈ `Users` join (the team-manager guard: an ACTIVE team, an ACTIVE person whose `user_id` is the caller, that user ACTIVE).

- `TeamService.activeManagedTeamIds(userId)` (the `can.schedule` flags) is `isActiveManager`'s join without the team id: a plain read, no lock.
- `TeamCapacityService` owns `team_capacity_periods` and reads and locks `TeamService.Teams`. Every write: the capacity-write listeners lock their rows for the team first (`flow/`'s binding row), then `Teams.lockActiveForWrite(teamId)` (`FOR NO KEY UPDATE`), then `TeamService.lockedIsActiveManager` (`FOR SHARE OF teams, people`, the guard's second run), then the writes. No plan lock. Reads join `Teams` for the `active()` predicate.
- `TeamService.delete` WRITES `team_capacity_periods` through `deleteCapacityPeriodsOf` (the team's ACTIVE periods soft-deleted inside its locked transaction, after the milestone 409; the count goes to `team.deleted`). `team_capacity_periods.team_id → teams(id)` has no `ON DELETE` rule: teams are only soft-deleted.
- `ck_team_capacity_periods_wip` (`wip_limit` NULL or 1..99) and `ck_team_capacity_periods_md` (`>= 0`) back the validator up; the unique index also serves the per-team reads (no separate `team_id` index). `TeamCapacityLifecycleTest` pins them.
- **Provenance columns.** `source` (`MANUAL` or `FLOW`, `ck_team_capacity_periods_source`; Kotlin `CapacityPeriods.capacitySource`, because Exposed's `Table.source` is taken), `flow_sprint_id`, `flow_sprint_name`. `create` writes `MANUAL`; `update` (the PUT) always leaves the period `MANUAL` with the sprint columns cleared, even with equal figures (`CapacityUpdateOutcome.sourceBefore`; `planning-model.md` "Team capacity periods").
  `planning/TeamViewRows.kt`, `TeamLoadRows.kt` and `BaselineCaptures.kt` (`activeCapacityPeriodsOfActiveTeams`) read the periods through `teams/TeamCapacityRows.kt` (`activeCapacityPeriods`, the one ordered ACTIVE query; `toCapacityPeriodResponse`, the one row-to-wire mapping).
- **`applyImport` is the ONLY writer of `source = 'FLOW'` rows** and the only way `flow/` writes `team_capacity_periods` (`teams/` names no `flow/` type: it takes the guard and a `decide` lambda that `flow/` fills with its kernel's answer).
  ONE transaction (the steps and the per-item checks: `flow-sync.md` "The apply"): the listeners' locks (the team's binding row), `Teams.lockActiveForWrite` (gone = 404), the guard's second run (a manager cleared while the request waited is a 403 and nothing is written), the team's ACTIVE periods read under the lock, `decide`, then removals, updates and creates (deletes before inserts: a freed date can be taken again). No plan lock and no revision: capacity is team data.
- **A MANUAL period is never written, twice over.** `requireOnlyFlowPeriodsChanged` checks every update and delete against the rows read under the lock (FLOW, this team, each period once; every new date free among the periods that remain) and aborts with an `IllegalStateException` (a bug: a 500, nothing written); and every `UPDATE`'s own `WHERE` adds `source = 'FLOW'` and checks the row count.
- **No wait cycle through the apply.** It takes the global capacity-write order below and nothing else: no connection-row lock, no mirror or binding row written, so `FlowMirrorStore.replace` (connection row) and a bind (connection row `FOR SHARE`, its own team's binding rows, then the team row `FOR SHARE`) cannot close a cycle with it; it waits only on the binding row, then on the team, manager and person rows, whose holders wait on nothing the apply holds.
  The mirror is read in ONE statement (`FlowMirrorStore.teamSprintsOf`), so "absent from the mirror" and "its sprints" are decided by one snapshot.
- **The connector seam** (`teams/TeamCapacityListeners.kt`; the prune it carries: `flow-sync.md` "The capacity write's prune"). `CapacityWriteListeners` (published empty by `configureDatabase`, filled by `configureFlow`) holds the `CapacityWriteListener`s that `TeamCapacityService` calls INSIDE every write's transaction: `lockBeforeTeam(teamId)` BEFORE `Teams.lockActiveForWrite` (the connector takes its own rows for the team first, then the team, never the reverse;
  it answers the ids it locked) and `settle(teamId, locked, trail)` after the write's last statement, only for a write that changed a period; the connector prunes ONLY what it locked and locks nothing new. A failure in either aborts the write; what must wait for the commit (the audit line) is queued on the caller's `CapacityWriteTrail`.
- **The one global lock order of the capacity writes:** the connection row, the binding row, the team row, the manager and person rows, the acknowledgement rows. The one listener is `CapacityAcknowledgeService`'s `lockBindingsBeforeCapacityWrite` / `pruneInCapacityWrite` ("Flow", below).

A manager change (`TeamService.update`, `FOR NO KEY UPDATE`) or a re-link or delete of the manager's person either commits first (403 under the lock, no bump) or waits.
  `FOR SHARE` is refused with an aggregate, so the twin reads rows, never `count()`.

- **Dependencies.** `DependencyService` reads `Milestones`, `Projects`, `Programs`, `WorkStreams` and `Teams` under the plan lock on a write: `dependencyChain` (the SUCCESSOR's project chain), `isActiveEndpoint`, `resolveEndpoints` (a milestone's name, project and team, a project's name and DERIVED span over its scheduled ACTIVE milestones; names read WITHOUT an `active()` filter, since an active milestone's project and team are active) and `loadTimePointGraph` (every active milestone's `(id, project_id)` and every active dependency: the cycle check's input).

- `PublicHolidayService` WRITES only its own table (hard delete) and only inside `withPlanWrite` (so it takes the lock and bumps the revision like every plan write); it reads no other feature's table.

### Jira

Files: `jira/Jira{ConnectionService,MappingStore,TestRecorder,IssueStore,BindingService,AcknowledgeService,RunStore,ImportService,ImportApply,Census}.kt`, `JiraBindingNodes.kt`, `DeviationViewService.kt`, `DeviationViewRows.kt`, `DeviationCoverageRows.kt`, `JiraLinksView.kt`, `JiraCoverage.kt`. Nothing here is plan state except the import's apply: a connection, a binding and an observation take no plan lock and bump no revision. Each part below is one service.

#### Jira connections

- `JiraConnectionService` reads and writes its own table `jira_connections` (the registry: soft delete) and reads no other feature's table except `sync_runs`, through `SyncRunService.recentRunsInTransaction`, for each response's derived `status` in the same transaction. Its `delete` is ONE transaction that also: soft-deletes the connection's ACTIVE `jira_bindings` (`uq_jira_bindings_node_active` has no connection column, so a binding left active on a deleted connection would block its node for good; the count goes to the `jira.connection_deleted` audit as `bindingsUnbound`);
  hard-deletes the connection's `sync_runs` (`SyncRunService.deleteForConnectionInTransaction`) and its `jira_issues` (`JiraIssueStore.deleteForConnectionInTransaction`; the count rides `JiraConnectionDeleteOutcome.censusDeleted` to a log INFO after the commit, no audit field); and sets `api_token` NULL.
- **Encrypted `api_token`** (`enc:v1:` envelope, or NULL on a deleted row only: `ck_jira_connections_api_token` and `_live`). Decrypted by exactly three readers: `readForTest` (the Test connection), `readForPeek` (the target with the token decrypted in memory plus the mapping state, ONE short transaction before the Jira call, none across it) and `readForBind` (the target, mapping state and `enabled`, one short transaction before the bind's Jira call; the only one a non-ADMIN can trigger). The Jira sync run is a second CALLER of `readForBind`, not a fourth decrypt site.
  A decrypt failure reads as a null token, never an exception (the run then reports the typed `TOKEN_UNREADABLE`). Never on a read path (the response carries `hasApiToken`); registered with the boot backfill (`EncryptedAtRest`).
- **A stored Test connection** (`JiraTestRecorder`, over the same table, never selects `api_token`) records `cloud_id`, `last_tested_at/ok` (the real verdict) and, whenever the `field` and `issuetype` probes both answered (a failed other probe notwithstanding), the `discovery` snapshot (up to ~300 KB, so the registry's reads select every column but `discovery`) under a row `FOR NO KEY UPDATE`, skipped when the row was edited since it was read. A change of token, account email, auth scheme or project keys clears `last_tested_at/ok`.
- `poll_interval_minutes` (nullable, CHECK 5..1440, NULL = manual only) is written by `create` and `update`; a PUT is a full replace, so a PUT without the member resets it to the default 15.
- **The mapping document** (`JiraMappingStore`, selects only `mapping` and `discovery`, never `api_token`): `writeMapping` locks the row `FOR NO KEY UPDATE` (so it serializes with a Test connection replacing the snapshot), validates against the snapshot it just read (a missing one is a 409), writes the canonical text and NOT `updated_at` (a mapping is not an input of a Test connection, so a PUT landing between `readForTest` and `recordTest` must not make the latter drop its result), and stamps `mapping_changed_at` when, and only when, the canonical document differs from the stored
  one (the run's signal to read in full). It rewrites nothing else: bindings and observations are untouched.

#### Jira census

- `JiraIssueStore` OWNS `jira_issues` and the `jira_connections.census_at` column (the `Connections` object declares it; ONLY the store writes it, `stampCensus`). `upsert` (`upsertRows` over `(connection_id, issue_id)`, ONE short transaction per chunk, every column of a row set so a fresh read overwrites) first takes the connection row `FOR SHARE` and skips the write when it is no longer ACTIVE: a delete holds `FOR NO KEY UPDATE`, so a racing run either finishes first (the delete then removes its rows) or finds the connection gone, and no mirror row outlives its connection.
  `index`, `delete` (by ids; the caller chunks by `RUN_CHUNK` = 100) and `censusAt` are plain reads and writes; none takes the plan lock or touches a revision.
- **The run writes it** (`JiraCensus.kt`; the passes, the prunes and the self-healing: `jira-sync.md` "The census"): rows are flushed through `upsert` in `RUN_CHUNK`s, the run prunes against the sweep's listing in `RUN_CHUNK` batches and `stampCensus` writes `census_at`; a child listing that hit the page ceiling prunes NOTHING.
- The deviation view is the only VIEW that reads it (`DeviationCoverageRows.kt`). The mirror keeps Jira business text in PLAINTEXT like `jira_observations` (`security.md` "Encryption at rest"); a row is kept only for a type the run's sweeps ask for, so an issue of an unlisted type never flaps in and out.

#### Jira bindings and the bind

- `JiraBindingService` OWNS `jira_bindings` and writes the FIRST `jira_observations` row of a bind (`JiraObservations.kt`: the table object the run's observer upserts through). It READS `planning`: `OwnerChains.kt`'s `programChain`, `projectChain`, `milestoneChain` (the ACTIVE chain: the guard's input and the "is this node dead?" test of the inline release) and, in `JiraBindingNodes.kt`, the node tables for the nodes' names (batched per level, no `active()` filter: nodes a page of live bindings sits on), the `lastKnownChain` of a binding whose node is gone (the unbind guard:
  the owner columns WITHOUT any `active()` filter, for the guard only) and the list's live-node and `q` sub-queries (a binding is listed only while its node and every ancestor are ACTIVE). It READS `JiraConnectionService.Connections` (`site_url`, `enabled`; never `api_token`, never `discovery`) and `Users` and `People` through `creatorsOf` (the ACTIVE person, else the login's display name, never an email). The guard is `requireOwnerOrAdmin`.
- **Locks, in this order, all inside the bind's one transaction (the Jira call is made BEFORE it, in the route, never inside it):** (1) `pg_advisory_xact_lock(BIND_LOCK_KEY)`, ONE global transaction-scoped advisory lock taken first by every bind (binds are human clicks of a few milliseconds, so global serialization costs nothing and makes the checks exact; the cross-connection rule is a check over rows that do not exist yet, which no row lock can serialize);
  (2) the connection row `FOR SHARE` (conflicts with the delete's and edits' `FOR NO KEY UPDATE`: a delete racing a bind either commits first, the bind is a 400, or waits and then unbinds the committed binding); (3) the node's own row `FOR SHARE` (`lockNodeShared`; conflicts with its soft delete and owner change: either the delete commits first, the bind is a 404, or the binding is released by the next bind or the run's sweep); never an ancestor's row, so no lock cycle with a plan writer that updates a chain top-down;
  (4) the caller's person row `FOR SHARE` inside the guard's second run (`PersonService.lockedActivePersonIdOf`); (5) the conflicting ACTIVE bindings `FOR NO KEY UPDATE`, in id order.
- The connection row is selected WITH its `project_keys` in that same locked statement and the issue key's project is re-checked against them, so a `projectKeys` PUT that lands while the Jira read is in flight cannot commit an out-of-scope binding (`JiraBindingGuardRaceTest`).
  Nothing else creates an active binding while the advisory lock is held (unbind, the connection delete and the sweep only free rows), so the node check, the issue check (this connection AND every other ACTIVE connection with the same `LOWER(site_url)`) and the insert are exact, and the two V21 unique indexes are a pure backstop (`ErrorHandling.kt` carries no wording for their 23505s, so a violation that escaped the locked checks answers the generic `409`).
- A conflicting binding of the ISSUE whose node (or any ancestor) is soft-deleted is RELEASED (soft-deleted in the same transaction, reported to the route for the `jira.binding_released` audit after the commit); a live holder is a `409 already-bound`. **Residual window, named:** an ANCESTOR's owner changed (or the caller's right through an ancestor revoked) between the chain re-read and the commit is not excluded, because only the node's own row is locked; the effect is a binding made by a caller who stopped owning the chain milliseconds earlier.
- `jira_observations.binding_id` and the binding FKs to `programs`, `projects`, `milestones`, `users` and `jira_connections` have no `ON DELETE` rule (all soft-deleted).

#### Jira acknowledge

- `JiraAcknowledgeService` (`POST` and `DELETE /integrations/jira/bindings/{id}/acknowledge`) OWNS `jira_deviation_acknowledgements` (keyed `(binding, kind)`) and WRITES nothing else: not `jira_bindings` (not even `updated_at`), no plan lock, no revision bump, no `plan_state` read.
- **Every write of the table holds the binding's row lock** (`lockActiveForWrite`, first): `acknowledge` is delete-the-target-kinds then ONE `insertRows` (the stamps of the lines it covers, each with its own fingerprint), `unacknowledge` deletes the named kind's row or every row of the binding, and no concurrent writer can interleave. A held request re-reads the rows as they are when it gets the lock (`JiraAcknowledgeRaceTest`).
- It READS the ACTIVE chains (`activeChain`), `Users` and `People` through `creatorsOf` (`acknowledgedBy`: the ACTIVE person's name, else the login's display name, never an email) and, to recompute the one binding's deviations IN its own transaction, everything the deviations view reads (`DeviationViewService.computeBindingInTransaction`). The scope names the binding's connection too, so only that connection row (and its discovery) is decoded.
- **Locks, one short READ COMMITTED transaction:** (1) the binding row `FOR NO KEY UPDATE` (gone = 404); (2) the caller's person row `FOR SHARE` inside the guard's second run (`lockedActivePersonIdOf`; the unbind's order: a person writer never waits for a binding row, so no cycle);
  (3) only for a caller who is neither ADMIN nor on the node's owner chain and only on a MILESTONE binding: the milestone's STORED team (re-read with the chain) and that team's manager person, both `FOR SHARE` in one statement (`TeamService.lockedIsActiveManager`, the schedule PUT's and the Flow acknowledge's twin).
- **Why no cycle:** every writer of `teams` and of `people` locks its own row and never waits for a `jira_bindings` row, so nothing holds a team or person lock while waiting for a binding row; the order (binding, person, team, manager person) is the Flow acknowledge's with the caller's person added in front. The row lock is what makes the compare exact: the run's observation write locks the same binding row first (`JiraRunStore.lockActive`), so the Jira side cannot move under the compare;
  the plan side is read statement by statement, so an edit landing in between makes the compare a `409` or, at worst, accepts the fingerprint of a mixed state, which is harmless (a stored fingerprint is re-compared on every read, such an acknowledgement just reads `current = false`).
- **Residual window:** the milestone row itself is not locked, so a team change committing between the guard's re-read and the commit is judged on the old team (the same class as an ancestor owner change; the effect is one acknowledgement stamp, never plan data; locking the milestone row here could deadlock against the import apply, which locks milestone rows before binding rows).
- `ack_by_user_id` has no `ON DELETE` rule: a soft-deleted login keeps its acknowledgement and reads `by = null`; a retired kind's row is ignored on read and cleared by the kind-less withdrawal.

#### Jira run store

- `JiraRunStore` is the run's database side. It OWNS the upserts of `jira_observations` (`upsertRows` over `binding_id`, one transaction per chunk of 100 bindings, EVERY column of the row set so a fresh read always carries `gone = false`) and the `gone` flag: `markGone` and `clearGone` (`OUT_OF_SCOPE`, refined to `DELETED` or `FORBIDDEN` by the run's probe via `recordProbe`, which stamps `gone_probed_at` and, for a 200, keeps the validated issue key in `gone_probed_key` and moves the binding's `jira_issue_key` to it).
  The stored reason is never `MOVED_OUT` or `NOT_LISTED`: the API derives those wire values from `OUT_OF_SCOPE` plus a non-null stamp plus the key against the connection's current project keys (`wireGoneReason`). The four writers (`writeObservations`, `markGone`, `clearGone`, `recordProbe`) set or clear the stamp and the key with the flag; the bind and the import's `insertFirstObservation` rely on the column default (gone = false, stamp NULL).
- A dead node's or a deleted connection's binding stays a row and is simply not read into any answer.
- It WRITES `jira_bindings.marked_as_deleted` for the node sweep (`releaseDeadNodeBindings`: the connection's ACTIVE bindings whose node or any ancestor is soft-deleted, `NODE_GONE`). It READS `jira_bindings` (**every read filters `Bindings.active()`**: a deleted connection's rows stay in the table) left-joined to `jira_observations`, and, through `JiraBindingNodes.kt`'s `liveNodeIds`, the node tables for a node's liveness (decided in Kotlin: `NOT (a OR b OR c)` over the three nullable node columns is NULL, not true, for a dead node).
- **A run takes no plan lock, bumps no revision and holds no transaction across a Jira call.** Each write transaction re-selects its bindings `active()` in ID ORDER: `FOR NO KEY UPDATE` for the chunk that may rewrite a key (never upgraded from `FOR SHARE`) and `FOR SHARE` for the gone-flag writes (the probe's answer takes `FOR NO KEY UPDATE` when it carries a key). So a binding unbound after the run started is skipped (never resurrected, never an FK failure) and an unbind waits for the chunk or has won.
  The run's transaction takes binding rows and nothing before them, so the bind's order (advisory lock, connection, node, person, binding rows) still holds. A moved issue's new key (an observation whose key differs from `jira_issue_key`) is written to `jira_bindings.jira_issue_key` in the same chunk, with a new `updated_at` for those rows only.
- **Residual deadlock, named:** the connection delete's `UPDATE` of all its bindings locks rows in scan order, not id order, so a chunk and a delete can in theory lock two rows in opposite orders (`40P01`); PostgreSQL aborts one, the run ends `FAILED`/`INTERNAL` (class names only in the log) and the next run recovers on its own. A binding created after the run's start snapshot waits for the next run.
- `JiraObserver` itself touches no table. The run asks `JiraConnectionService.runnableState` (its own short transaction) before every search page and stops with `CONNECTION_GONE` or `CONNECTION_DISABLED` once the connection is deleted or disabled.

#### Jira import

- **The preview** (`JiraImportService.read`) WRITES nothing and takes NO lock: ONE `READ ONLY REPEATABLE READ` transaction (`SNAPSHOT`) that reads the plan revision FIRST, then `PublicHolidays`, the picked work stream's active tree (each node's owner for the guards' chains), ALL active `programs.name` (the global name rule), the ACTIVE `teams` (the caller's managed teams through `TeamService.activeManagedTeamIds`, which reuses this transaction) and the active bindings of the browsed issues on every active connection of the site.
  `requireShape` and `namedChains` are plain short reads (for a rooted import also the root's `activeChain`, its place under the picked stream and, in `resolveRoot`, its active `jira_bindings` row, no lock). The browse calls Jira outside every transaction; under an active filter it also makes one short read-only read of `jira_bindings` per round of by-id parent reads (`liveHeldIssueIds`, no lock), BETWEEN Jira calls, never inside one.
- **The apply** (`JiraImportApply.kt`, `JiraImportService.apply`) is the ONE Jira write that moves the plan. It WRITES in ONE `withPlanWrite` (one bump, also when everything is skipped): `programs`, `projects`, `milestones` through `PlanNodeInserts.kt` (milestones inserted with `schedule_revision = revision + 1`); the dates, `schedule_revision` and `updated_at` through `writeSchedules` at `revision + 1` for the scheduled ones (the third writer of those columns, beside `MilestoneService.schedule` and `TeamScheduleService`;
  a client at the answered revision is not stale and a view older than the import is); and `jira_bindings` and `jira_observations` through `JiraBindingService.insertBoundLocked` (the dead-node holders it finds are soft-deleted: the binding's own release). It writes dates only on a milestone it just inserted, so it never clears a pin.
- **Lock order, which nothing may invert:** the plan lock (`plan_state FOR UPDATE`), then `pg_advisory_xact_lock(BIND_LOCK_KEY)`, the connection row `FOR SHARE` (gone `404`, disabled `400`, project keys moved since the browse `400`, `mapping_changed_at` or `discovered_at` moved `409`), the caller's person `FOR SHARE`, the named defaults' chains (and the rooted import's chain, re-read and guarded the same way), the owner (`requireActiveOwner`) then every `overrides.ownerPersonId` (distinct, ascending, after the dialog's owner) and every named team (`requireActiveTeam`) `FOR SHARE`,
  the caller's managed teams (`lockedIsActiveManager`), then the plan side re-read (tree, names, holders, calendar: plain reads, exact under the lock), the kernel over THOSE rows, (a rooted import: the root's own row must be `ALREADY_BOUND` to the root node through this connection, else the `409`), the guard on every ticked CREATE or BIND row's target, the dead holders to release locked `FOR NO KEY UPDATE` in ONE `ORDER BY id` statement (the run's sweep updates in id order), each written milestone's team `FOR SHARE`, then top-down, per row, the insert of a CREATE's node or
  `lockNodeShared` on a BIND's target, `writeSchedules`, and per written row `insertBoundLocked`.
- **No cycle:** a bind holds the advisory lock and waits only on node, person and binding rows; node rows are held by plan writers (never concurrent with the import, which holds the plan lock), person rows by person writers, binding rows by an unbind or the run's sweep, none of which waits for the advisory lock; and the import takes the advisory lock before touching any row (`JiraImportApplyRaceTest` races one against the other and pins that an import waiting for the plan lock holds no advisory lock). A rooted import adds NO lock.
  **Accepted:** a root unlinked by someone else in the instant after the holders are read still gets its children under the root NODE, and a root moved to another work stream meanwhile leaves every ticked row `NO_PARENT` (`CHANGED` where a default project is sent); either way nothing is written.
- The Jira browse happens BEFORE the transaction: the plan lock is never held across HTTP. **`NAME_TAKEN` is decided in Kotlin** from the names read under the plan lock (programs: every active `LOWER(name)`; projects per parent program; milestones per parent project) plus the batch's own earlier rows: exact because every creator of these rows holds the plan lock. The `uq_*` indexes stay the backstop: a `23505` aborts the whole transaction (it cannot be caught per row) and is the central whole-request `409`.
  Residual: PostgreSQL `LOWER()` vs Kotlin `lowercase()` disagreeing on an exotic character. Measured hold: `JiraImportScaleTest`, `build-times.md`.

  ACTIVE bindings ⋈ connections aliased as the peer, the SAME `site_url`, the very rule `bindingOnSameSite()` states for the Deviations view), so the linked verdict is computed once per row.

### Sync

Files: `sync/SyncRunService.kt`, `ConnectionRegistry.kt`, `SyncStatus.kt`.

- `SyncRunService` OWNS `sync_runs` and reads no other table. `sync/ConnectionRegistry.kt` (`runnableStateOf`, `isRunnable`, `pollRowsOf`) reads a connector's connection table passed in as a parameter, only through the `ConnectionColumns` interface (name, enabled, interval, `updated_at`, `marked_as_deleted`: no credential column; the connector's own mapper adds its `ready` and `changedAt` columns). `statusesInTransaction(kind, …)` (`SyncStatus.kt`) is the one status reader both connectors call.
  `sync/` imports no connector package: the registry is `SyncConnectors`, filled by `configureJira` and `configureFlow`.
- `sync_runs.kind` stores the `SyncKind` NAME (`JIRA` or `FLOW`); the V21 CHECK admits exactly those two, and a persisted enum value is never renamed or removed.
- **`claim` is ONE transaction:** finish any unfinished row of the `(kind, connection)` older than `sync.maxRunMinutes` as `ABANDONED`, prune the FINISHED rows to the newest 49, INSERT the unfinished row. A `23505` on `uq_sync_runs_running` is the `409 run-in-progress` (the abandon and the prune roll back with it, harmlessly). The partial unique index IS the lock (`sync.md` "The run registry and the claim" for the replicas): no advisory lock, no `SKIP LOCKED`.
  `finish` updates `WHERE finished_at IS NULL` only, so a late finish never rewrites an abandonment.
- **The claim takes the CONNECTION row `FOR SHARE`** (through `Connector.lockActiveInTransaction`, the connector's own service: `JiraConnectionService.lockActiveInTransaction` or `FlowConnectionService.lockActiveInTransaction`, on the ACTIVE row) BEFORE it touches `sync_runs` (`lockActiveConnection`), against the delete's `FOR NO KEY UPDATE` on the same row followed by its run purge. A claim racing a delete therefore lands first (the delete removes its row) or is refused `400` after it (`SyncClaimDeleteRaceTest`, and `SyncClaimDeletedConnectionTest` through the real observers);
  no run is ever left for a deleted connection, and `sync_runs` needs no FK or sweep.
- `recentRuns` and `recentRunsInTransaction` read `started_at`, `finished_at` and `outcome` of a connection's newest 50 rows for the scheduler's due rule (one indexed `LIMIT` per connection, `idx_sync_runs_connection`); the scheduler writes nothing but through `claim`. The timeline views' Jira fold reads the REFERENCED connections' newest runs through `DeviationViewService.siteStatesInTransaction` (one indexed `LIMIT` read per connection inside the view's snapshot, none for a plan without a binding); `JiraCoverageService` reads `lastSucceededInTransaction`;
  `telemetry/` reads through `TelemetrySync`.

### Flow

Files: `flow/Flow{ConnectionService,MirrorStore,TeamBindingService,TeamService}.kt`, `CapacityImportService.kt`, `CapacityDeviationService.kt`, `CapacityAcknowledgeService.kt`.

#### Flow connections and the mirror

- `FlowConnectionService` reads and writes its own table `flow_connections` (the registry: soft delete, no plan lock, no revision) and nothing of any other feature's but through the owners' own methods. Its `delete` runs in ONE transaction under the connection row `FOR NO KEY UPDATE` and: sets `api_token` NULL (`enc:v1:` envelope, or NULL on a deleted row only: `ck_flow_connections_api_token` and `_live`); soft-deletes the connection's ACTIVE `flow_team_bindings` (the count `bindingsUnbound` goes to the `flow.connection_deleted` audit;

- `flow/` WRITES no other feature's table; the capacity import's apply writes `team_capacity_periods` only through `TeamCapacityService.applyImport` ("Teams").
- **`FlowMirrorStore`** OWNS `flow_teams`, `flow_sprints`, `flow_members` and the `flow_connections.teams_at` column (the `Connections` object declares it; ONLY the store writes it). `replace` (the run's one write, `FlowObserver`) is ONE transaction: the connection row `FOR NO KEY UPDATE` (taken at its final strength, since the same transaction stamps `teams_at` on that row: never `FOR SHARE` upgraded by the UPDATE;
  a delete, an edit or a second replace queues on it, so a racing run either finishes first and the delete removes its rows, or finds the connection gone and writes nothing: no mirror row outlives its connection), then the three tables' old rows deleted, the new ones inserted by multi-row `insertRows` (fitted to the columns first: text cut, control characters to spaces, an out-of-range figure dropped, a repeated key collapsed to the first), `teams_at` stamped. A failure rolls the whole document back and the previous one stays.
  The V31 `sprints_complete` flag and the truncated-document rules (`keepAbsentTeams`): `flow-sync.md` "The run".
- `replace` takes no plan lock, bumps no revision and holds no transaction across an outbound call. Its `FOR NO KEY UPDATE` does not conflict with an FK check's `FOR KEY SHARE`, so a binding insert is never stalled by a replace. It writes no acknowledgement itself: its `afterWrite` block runs inside the transaction after `teams_at` is stamped, and the run fills it with `CapacityAcknowledgeService.pruneConnectionInTransaction`, which takes the binding rows AFTER the connection row.

#### Flow bindings and reads

- `FlowTeamBindingService` OWNS `flow_team_bindings` (the writes `bind`, `unbind`, `match`; the reads `bindingsOf`/`teamIdOf`, every one filtering `Bindings.active()` AND joining `TeamService.Teams` on `active()`). It READS `teams` (active ids and names), LOCKS the team row `FOR SHARE` in a link or a match (it writes no `teams` row), reads the connection row (`FOR SHARE`: enabled) and the mirror's `flow_teams` (the Flow team's name). `FlowTeamService` (the Flow team list and the team panel) is read-only over the mirror, the bindings, the registry and `teams`.
- **Lock order of a link:** the advisory bind lock (`FLOW_BIND_LOCK_KEY`), the connection row `FOR SHARE`, **the linked team's OWN binding rows `FOR NO KEY UPDATE` (before the team row, because a capacity write holds a binding row and then waits for the team row `FOR NO KEY UPDATE`)**, the team row `FOR SHARE`, the guard's team and person rows, then the Flow team's holder binding rows (other teams' bindings, taken after the team share: safe, because the capacity write holding one of those waits for THAT team's row, which this link does not hold) and the insert.
  **Of a match:** the advisory bind lock, the connection row, ALL of the connection's binding rows `FOR NO KEY UPDATE`, then the candidate (unbound) teams `FOR SHARE`.
- `flow_team_bindings.team_id → teams(id)`, `created_by_user_id → users(id)` (a plain `long` column in Exposed: `flow/` imports no `users` type) and `connection_id → flow_connections(id)` have no `ON DELETE` rule: all are soft-deleted.
  **A soft-deleted team leaves its binding ACTIVE** (`teams/` may not name `flow/`, so `TeamService.delete` cannot unbind), and `uq_flow_team_bindings_flow_active` would then block that Flow team for good: every read (`bindingsOf`, the match, the team panel) filters on ACTIVE teams, and the link and the match release a dead-team holder of the Flow team inside their own transaction (soft-delete the binding, the Jira bind's dead-node release).
  The two partial unique indexes are a pure backstop under the advisory bind lock and have no `ErrorHandling` wording (`FlowBindingGuardRaceTest` pins the Kotlin 409 text).
- **`CapacityImportService`** is READ-ONLY: one `READ ONLY REPEATABLE READ` transaction over the binding (`bindingOf`), the connection's `time_zone`, `public_holidays`, the mirror's `flow_teams` and `flow_sprints` and, through `TeamCapacityService.importRowsOf`, the team's ACTIVE periods with their provenance columns. The PREVIEW writes nothing. The APPLY writes `team_capacity_periods` ONLY through `TeamCapacityService.applyImport` and reads the same inputs inside that transaction, under the team's binding row lock and the team row lock (plain reads;
  the Flow team, its `sprints_complete` evidence and its sprints in ONE statement). An incomplete snapshot previews an empty plan and the apply rejects every write as `CHANGED` (`flow-sync.md` "The apply").
- **`CapacityDeviationService`** (`GET /views/capacity-deviations`) is READ-ONLY: one `READ ONLY REPEATABLE READ` transaction over `public_holidays`, `flow_connections` (the scheduler's eight poll columns plus `time_zone`, NEVER `api_token`), the newest `sync_runs` (`statusesInTransaction(SyncKind.FLOW, …)`), `activeBindingsWithTeams` (ACTIVE bindings of ACTIVE teams), `FlowMirrorStore.teamSprintsOf` (the team and its sprints in one statement per binding) and the bound teams' ACTIVE periods (`importRowsOfTeams`, one statement grouped by team).
  Nothing is locked, written or audited, and no revision is read: capacity periods are team data.

#### Flow capacity acknowledgements

- `CapacityAcknowledgeService` OWNS `flow_capacity_acknowledgements` and READS `flow_team_bindings ⋈ teams` (ACTIVE both) and, through `CapacityDeviationService.computeBindingInTransaction`, the view's inputs for ONE binding. It writes no other table. It is the table's only writer.
- **Lock order, the unbind's shape:** the binding row `FOR NO KEY UPDATE` FIRST (`lockActiveForWrite`), then the guard's team and person rows `FOR SHARE` (`TeamService.lockedIsActiveManager`), then the acknowledgement rows. No plan lock, no bind lock, no connection row. **Invariant: every write of a binding's acknowledgement rows holds that binding's row lock**, so no two multi-row writes lock one binding's rows in opposite orders; nobody goes binding to connection (the binding-first paths never take the connection row).
- **No cycle.** The acknowledge is one binding-first path (a `FOR SHARE` on a team never waits for a binding row); the capacity writes are another (binding row, then the team row `FOR NO KEY UPDATE`, then the guard's rows); a link holding the team `FOR SHARE` while it waited for that team's binding would close a cycle with them, so the link takes its OWN team's binding rows BEFORE its team `FOR SHARE` (`FlowTeamBindingService.bind`, pinned by `CapacityAcknowledgeRaceTest`). A team delete locks the team row and touches no binding.
- **A row lives only while its deviation row is listed** (`flow-sync.md` "The lifetime of an acknowledgement"). `pruneInCapacityWrite` does the prune for a team's binding INSIDE a plan-side capacity write's own transaction, after its period writes (`teams/`'s `CapacityWriteListeners` calls it, `configureFlow` registers it);
  `lockBindingsBeforeCapacityWrite` takes the team's ACTIVE binding row(s) `FOR NO KEY UPDATE` BEFORE the write's team row (whether or not the binding has stored rows: an acknowledge in flight could be about to store one), so two writes of one team, or a write and an acknowledge, queue at the binding row and the second sees the first's committed periods.
- `pruneConnectionInTransaction` runs INSIDE the run's `FlowMirrorStore.replace` transaction (its `afterWrite`) and deletes the unlisted rows of every binding of the connection in the **connection-first order: the connection row (the replace), then the binding rows `FOR NO KEY UPDATE` in id order (only bindings that have stored rows), then the acknowledgement rows**, one `DELETE`. `Acknowledgements.deleteForConnectionInTransaction` (the connection delete, after its soft delete of the bindings) removes every row of the connection's bindings.
- `binding_id → flow_team_bindings(id)` and `ack_by_user_id → users(id)` (a plain `long` in Exposed: `flow/` names no `users` type) have no `ON DELETE` rule: bindings and users are only soft-deleted, so the rows of an unlinked binding or a deleted team go at the connection's next run (and a deleted connection's with it; those of a connection deleted before the prune existed stay, invisible: every read joins an ACTIVE binding of an ACTIVE team). A test that hard-deletes bindings or users removes these rows first (`removeFlowFixtureRows`).

## Idioms

### Soft delete

`users`, `people`, `teams`, `work_streams`, `programs`, `projects`, `milestones`, `dependencies`, `team_capacity_periods`, `baselines` (the header), `jira_connections`, `jira_bindings` (an unbound binding stays as history), `flow_connections` and `flow_team_bindings` are **soft-deleted**: rows are flagged, never physically removed; every business entity follows the same convention. Only the tables of "The hard-delete tables" and the frozen rows are exceptions.
To add soft delete to a new entity follow the established pattern (reference implementation: `users/UserService.kt`):

1. **Migration.** `marked_as_deleted BOOLEAN NOT NULL DEFAULT FALSE` in the CREATE (a retrofit adds the column plus `CREATE INDEX idx_<t>_marked_as_deleted ON <t>(marked_as_deleted)`).
2. **Exposed table.** Declare it `: UIntIdTable("…"), SoftDeletable` with `override val markedAsDeleted = bool("marked_as_deleted").default(false)`; the ONE `active()` predicate, `nowMillis()` and `lockActiveForWrite` come from `infra/db/SoftDelete.kt` (no private copies).
3. **Filter every read** (`read`, `list`, `count`, any lookup such as `findWithIdByEmail`) with `… and active()`, in the shared list predicate so the `count()` (total) and the row select stay consistent.
4. **`delete` flips the flag.** `update({ (id eq id) and (markedAsDeleted eq false) }) { it[markedAsDeleted] = true }`, returning the affected-row `Int`; guard `update` mutations the same way. The route maps `0` to `404` (`orNotFound`, `conventions.md`), so a missing-or-already-deleted row is `404`, not `204` (`UserService.deleteGuarded` shows the shape, adding the last-admin check inside the same transaction).
5. **Routes need no special-casing.** They key `404`/`204` off the row count and the `active()`-filtered `read`.

**`infra/db/Sql.kt`** (ported from Lettuce with the first list endpoint): `containsNormalized` is the case- AND accent-insensitive substring filter over `public.unaccent` (V4); every per-column substring filter MUST use it.

#### Frozen rows

The four row tables (`baseline_projects`, `baseline_milestones`, V33's `baseline_dependencies`, `baseline_capacity_periods`) are never updated, soft-deleted or hard-deleted. A `BEFORE UPDATE OR DELETE … FOR EACH ROW` trigger plus a `BEFORE TRUNCATE … FOR EACH STATEMENT` one (`forbid_baseline_row_change`, Flow's `metrics.forbid_snapshot_change` ported WITHOUT its purge bypass) raises for every such statement.
The header `baselines` has the TRUNCATE twin and its own `forbid_baseline_header_change`: DELETE refused, and `id`, `plan_revision`, `created_by_user_id`, the counts and `created_at` immutable; name, description, `updated_at` and the flag stay writable.
The rows of a soft-deleted baseline are kept as history (no purge exists; a future one adds its own bypass in its own migration). They hold no FK to a live row, so a frozen copy reads the same whatever happens to the live milestone, project or team.

A clash with an **active** row raises `23505` to `409`, mapped centrally in `plugins/ErrorHandling.kt`, which names WHAT clashed per constraint: extend `UNIQUE_CONSTRAINT_DETAILS` when adding one. ### Row locks vs. FK locks

PostgreSQL's foreign-key check takes `FOR KEY SHARE` on the REFERENCED row for every child insert and keeps it until the inserting transaction ends. A long transaction whose inserts reference a parent row therefore holds key-share locks on every parent it touched for its whole run; `SELECT … FOR UPDATE` on that parent conflicts with `FOR KEY SHARE` and would wait behind it (Flow hit this with its long-running derive job against team rows; Astrolabe's planning writes are the same shape).

**Lock a row `FOR NO KEY UPDATE` unless the write changes its key.** That mode conflicts with itself and with `UPDATE`/`DELETE` (writers of the row, e.g. a soft delete racing a child insert, still serialize) but NOT with `FOR KEY SHARE`, so FK locks never stall it. `lockActiveForWrite` (`infra/db/SoftDelete.kt`), `TeamService.update`, `PersonService.update`/`delete` and `PasswordResetService.lockUser` (the active `users` row) follow it;
none of them touches `id`, and the unique indexes on these tables are partial or expression indexes (`uq_teams_name_active`, `uq_users_email_active`), which PostgreSQL does not count as key columns, so a rename is still a non-key update.

Plain `FOR UPDATE` is for a row nothing references from a long transaction, or for `SKIP LOCKED` claims. `users` is referenced only by columns no long transaction inserts (`updated_by_*`, `people.user_id`, `user_disabled_features.user_id`, `password_reset_tokens.user_id`: short inserts only) plus `baselines.created_by_user_id`, inserted inside the plan-locked baseline create (tens of milliseconds):
its FK check holds `FOR KEY SHARE` on the creating user's row until the create ends, so a plain `FOR UPDATE` on that user waits for the create, boundedly, and cannot deadlock with it (the create waits on no `users` row lock, and the user-row writers take no plan lock): `UserAdminGuard.lockedActiveAdminCount`. A new `FOR UPDATE` on an FK-referenced row needs that justification in a comment.

Flow pinned both halves with `RowLockVersusDeriveTest`; Astrolabe's planning writes take ONE lock instead, on `plan_state` ("The plan (V12)"), and `PlanStateTest`'s lock-wait barrier tests (a raw JDBC session holds the lock, the request waits, the release lets it complete) descend from that test. The plan's **count-the-children-then-delete** needs more than a parent-row lock: a child INSERT's FK check takes only `FOR KEY SHARE`, which `lockActiveForWrite`'s `FOR NO KEY UPDATE` does not block, so the count runs under the `plan_state` lock that every child create also holds.

### The DATE column idiom

Files: `infra/db/LocalDateColumn.kt`, `infra/validation/Dates.kt`.

Dates are Postgres `DATE` (day precision; the planning tables from V12), bound through a repo-local column type because `exposed-r2dbc` 1.6.0 ships no date module (no `exposed-java-time`, no `exposed-kotlin-datetime`, and none is added): `exposed-core`'s abstract `LocalDateColumnType<T>` and `exposed-r2dbc`'s `DateTimeTypeMapper` recognise such a column.
`JavaLocalDateColumnType` implements the two conversions (`kotlinx.datetime.LocalDate` to and from `java.time.LocalDate`) **and overrides `notNullValueToDB` to return the `java.time.LocalDate` itself, which is load-bearing**: the 1.6.0 base class is NOT zone-free (it builds `java.sql.Date(atStartOfDayIn(TimeZone.currentSystemDefault()))`), so every write and every WHERE parameter would pass through the JVM default zone and the Julian/Gregorian cutover (measured: UTC stored `1500-01-01` as `1499-12-23`; Pacific/Kiritimati stored `1994-12-31` as `1995-01-01`; `0100-02-27` was a 500).

The mapper only unwraps `java.sql.Date`/`Time`/`Timestamp`, so a `java.time.LocalDate` reaches `Statement.bind` unchanged and r2dbc-postgresql's native codec encodes the calendar date; `nonNullValueToString` is the ISO `'YYYY-MM-DD'` for the same reason. A table declares `val day = localDate("day")` (`Column<java.time.LocalDate>`, `.nullable()` as usual).
The wire format is an ISO `YYYY-MM-DD` string (`type: string, format: date`; DTO fields are `String`) parsed by `parseIsoDate(value, field)` (400 "<field> must be a YYYY-MM-DD date" for a bad shape or a non-calendar day, and "<field> year must be between 1900 and 2999" outside that calendar: a belt on top of the zone-free column) and `requireDateOrder(start, end)` (400 "End must not be before start"; an end equal to the start is a one-day span); a `CHECK (end_date >= start_date)` in the migration is the backstop.

Pinned by `LocalDateColumnTest` (a scratch table by raw DDL): round-trips of the epoch, the DST-change days and the historical traps (`1500-01-01`, `0100-02-27`, Kiritimati's skipped `1994-12-31`, Apia's skipped `2011-12-30`); the STORED text (`::text`, over raw JDBC) of an insert, an update and a WHERE parameter is the calendar date under every swapped JVM default zone (UTC, Kiritimati, Apia, Pago_Pago, Warsaw, Sao_Paulo); `greaterEq` and `orderBy` follow date order; a `CHECK` violation surfaces as SQLSTATE 23514.

### The NUMERIC column idiom

`milestones.estimate_md` is `NUMERIC(8,2) NOT NULL CHECK (estimate_md >= 0)`, declared in Exposed as `decimal("estimate_md", 8, 2)` (`Column<BigDecimal>`) with **no repo-local column type**: none of `exposed-r2dbc` 1.6.0's type mappers names `BigDecimal`, so the binding rides the default mapper. The wire is a JSON number (`estimateMd: Double`, `type: number, format: double`);
the server validates it (finite, `0 <= x < 1_000_000`, and `BigDecimal(x.toString())` with at most two decimals: `validateMilestoneFields` over `validateManDays`, `planning/Milestone.kt`) so the stored value is EXACTLY the sent one, never a silent rounding.

Pinned by `DecimalColumnTest` (a scratch table by raw DDL, the `LocalDateColumnTest` shape): insert, select, update and a WHERE parameter for `0`, `0.1`, `12.25`, `999999.99`, the stored `::text` over raw JDBC equal to the sent value at scale two (`0.1` is stored `0.10`), and `greaterEq`/`orderBy` in numeric (not text) order; and `MilestoneTest` over HTTP.

### Jsonb and canonical JSON

**`infra/db/Jsonb.kt`** is a repo-local `jsonb` column type, because `exposed-r2dbc` 1.5.0 ships no JSON column type: it implements Exposed's `JsonColumnMarker`, which its `PostgresSpecificTypeMapper` already binds (a null via `bindNull(index, Json::class)`, a `String` via `bind(index, Json.of(value))`), so no reflection into the raw `Statement` is needed. Values are the caller's JSON text verbatim;
PostgreSQL's own `jsonb` storage reformats regardless (whitespace, key order), so "round-trips" means the same VALUES survive, not the same bytes.

**The one exception to "same values" is U+0000.** PostgreSQL `jsonb` and `text` cannot store a NUL (SQLSTATE 22P05 for jsonb; `22021` for text). Every payload that goes through `canonicalJson` (`infra/json/CanonicalJson.kt`) therefore has each U+0000 in a string value AND in an object key replaced with U+FFFD, before the text is hashed, so the stored text and its sha256 agree (U+FFFD marks that something was there and cannot merge the tokens around it, which dropping the character would).
`String.replaceNul()` (same file) applies the same rule to free text bound for a `text` column that is not a canonical JSON payload (a database exception's message can quote the offending value).

**`infra/json/CanonicalJson.kt`** is canonical JSON for anything stored through `Jsonb.kt`: object keys sorted RECURSIVELY (arrays keep their own order, since position is meaning), rendered via kotlinx.serialization's compact `JsonElement.toString()`, plus a `sha256Hex` digest. Two payloads that differ ONLY in object key order canonicalize to byte-identical text and equal digests (key-order independence, not structural equality: number spelling is not normalized, `1`, `1.0` and `1e0` stay distinct).
**The output must stay byte-stable**, since stored text and sha256 are compared against stored rows.

**Consumers** (`jira_connections`): `project_keys` (an array, `infra/json/JsonArrays.kt`), `discovery` (the field and issue-type snapshot, `JiraDiscovery.toStoredJson()`) and **`mapping`**: the `@Serializable` `JiraMapping` document (`jira/JiraMapping.kt`) encoded with `encodeDefaults` and no nulls, then `canonicalJson`, so two PUTs that differ only in key order or in an omitted default store the same text and the same `sha256Hex` (the `jira.mapping_changed` audit digests). The column is read whole and decoded (`parseStoredMapping`; `{}` = unset), never filtered in SQL.
Numbers keep their spelling through `jsonb` (`manDaysPerUnit` 0.5 stays `0.5`), so a re-read digest equals the written one. Pinned by `JsonbColumnTest`, `CanonicalJsonTest` and `JiraMappingTest`.

## Tables by feature

What the DDL does not say: locks, uniqueness, retention, the reasons. The columns and CHECKs are in the migration files (`MigrationChecksumTest` pins their bytes).

### Per-user permissions (V11)

`user_permissions` is the **grant** set: a row means held, no row means not held, the opposite polarity of V5's disabled set, so the empty table needs no backfill and nobody starts with a right. The Kotlin `Permission` enum (`users/User.kt`) is the whitelist (no CHECK, the V5 precedent); `UserService.UserPermissions` is the Exposed table, a hard-delete join table like `user_disabled_features`.
`PUT /users/{id}/permissions` replaces the set wholesale inside one transaction that first locks the user row `FOR NO KEY UPDATE` (`replacePermissions`: concurrent PUTs serialize instead of racing on the primary key, and the previous set it returns is exact for the audit event). `UserService.hasPermission` reads the table per call, never cached (`authorization.md` "Roles vs permissions"). `ON DELETE CASCADE` is inert (users are only soft-deleted); a soft-deleted user's rows stay, unread.

### Credential revision (V7)

`users.credential_revision` is an internal nonnegative BIGINT generation, initially zero. Every password update or reset and every conditional bootstrap rotation increments it atomically in SQL with the hash update; soft delete and role changes do NOT bump it (the access check compares the stored role separately; a delete is `user_gone`). It is not exposed in user DTOs. What carries and compares it (signed tokens, pending MFA challenges, the per-request access check, a reset grant): `security.md` "JWT model", "The request and the grants";
`password_changed_at` is a timestamp, not an authorization boundary.

### Password reset tokens (V8)

Single-use grants (`security.md` "The request and the grants"): only the SHA-256 digest of the emailed token is stored (`token_hash` PK), with the account snapshot it was issued against and `expires_at`; `user_id` references `users` with `ON DELETE CASCADE`. A hard-delete table; expired rows are pruned opportunistically.

### Telemetry (V9)

`ops.telemetry_processes` and `ops.telemetry_samples` (`telemetry/TelemetryStore.kt`, `observability.md` "Telemetry") live in the `ops` schema. A process row is one JVM run (`role` is the constant `"app"`). `telemetry_samples` is ONE narrow table for every metric, `resolution` the sample width in seconds (raw: the sampler's real interval, 60..1800 and a divisor of 3600; hourly rollup: 3600; the tier is `resolution < 3600` and the CHECK enforces it), so a metric is added in `TelemetryMetrics.kt` with no migration. Timestamps are epoch-millis `BIGINT`;
the cluster section's rows are attributed to the process that took the lock. Writes go through `insertRowsIgnoringConflicts`; every statement runs under the transaction's `queryTimeout`.

**The prune is a hard-delete exception**: samples are regenerated, high-volume observations with no reader once old, so raw rows older than 7 days, hourly rows older than 90 and processes unseen for 90 days are deleted (their samples cascade, `ON DELETE CASCADE`; an index on `process_id` keeps that cascade off a table scan). The prune runs inside the telemetry cluster transaction under `TELEMETRY_LOCK_KEY`, and a row exactly at its cutoff stays. `TelemetryStoreTest` and `TelemetrySamplerTest` empty `ops` before each test.

### The plan (V12)

`plan_state` (one row, `CHECK id = 1`: the plan's monotonic `revision` and the lock row), `work_streams`, `programs`, `projects` (DDL, constraints and uniqueness scopes: `planning-model.md`). Dates are `DATE` through `LocalDateColumn.kt` (each pair with a `CHECK` backstop); ids are `SERIAL`; every node has `owner_person_id INTEGER NOT NULL REFERENCES people(id)`.

**Every write of these tables, and of `milestones`, `dependencies`, `team_milestone_orders`/`team_order_state`, the work stream and program orders (V34), `public_holidays`, the `baselines` registry with its frozen rows and the milestone pin (`MilestoneService.pin`), runs in `withPlanWrite`** (`planning-model.md` "The lock protocol"). **This is the one deliberate PLAIN `FOR UPDATE` on a table the code treats as a lock row**: nothing references `plan_state` by a foreign key (no FK check can queue behind or in front of it) and its key never changes.
All plan writers serialize there, so the node services take no per-row locks, the delete's child count is race-free and the ranking compares `expectedRevision` atomically against `plan_state.ranking_revision` (V18). Reads (`PlanViewService`, `RoadmapViewService.view`) read the revision first without the lock (`SNAPSHOT, readOnly`).

### The roadmap rank (V13)

`roadmap_entries (project_id PK → projects, position CHECK >= 1, uq_roadmap_entries_position UNIQUE (position) DEFERRABLE INITIALLY DEFERRED)` (`planning/RoadmapService.kt`; semantics: `planning-model.md` "The global project rank"). One row per RANKED project; no row means unranked. **Positions are dense 1..n**, kept so by the two writers, both inside `withPlanWrite`: `replaceRanking` (`DELETE` all, then one `insertRows` with positions 1..n in the given order) and `removeFromRanking` (delete the row, then ONE `UPDATE … SET position = position - 1 WHERE position > ?`);
both then stamp `plan_state.ranking_revision`.

**`DEFERRABLE INITIALLY DEFERRED` is load-bearing**: an immediate unique constraint is checked row by row, so the sweep (and any reorder that swaps two positions in one statement) can collide with a not-yet-updated neighbour depending on physical row order; deferred, the check runs once at commit, when the table is dense again. The cost is that a genuine duplicate surfaces at COMMIT, not at the statement (only a bug can produce one: every writer holds the plan lock).
`project_id` has no `ON DELETE` rule: projects are only soft-deleted, and the delete hook removes the entry in the same transaction. A hard-delete table.

### The team milestone order (V17)

`team_milestone_orders (milestone_id PK, team_id, position CHECK >= 1, uq_team_milestone_orders_position UNIQUE (team_id, position) DEFERRABLE INITIALLY DEFERRED)` and `team_order_state (team_id PK, revision, updated_at)` (`planning/TeamOrderService.kt`; semantics: `planning-model.md` "The team milestone order").
The roadmap rank's shape, per team: one row per LISTED milestone, **positions dense 1..n per team**, kept so by the writers inside `withPlanWrite`: `replaceOrder` (`DELETE` the team's rows, one `insertRows` with positions 1..n) and `removeFromTeamOrders` (delete the rows, then one `UPDATE … SET position = position - 1 WHERE team_id = ? AND position > ?` per removed row, highest position first).
**`DEFERRABLE INITIALLY DEFERRED`** for the roadmap's reason: the sweep and a swap are single statements an immediate check can reject depending on physical row order (`TeamOrderLifecycleTest` pins the swap, the commit-time duplicate and the CHECK). `team_order_state.revision` is the plan revision at which the team's order was last written (the first write inserts the row, later ones update it; a removal never touches it): the order PUT's `expectedRevision` compares against it, so another team's reorder never stales this one. Both tables are hard-delete.

### The public holidays (V19)

`public_holidays` is Flow's registry, ported, with a real `DATE` (the `localDate` column) instead of Flow's `VARCHAR(10)` and **no seed**: the `POLISH` preset endpoint is the path (`planning-model.md` "The calendar"). One global dictionary, unique per date (`uq_public_holidays_date`; a duplicate is `23505` to the central `409`, the plan lock rolled back with it). Every create, delete and preset application is one `withPlanWrite`; the preset selects the year's existing dates under the lock and inserts the rest with `insertRowsIgnoringConflicts` (one statement).

### The baselines (V20)

`baselines` and its four row tables (`planning/BaselineService.kt`; semantics: `planning-model.md` "Baselines"). `plan_revision` is the plan revision the baseline EQUALS: the one its creation left behind (`revision + 1` inside `withPlanWrite`, which hands the block the OLD revision), so a view whose revision equals it shows zero movement. The row tables are FROZEN ("Frozen rows"); every id column but `baseline_id` is a plain `INTEGER` (no FK); `ck_baseline_*` CHECKs mirror the live tables'.
V33 adds `dependency_count` and `capacity_period_count` to the header: NULL (both together, `ck_baselines_capture_counts`) = taken before 1.26 or by a build that does not know them, NOT captured, never zero. It replaces V20's header function and leaves V20's bytes; a 1.25 build on this schema writes NULL counts and no new rows.
Every write runs under the plan lock. Pinned by `BaselineTest`, `BaselineCopyTest`, `BaselineCaptureTest` (the copies, the triggers, a NULL-count header) and `MigrationChecksumTest`.

### The milestone pin (V25)

`milestones.pinned BOOLEAN NOT NULL DEFAULT FALSE` and `ck_milestones_pinned_scheduled CHECK (NOT pinned OR start_date IS NOT NULL)` (a pin needs dates). The pin is advice to the planner (`planning-model.md` "The pin"; `scheduling.md` "The auto-proposal"): a baseline does not freeze it (V20 is untouched) and it is not part of `schedule_revision`.

**The writers of `milestones.start_date`/`end_date` are exactly three, each keeping the CHECK true by clearing the pin on an unscheduled write:** `MilestoneService.schedule`, `writeSchedules` (`MilestoneScheduleWrite.kt`) and the insert of a new milestone (`insertMilestoneRow`; the clearing rule: "The pin"). `MilestoneService.pin` is the only writer that sets the flag TRUE, under `withPlanWrite` with the schedule PUT's guard re-run inside (`TeamService.lockedIsActiveManager`).
A new writer of the dates must clear the pin the same way, or the CHECK turns its miss into a 500 (`MilestonePinTest` pins the CHECK).

### The Jira sync tables (V21)

`jira_connections`, `jira_bindings`, `jira_observations`, `sync_runs` (`jira/JiraConnectionService.kt`; the registry is ADMIN only).

- `api_token` is the application's first encrypted-at-rest column (a `FieldCipher` envelope). `project_keys`, `mapping` and `discovery` are the first `jsonb` columns ("Jsonb and canonical JSON"): `project_keys` goes through `JsonArrays.kt`'s `stringArrayJson`/`parseStringArray`, and `mappingSet` is `mapping <> '{}'`. The site is a connection's identity: a PUT with another `siteUrl` is a 409, so the cloud id, discovery, mapping and bindings always describe one site.
- `jira_bindings`: `ck_jira_bindings_node` (exactly one node column set, and it is the one the level names); `uq_jira_bindings_node_active` and `uq_jira_bindings_issue_active` (1:1 both ways over the ACTIVE rows); an index per node column; no `ON DELETE` rule (the nodes are only soft-deleted).
- `jira_observations` stores Jira's dates AS OBSERVED, so there is no start/end order CHECK (an end before the start is a deviation to show, not a row to refuse). `gone_reason` is written `OUT_OF_SCOPE` by the sweep and refined to `DELETED` or `FORBIDDEN` by the run's probe. `gone_probed_at` (V27) is the probe's last ANSWER (200, 404 or 403) for the current vanish, NULL until one comes, cleared with `gone`; a failed, cut or over-cap probe stays NULL and is retried by a later run;
  V27 has no backfill, so a row flagged before it is probed by the next run (`JiraSchemaTest` pins the column and the CHECK).
- `sync_runs` has no FK on `connection_id` (the kind decides the table); `uq_sync_runs_running ON (kind, connection_id) WHERE finished_at IS NULL` is the single-writer claim, with `idx_sync_runs_connection`.
- **V22.** `poll_interval_minutes INTEGER DEFAULT 15` (`ck_jira_connections_poll_interval`: NULL = manual only, else 5..1440; the DEFAULT backfilled every existing connection).
  Its three `jira_bindings.ack_*` columns, unread and unwritten once the per-deviation acknowledgement (V28) replaced them, were dropped by **V30** (`JiraSchemaTest` pins their absence, `created_by_user_id` the one foreign key to `users` left): a build that still declares them can no longer run on the database, the build before it can, and the earlier whole-binding acknowledgement stamps are recoverable only from a pre-upgrade dump.
- **V29, `jira_observations.gone_probed_key VARCHAR(50) NULL`:** the issue KEY the run's by-id probe last got with a 200 for a gone binding (NULL: no such answer, no backfill; the wire reason derived from it: "Jira run store"). **Deliberately no CHECK tying it to `gone` or `gone_probed_at`** (unlike V27): an older build still ran on this schema and clears those two without knowing this column, so such a constraint would fail its writes; readers take the key only from a gone, probed row and every writer that sets or clears `gone` resets it. No index;
  a gone, probed row may carry a stale key until its next re-ask. `JiraSchemaTest` pins the nullable `VARCHAR(50)`, that a non-gone row may hold it and that 51 characters is SQLSTATE 22001.
- Pinned by `JiraSchemaTest` (every CHECK, the partial indexes and the foreign keys of all four tables at the database), `JiraConnectionTest`, `JiraBindingTest`, `JiraBindingLifecycleTest`, `JiraBindingRaceTest`, `SyncRunServiceTest`, `SyncRunnerTest`, `EncryptedAtRestBootTest` (the backfill) and `MigrationChecksumTest`.

### The Jira census (V23)

`jira_issues`, keyed `(connection_id, issue_id)` with `ix_jira_issues_parent`, and `jira_connections.census_at` (when the child level was last fully censused; NULL for every connection that predates it, which makes its first run a full read). The mirror is the latest observed CENSUS of a connection's scope (the mapped levels plus the child level the roll-ups read): one row per issue, overwritten by every run, pruned by the run's sweeps, hard-deleted with its connection, a second documented hard-delete exception beside `jira_observations`. No soft delete, no revision, no plan lock.
The row is built by `CensusIssue.of` (`jira/JiraIssueStore.kt`), which fits every string to its column and clamps the points like an observation's estimate, so a statement cannot fail on a site's odd value; written only by `JiraIssueStore` in `RUN_CHUNK` transactions. Pinned by `JiraSchemaTest` (the key, the foreign key, the CHECKs, the column widths, the index, the nullable `census_at`) and `JiraIssueStoreTest` (the `FOR SHARE` vs `FOR NO KEY UPDATE` race between a run's census write and the connection delete).

### The Jira deviation acknowledgements (V28)

`jira_deviation_acknowledgements`: "known, leave it" for ONE deviation of a Jira binding (`jira/JiraAcknowledgeService`; `jira-sync.md` "Acknowledge"). It is V26's shape with the Jira key: **one row per `(binding, kind)`**, because the deviation kernel raises each `DeviationKind` at most once per binding, so `uq_jira_deviation_acks_key ON (binding_id, kind)` is a plain unique index (both columns NOT NULL: no `NULLS NOT DISTINCT`, which V26 needs for its NULL sprint).
`ck_jira_deviation_acks_kind` pins the SHAPE of `kind` (`^[A-Z][A-Z_]{0,31}$`), not the vocabulary, so a kind added to `DeviationKind` later needs no migration and a stored kind the code no longer knows is ignored on read; `ck_jira_deviation_acks_fingerprint` is `^[0-9a-f]{64}$` (the per-line fingerprint, `fingerprintOf` of the one `Deviation`, severity included). `binding_id` is `INTEGER` (`jira_bindings.id` is `SERIAL`), `ack_by_user_id` `BIGINT`;
no `ON DELETE` rule: bindings and users are only soft-deleted, so unbinding keeps the rows as history (a re-bind makes a new binding id).

**Hard rows, no `marked_as_deleted`** (the `flow_capacity_acknowledgements` class): a withdrawal DELETEs, a re-acknowledge rewrites the stamp, the stored fingerprint is compared with the line's on every read (a stale row is an open line again); a line that leaves the list and returns identical stays acknowledged (no pruning). Not plan state: no plan lock, no revision. Pinned by `JiraSchemaTest` (the key, both foreign keys, both CHECKs and the NOT NULLs by SQLSTATE) and `MigrationChecksumTest`.

### The Flow sync tables (V24, V31)

### The capacity acknowledgements (V26)

`flow_capacity_acknowledgements` (`flow/CapacityAcknowledgeService.kt`; `flow-sync.md` "Acknowledge"). `sprint_id` is Flow's sprint id; **NULL is the binding's `TEAM_GONE` row** (the one deviation a gone team has), so `uq_flow_capacity_acks_key ON (binding_id, sprint_id) NULLS NOT DISTINCT` (Postgres 18, the V15/V21 idiom) makes the team row collide with itself. `ck_flow_capacity_acks_sprint` (NULL or >= 1) and `ck_flow_capacity_acks_fingerprint` (`^[0-9a-f]{64}$`).
**Hard rows, no `marked_as_deleted`** (a stamp like `jira_observations`): an un-acknowledge DELETEs, a re-acknowledge rewrites `fingerprint`, `ack_at` and `ack_by_user_id` (acknowledge-all deletes the named keys and re-inserts them in one multi-row statement, so those rows get a new `id`; both under the binding row lock); the stored fingerprint is compared with the row's on every read, so a stale row is simply an open one again.
**A row lives only while its deviation row is listed** (the prune: "Flow capacity acknowledgements"), so the table is bounded by the listed rows, plus the plan-side residual of a deleted team. Not plan state: no plan lock, no revision.

### The saved proposals (V32)

`saved_schedule_proposals` (`planning/SavedProposalService.kt`; semantics: `scheduling.md` "Saved proposals"). One row is the SERVER's own `CrossTeamProposal` (`document`) and, for a partial selection, its `ScheduleCheckResponse` (`check_document`, NULL = every move ticked), stored through `jsonb` and `canonicalJson`. `format` is `STORED_PROPOSAL_FORMAT`: a row of another format is UNREADABLE (never decoded); `StoredProposalFormatTest` fingerprints the two documents' serial shape.
