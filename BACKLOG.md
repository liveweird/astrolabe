# Product backlog

Updated 2026-11-07. This file tracks **outstanding work only**. Implemented behaviour and release history belong elsewhere:
- [README.md](README.md);
- the [application changelog](web/src/changelog/entries.ts);
- the topic guides under `.claude/docs/`.

Entries are proposals, not delivery commitments.

**Status tags.** Every top-level item under a `##` section opens with one tag:
- `[next]`: what comes next;
- `[todo]`: confirmed, to do;
- `[new]`: proposed, not yet confirmed. That includes the decisions only the user can take. Claude adds items as
  `[new]`, and only the user promotes them;
- `[parked]`: deliberately set aside until a trigger;
- `[blocked]`: waiting on someone or something else.

The `backlog` mod (`liveweird/claude-mods`) summarises the tags on the status line and in `/backlog`.

## Increments (the roadmap, `.claude/docs/product.md`)

Each increment gets its own plan (architect) before implementation. The domain sketch is `.claude/docs/planning-model.md`; the timeline approach is `.claude/docs/timeline.md`.

- [new] **Paged lists for work streams and programs.** Projects and milestones have them since v0.4 (the dependency pickers); the plan view is still the only read surface of work streams and programs. Add theirs per `list-endpoints.md` with their first consumer.
- [new] **Flag a milestone that lost its last working day to a holiday (D2).** The schedule PUT refuses a span with no working day, but a holiday added later leaves such a milestone with its dates (it loads nothing and splits no idle gap); mark it on the project and team pages.
- [new] **A per-link slack figure in the Dependencies table.** The Slack column is per milestone; a link's own slack (`actual - required`) is already computed server-side for the critical path.
- [new] **The critical path on the team page / the roadmap.** It rides the project view only; the team view answers `critical: false` on its links and the roadmap has no path.
- [new] **Ghost rows for chain members beyond the direct neighbours, if the Critical chain list proves insufficient.** Farther chain members are a list (names, dates, hops, slack), not timeline rows.
- [new] **A cross-team proposal run.** The v0.8 proposal places ONE team's milestones with the other teams' dates fixed (a later run after another team accepted may move milestones again: the fixed point is per team). A run over several teams (or all) in dependency order would settle in one pass; it needs an ordering of the teams and a bigger preview.
- [new] **Auto-proposal alternatives the user did not choose (v0.8 Q1b/Q6b).** A keep-what-fits mode (a scheduled milestone keeps its dates while it still fits; Q1b), a start bound from the project's target window (Q6b), proposals that persist and can be shared or compared (today a proposal is ephemeral, a page-local state). Build one only if the pure re-plan proves too noisy.
- [new] **A "pin this milestone" flag for the proposal.** The proposal uses a milestone's current dates as a tiebreak only; a manager who wants one kept where it is has no way to say so except accepting the others. A per-milestone pin (kept as a fixed milestone by the kernel) would do it.
- [new] **Link warnings for the ticked subset only.** The proposal's link check assumes every move is accepted (v0.8 default); when a manager unticks moves the red "would violate" badges still describe the all-accepted plan. Recompute the verdicts client-side for the ticked subset, or ask the server for them.
- [new] **Baselines of links and capacity (v0.9 Q1b).** A baseline freezes the dated structure only (milestones and projects); links, capacity periods, holidays and team orders are not copied, so a dependency added or a capacity cut since the baseline shows nowhere. A full plan copy would add three frozen tables and a bigger comparison.
- [new] **Per-team baselines taken by the manager (v0.9 Q3b).** A baseline is plan-wide, taken by ADMIN or a `ROADMAP_EDITOR`; a team manager who wants "my team as of Monday" has no way to take one (and a per-project one for the owner).
- [new] **A diff between two baselines.** The comparison view compares one baseline with the live plan only; "Q1 commitment against Q2 commitment" needs a second frozen side.
- [new] **Take a baseline automatically at a release or tag.** Baselines are taken by hand; a scheduled or release-triggered snapshot (and the cap of 100 it would eat into) is not built.
- [new] **Rank movement against a baseline on the roadmap.** The frozen `rank_position` is stored in `baseline_projects` but not shown; the roadmap overlay draws spans only.
- [new] **Appended rows for removed projects on the plan pages.** The roadmap and programs overlays draw a shadow bar for a project that exists now; a project deleted since the baseline appears only on the comparison page.

- [new] **A per-level issue-type include list (Q2b).** A level maps to a Jira hierarchy level, so every non-sub-task type at it counts; let the mapping name the types that count (milestone = Story and Task but not Bug). The 1.4 child level (the roll-up and `CHILDREN_DONE`) has the same rule: every non-sub-task type under the epic counts.
- [new] **Owner matching from the Jira assignee.** The import and the Deviations page could propose a plan owner from the Jira assignee (people have an email); nothing reads the assignee today.
- [new] **`DELETED` vs `OUT_OF_SCOPE` by a per-issue 404.** The sweep cannot tell a deleted issue from one moved out of the project keys or hidden by a lost permission and flags all `OUT_OF_SCOPE`; a `GET /issue/{id}` 404 on a flagged binding would say `DELETED`.
- [new] **Raise the id-only page size (A4).** The sweep reads `fields=id` at the 100 a page Flow verified; Jira may allow up to 5,000 for an id-only read. Measure on a real site before raising `jira.pageSize` for the sweep. `jira.pageSize` is ONE global setting validated to 1..500 (it also sizes the run's full read), so raising the sweep alone needs a separate setting.
- [new] **Webhooks instead of polling.** Jira can push issue changes; a receiver would replace the 1.3 poller, but needs an inbound, authenticated endpoint the app does not have.
- [new] **Read bound Jira issues by `id in (...)` chunks if a real site's mapped types still exceed the ceiling.** The run's full read is limited to the mapped levels' types (200 pages x `jira.pageSize`, 20,000 issues at 100 a page); if a real site still has more issues of those types than that, read the bound ones by `id in (...)` chunks instead (unverified on a real site, and a static stub cannot answer arbitrary id sets).
- [new] **Link and unlink program-level Jira bindings outside the connection page.** In 1.1 a program binding can only be made and removed on a connection's page (ADMIN): the plan has no program page, and no non-admin can link one from the UI (the project page links the project and its milestones, and unlinks them for the owner). A program owner would need an action on the Plan or Programs page, with the same `can.edit` gate and the bind dialog fed by a chip-style read of the program's links.
- [new] **A Plan-page entry point for the import (1.2 decision B).** The API lets an owner of every target import and is tested for it, but "Import from Jira…" is only on the connection page (ADMIN's). Add a work-stream menu entry on the Plan page, the connection picked as the bind dialog does it (from `GET /views/deviations` `connections[]`).
- [new] **Copy a project's target window from Jira (1.2 decision C).** The import copies milestone dates only; a project's target window is not copied from Jira's project-level dates (the `TARGET_DIFFERS` info shows them afterwards). Copy it where the caller may set it (`requireTargetWindowEditorOrAdmin`).
- [new] **A per-row owner override in the import.** One owner (a person picked in the dialog) goes onto every program and project the import creates; the team already has a per-row override (`overrides.teamId`), the owner has none.
- [new] **`id in (...)` for the import apply's re-read.** The apply re-runs the preview's whole browse and matches by id (a static stub cannot answer `id in (...)`, and one `GET /issue` per row would be slow); on a real site a chunked `id in (...)` read of the ticked issues would be cheaper. Only worth it if the re-browse proves slow there (the browse has a 170 s deadline).
- [new] **Browse unmapped intermediate levels in the import.** The browse reads only the mapped levels' types, and `fields.parent` holds the direct parent only, so an item under an unmapped level (an epic under an unmapped initiative under a mapped program) is an orphan: the default parent, else `NO_PARENT`. Also browse the unmapped types in between to walk the chain.
- [new] **Axe over the import outcome's skipped table.** The e2e never shows that list: the UI sends only ticked rows, so a first import skips nothing (the virtualised preview table is scanned since the 2026-11-07 maintenance pass, `jira-import.spec.ts`). - [new] **Suggest a match for renamed items in the import preview.** Linking is by exact name (case-insensitive), so an unlinked item renamed in Jira previews as a new one and importing it would add a duplicate; the preview could propose the nearest unlinked sibling as a BIND to confirm.
- [new] **The view-fed Jira chips lost 1.1's "may be out of date" qualifier.** The timeline views carry no connection status (a per-site status on `jiraSites` would bring it back); until then the project and team chips show the last observation, and currency lives on the Deviations page.

- [new] **Acknowledge one deviation, not the whole list (1.3 Q3c).** An acknowledgement keys on the binding's whole deviation list, so any change reopens every line of it; a per-kind (or per-deviation) fingerprint would keep the unchanged ones acknowledged, at three times the UI.

- [new] **A claim racing a connection delete leaves an unpruned `sync_runs` row (1.3).** The scheduler's claim and the manual route can both insert a run for a connection that is deleted a moment later; the row is never pruned. Prune by connection at claim time or sweep orphans.
